## 现象

`T-0199` 的结果是 `done`、验收 `strong-pass`（18 passed），但 **代码根本不存在**：

- 结果里 `head: b87021202981e57c3825908f82485cbef2b6de07`
- 该提交在本机 light 仓 `git cat-file -t` **不存在**
- 远端 `git ls-remote origin '*0199*'` **无任何分支**（`task/T-0199` 从未推上来）
- 结果里 `changed_files: []`、`out_of_paths: []` —— 自己都承认没改文件

`hive land T-0199` 才报「代码仓里没有 origin/task/T-0199 分支」。也就是说：
**卡已经标 done 了，工作却无法合入，而且没有任何一处提前报警**。
等发现时只能 `retry --fresh` 重做，agent 那 18 个用例、E016/W016 的活全丢。

同批次其它卡都正常（T-0194/T-0195/T-0200 的 head 都能在 origin 找到并 land 成功），
所以这不是普遍现象，而是**缺一道校验**。

## 根因（待确认，请沿这条线查）

结果落盘时没有校验「报告出来的 head 是不是真的在远端可获取」：

1. `worker` 写 `results/<tid>.json` 时，`head` 直接取本地 worktree 的 `rev-parse`，
   不校验 `git ls-remote origin refs/heads/task/<tid>` 是否等于它；
2. `_finish` / `submit_result` 判 `status=done` 时只看 `verify` 返回码，不看分支在不在；
3. `changed_files` 为空本身就该是**异常信号**（一张改代码的卡零改动 = 没干活或没提交），
   却没有触发任何 warning；
4. `land` 是唯一堵住的地方，可它已经太晚——卡已 done，看板上和真完成长得一模一样。

## 期望

在「产结果」和「判完成」之间加闸，宁可判失败也不要假成功：

- **写结果时**：`git ls-remote origin refs/heads/task/<tid>`，取回的 sha 必须 == 报告的 head；
  不一致就 `status=failed`，`error` 写明「head 未推送/不一致：本地 X，远端 Y/无」。
- **判 done 时**：`changed_files` 为空 → 直接 failed（错误信息点名「零改动」），
  除非卡片显式声明 `allow_empty_diff: true`（纯调查/台账类卡才用）。
- **land 前置**：把「分支不存在」从「唯一防线」降级为「兜底」，主防线在提交侧。
- 可选：`hive doctor` 加一条巡检——扫所有 `done` 卡的 head，不在 origin 的列出来。

## 验收

1. 造一个「本地有提交但没推」的结果（`head` 指向把 `origin/task/<tid>` 删掉后仍存在的
   sha），`hive result` 应拒绝标 done / 或标 failed 并给出「未推送」原因；
2. `changed_files=[]` 的 done 结果 → 落地为 failed；
3. T-0194/T-0195/T-0200 这类正常卡**零影响**（head 在远端 → 照常 done）；
4. 补 `tests/test_result_head_guard.py`。

## 边界

- 只改「结果验收 / 完成判定」这一层，不动 `land` 的合并逻辑本身（它是对的）。
- 不要让校验变成对网络的重度依赖：`ls-remote` 一次即可，失败按「未推送」处理并重试一次。
- Windows agent（deepseek-win 是 `mode: manual`、仓库在 `G:/`）走的是同一条产结果链路，
  修复要在共用路径上生效，不要只在 FreeBSD 分支里加。
