# 模型与推理核（d=192/L=6，含 KV cache 与 bench）

## 背景

**200 tok/s 是工程问题，不是训练问题。** 必须在训练前就把推理路径打通并测出数字，
否则训完才发现速度不达标就白训。

当前 `model.py` 的 `forward` **每次全量重算整个序列**，decode 复杂度是 O(T²)。
不加 KV cache 不可能达标。

## 已实测的规模上限（本机 Xeon E5-2643 v2，12 线程，无 AVX2）

| d | FFN | L | 单 token | 估算 tok/s |
|---:|---:|---:|---:|---:|
| 128 | 320 | 4 | 1.77 ms | 564 |
| **192** | **512** | **6** | **3.53 ms** | **283** |
| 256 | 704 | 6 | 5.34 ms | 187 |
| 320 | 832 | 8 | 9.47 ms | 106 |
| 512 | 1344 | 8 | 248.82 ms | 4 |

**目标配置：`d=192, L=6, H=6, vocab=4096, max_seq=512`**，约 3.4M 参数。
本机应测到 ≥ 250 tok/s（比合成基准略低），给目标机留余量。

`d=512` 掉 20 倍是 cache 溢出（L3 25MB 被 12 线程分食）—— 请注意这是**工作集**问题。

## 要做的事

### 1. 新增配置档 `configs/demo-3m.json`

```json
{"vocab_size": 4096, "dim": 192, "n_layers": 6, "n_heads": 6,
 "ffn_mult": 4.0, "max_seq": 512, "qk_norm": true, "tie_embedding": true}
```

`lightprism config configs/demo-3m.json` 必须报出约 3.4M 参数。

### 2. KV cache（核心工作）

- 给 `Attention` / `Block` / `LightPrismModel` 加可选的 `past_kv` 参数
- 新增 `model.incremental_forward(input_ids, past_kv)` → `(logits, new_kv)`
- **必须保证数值一致**：同一序列，「全量重算的 logits」与「增量算的 logits」
  在 `atol=1e-4` 内相等。这条要有测试（`test_kv_cache_matches_full`）
- RoPE 位置编码在增量模式下要用**绝对位置**，不能每次从 0 开始

### 3. `scripts/bench.py`（口径必须写死）

```
单线程（torch.set_num_threads(1)）
贪心解码
prompt 长度 32
生成 200 token
丢弃前 10 token 作为预热
报告：tok/s、峰值 RSS（读 /proc/self/status 的 VmHWM）
```

**口径写死在脚本里，不接受命令行覆盖** —— 不写死口径的「200 tok/s」是假的。
如果要做单线程 vs 多线程对比，另开 `--mode` 参数并分别报告。

### 4. 单线程优先

目标机是 8GB 内存的 5 代酷睿，可能是 4 核。**以单线程数字为准**，
多线程作为加速项单独报告。多线程在 decode 阶段往往因同步开销反而更慢，要实测。
