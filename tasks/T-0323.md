## 背景

测试质量评分 8.0/10 的扣分点写得很明确：**单仓测试、无覆盖率门**。8489 用例 0 失败是结果指标，没有覆盖指标就不知道哪些路径没人触达——而这正是 AI 生成代码最容易钻的盲区。

注意：`.gitea/workflows/ci.yml` 头部注释写明 `pytest-cov` 曾装上但从未使用、2026-08-22 已去掉。**不要装回 pytest-cov**，用 `coverage` 独立跑。

## 要做什么

1. `scripts/check_coverage.py`（纯标准库）：
   - 输入 `coverage.json`（`coverage json` 产物），默认路径 `coverage.json`，`--coverage-json` 可指定；
   - 只统计四个核心文件的行覆盖：`src/lexer.py`、`src/light_parser_v3.py`、`src/compiler.py`、`src/code_generator.py`；
   - 默认阈值 70（`--min` 可调），逐文件判定，低于阈值列出**未覆盖行号区间**（压缩成 `12-18, 40, 55-57` 形式）；
   - rc 契约：`0` 全达标、`1` 有文件不达标、`2` 输入缺失/格式错误（并打印「怎么生成」的一行命令）。
2. `.coveragerc`：`source = src`，`omit = tests/*, tools/*, examples/*, scripts/*`。
3. `.gitea/workflows/ci.yml` 增加一步（放在现有 pytest 之后，不改动既有测试选择与超时预算，新增步骤 ≤180s）：
   `coverage run -m pytest -q <现有选择>` → `coverage json` → `python scripts/check_coverage.py`。
   若 CI 里跑全量会超预算，允许复用已有 pytest 选择，但必须在 yml 注释里写清「覆盖统计的范围 = 这一步的测试选择」。
4. `tests/test_coverage_gate.py`：用伪造 `coverage.json` fixture 测边界——69.9 红 / 70.0 绿、单文件缺失、未覆盖区间格式化、rc 契约、`--min 0` 放行。
5. 在 `docs/` 现有测试相关文档（或新 `docs/覆盖率门禁.md`）写：报告在哪看、未覆盖路径如何反馈成 lightharness 的「故意触发边缘情况」用例。

## 不要做什么

- 不给全仓设门槛（只四个核心文件），不因覆盖率删测试或加 `# pragma: no cover` 糊过去。
- 不引入 pytest-cov；不改变现有 CI 的测试选择逻辑与超时数值。
- 不动 `.github/workflows/`（另一套流水线，另开卡）。

## 完成标准

- `python -m pytest -q tests/test_coverage_gate.py` 全绿。
- summary 里贴：本机跑出的四文件真实覆盖率数字（若本机跑不动全量，注明用了多大子集）、CI 新增步骤的 diff。
