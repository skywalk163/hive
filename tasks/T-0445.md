# 光明：Windows 上偶发「内存错误 / 栈溢出」，把下游判据打成假红（先做最小复现与归因）

> 来源：lightharness T-0442（工具层 5 缺陷）验收期间，2026-11-23 Windows 主机实测。

## 现象

同一份代码、同一台 Windows 机器、同一版光明：

- `tests/unit/test_工具执行.py` 里 2 条用例报「内存错误」（光明把 `MemoryError` 显示为中文），同一文件的其余 18 条绿；
- `examples/test_R42_真实工具链.light` 报栈溢出（Python 递归上限）；
- 换到 192.168.0.88（FreeBSD 15.1，python3.12）同一份快照，同文件全绿；
- 隔一天同一台 Windows 复跑，**又全绿**。

也就是说这是**偶发**、且只在 Windows 侧出现：既可能是光明代码生成器在大模块上递归/复制过深（AST 展开、字符串拼接、嵌套结构导致指数级增长），也可能是宿主资源瞬时不足。目前没有最小复现，任何「已修复」的结论都不成立——这张卡要先把这件事钉死。

## 这一轮要交付什么

1. **最小复现**：把 lightharness 的两个红用例缩到一个或几个 `.light` 文件，稳定（或高概率）复现 `MemoryError` / `RecursionError`，产出可独立运行的脚本；不允许依赖 lightharness 全仓、外网或特定目录残留。
2. **归因报告**：明确是光明侧（词法/语法/代码生成/编译期常量折叠/字符串拼接）还是宿主侧（内存上限、递归上限、编码）。给出证据：进程峰值内存、递归深度栈、生成的 Python 源规模（行数 / 字符数）、失败点调用栈。
3. **修复或明确边界**：
   - 若属光明侧，修生成器/解析器的深递归或重复复制，并补大模块判据；
   - 若确属宿主资源，卡面写清阈值与证据，给出可操作建议（如 `PYTHONRECURSIONLIMIT`、分模块编译），并**转 closed 说明不是光明缺陷**，不许硬凑成「修好了」。

## 判据

新增 `tests/test_R225_win_memory.py`：

1. 最小复现用例：在 Windows 上 10 次连跑，修复前至少失败 1 次可复现（失败样本写进卡）；修复后 10 次全绿，且峰值内存有记录；
2. 大模块编译/运行基线：构造 ≥200KB / ≥4000 行的 `.light`，编译耗时与峰值内存有上限断言（阈值在卡内实测后定，不许拍脑袋）；
3. FreeBSD（192.168.0.88）同文件同样全绿，防止把 Windows 修复变成 POSIX 回归。

反证：故意把生成器的递归改回旧实现 → 第 1/2 条必须真红。

## 红线

- 不许把 lightharness 的红用例改成 skip / xfail 来「变绿」；
- 不依赖外网、真实凭证、特定目录残留；复现脚本自带 fixture；
- 若最终判定为宿主问题，必须留下「为什么是宿主」的硬证据（同机连跑统计 + 内存曲线），否则不许关闭；
- 不做无关重构，不动 L0 核心字与语法契约。

## 已知线索

- 失败点集中在「让光明编译并运行较大的 harness 模块」这一路径（`src/工具执行.light` 相关用例、`examples/test_R42_真实工具链.light`）。
- Windows 侧 python 3.13.18，光明的中文异常名把 `MemoryError` 显示为「内存错误」，容易和「编译器内存不足」混淆，归因时注意区分。
- 失败的两次都发生在多文件连跑、机器已跑过其他编译任务之后；疑似累积/瞬时资源，非确定性输入。
