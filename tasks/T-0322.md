## 背景

评审指出：lightharness 的 240 个模块是真实工程体，但「每个模块编译通过不等于可用」。要跑**场景级**回归——比如「发起一个 HTTPS 请求并解析 JSON 响应」作为一个场景，而不是「网络请求模块存在」作为一个能力。

lightharness 在本机路径 `../lightharness`（各 agent 机器上按需设置 `LIGHTHARNESS_DIR`）。本卡在 **light 仓**内落测试，跨仓只读，不修改 lightharness。

## 要做什么

1. `tests/dogfood/test_lightharness_smoke.py`：
   - 模块发现：`LIGHTHARNESS_DIR`（缺省 `../lightharness`），目录不存在 → `pytest.skip` 且打印「未找到 lightharness，跳过（不是通过）」；
   - 抽样**确定化**：按相对路径排序取前 N（N 由 `LIGHT_DOGFOOD_LIMIT` 控制，默认 20），**禁止随机**；用参数化生成用例，用例 id 带模块路径；
   - 每个模块跑 `python -m cli.light check <file>`（纯语法/类型检查，不执行副作用代码），记录 rc 与 stderr 首行。
2. 基线机制：
   - `tests/dogfood/baseline.json`：首次落地时记录**当前失败模块清单**（诚实记录欠账，不是清零）；
   - 断言：`失败集合 ⊆ 基线集合`，新增失败即红；基线只能**缩小**，测试里检测「基线里有但这次已通过」的条目并提示可从基线删除；
   - 报告写 `build/dogfood_report.json`（模块、rc、耗时、错误码首行）。
3. 场景级（不止编译）：挑 5 个可执行模块，真跑其入口（`python -m cli.light run`），断言 rc=0；跑不动的用 `xfail(strict=True)` 并在 `docs/吃狗粮回归.md` 写明原因。
4. `docs/吃狗粮回归.md`：怎么跑、报告字段、基线怎么更新（只能下调，上调需说明理由）、如何把新发现转成 light 缺陷卡。

## 不要做什么

- 不修改 `../lightharness` 下任何文件（只读）。
- 不修 light 本体缺陷；发现即写进报告并在 summary 里给「建议开卡」清单（文件 + 行 + 现象 + 最小复现）。
- 不把基线调大来让测试变绿。
- 不联网（本地模块发现即可；需要网络的场景标 xfail 并注明）。

## 完成标准

- `python -m pytest -q tests/dogfood/` 全绿（无 lightharness 时允许全 skip，但 summary 必须说明本机是否具备条件）。
- summary 里贴：抽样模块数、通过/失败/基线欠账数、5 个场景结果、建议开卡清单。
