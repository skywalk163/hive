## 背景：主控被「假红」骗了一次

2026-11-21 主控（FreeBSD fb98）复核 T-0433 时，按卡面 verify 跑了真正的门禁：

```bash
sh scripts/gate.sh
```

结果 **FAIL 7 条**，全部长这样：

```
# github.com/lightmem/kernel
../../../go/pkg/mod/modernc.org/libc@v1.55.3/libc.go:35:2:
  github.com/mattn/go-isatty@v0.0.20: Get "https://proxy.golang.org/...": i/o timeout
FAIL github.com/lightmem/kernel [setup failed]
```

**这不是代码问题，是本机连不上 proxy.golang.org**。换成国内代理后立刻全绿：

```bash
GOPROXY=https://goproxy.cn,direct sh scripts/gate.sh
========== R15 门禁矩阵 ==========
PASS: 13    FAIL: 0    SKIP: 2    模块数: 2
```

危害：`gate.sh` 的失败**看起来和真失败一模一样**（`FAIL ... [setup failed]`），
主控若不了解 Go 代理这层，会直接把卡打回、或者误判「这批改动引入了回归」，
白白浪费一轮返工。T-0433 主控就差点这么干。

## 期望修法（小而准）

1. **`scripts/gate.sh` 增加可操作提示**：当 go 步骤失败、且输出里命中
   `i/o timeout` / `proxy.golang.org` / `dial tcp` / `[setup failed]` 时，
   在汇总前多打一行，例如：
   ```
   ！ 检测到 Go 模块下载超时：这是网络/代理问题，不是代码问题。
     墙内或离线环境请重试：GOPROXY=https://goproxy.cn,direct sh scripts/gate.sh
   ```
   只在命中时打印，正常路径一个字都不多。

2. **文档记一笔**：`CONTRIBUTING.md`（构建/门禁章节）与 `AGENTS.md`（开发约定）
   各加一句「离线或墙内需配 `GOPROXY`」，并说明**看到 `[setup failed]` 先怀疑网络**。

3. 不要做的事：**别把 go 步骤改成容忍失败**（那会让真回归也变绿）；
   也别在 gate.sh 里硬编码 GOPROXY（改变默认行为，可能让 CI 行为漂移）。
   只做提示 + 文档。

## 判据（可反跑）

```bash
# 1) 正常网络下：gate.sh 输出里不得出现上面的提示（不能每个环境都刷）
sh scripts/gate.sh >/tmp/g.txt 2>&1; grep -c 'Go 模块下载超时' /tmp/g.txt   # 期望 0

# 2) 文档确实写了
grep -l 'GOPROXY' CONTRIBUTING.md AGENTS.md

# 3) 反跑（可选，需能复现超时）：临时 GOPROXY=off 跑一次
GOPROXY=off sh scripts/gate.sh; echo rc=$?    # 期望非 0 且输出含提示
```

反跑要点：第 3 条在能复现「下载失败」的机器上做；若本机模块已全部缓存，
`GOPROXY=off` 可能仍然全绿 —— 那时用 `GOFLAGS=-mod=mod GOMODCACHE=/tmp/emptycache GOPROXY=off`
构造一个干净模块缓存来复现。
