# 投票闸门 `store_behind` 硬拒绝：落后节点互相否决，无主窗口被拉长

## 一、现象

选举期间反复出现 `本轮选举未获多数：term=N（1/3 票）`：票池里明明有 3 个节点，
候选人只拿到自己 1 票。排除网络不可达后，剩下的解释就是同伴**明确拒绝投票**，
其中一条硬拒绝规则就是 `store_behind`。

## 二、证据锚

- `hive_cluster.py#L2850-L2863`：

  ```python
  my_seq = self.store.commit_seq() if self.store else 0
  cand_seq = int(cand.get("last_store_seq") or 0)
  behind = cand_seq < my_seq
  if behind and not forced:
      return 200, {"granted": False, "reason": "store_behind", ...}
  ```

- 同段注释（`#L2852-L2856`）自己写明：「hive 的 store 只是缓存、git 才是事实账
  （见 StoreReconciler），落后能在当上主控后从卡面补回来」——即代码作者自己也认为
  这不是安全红线，却用了硬拒绝。
- 分区时各节点 commit_seq 必然不一致，于是**互相**认为对方落后 → 全员拒票 →
  直到同伴被 `dead_timeout=15s` 判死、quorum 退化为 1 才「当选」（见 T-0294）。

## 三、为什么是缺陷

- store 是可重建缓存，不是唯一事实源；用缓存序号做选举否决权，等价于把
  「数据新鲜度」错误提升为「选举资格」，在分区场景必然导致长时间无主。
- 与 T-0294 的退化 quorum 叠加，会产生「先全员拒票、再孤身称主」的错误主节点，
  比单纯选不出来更危险。

## 四、修复方向（只改 `hive_cluster.py`）

1. 默认**允许**落后候选当选：投赞成票，但把落后量写进 `leader_forced` / 新事件
   （如 `vote_store_lag`）留痕，并在候选人当选后**强制先 reconcile** 再服务写请求。
2. 保留「严格模式」作为可选策略（环境变量或构造参数，默认关闭），供管理员选择
   「宁可没有主控，也不接受落后节点」；严格模式命中时必须 emit 明确原因。
3. 与当选后的 `StoreReconciler` 对齐：上任后先对齐 `commit_seq`，再开放 claim/submit。

## 五、验证方式（修复后应全绿）

```bash
python -m pytest -q tests/test_vote_store_behind.py
python -m pytest -q tests/test_cluster_sync.py
```

新增测试至少覆盖：默认模式下落后的候选人也拿到赞成票且留痕；
严格模式仍拒绝并给出 `store_behind`；落后当选后 `commit_seq` 被对齐。

## 六、风险与边界

- 允许落后主会带来短暂的「读到旧状态」窗口，**必须**与「上任先 reconcile」配套，
  否则本卡会引入新的不一致。
- **不改** quorum / 退避（T-0294），不改地址校准（T-0293），不改 `hive.py` 的提交逻辑（T-0296）。
- 不改 `state.json`、不改运行时配置；不动其它卡面与 agent 配置。
