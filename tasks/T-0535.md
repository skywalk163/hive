## 背景

T-0497 双级可见性卡在领卡时踩到一个 hive 流程漏洞（结果摘要与 card 讨论已记录）：

- 领卡时 `hive_claim` 报「T-0497 已关闭」，但 git 卡面已是 `state: ready`（controller `reopen` 过）。
- 根因：`cmd_reopen()` 只改 git 卡面、删除 res/claim 分支，**没有清 store 侧**——leader store 里任务仍是 `done` 且留着归档结果，硬白名单式的领卡闸门因此挡住领取。
- 当时的处置是人工调 `store_retry("T-0497")`（`hive_store.Store.retry(clear_result=True)`）把 store 侧 task 置回 `ready` 并清掉陈旧结果，才领到卡。

T-0497 明确建议：**单开一张卡让 `hive reopen` 在 store 模式下补 store 清理**，否则每次重开都要人工修台账。扫 T-0498~T-0531 全部卡面/结果，没有任何卡覆盖这个问题。参见收口报告 §3.2 第 4 项。

## 目标

1. `cmd_reopen()`（含 CLI 与 MCP controller 入口走的同一条实现）在 store 模式下做与 git 侧一致的清理：
   - store 侧 task 状态置回 `ready`（不是 `assigned`/`done`）；
   - 清掉该 task 的陈旧 result（含 results 分支对应记录）；
   - 清掉/重置 claim、lease、archive_pending 等关联状态，使 `hive_claim` 能立即重新领取。
2. Git 侧与 store 侧清理保持原子语义：任一侧失败要有明确报错，不留"git ready 但 store done"的半状态。
3. 补回归判据覆盖 reopen 后立刻 claim 成功的完整回路（当前应红：reopen 后 claim 被 store 闸门挡住）。

## 交付物

- `hive.py`（`cmd_reopen` 及其共用实现）
- 可能的 `mcp_server.py` / controller 工具面（若 reopen 有独立入口）
- `tests/test_reopen_store_cleanup.py`（新增回归）

```
python -m pytest -q tests/test_reopen_store_cleanup.py

python -m pytest -q tests/test_mcp_controller.py
```

判据要求（用临时 store + 临时 git 仓起测试夹具，不碰生产 store）：
- 建一张卡 → submit（store 记 done）→ reopen → 断言 store 侧 task.state=ready、result 不存在、claim/lease 清空；
- reopen 后 `hive_claim` 立即成功（当前代码在这步失败，构成反证）；
- 反证：临时把 store 清理调用去掉 → claim 被挡的用例转红；恢复后全绿；
- git→store 状态不一致（如 git ready / store done）的场景有明确报错，不静默。

## 红线

- 不改 claim/submit/land 的正常路径语义；
- 不绕过 result 闸门（T-0205 的结果验收漏洞修复必须保留）；
- store 未启用（git-only 模式）时 reopen 行为不变（向后兼容）。
