# 定义并落盘「编辑前后」日志格式

> 这是 LightPrism 修复样本（`<V:ERR=…>` → `<V:PASS>` 配对）的**唯一**可能来源。

## 背景（为什么必须做，不是「为了更好」）

`lightprism/docs/样本导出.md` 已证明：`light ai check` 的报错归档**结构上导不出修复样本**。

- `source_hash` 是对**出错那一刻**的源码算的；
- 代码没改 → hash 匹配 → 现跑必然仍失败；
- 代码改好 → hash 变了 → 永远关联不上那条记录。

实测证据（同文档 §2.2）：把 `打印(甲[9])` 改成 `打印(甲[0])` 后，
hash 从 `3f8e1a3acc644768` 变成 `1284d1e5c731b464`，记录直接落 `skipped_no_source`。

所以「同一文件从坏到好」的配对只能来自**记录了编辑动作的日志**。而
`docs/样本导出.md` §4 明确写了：**该格式目前不存在**。核对现状（2026-11-11/12）：

```
lightharness/logs/           只有 day2-deep/ day3/，是过程产物
lightharness/logs/T4_watch.jsonl 一类是进程监控，不含编辑前后内容
```

不用这个格式的后果：LightPrism 判据 ②（真实一次通过率）与真实决策监督**永远无法评测**，
只能拿「JSON 精确匹配代理」凑数。

## 要做的事

### 1. `docs/编辑日志格式.md`：定义 schema v1（JSONL，一行一条）

一条记录 = **对同一个文件的一次编辑 + 编辑前后各一次 `light ai check` 的结果**。

必须包含字段（命名可调，语义不许少）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `schema_version` | int | 固定 `1` |
| `event_id` | str | `<hostname>-<microsecond>-<rand>`，用于多节点去重 |
| `ts` | str | ISO8601 带时区，如 `2026-11-12T17:30:00+08:00` |
| `session_id` / `task_id` / `agent` | str \| null | 谁在什么任务里做的 |
| `repo` / `file` | str | `file` 用 **repo 相对路径**（不落绝对路径，避免泄露本机目录） |
| `file_hash_before` / `file_hash_after` | str | 换行归一化后 `sha256(...)[:16]`，与 light 归档同口径 |
| `edit_kind` | str | **`FR` / `RW` / `PATCH`** —— 必须与 LightPrism 决策点 `EDIT` 的选项集对齐 |
| `diff` | obj | `{unified: str}` 或 `{before: str, after: str}`；超大文件允许截断但要标 `truncated` |
| `check_before` | obj \| null | `{ok, code, severity, stage, message}`，取 `light ai check --run --json` 的**首条 error 级诊断** |
| `check_after` | obj \| null | 同上 |
| `outcome` | str | `fixed` / `still_failing` / `regressed` / `unknown`，**由前后 check 推导，不许人填** |
| `light_version` / `backend` | str | 复现所需 |

`outcome` 的判定规则要写死并测试：
`check_before.ok=false ∧ check_after.ok=true → fixed`；
`false→false → still_failing`；`true→false → regressed`；任一缺失 → `unknown`。

### 2. `scripts/编辑日志.py`：写入 + 校验 + 回放（纯标准库，单文件可跑）

- `record(...)`：append 到 `$LIGHTHARNESS_EDIT_LOG_DIR` 或 `~/.lightharness/edits/<YYYY-MM>.jsonl`；
  **append-only**，同一 `(file_hash_before, file_hash_after, ts)` 重复不写第二次；
- `validate <path>`：逐行校验 schema，非法行**报行号**，不要静默跳过；
- `dump --json`：按 outcome/时间过滤，给下游导出器用；
- `--self-test`：不依赖外部文件，内置 4 条 fixture（fixed / still_failing / regressed / unknown）
  跑通 schema + 去重 + outcome 推导。

### 3. 接一个**真实编辑路径**，证明格式能被写出来

`scripts/安全替换.py` 已具备「词法感知替换 + `--out` 落盘 + 拒绝覆盖输入」，
是最自然的挂载点。要求：

- 加 `--edit-log`（默认开）：成功写盘后记一条 `edit_kind`（整串替换记 `PATCH`，
  全文件重写记 `RW`，逐个标识符替换记 `FR`，按实际行为选，不要乱标）；
- 加 `--check`：编辑前后各跑一次 `light ai check --run --json --no-corpus`
  （`--no-corpus` 是为了不污染 `~/.light/error_corpus`），填 `check_before/after` 与 `outcome`；
- 不传 `--check` 时 `check_*` 写 `null`、`outcome=unknown`，**不许猜**。

### 4. `tests/test_编辑日志.py`

至少覆盖：schema 必填字段缺失要报错、outcome 四种推导、重复 append 去重、
`file` 必须是相对路径（拒绝 `/` 开头）、`edit_kind` 只接受 FR/RW/PATCH。

## 完成标准

```sh
python scripts/编辑日志.py --self-test          # 全绿
python -m pytest -q tests/test_编辑日志.py       # 全绿
python scripts/安全替换.py --self-test           # 原有自测不许回归
```

再加一条**端到端证据**（贴进 PR 描述，不许只写「已实现」）：

```sh
# 造一个坏文件 → 修好 → 看日志里是不是 fixed
python scripts/安全替换.py /tmp/bad.light '甲[9]' '甲[0]' --out /tmp/fixed.light --check
python scripts/编辑日志.py dump --json | tail -1
# 期望：check_before.ok=false、check_after.ok=true、outcome="fixed"
```

## 禁止

- **不要伪造日志**。`--check` 跑不出真实结果就写 `null` + `unknown`，不许手填 `fixed`。
- **不要落绝对路径**（`file` 必须 repo 相对），`diff` 里若含本机路径要打码。
- **不要改 lightprism 仓**：解析器/导出器是另一张卡（跨仓，走新卡）。
- 不要动 `scripts/安全替换.py` 的既有替换语义与 `--self-test`，只加日志与 check 钩子。
- 不要引入第三方依赖（纯标准库）。

## 已知事实（本机 2026-11-12 实测，省得你再摸）

```sh
# 真实 checker 可用，退出码 1=有 error 级诊断
python3 /home/skywalk/dswork/light/cli/light.py ai check /tmp/bad.light --run --json --no-corpus
# stdout 最后一行是一个 JSON：{"schema_version":1,"ok":false,"diagnostics":[{code,severity,stage,line,message,hint,...}]}
```

`diagnostics` 里同时有「语法检查」和「运行」两个 stage 的诊断，取**第一条 `severity=="error"`** 即可。
