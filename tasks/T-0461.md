# light-mcp：把 check / run / patch 变成 agent 能直接调的三个工具

## 背景

光明的 AI 能力目前全是 **CLI 子命令**：`light ai check --json`、`light patch`、`light run`。
agent 要自己拼 shell、自己解析 stdout、自己处理编码——每一步都可能翻车（中文路径、Windows 代码页、超时）。

MCP 是当下 agent 的统一工具面：接上之后，任何支持 MCP 的宿主（Cursor / Claude Code / WorkBuddy / 各种 agent 框架）都能**零代码**调用光明。这既是体验问题，也是**分发渠道**问题——竞品（如 MoonBit）已经用 `SKILL.md` + Wasm skill 在占这个位。

`mcp.example.json` 现在是 0 字节占位。

## 要做什么

纯标准库实现一个 stdio MCP server（**不要引 `mcp` SDK，不要新增依赖**），骨架照 `C:/dswork/hive/mcp_server.py` 的 JSON-RPC 写法：

`mcp/light_mcp.py`，支持 `initialize` / `notifications/initialized` / `tools/list` / `tools/call` 四个方法，暴露三个工具：

| 工具 | 入参 | 返回 |
|---|---|---|
| `light_check` | `path`, `strict?: bool`, `run?: bool` | `light ai check --json` 的原样 JSON + `ok` |
| `light_run` | `path`, `args?: string[]`, `timeout_s?: int` | `{rc, stdout, stderr, duration_ms}` |
| `light_patch` | `path`, `span: {line, column, end_column}`, `replacement` | `{new_text}`（**只返回，不写盘**） |

要求：

1. **永不抛未捕获异常**：工具内部错误走 `{"content":[{"type":"text","text":"..."}],"isError":true}`，进程不退出。
2. 所有返回都是**结构化 JSON 字符串**，字段名与 `light ai check --json` 保持一致（agent 要能跨两个入口复用解析逻辑）。
3. `light_patch` 的 span 语义必须和 `light patch` 一致（行/列 1-based，端列不含）。复用 `src/patch_engine.py`，不要重写。
4. 中文路径、Windows 编码：统一 `encoding="utf-8"` + `errors="replace"`，子进程给 `PYTHONIOENCODING=utf-8`。
5. `mcp/README.md`：一页说清怎么在宿主里配（含 `mcp.example.json` 的完整示例，含 Windows 路径写法）。
6. `mcp.example.json`（仓库根，0 字节那个）填成可用配置。

## 不要做什么

- 不改 `cli/light.py`（T-0464 地盘）
- 不加依赖、不联网、不实现 HTTP/SSE 传输（只 stdio）
- 不在 MCP 层做业务判断（比如"这个错误该不该修"）——只搬运结构化结果
- 不写盘（`light_patch` 只返回新文本）

## 完成标准

- `tests/test_T0461_mcp.py`：
  - 起子进程，喂 `initialize` → `tools/list`，断言三个工具名齐全、schema 有 `inputSchema`
  - `light_check` 对坏文件返回 `ok:false` 且 `diagnostics` 非空；对好文件 `ok:true`
  - `light_patch` 返回的 `new_text` 与 `light patch` 命令行输出一致（同输入对比）
  - 传一个不存在的 path，断言 `isError:true` 且进程仍活着（后续还能响应一次 `tools/list`）
- `mcp.example.json` 能被 `json.load` 解析且含一个 server 条目
