## 背景

T-0540（基线红灯与 worker 崩溃收口）在干净 HEAD `f91285c` 上跑全量
`python -m pytest -q tests`（FreeBSD 15.1 / `fb98` / Python 3.12.13 / pytest 8.4.2 /
xdist -n 4，3051 例 / 1483.66s）结果：**3024 passed / 16 skipped / 4 xfailed / 7 failed**。
其中 1 条是 T-0540 卡内的 R23（已修），另 6 条与本卡无关，是同一批
**注册表 168 vs 160 计数漂移**的余波。T-0540 已按「不越界」红线未改，本卡收口。

## 现状（本 HEAD 实测，2026-11-28）

单跑这 6 条恒红（非偶发，隔离复跑签名一致）：

```
python -m pytest -q tests/test_T0501_命名映射表.py tests/test_T0511_守卫一致性回归.py
→ 6 failed, 11 passed in 44.31s
```

- `tests/test_T0501_命名映射表.py::test_与真实注册表逐位一致` —— 反向判据点名 5 个
  「既不在 §6 映射表基线、也不在不上叶子表、也不以 mcp__ 开头」的工具：
  `交付登记`（域 其他）、`交付列出`（域 其他）、`交付完成`（域 其他）、
  `交付关联`（域 其他）、`查询会话`（域 session）。
- `tests/test_T0511_守卫一致性回归.py` 5 条 —— 断言写死注册表 160、`档位计数`
  = `{read_only:72, reversible:36, semi:5, irreversible:47}`，而本机 real 驱动打出
  `总数=168`、不可逆 48，于是 `168==160`、`48==47`、
  `日志 确认项 47 != 46` 全部失败。

## 根因（与 T-0533 同类，判据环境依赖）

这不是守卫逻辑缺陷，也不是映射/分级表缺项，而是**判据把随环境/插件配置变化的
注册表规模写死成基线**：

1. 注册表规模取决于运行环境的 lightplugin 挂载与 MCP 配置。本卡本机
   `LIGHTPLUGIN` 兄弟仓存在（`/home/skywalk/.hive/wt/lightplugin`），
   `组装注册表()` 实得 **168**；T0511 文件头第 36–39 行自己已记录
   「当前 main 注册表是 160/72/36/5/47（8 条已不在注册表）」——两份口径并存。
2. T0501 §6 映射表基线固定 160 行（`基线工具数 == 160`、`编号 0..159`），
   注册表新增的 5 个「交付/查询会话」工具没进这张基线，反向判据即判红。
3. **同类问题已由 T-0533（已合入）在 T0508 上根治**：
   `tests/test_T0508_可逆性分级.py` 现在从真实 `组装注册表()` 的 dump 实时推导
   总数/四档计数（不写死），只保留「静态分级表条数 >= 注册表总数」的关系断言 +
   关键工具逐名钉位，插件关（REG=160）/开（REG=168）两种环境都绿。
   T0501/T0511 尚未套用这个口径。

判据强度不能降：修完必须在 160 与 168 两种注册面下都绿，且关键工具的档位/
映射逐名断言必须保留——不是把红断言删掉或放宽到「>=0」。
