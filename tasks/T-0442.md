## 背景

lightharness 是给 LLM 编码代理用的 harness（工具：`bash` / `read_file` / `write_file` / `search_files`）。
工具层是代理感知环境的唯一入口：它把失败当成功、把成功当失败，代理就会在错误的地基上继续叠操作。
本次实测中，两轮任务卡死均由工具层问题直接引发。以下 5 处缺陷必须逐条修复，
保持向后兼容（**不改变成功路径的返回结构**），每条补一个回归测试锁住行为。

## 缺陷 1：`search_files` 内容模式的「匹配行」字段恒为空 【高】

- **复现**：`search_files(模式="内容", 查询="lightharness")`。
- **实测**：命中 10 个文件，但每个结果的 `"匹配行"` 字段全部是空字符串 `""`。
  文件名本身不含 "lightharness" 的（如 `README.md`、`pytest.ini`）显然靠内容命中，却拿不到任何命中上下文。
- **后果**：代理搜到文件后仍必须再开一次 bash 跑 grep 才知道命中了什么，一次调用被迫变两次；
  对「定位某段代码残留」类任务基本不可用。
- **期望**：内容模式命中时，`匹配行` 返回实际命中行的文本（建议带行号，如 `"75:        r'G:\\dswork\\...'"`）；
  多处命中至少返回第一处；无命中保持空串。

## 缺陷 2：`bash` 执行失败命令时退出码误报 0 【高】

- **复现**：执行 `echo x > /tmp/probe.light`（在受限工作目录下重定向被系统拒绝）。
- **实测**：`"错误": "sh: cannot create /tmp/probe.light: 拒绝访问"`（stderr 有实质错误内容），
  但 `"退出码": 0`。
- **后果**：代理按退出码判断「写成功了」，实际文件根本没落地。这类「stderr 骂人、退出码报喜」的误报
  会让代理在错误状态上继续叠加操作。
- **期望**：退出码如实透传 shell 的真实退出码；若 stderr 非空而退出码为 0（重定向失败等 shell 层错误），
  至少返回非 0，或附加明确的失败标记。

## 缺陷 3：命令被超时 SIGTERM 杀死后，返回「空输出 + rc=-15」且无任何超时说明 【高】

- **复现**：执行任何会卡住 30 秒以上的命令（如一条等待网络/凭证输入的 `git push`）。
- **实测**：`"输出": ""`、`"错误": ""`、`"退出码": -15`。没有任何一句话告诉代理「命令超时被杀」。
- **后果**：rc=-15 需要代理自己猜是 SIGTERM；输出为空则完全无法区分「卡死被杀」和「正常无输出」。
  本次会话里代理一开始就把 -15 当成了普通失败，浪费了整轮诊断。
- **期望**：超时杀进程时，显式注明「命令执行超过 30 秒被强制终止（SIGTERM）」，
  并尽量附上被杀前已产生的部分 stdout/stderr；退出码字段建议规范化（如保持 -15 但在错误字段写明原因）。

## 缺陷 4：长命令 30 秒超时偏紧，且交互式卡住时静默挂起无提示 【高】

- **复现**：`git push` 到需要凭证的 HTTP 远端，git 提示 `Username for 'http://...': ` 等待 stdin ——
  该提示没出现在 stdout/stderr 里，命令静默挂到超时。
- **后果（实测两次）**：本会话中 `git push` 因此连续两轮空手而回；代理无法从返回值中得知「它在等我输入」。
- **期望**：
  - 至少其一：超时上限可由调用方指定（如参数 `timeout`，默认 30s）；或对已知的网络类命令放宽；
  - 子进程 stdin 置为关闭（`stdin=DEVNULL`），让交互式提示（Username/Password 等）立刻失败而不是挂 30 秒；
    git 挂起前打出的 `Username for ...` 提示应能出现在 stderr 里供代理识别；
  - 失败信息里给出可操作建议（如「命令可能在等待终端输入」）。

## 缺陷 5：疑似同一条 bash 调用被执行两次，成功路径的输出被吞掉 【高】

- **复现**：一条 `git add ... && git commit ... && git push ...` 的 `&&` 链。
  仓库实际状态显示 commit 已成功创建（`git log` 可见提交），但工具返回的却是**失败那次**的输出
  （「无文件要提交，工作区干净」，退出码 1）——看起来同一调用被跑了两次，第一次的成功输出没有返回给代理，
  只有第二次扑空的输出。
- **后果**：代理看到 rc=1 认为提交失败而走重试/诊断路径；若链条后面还有 push 等步骤，
  会因为 commit 返回非 0 被 `&&` 短路，永远不执行——本次正是因此漏推了一次。
  属于「成功输出被吞 + 疑似重复执行」的组合缺陷。
- **期望**：
  - 排查同一调用是否被重试执行（幂等命令会被第二次运行掩盖第一次的结果，非幂等命令则产生副作用）；
  - 若确有重试机制，只应重试在**工具调用层**失败（超时/无响应）的调用，
    且要把两次尝试的输出都返回或在错误字段说明「第一次已成功」；
  - 正常单次执行时必须返回**那一次**的完整输出与退出码，不得只回显末次。

## 实现线索（供参考，不限于这些文件）

- `src/工具_搜索文件.light`：`搜内容()` 命中时写死 `"匹配行": ""`，需按行读取并返回命中行文本 + 行号。
- `src/工具_bash.light`：`bash处理()` 有两条执行分支——有任务控制上下文时走 `进程树`，
  否则走 `外部命令.执行命令(命令, 真, 根, 空, 30)`；两条分支的超时/退出码/stdin 行为需要一起收口。
- `stdlib/外部命令.py`：`执行命令()` 的 `subprocess.run` 未传 `stdin=DEVNULL`；
  `TimeoutExpired` 分支返回 `返回码=-1`、`标准错误="命令超时（N秒）"`（需核对与 bash 工具实际观察到的 -15 的路径差异）。
- 若确认存在工具调用层重试，排查其所在模块（工具执行 / 代理循环 / web 服务端），禁止对非幂等命令盲目重试。

## 验收标准（每条缺陷对应）

1. 构造含关键词的文件，`search_files` 内容模式返回非空「匹配行」且带行号；
2. 构造必失败的 shell 命令（如 `ls /不存在的路径`、重定向被拒场景），退出码非 0；
3. 构造 `sleep 60`，返回值明确含「超时被终止」字样；
4. 构造等待 stdin 的命令（如 `git push` 到需凭证远端，或直接 `cat` 无输入），立即失败并给出「等待输入」类提示，
   而不是挂 30 秒；调用方可用参数覆盖超时；
5. 对 `mkdir` / `git commit` 这类非幂等命令做 10 次连续调用压测，
   断言每次返回的都是该次自己的输出、无重复执行的副作用（如目录已存在报错）。
