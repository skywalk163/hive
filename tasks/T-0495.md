## 背景

T-0443 已把判据 ③ 的剩余缺口归到「早收尾失败」，不是预算不够：55 条 test 目标最长 434 token，512 预算对任何样本都不短；A 组仍截断 3 条 → 3 条都是「该吐 `<V:…>` 时没吐」。

但代码里还留着一处**口径漏洞**和一处**未核对的一致性**：

1. `generate()` 用 `truncated = len(generated) >= max_new` 从长度反推截断。若模型**恰在第 max_new 步吐完收尾 token**，循环 `break` 时 `len == max_new`，会被误记成截断，再由 `n_struct_ok_all` 算成失败——这是把「刚好卡点上完成」判成失败。
2. 判据 ③ 用 **free（不约束）** 生成，`constrained` 只做对照。两条路径的停止条件不同：free 只能靠模型自己吐 `<V:…>`，constrained 在 `</CODE>` 后由白名单逼出验证 token。目前没有一份「允许集 × 停止条件」的一致性核对，谁对不上说不清。

## 目标

1. **修边界**：`generate()` 增加显式 `stopped` 标志，`truncated = not stopped`，不再用长度反推；「第 max_new 步正好收尾」必须判 `truncated=False`。返回值字段名不改（`truncated` 语义修正，不新增破坏性字段）。
2. **一致性矩阵**：输出 free / constrained × `</CODE>` 后的允许集与停止条件对照表（`allowed_next()` 与实际 `stop` 判定的差异逐项列出），只报告，不改判据。
3. **归因工具**：新增 `scripts/attribute_truncation.py`，读 `generated_samples.jsonl`（已有 `free_truncated / free_n_tokens / free_n_decision / free_problems / constrained_problems / constrained_truncated`），输出三类计数与逐条清单：
   - `early_stop`：未吐 `</CODE>` 闭合，或缺结尾 `<V:…>`
   - `true_illegal`：结构闭合了但缺段 / 决策重复 / 验证错位
   - `truncated`：撞上限且未收尾
   支持 `--json` 与 `--input`（默认 `lightprism_out/generated_samples.jsonl`）。
4. **报告**：`reports/截断归因_2026-11-26.md` 写清 3 条截断的成因分类框架、复现命令、以及「不得通过改分母 / 降默认预算 / 把 free 换成 constrained 来美化 ③」的声明。本地只有 CPU 2 epoch 的 16 条产物时，只做工具链路验证，**不当判据结论**。
