## 背景

T-0520 在修 `src/安全策略.light` / `src/溢出.light` / `src/溢出保留.light` 三条确定性逻辑缺陷时定位到一个**共同根因**（卡面与大厅留言均有实测，见 `hive/results/T-0520.json` 与 hall 消息 `fb98-1795705321818526`）：

> 光明编译器对 `(x + y) // z`、`(x + y) % z` 这类「括号内含加法的表达式后接整除/取模」会**静默丢掉 `//` / `%` 运算**。
> 实测：`(4 + 1) // 2` → `4`（应 2）；`(0 + 10 + 1) // 2` → `10`（应 5）；`(100 + 50) % 4294967296` → `150`（应 150，碰巧对）；`设 甲 为 0 + 10 + 1` 再 `甲 // 2` → `5`（拆成中间变量正确）。

T-0520 只按允许路径用中间变量规避，没有动编译器。**T-0529 修的是另一个不同的 bug**（`_fold_binary_spine` 在左操作数优先级更低时漏给左操作数加括号，导致 `如果 (A 或 B) == 假:` 反转），与本卡的 `//`/`%` 丢失无关，不要混淆，也不要重复那个修复。

这是全语言级别的正确性缺陷：任何 `.light` 代码写 `(a+b)//c` 或 `(a+b)%c` 都会静默算错，影响面远大于 T-0520 的三处。

## 目标

1. 在 `light-merge` 的编译器里定位并修复 `(x + y) OP z`（OP ∈ `//`、`%`，且左操作数是带加法的括号组）丢运算的根因——预期在 `src/parser_expr.py` / `src/ast_nodes*.py` / `src/code_generator*.py` 的二元链处理，或 `light6.py` 入口所用的生成路径。先用最小复现脚本确定到底在哪一层丢的，再改。
2. 新增回归判据覆盖整除/取模在「括号含加法」「括号含减法」「连续加法」「多层括号」「与乘法/比较混排」等形态下的正确输出，并验证拆成中间变量的写法仍正确（等价性）。
3. 回归不破坏 T-0529 刚修的括号优先级（`如果 (A 或 B) == 假:` 等 10 条）与既有二元运算链。
