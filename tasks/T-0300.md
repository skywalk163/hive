# 同步 tests/test_cluster.py 三条旧用例到 T-0295 的 store 新鲜度契约

## 一、现象

`python -m pytest -q tests/test_cluster.py` 在 main（`7d3e1ee`）上确定性 3 failed：

```
FAILED tests/test_cluster.py::test_store_election_restriction
FAILED tests/test_cluster.py::test_force_vote_overrides_store_behind
FAILED tests/test_cluster.py::test_force_vote_can_be_disabled
3 failed, 69 passed
```

## 二、根因

T-0295（`d91dd16`）把投票闸门 `store_behind` 从「硬拒绝」改成**默认放行**：
store 只是缓存、git 才是事实账，落后候选照拿赞成票并 emit `vote_store_lag`；
只有显式 `strict_store_freshness=True` 才拒票并给出 `store_behind`。
配套新用例 `tests/test_vote_store_behind.py` 已按新契约写好（默认放行 / 严格拒票 /
force 在严格模式下仍可覆盖 / `HIVE_CLUSTER_STRICT_STORE_FRESHNESS` 开关）。

但 `tests/test_cluster.py` 里这三条旧用例仍按「默认硬拒绝」写，其中：
- `test_store_election_restriction`：默认模式下断言拒票 → 现在会放行；
- `test_force_vote_overrides_store_behind`：默认模式下断言无 force 拒票 → 现在会放行；
- `test_force_vote_can_be_disabled`：断言 `allow_forced_promote=False` 时 force 也拒票，
  但默认模式下 store 闸门根本不生效，自然不会拒。

T-0295 的 paths 只覆盖了 `hive_cluster.py` + `tests/test_vote_store_behind.py`，
这三条因此一直红着（T-0299 的总结也原样记录过）。

## 三、目标

只改 `tests/test_cluster.py` 这三条用例，让它们**显式打开 `strict_store_freshness=True`**
再断言 store 闸门行为（保留它们原本要测的语义），不改实现：

1. `test_store_election_restriction`：`cluster_factory("a", store_enabled=True,
   strict_store_freshness=True)`，断言 `granted is False` + `reason == store_behind`
   + `strict is True`。
2. `test_force_vote_overrides_store_behind`：同样打开严格模式；无 force → 拒票
   `store_behind`；带 `force` → 赞成 + 留 `leader_forced` 审计事件。
3. `test_force_vote_can_be_disabled`：严格模式 + `allow_forced_promote=False`；
   带 force 仍拒票 `store_behind`（这是「宁可没主控也不接受落后节点」的出口）。

## 四、红线

- 不改 `hive_cluster.py` 任何行为（默认放行是 T-0295 的既定契约，改回去会与
  `tests/test_vote_store_behind.py` 冲突）；
- 不改默认值、不加新配置项；
- 只动 `tests/test_cluster.py`，不动其它测试与卡面。

## 五、验收

```
python -m pytest -q tests/test_cluster.py
```

全绿（72 passed），且 `tests/test_vote_store_behind.py` 仍全绿。
