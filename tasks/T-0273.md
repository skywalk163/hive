# lightharness 没有 pyproject，连 `pip install -e .` 都做不到

## 现状

```
$ ls lightharness/pyproject.toml lightharness/setup.py
# 都不存在

$ ls lightharness/.github/ISSUE_TEMPLATE/
config.yml            # 只有一个，没有 bug_report / feature_request

$ ls lightharness/{SUPPORT,CODE_OF_CONDUCT}.md
lightharness/CODE_OF_CONDUCT.md     # 有
# SUPPORT.md 没有
```

对照：`light` 有完整的 `LICENSE/CONTRIBUTING/SECURITY/SUPPORT/CODE_OF_CONDUCT` +
4 个 issue 模板 + `pyproject.toml`。`lightharness` 差一截。

### 这不是「形式主义」，它有一个具体的下游影响

`light` 的 CI 里有这段（`.github/workflows/ci.yml:131-150`）：

> `tests/unit/test_builtins_drift.py`（2 条 LH 用例）与
> `tests/unit/test_LH34_中文关键字参数.py`（2 条 LH 用例）要读它的 `stdlib/builtins.py`
> …
> run 41289797116 上这 **9 条（7 errors + 2 failed）**签名全是那里的 `FileNotFoundError`。

也就是说：**`lightharness` 没有以「可被安装/可被发现」的形式存在，是 `light` CI 那 7 errors 的直接原因**。
`light` 那边已经用「sibling 缺失就 skip」绕过了，但那是绕过，不是解决。

## 起点线索

- `lightharness/运行.py` 是入口（我看到 `ROOT = ...`、`sys.path.insert` 之类，说明它按脚本跑）
- `lightharness/CHANGELOG.md:76` 最新是 `## [v0.5.0-rc1] — 2026-10-28` → **版本号真源在这**
- `lightharness/smoke.sh` 存在（8104 字节）
- `lightharness/tests/` 有 32 个条目
- `lightharness/CONTRIBUTING.md` 和 `SECURITY.md` **已存在**（这点比 hive / lightmem 好）

## 目标

### 1) 补 `pyproject.toml`

先看 `运行.py` 的模块结构（是 `py-modules` 还是 `packages`），照 `hive/pyproject.toml` 的风格写：

```toml
[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[project]
name = "lightharness"
# 版本号真源：CHANGELOG.md 首条 `## [vX.Y.Z]`。本字段必须跟它一致。
version = "0.5.0rc1"
description = "用「光明」中文编程语言复刻 dsh（DeepSeek Harness）"
readme = "README.md"
requires-python = ">=3.10"
license = { file = "LICENSE" }
dependencies = []

[project.scripts]
lightharness = "lightharness:main"     # ← 入口函数名要先确认，见下
```

⚠️ **不要照抄 `hive` 的 `py-modules` 列表**。`lightharness` 的结构不一样（有 `src/`、`stdlib/`、
`data/`），先 `ls` 再决定。如果它本来就是「一堆扁平 .py + 一个 运行.py」，那用 `py-modules`；
如果有包目录，用 `packages.find`。

**注意 PEP 440**：`v0.5.0-rc1` 在 pyproject 里要写 `0.5.0rc1`（不能带 `-` 和 `v`）。
这是最容易错的一点。

### 2) 让 `pip install -e .` 真的能跑

这是**本卡的硬判据**。写完必须实测：

```bash
cd /home/skywalk/dswork/lightharness
python -m pip install -e . 2>&1 | tail -5
lightharness --help 2>&1 | head -5
```

如果入口函数不存在（`运行.py` 里没有 `def main()`），有两个选择：

**甲**：在 `运行.py` 里加一个薄 `main()` 包装（**但这会动 `运行.py`，不在本卡 `paths` 里**）
**乙**：不要 `[project.scripts]`，只做「可被 pip 安装、可被 import」的包

建议选**乙**：本卡不动 `运行.py`，`[project.scripts]` 留到以后单独一张卡。
只要 `pip install -e .` 成功 + `import lightharness` 通，就已经解决了「不可被发现」的问题。

> 如果连「可被 import」都做不到（比如目录名有中文、模块名不规范），
> 那就**明确报告做不到**，并写清卡在哪。不要为了交付而假装成功。

### 3) 补 `SUPPORT.md`

照 `light/SUPPORT.md` 的结构（我看过，是「支持范围表格 + 优先渠道」的写法），改成 lightharness 的：

| 类别 | 是否支持 | 渠道 |
|---|---|---|
| 移植问题（上游 dsh 版本对齐） | ✅ | issue |
| 光明语言本身的 bug | ❌ → 转 `light` 仓 | light/issues |
| 插件加载 / lightplugin 集成 | ✅ | issue |

**关键一条**：明确区分「lightharness 的问题」和「light 语言本体的问题」。
这是这个仓最容易被误归类的地方 —— `docs/光明语言问题记录.md` 那套 LH 编号就是为这个存在的。

### 4) 补两个 issue 模板

照 `light/.github/ISSUE_TEMPLATE/` 的格式（`bug_report.md` + `feature_request.md`），
`bug_report.md` 必须有的字段：

```yaml

- 操作系统：
- Python 版本：

（最小 .light 片段）

## 期望 vs 实际

## 归因（重要）

- [ ] 是 light 语言本体的缺陷（→ 请附 LH 编号，或转 light/issues）

```

「归因」那个 checkbox 是本模板的核心价值。
