## 背景

现在只有人（总控）会写任务卡。T-0110~T-0114 这五张全是我手写进仓库的 ——
写一张卡要读代码、想清楚 paths 和 verify、组织语言，几分钟到十几分钟。
agent 一天能干 20 张卡的活，但**只有等人把卡写出来才能开始**。吞吐卡在出题这一端。

要破这个瓶颈，得让 agent 也能出题。但不能让 agent 直接往 `tasks/` 里写 ——
「谁出题谁做题」，验收会失去意义。所以走 **草稿 → 人确认 → 转正** 的三段式。

## 目标

给 hive 加一套「任务卡草稿」的目录约定和命令。**hive 自己不调 LLM**（保持零依赖，
内容由 agent 生成，hive 只管格式、校验和入队）。

1. **目录约定**：`drafts/`，每张草稿一个 `<名字>.md`，和正式任务卡同样的
   frontmatter 格式（缺 `id` —— 转正时才分配）。`hive init` 要建这个目录。
2. **`hive draft new --title ... --repo ... [--file <name>.md]`**：
   从模板生成一张草稿（含「背景 / 目标 / 红线 / 验收」四段骨架 + 常见字段注释），
   打印路径，让调用它的 agent 照着填。
3. **`hive draft show <file>` / `hive draft list`**：看草稿内容和清单。
4. **`hive draft lint [<file>]`**：不传就 lint 全部。逐条报问题：
   - 缺必填字段：`title` / `repo` / `paths` / `verify`；
   - `repo` 没有登记在任何 agent 名下（这样的卡永远派不出去）；
   - `verify` 一条都没有，或全是弱验收（判定规则见 T-0122，本卡先只检查「至少一条」）；
   - `depends_on` 指向不存在的卡；
   - `needs` 里的能力**没有任何 agent 满足**（这是 T-0102 那种僵尸卡的成因，必须拦住）；
   - `paths` 为空（允许，但报 warning：意味着不限制改动范围）。
   有 error 就退出码非 0，`--json` 给机器读。
5. **`hive draft adopt <file> [--id T-xxxx]`**：校验通过后
   - 分配正式 id（不传就用当前最大号 +1）；
   - 补齐 `state: ready` / `owner: null` / `created` 等字段；
   - 从 `drafts/` 移到 `tasks/T-xxxx.md`；
   - `commit_and_push`。
   lint 不通过的草稿拒绝转正。
6. 转正确认后打印下一步：`hive dispatch` 或 `hive assign T-xxxx --agent <name>`。

## 红线

- hive 本体**不引入 LLM 调用、不加第三方依赖**；草稿内容永远由 agent 或人写。
- `tasks/` 只能由 `draft adopt` 或 `task new` 写入，不要让 agent 直接碰。
- lint 的 error / warning 分级要清楚：阻挡转正的才算 error。
- 别改现有 `task new` 的行为（老命令继续能用）。
- 别动 `tasks/T-01*.md`、`results/*.json`。

## 验收

`git show --stat HEAD` 覆盖 `hive.py` + `tests/` + `docs/操作手册.md`；verify 全过。

## 备注

设计意图值得写进 `docs/操作手册.md`：草稿是**给人 review 的界面**。
agent 出草稿是廉价的、可以一次出十张；人只做「同意/打回」这个 O(1) 的判断，
而不是从零写卡。这个比例才是能不能把吞吐真正提上去的关键。
