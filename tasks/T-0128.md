## 背景

T-0127 交付 LLM 总控后，我（workbuddy）用真 MCP stdio 客户端驱动 controller 角色实跑了一轮
decision-point 走查（场景：1 张 needs_review、1 张结果红、1 对互相冲突的卡、1 张 blocked）。
跑的时候发现一个真 bug：

`hive_land` **已经传了 `apply=true`**，合入遇到冲突时返回的错误信息却是
「合入没成功（**默认只预演，什么都没动**）」。这句话只在不传 `apply` 时才成立。

危害很直接：LLM 总控是靠读这条 message 决定下一步的。传了 apply=true 却被告诉"你在预演"，
它会误判自己还在 dry-run 模式，可能反复重试同一个 land，或者错误地把状态归因为"我没申请真合入"。
`err()` 也没带 `applied` 字段，调用方无法从结构化数据里分辨。

（该措辞自 T-0123 起就存在，只是一直没有"传了 apply 又撞冲突"的实跑路径暴露它。）

## 目标

改 `mcp_server.py` 的 `t_land`，让冲突时的返回信息与实际的 `apply` 一致：

1. **message 分叉**：`apply=false` 时保持原样「合入没成功（默认只预演，什么都没动）」；
   `apply=true` 时改成明示"已申请真合入、因冲突未改动"，并保留"绝不自动解冲突"的红线表述。
2. **补结构化字段**：冲突分支的 `err(...)` 里加 `applied=<apply>`，让调用方不依赖自然语言也能判断
   这次到底有没有申请真改。（成功分支本来就已带 `applied`，保持一致。）
3. **测试**：在 `tests/test_mcp_controller.py`（或新增）加一例，造一对互相冲突的卡，断言
   `apply=true` 时的 message 不含"默认只预演"、含 `applied=true`、且 `conflicts` 正确；
   再断言 `apply=false` 时 message 仍含"只预演"（防止改坏 dry-run 语义）。
4. `docs/MCP接入.md` 若提到 land 冲突的返回措辞，同步一句。

## 红线

- **不改** `hive_land` 的合并/冲突判定逻辑，不动 `cmd_land` / `land_one` 的任何行为，
  不改成功分支的措辞与 `applied` 字段。
- **不引入** 任何第三方依赖。
- 不把"冲突"软化成 warning —— 冲突仍然是 `status=error`，卡仍然会被标 `conflict` 状态。
- 绝不自动解冲突、绝不 force push，这两条原样保留。

## 验收

- `git show --stat HEAD` 覆盖 `mcp_server.py`、`tests/`、`docs/MCP接入.md`、`CHANGELOG.md`。
- 新用例绿；全量 pytest 无回归。
- 复现实跑：传 `apply=true` land 一张冲突卡，返回的 message 明确表达"申请了真合入但因冲突没动"，
  且 `applied=true`、`conflicts` 列出冲突文件。
