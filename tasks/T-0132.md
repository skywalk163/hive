## 背景

`docs/lessons.md` 自己写着「不是流水账，是『同类坑别再踩第二次』」，来源包括实跑、排查和
summary。今晚（T-0128 / T-0129 / T-0130，加上 light 仓库回退那次）踩到四条**非显然**的坑，
目前只记在会话记忆里，没落到项目自己的 lessons 里——下次换个人/换个会话就会再踩一遍。

## 目标

给 `docs/lessons.md` 补一节（放在「五、hive 的用法」之前，作为「四、排查与代码陷阱」；
若已有四则顺延），四条，每条按现有格式**现象 → 原因 → 以后怎么做**：

1. **「只构造对象」也可能有破坏性副作用**
   `Worker.__init__` / `Worker.loop()` 曾无条件 `reset --hard origin/main`，于是
   `hive take` / `work` / `submit` 会把协调仓里未提交的已跟踪改动（写到一半的 `drafts/` 草稿）
   静默抹掉。
   → 排查静默数据丢失用最小实锤法：**把一个已跟踪文件改脏 → 只触发可疑动作 → 看文件还在不在**；
   写会动工作区的代码前先想清楚它跑在主工作区还是独占 clone（MCP 用独占 clone 就是为此）。

2. **错误信息必须和实际参数一致**
   `hive_land` 传了 `apply=true` 撞冲突时，仍回「默认只预演，什么都没动」——这句话只在不传
   apply 时成立。LLM 总控靠读 message 判断自己在什么模式，会被误导成"我还在 dry-run"然后反复重试。
   → 断言错误信息时要覆盖「不同入参下措辞是否还成立」；单测只断言 `status` / `conflicts` 不够，
   **实跑一轮 decision-point** 才暴露得了这类问题（本条就是实跑时发现的）。

3. **`0` 是假值，别用 `or` 判断"有没有设置"**
   `int(card.get("max_retries") or DEFAULT_MAX_RETRIES)` 会把显式设置的 `max_retries: 0`
   误判成"没设置"而退回默认 3，于是「一次都不许自动重派」永远不生效。
   → 判断有没有设置用 `is None`（或 `== ""`），别用 `or`。

4. **代码被回退后，卡片记录要同步「记作废」**
   hive 的记录和代码仓库会脱节：把 light 仓库的 commit 撤掉后，hive 里对应卡片仍显示
   `done/closed`，会骗人以为改动还在。
   → 撤销代码后同步给卡片加作废备注：`hive close <tid> --note "作废（日期）：…"`
   （`cmd_close` 可重复调用，只追加备注，不会报错）。
