## 背景

2026-10-25 凌晨 Gitea（`192.168.1.5:3000`）**约 12 小时不可达**。期间跑
`hive land T-0139 --apply`，命令**静默挂起**：没有任何输出、一直不返回，
看起来像「在正常工作」——实际上它卡在 `fetch` 上。当时是靠杀进程才发现，
差点误判成「命令成功但没输出」。

根因很具体：`run()` **早就有 `timeout` 参数**（hive.py 约 102 行定义、
116 行传给 `subprocess.run`），但全仓只有两处跑卡命令传了它
（约 1468 / 2339 行，`timeout=1800`），**git 的 `fetch` / `push` /
`clone` / `ls-remote` 一个都没传**。`subprocess.run` 不传 `timeout`
就是无限等，网络一断就永远卡住。

这不是理论风险，是已经发生过一次的真事故。后来定的替代作业方式
（本地预演 + patch 存档）能救急，但那是绕过，不是修。

顺带说清楚评审里提到的另一个担心：**「脑裂」不是真问题**。`git push`
非快进被服务端拒绝，本身就保证只有一个 worker 抢到卡。真正的风险是
**远端不可达时挂起**——也就是这张卡要修的东西。

## 目标

1. 给**网络类** git 操作（`fetch` / `push` / `clone` / `ls-remote`）传默认超时，
   超时后抛明确的 `HiveError`：**说清是超时、哪个远端、建议先查连通性**，
   而不是无限等、也不是静默退出。
2. 超时值要**可配置**：走一个常量（如 `NET_TIMEOUT_S`，默认 120 秒上下），
   必要时允许环境变量覆盖。别散落各处写魔数。
3. 超时路径**不能留半成品状态**：`land` 的临时 worktree、`.hive/land` 残留
   必须照常清理；超时后卡的状态不能被写坏（不能变成半 assigned）。
4. **本地** git 操作（`rev-parse` / `show` / `hash-object` / `commit-tree` 等
   不碰网络的）**不加超时**，别为它们引入任何新的失败路径。

## 红线

- **不许动 `run()` 的编码**：`encoding="utf-8", errors="replace"` 是 T-0143
  刚定的，改坏了 Windows 又会往 blob 里写 GBK。
- **不许给非网络操作加超时**——慢机器上大仓的 `git show` 也可能慢，
  误杀了比不设超时更糟。
- **不许让超时掩盖真实错误**：超时报「超时」，网络拒绝报「被拒绝」，
  别都归成一句「远端不可用」。
- 不许改 `run()` 的签名语义（`timeout=None` 仍表示不限制）。

## 验收

- 新测试：起一个永不返回的命令，断言 `run(..., timeout=N)` 在 N 秒后
  抛 `HiveError` 而不是挂着（用很小的 N，别让测试变慢）；
- 新测试：断言网络类 git 调用点确实传了超时（参数级守卫，别只测行为——
  本机网络正常时行为测不出来）；
- `git show --stat HEAD` 覆盖 `hive.py` + `tests/test_git_timeout.py`；
- 全量 `python3 -m pytest tests/ -q` 通过。
