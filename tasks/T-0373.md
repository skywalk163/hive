# 64K 词表构建：按 `docs/词表预算.md` 落表，替换 4096 演示词表

> 来源：`tasks/00_总纲与分发顺序.md` §七「不在本批范围 —— 64K 词表（另开卡，demo 验收后）」；
> `README.md` 词表表（`reserved 1536 | 1024—2048`）；
> `docs/词表预算.md`（**唯一事源是代码** `src/lightprism/vocab.py::DEFAULT_BUDGET`）。
> 前置：demo 已验收（T-0334 等已 done），本卡把 v0.1 的重分配从「文档/预算」推进到「真词表」。

## 一、当前状态（实测）

- `data/unified/vocab_4096.json` 实际 size **2900**，control span `[2868, 2900)`；
- `DEFAULT_BUDGET` 已写 64K 分配表，但**尚未产出 64K 词表文件**；
- 尚未验证：64K 词表下 demo 尺寸模型（3.4M）还能不能跑，以及 `ppl` / 结构合法率是否变差。

## 二、要做什么

### 2.1 落出真实 64K 词表

按 `DEFAULT_BUDGET` 七个槽位逐槽构建并合并：

| 槽位 | 额度 | 构建要求 |
|---|---:|---|
| `l0_core` | 44（精确） | 从 `light/docs/language/l0-core.md` 权威表读，**一字一 token**，不许被 BPE 拆分 |
| `l1_l2_syntax` | 8192 | 语料高频语法组合（`data/corpus/`） |
| `stdlib_names` | 10240 | 从 `light` 的 stdlib 导出名提取 |
| `chinese_bpe` | 34804 | 中文自然语言 BPE，取整余量落这里 |
| `code_reserve` | 10240 | 数字/运算符/标点/标识符片段 |
| `decision` | 320 | 首批 19 个 + 预留，占比 ≤2% |
| `validation` | 160 | `light ai check` 诊断码映射 |
| `reserved` | 1536 | 后续决策点/实验 token/控制符 |

- 产物：`data/vocab_64k.json` + `data/vocab_64k.manifest.json`（含各槽位实际占用、合计、
  每槽 sha256、与 `DEFAULT_BUDGET` 的逐项对账）。
- **合计必须精确 65536**，`VocabBudget.problems()` 返回空列表。

### 2.2 与 4096 词表的可比性

- 新增 `src/lightprism/demo/vocab_build.py` 的 64K 分支（同一条流水线，不另写一套）。
- 用**同一份语料**分别在 4096 / 64K 上做 tokenizer 覆盖率统计（未登录率、平均 token 数），
  报告里出对照表。
- 模型侧：`configs/demo-3m.json` 的 `V` 必须同步改成实际词表大小并**重建 config**；
  **不要**把 64K 词表塞给 V=4096 的模型**并声称跑通了**——embedding 尺寸不匹配必须报错。

### 2.3 冒烟

- 用 64K 词表跑 20 步训练 + 若干条生成，`light ai check` 真跑；
- 报告 64K 下的结构合法率与 4096 下的对比，**两组都必须贴原始输出**。

## 五、禁止

1. 不改 `l0_core` 精确 44；不许让 BPE 吃掉 L0 核心字。
2. 不靠「多出来的额度悄悄空着」凑 65536 —— 余量必须显式进 `reserved`（`VocabBudget.problems()` 第 2 条）。
3. 不改 `configs/demo-3m.json`、不改既有验收数字。
4. 不宣称「64K 让效果更好」除非有同参对照；单次冒烟只能说明「能跑」。
5. 若与 T-0371 同时改词表，**必须串行**：T-0371 的 `<PY>`/`<LIGHT>` 标记也要在 64K 表里存在，
   否则两卡合并后测试会红。
