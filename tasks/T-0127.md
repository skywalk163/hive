## 背景

T-0125 做了 worker 看门狗，T-0126 做了确定性总控 `hive orchestrate`（watchdog→dispatch→land→doctor
的死循环）。但 orchestrate 是「脑」的极致简化版：它只在 verify 全绿时自动 land，遇到**需要判断的卡点
就绕开**——`needs_review`（人工验收闸）、`conflict`（合入冲突）、`failed`（验收挂了）、`blocked`
（等资源），以及「哪张 ready 卡派给哪个 agent」这种带偏好的抉择。这些恰恰是人/LLM 才擅长的。

controller MCP 已经把 `hive_land / hive_close / hive_retry / hive_assign / hive_dispatch /
hive_gc / hive_watchdog` 这 7 个会改动 main 的工具，加上只读的 `hive_whoami / hive_list_tasks /
hive_get_task / hive_stats / hive_doctor` 暴露出来。本卡要做的，是一个**以 LLM 为决策核心的总控**：
每轮把 hive 当前状态喂给 LLM，让它从这套 controller MCP 工具里挑一个动作执行，直到它认为没事可做。

这样「带判断的总控」和「确定性的 orchestrate」互补：orchestrate 跑量产、跑稳定路径；LLM 总控处理卡点、
做分派偏好、在人工闸上做保守决策。

## 目标

新增 `hive llm` 子命令（LLM 总控），落在新建 `llm_controller.py`（标准库实现，零第三方依赖，和全仓一致）：

1. **工具后端 `ToolBackend`**：把 controller MCP 工具面封装成 `{list_tools, call_tool}` 两个方法。
   - `InProcessBackend`：直接复用 `mcp_server.HiveMcp` 的 handler（`HiveMcp.HANDLERS`），工具 schema
     取自 `mcp_server.TOOLS` 中 controller + 只读 introspection 那部分，再加一个合成工具 `done`
     （表示「本轮无事可做，停」）。这样 LLM 驱动的工具面 == controller MCP 工具面，同一套 prompt
     既能驱动 in-process 后端、也能驱动真正的 MCP server。
   - `McpStdioBackend`（可选，`--mcp`）：真正 spawn `mcp_server.py --role controller`，走
     JSON-RPC 握手（initialize → tools/list → tools/call），证明它是货真价实的 MCP 客户端。

2. **LLM 客户端 `LlmClient`**：
   - `OpenAiClient`：标准库 `urllib.request` POST 到 `${OPENAI_BASE_URL}/chat/completions`
     （model = `${OPENAI_MODEL}`），system prompt 带工具 schema，要求模型只回一个 JSON 动作
     `{"tool": <name>, "arguments": {...}}`；带兜底解析（抠出第一个 `{...}`）。
   - `HeuristicClient`（默认无 key 时的可用回退）：确定性策略——landable 非空就 land、ready 非空就
     dispatch、其余 decision 卡点（needs_review/conflict/blocked）不自动动、跑一轮 watchdog 后 `done`。
     等价于「不会做危险决策的 orchestrate」。
   - `MockClient`：吃一个 script 列表，依次返回，测试用（不入 CLI，仅供单测 import）。

3. **决策循环 `ControllerLoop`**：
   - 每轮：调 `hive_whoami`（controller）拿 `todo` 快照 → 渲染成紧凑文本 → 问 LLM 要下一个动作 →
     执行 → 把 (action, 结果) 塞进滚动历史（最多 8 条，防绕圈）→ 回到开头。
   - LLM 回 `done`、或到 `--max-iter`（默认 12）、或 `--stop-file` 出现、或一轮无动作 → 退出。
   - **安全闸**：未传 `--apply` 时，所有 mutating 工具强制 `apply=false`（只预演）；prompt 里也明确
     告知 PREVIEW 模式。和全仓「破坏性操作默认 dry-run」一致。

4. **CLI 接线**：`hive.py` 加 `llm` 子命令，参数
   `--agent`（默认 `controller`）、`--dir`、`--llm openai|heuristic`（默认 heuristic）、
   `--model/--base-url/--api-key`（覆盖 env）、`--apply`、`--max-iter`、`--stop-file`、`--once`
   （只跑一轮决策就退）。

5. **测试 `tests/test_llm_controller.py`**（接 `world` 夹具）：
   - `InProcessBackend` 的 `list_tools` 含 12 个 MCP 工具 + `done`；`call_tool` 返回 dict 信封。
   - `MockClient` 驱动 loop：`apply=True` 时把一张 done 卡 land 成 closed；`apply=False` 时同卡保持 done。
   - needs_review 卡点：`MockClient` 返回 `hive_land{apply:true}` → 卡被合入关闭（验证 LLM 能在人工闸上决策）。
   - `OpenAiClient` 解析：mock `urllib.request.urlopen` 返回 JSON 动作，验证解析与 apply 强制覆盖。
   - `HeuristicClient`：preview 模式下不改动任何卡（跑完仍是原状态）。

6. **文档**：`docs/操作手册.md` 加 §6.3「LLM 总控 `hive llm`」；`docs/MCP接入.md` §4 补一句 LLM 总控是
   controller MCP 的「带判断客户端」。`CHANGELOG.md` 加 0.9.7 条目。

## 红线

- **不改** `mcp_server.py` 的现有工具语义/handler，只新增读取式复用与 `done` 合成工具。
- **不引入** 任何第三方依赖（无 openai / httpx / requests 包），LLM 调用只用标准库。
- **不自动解冲突、不 force push**：`hive_land` 冲突时只回 error，LLM 总控不得尝试自行解冲突。
- **默认不 `--apply`** 时绝不改动 main（mutating 动作一律 apply=false）。
- 不替人工闸（needs_review）做「无脑 land」：默认 heuristic 在 needs_review/conflict 上 `done` 留给人工；
  只有 LLM 显式决策 + `--apply` 才会动这些卡。
