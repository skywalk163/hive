# 仓内 config.json 与运行时配置分叉：排障时看到的选举参数是错的

## 一、现象

在 `~/dswork/hive` 里 `cat config.json` 得到：

```json
"name": "macos",
"leader_priority": 2,
"preferred_leader": ""
```

据此判断「本机 priority=2、没有首选主控」，与集群实际行为完全相反。真实生效的是
`~/.hive/cluster/config.json`：

```json
"name": "laiweilideMacBook-Air",
"leader_priority": 1,
"preferred_leader": "laiweilideMacBook-Air"
```

## 二、证据锚

- 运行中的进程（PID 11715）：
  `hive.py --dir /Users/skywalk/dswork/hive cluster serve --port 8788 ...
  --state-dir /Users/skywalk/.hive/cluster --name laiweilideMacBook-Air`
- `hive_cluster.py#L373-L385`：`Config` 只读 `state_dir/config.json`；
  `--name` 等构造参数优先级高于该文件。
- `hive_cluster.py#L560-L594`：`Config.save()` 也把改动写回 `state_dir/config.json`。
- 因此仓内的 `hive/config.json`（name=macos）从未被加载；`hive cluster status`
  显示 `laiweilideMacBook-Air` 而不是 `macos`，可直接证明。

## 三、为什么是缺陷

1. 仓内存在一个看起来合法的 `config.json`，用户/agent 会默认它就是生效配置；
   实际生效的是 `--state-dir` 下另一份，两份内容相反（priority 2 vs 1、
   首选为空 vs 首选自己）。
2. 本次排障已实际踩中：按仓内配置推断「priority=2 应该能当选」，
   而现场是「本机自我首选 + priority 1 + 不抢占」，结论完全走偏。
3. 与 T-0297（自身 last_seen 陈旧）叠加时，更缺少一个可信的「配置从哪里来」入口。

## 四、修复方向（最小改动）

1. `cluster serve` 启动时检测：若 `--dir`（或 cwd）下存在 `config.json`，
   且它不是 `state_dir/config.json`，打印一条 warning：
   「<路径> 不会被读取；实际配置：<state_dir>/config.json」。
2. `hive cluster status` 增加一行显式输出：
   `配置 <state_dir>/config.json  name=… priority=… preferred=…`
   让人无需 `ps`/猜目录就能核对生效值。
3. 可选：提供 `hive cluster config-path`，只打印实际配置文件路径。
4. 文档 `docs/集群服务.md` 明确：`config.json` 属于 state_dir（默认
   `~/.hive/cluster/`），仓内只保留 `config.example.json`。

## 五、红线

- 不改变现有配置的读写位置与格式，不让老 state_dir 失效。
- 不在日志/status 里输出 token 等敏感字段。
- 改动不影响选举逻辑本身（priority / preferred 的语义保持不变）。

## 六、验收

- 启动日志能看出「仓内 config.json 未被读取」这一事实（或明确不告警的条件）。
- `cluster status` 能直接看到生效配置的路径与 name/priority/preferred。
- `python -m pytest -q tests/test_cluster.py` 全绿。
