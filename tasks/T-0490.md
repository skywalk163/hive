# P0：max-steps 后「继续」显示排队却无输出、停止按钮消失、切回会话历史空白——定位与修复

## 现场（用户 2026-11-25 报告，截图 http://127.0.0.1:23506）

会话「481和486」长任务跑到单轮 96 步上限后：

1. 出现横幅「本轮达到步数上限（96 步），已暂停。发送『继续』，或 /goal 可接管。」+「继续」按钮。
2. 紧接着出现「服务端已排队（位置 1）：当前会话正在跑，本条结束后自动执行。」
3. 输入/点击「继续」仍卡住；顶栏红色「停止」按钮不见了；输入框旁出现「排队中 0 行」。
4. 昨天点了别的 chat 再点回来，历史消息看不见了；但此时可以输入、有响应。
5. 用户怀疑是 goal 续跑/队列死锁。**结论：不是 goal 死锁**（见下）。

## 只读定位结论（已完成，可直接照此改，不要重复排查）

### A. 横幅与文案出处
- `webui/app.js:452-488`：renderStats→handleEndReason；max-steps 分支 461-465 addSystem 提示；477-487 offerContinueButton 生成「继续」按钮，点击 `sendMessage("继续")`。
- 服务端统计帧 `src/web服务器.light:619-662`，T-0453 在 645-652 把结束原因归一为 completed/max-steps/max-tokens/aborted/error。轮次结果 max-steps 构造见 `src/代理.light:545-548`（异步版 623-627）；上限 96 见 `src/步数上限.light` + `web服务器.light:1077-1080`。
- 「服务端已排队（位置 N）：…本条结束后自动执行。」纯前端 `webui/app.js:1519-1525`（HTTP 202 分支）；202 由服务端 `web服务器.light:983-1001` 判忙入队产生。
- 「排队中 N」角标 `webui/index.html:140-142` + `webui/app.js:1159-1170`，只是本地队列非空的表现，不是死锁证据。

### B. 停止按钮为何消失
- `webui/index.html:106` 初始 disabled；`webui/app.js:1223-1248` setStreaming(on) 中 `sendBtn.disabled=on; stopBtn.disabled=!on`。
- max-steps 时后台轮次已结束、SSE 尾帧发出，`[DONE]` 后 finally（app.js:1545-1551）setStreaming(false) → 停止按钮变灰。这是状态自洽的设计表现，不是要修的「消失 bug」。
- 但真实缺口：停止只做前端 `AbortController.abort()`（app.js:1584-1587），不中止服务端。`src/任务控制.light:99-116` 有真正的「请求停止」，全仓无调用点，Web 无 stop HTTP 接口。

### C. 「继续」卡住的真正原因（已排除 goal 死锁）
- 「继续」是普通中文文本 POST（`webui/app.js:481-486`→`sendMessage`，1448-1552），不是 /goal、不是协议命令；服务端当普通用户文本跑一轮（`web服务器.light:919-920`）。
- **T-0453 的核心死锁（占用释放后不拉起待办）在源码中已修好**：`web服务器.light:2974-2993` 释放前快照统计帧、提前 `队释放占用`(2985-2988)，再 `拉起待办消费`(2990-2993)；异常路径 3001-3017 兜底。不要重做 T-0453。
- 残余真实缺陷（用户现象的直接来源）：
  1. **202 入队的待办没有 SSE 落点**：`后台消费待办`(`web服务器.light:2798-2865`) 明确不推流、摘掉增量/工具回调（2832-2836），结果只落会话库。前端那条 SSE 早已结束，界面永远只显示「服务端已排队」，看不到这一轮输出 → 表现为「继续卡住/没反应」。刷新或切回会话才看得到。
  2. **释放与拉起竞态**：`拉起待办消费`(2780-2793) 在释放占用后才查深度+重试占用；无定时唤醒，链条可被延长。
  3. **120 秒静默丢弃**：`队待办超时秒=120`（2770-2772），2816-2821 超时直接丢弃，只打印日志、不回前端。
  4. **双轨队列**：前端 streaming 时本地排队（1452-1457）+ 服务端 202，setStreaming(false) 时 flush（1246-1247）；看门狗 30s 静默自愈（1186-1220）也会强制收口+flush，造成「排队中 0/位置1」等困惑态。
  5. **max-steps 统计帧到达时前端状态与实际服务端状态错位**：统计帧到了但 SSE 尾帧未到 / [DONE] 前，浏览器仍 streaming=true，点击「继续」只进本地队列。
- goal 续跑仅在 /goal 建目标后由 `续续跑决策`(`src/目标续跑.light:230-292`) 驱动；max-steps 明确返回「停止/max-steps」(249-252)，不续跑。本次不是 goal 问题。

### D. 切回会话历史空白
- 服务端读取正常：`web服务器.light:2231-2244` → `会话存储.light:264-284` 按 id 读 JSONL。实测 GET `/api/sessions/web_1795586330.9668267` 返回 10 条消息，与磁盘一致，最后一条正是后台消费落库的「继续」轮次。
- 前端 `selectSession`(`webui/app.js:1014-1075`) 只 fetch 一次 → `Messages.renderHistory`(`webui/messages.js:442-479`，内部 clear)；无后续刷新。若切走时 202 待办在后台跑并追加到会话库，返回时可能读到旧快照或空壳会话（索引里存在 0 消息会话，`会话存储.light:213-224`），表现为空白；fetch 失败分支（1071-1074）只 addSystem 不还原旧内容。
- 用户「此时可以输入、有响应」与此一致：history 已从 GET 重建，后续正常问答。

## 要做什么

1. **让 202 排队轮次在界面可见**（核心）：`webui/app.js:1519-1525` 收到 202 后不能只 addSystem；在排队消费落库后通过轮询 `/api/sessions/:id` 或服务端推送通知刷新当前会话视图（注意只刷新当前 id，别污染别的会话）。
2. **后端排队结果回写/通知**：`src/web服务器.light:2798-2865` 的 `后台消费待办` 落库后要给前端一个可见落点；至少写一条系统事件或提供状态查询端点，避免「排了队但永远看不到」。
3. **释放+拉起原子化/兜底唤醒**：`web服务器.light:2974-2993`、3009-3017；把释放与拉起放在同一临界区或加定时唤醒；120s 超时丢弃改为明确失败回执而不是静默吞。
4. **修前端状态机错位**：`webui/app.js:1223-1248`、452-488；max-steps 统计帧到达即本地收口，区分「流在收尾」与「服务端忙」，避免按钮态/本地队列/看门狗三者打架。
5. **切会话刷新**：`webui/app.js:1014-1075`；回放后若有后台待办在跑要订阅刷新；空历史给明确提示（「该会话暂无历史」）而不是空白。
6. **停止语义**（若范围内可做）：把 `src/任务控制.light:99-116` 的请求停止接到 Web，使红色「停止」真正中止服务端轮次；否则至少在提示中说明当前只断浏览器连接。
