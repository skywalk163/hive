# 推理提速到 ≥200 tok/s（V4）

## 背景

T-0334 实测 70.6–90.5 tok/s（9 次，中位 77.8），目标 ≥200——差 2.2–2.8×。
T-0331 的卡面要求「本机 ≥250」，实际只有 74–97，却因 bench 没有阈值断言而判 done。
计划书 §1.1 的 283 tok/s 是**逐 token 合成 kernel 基准**，不是真模型，必须先算清这笔账。

## 目标

1. 复盘 283 vs 77.8 的 3.6× 差异：合成基准与真实 decode 的差别（矩阵形状、线程数、
   是否含 RoPE/RMSNorm/softmax、BLAS backend），写进报告；
2. 至少落地一条提速路径并实测：
   - 换带 oneDNN/MKL 的 torch 构建（先确认 Ivy Bridge 无 AVX2 的天花板）；
   - 算子融合 / 降低 Python 层调度（prefill 与 decode 分离、KV 追加批量化）；
   - INT8 量化或更小 d（若改规模，必须同步 configs 并说明对 V2 的影响）。
3. `bench.py` 增加 `--min-tok-s N`（默认 0，行为不变）：低于阈值 exit 1。本卡 verify 用它。
4. `reports/提速方案与实测.md`：每条路径的实测数字与结论，不达标如实写。

## 红线

- 不改 `PROMPT_LEN` / `WARMUP_TOKENS` / 单线程口径；
- 不许拿多线程或合成基准数字冒充验收口径；
- 不许只改 bench 让它变绿。

## 验收

- `python3 -m pytest -q tests/test_bench_threshold.py` 全过；
- `python3 scripts/bench.py --config configs/demo-3m.json --tokens 200 --min-tok-s 200`
  退出码 0（本机口径；目标机见 T-0342）；
- 物理不可达时转 blocked 写清硬件瓶颈，不放宽判据。
