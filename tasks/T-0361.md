# Track B：MiniBridge 规格 + 三个 handler 落地（B1 进程编排 / B2 C FFI）

> 前置：`benchmarks/light-lang-bench/`（commit 见 `git log --oneline -- benchmarks/light-lang-bench`）。
> 本卡补齐原方案中只有设计、没有可执行产物的 **Track B**：
> MiniBridge 规格 + Python/Go/C 三个 handler + 路由配置 + 测试。
> 设计依据：`benchmarks/light-lang-bench/06-design/评测方案修订版.md` §3。

## 0. 背景与边界（先读，避免做偏）

Track B 测的是「光明作为**中文编排层**，通过 L4 外语引用调度其他生态」。
原方案把它当六语言对比，修订版已改为 **仅 Light 的能力展示**（不参与排名）——
本卡只做 Light 侧，**不要**去写 C++/Rust/MoonBit 版本。

**三个 handler 的语义必须极简且确定**，否则跨语言差异会污染「编排能力」的度量：

| handler | 语言 | 输入 | 输出（stdout，单行） | 用途 |
|---------|------|------|----------------------|------|
| `h_py_append` | Python | 一行 JSON（stdin） | `OK <累计行数>`，并把该行追加到 `out.log` | 测「有状态、落盘」 |
| `h_go_len` | Go | 一行 JSON（stdin） | `LEN <字节数>` | 测「纯计算、无状态」 |
| `h_c_hash` | C | 一行 JSON（stdin） | `HASH <FNV-1a 64位十进制的低32位>` | 测「FFI 直接调用」 |


## 2. 规格要点（写进 `07-track-b/规格.md`，必须自包含）

1. **路由决策必须在光明侧**：
   - 读 `route.conf`（每行 `service<TAB>handler`，`#` 开头为注释，空行忽略）；
   - 对每条输入记录取 `service` 字段，查映射得 handler 名；
   - 查不到 → 用 `default` 行（`route.conf` 必须含且仅含一行 `*<TAB>handler`）。
2. **handler 调用约定**（B1）：
   - 光明侧以**外部进程**方式启动 handler 可执行文件，把该行 JSON 从 stdin 传入（一行 + `\n`）；
   - handler 的 stdout 单行（不含 `\n` 或含均可，光明侧需 strip）作为该记录的处理结果；
   - 光明侧按输入顺序逐条打印 `service<TAB>结果` 到 stdout。
3. **错误处理**：
   - handler 退出码非 0 → 光明侧打印 `service<TAB>ERR`，**继续处理后续记录**，最终退出码 0；
   - 输入非法 JSON 行 → 跳过并在 stderr 打 `WARN invalid_json index=<n>`（与 MiniLog 一致）。
4. **B2 差异**：把 `h_c_hash` 从「启动进程」改为**直接 C FFI 调用**（见 §4），
   `h_py_append` / `h_go_len` 仍走进程方式。输出格式与 B1 完全一致
   （即：同一输入，`run_b1.sh` 与 `run_b2.sh` 的 stdout 必须**逐字节相同**）。

## 3. 判据

```sh
cd benchmarks/light-lang-bench/07-track-b
sh build.sh                    # 构建所有 handler + light 侧
sh run_b1.sh tests/case_basic.ndjson | diff - tests/expected_b1.txt   # 必须无差异
sh run_b2.sh tests/case_basic.ndjson | diff - tests/expected_b1.txt   # 必须与 B1 完全相同
```

- 另需一个**边界用例**：`route.conf` 中某 service 映射到不存在的 handler →
  该行输出 `ERR`，其余行仍正常，退出码 0。
- `git grep` 检查：`minibridge.light` 里**路由决策**（读配置、查表、默认分支）
  不得出现在 `引 ...:` 块内部；块内只允许 handler 调用或纯计算。

## 4. 【硬性环境限制】本机无 C 编译器 —— 必须实现降级路径

实测（2026-11-16，本机 FreeBSD）：

```
$ command -v gcc g++ clang
（gcc/g++ 缺失；clang = /usr/bin/clang 存在，但见下条）
$ light run examples/J阶段_L4_C_Go_MoonBit/J1_C_快速求和.light
→ 原生/`引 C:` 路径不可用（无 gcc，light 的 C 编译器探测顺序为 clang,gcc,cl，失败即报「未找到可用的 C 编译器」）
```

**因此本卡的可行做法**（按优先级）：

1. **B1 必须完全跑通**（进程方式，只用 Python + Go，本机均有：
   `go1.25.14`、`python3.12`）。B1 是 Track B 的核心交付，**不得因 B2 受阻而不交**。
2. **B2 允许在以下两种形态中择一**，并在 `规格.md` 与 `README` 明确标注属于哪种：
   - **(a) 真实 FFI**：若 `light run --backend src` 下 `引 C:` 可用（需 gcc/clang 成功编译），
     则实现真实 C FFI 调用；
   - **(b) 显式降级（允许）**：若 C 编译确实不可用，则 B2 用**光明侧的 `引 C:` 声明 +
     预编译 .so 缺失时的显式错误路径**演示边界，并**明确标记
     `B2_status=blocked_no_c_compiler`**，同时把 `run_b2.sh` 改为调用 B1 的等价路径
     并打印 `SKIP: no C compiler`（退出码 0，不算失败）。
     此时**必须在 `规格.md` 记录**：B2 的「FFI 直接调用」在本机未被实测验证，
     结论只能用于 B1。
3. **禁止**：为了「让 B2 通过」而把 `h_c_hash` 改成用 Python/Go 假装是 C；
   也禁止在没有编译器时伪造 `.so`。

> 组织者侧备注：这正是原方案 §风险 里「环境相关失败必须从语言能力指标剥离」的具体落地。
> B2 若因缺编译器跳过，应在最终报告中记为 **`environment_blocked`**，不计入 L4 引用成功率。
