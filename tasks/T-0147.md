## 背景

hive 的领取原子性来自 `git push` 非快进被服务端拒绝（hive.py `commit_file_to_ref`）。
T-0146 已经把「抢锁失败后的退避重试」做掉了，并且顺手修好了 `Hive.cmd_take`
（hive.py 约 1622 行）的顺序：

> cmd_take 现在是「**先 `w.claim(tid)` 抢锁，抢到才 `_assign_local` 写 owner/state**」。
> 抢不到时 `_assign_local` 根本不执行，所以不会出现「owner=A、租约却在 B 手上」的
> 半 assigned 状态。

但 **MCP server 的 `HiveMcp.t_claim`（mcp_server.py 约 491 行）还是旧顺序**：

```python
h._assign_local(tid, self.agent)          # ← 先写 owner/state 并 push main
h.commit_and_push(f"take {tid} -> {self.agent} (via mcp)")
w = self.worker()
if not claim and not w.claim(tid):         # ← 后抢锁
    return err(f"{tid} 领取失败（可能刚被别的 agent 抢走）")
```

问题：`_assign_local` 只是改卡文件 + push main，本身**不是原子抢锁**。两个 agent 几乎
同时调 `hive_claim` 同一张 ready 卡时，两边都可能通过开头的 `claim_info` 检查（此刻还
没人有租约），然后都去改卡、push main。即便其中一个 `w.claim` 失败，卡已经被写成了
`owner=A、state=assigned`，但 claim 租约在 B（或没人）手上——**半 assigned**。后续
watchdog / dispatch 看到 owner 有主就不会再派，卡就此卡死。

这正是 T-0146 自己记的遗留风险：「mcp_server.py 的 t_claim 仍先 assign 后 claim，
抢锁失败可能留半 assigned——本卡 paths 不允许改它，建议后续单开一张修。」

## 目标

把 `HiveMcp.t_claim` 的顺序改成和 `Hive.cmd_take` 完全一致：**先抢 claim 锁，抢到才
assign**。任何走 MCP 的 agent（不止 fb88-dsh）都不再能造出半 assigned 卡。

## 修复要点（对照 cmd_take 范本）

1. 开头先 `fetch` + 读 `claim_holder = _claim_holder(self.claim_info(tid))`；
2. 若 `claim_holder` 存在且 ≠ 自己 → 直接 `err(f"{tid} 已被 {claim_holder} 领取")`，
   **不要碰卡**；
3. `w = self.worker()`；若 `not claim_holder and not w.claim(tid)` →
   重新读 `claim_info` 把真正的主人带出来，`err(f"{tid} 已被 {holder} 领取，抢不到")`；
4. **只有锁到手之后**才 `h._assign_local(tid, self.agent)` + `commit_and_push`；
5. 备 worktree（`w.prepare(tid)`，若 `.hive/task.md` 不存在）；
6. 返回值和现有 `ok(...)` 结构保持一致（task_id / worktree / task_md / branch 等）。

## 红线

- **绝不 `git push --force`**（T-0146 脑裂红线）。抢锁的唯一来源就是 `w.claim` 的
  非快进拒绝；失败一律走 T-0146 的退避，不绕过。
- 不要为了"快"把 claim 和 assign 合成一次非原子提交。顺序固定为 claim → assign。
- 改动只限 `paths` 内的文件；别顺手重构 `t_claim` 之外的 MCP 工具。
- 行为要与 `cmd_take` 在「已有主 / 刚被抢 / 成功」三种结局上完全一致，包括错误信息文案，
  方便 LLM 总控读 message 判断自己处在什么状态。
