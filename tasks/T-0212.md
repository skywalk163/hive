## 症状

**读得通的写法，换到写就炸。** 两条同源，建议一起做：

```
# 1) 列表切片：读可以，写不行
设 表 为 [1,2,3,4]
打印 转字符串(表[1:3])        # ✅ [2, 3]
设 表[0:2] 为 [9,9]           # ✗ 语法错误：期望 右方括号「]」，但得到 冒号「:」

# 2) dict + 属性 + 索引：读可以，写不行（= L-255 / LH-33）
设 包 为 {"列": [1, 2]}
打印(包.列[0])                # ✅ 1（读走 _light_attr_get）
设 包.列[0] 为 5              # ✗ 'dict' object has no attribute '列'
```

## 根因

- 赋值左值（`src/parser_stmt.py`）只解析「名字 / 属性 / 单下标」，不认切片下标；
- 写侧的索引赋值直接发射 `对象.属性[索引] = 值` 的裸 Python 形式，dict 上不成立；
  读侧有 `_light_attr_get`，**写侧没有对称的 `_light_index_set`**。

## 影响

`dict` 里套列表是最常见的数据形状（看板配置、store 行、JSON 局部修改）。
「读得通 → 写得炸」是最容易让人怀疑自己的一类错误，而且报错指向 dict 没有这个属性，
与「我明明在用键」的直觉相反。

## 期望

`X.Y[i] 为 v`、`X[i:j] 为 v` 的写语义与 `X.Y[i]` / `X[i:j]` 的读语义完全对称，
覆盖 **dict / list / 类实例 × 单下标 / 切片**的组合。

## 落点

- `src/parser_stmt.py`：赋值左值支持切片下标；
- `src/code_generator.py`：补 `_light_index_set(对象, 键, 索引, 值)`
  （含切片版的 `_light_slice_set`），与读侧的 `_light_attr_get` 对称。

## 验收

新增 `tests/unit/test_LH38_下标与切片写.py`（`light run` 真跑），**组合矩阵全绿**：

| 容器 | 写法 | 期望 |
|---|---|---|
| list | `设 表[0] 为 9` | 生效 |
| list | `设 表[0:2] 为 [9,9]` | 生效，长度不变 |
| dict | `设 包["列"][0] 为 5` | 生效 |
| dict | `设 包.列[0] 为 5` | 生效（= L-255） |
| dict | `设 包.列[0:1] 为 [7]` | 生效 |
| 类实例 | `设 对.列[0] 为 5` | 生效（存量不许回退） |

外加一条**读-写对拍**：对同一组容器，先读后写再读，断言读写路径拿到的是同一处。

## 边界

- 只动赋值目标这一小块 + 写侧下标/切片的实现。
- 别改 `打印` / 表达式求值的既有行为。
