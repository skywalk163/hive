# leader 不刷新自身 last_seen：节点表永远停在启动时刻

## 一、现象

`~/.hive/cluster/state.json` 里本机（leader）记录：

```
laiweilideMacBook-Air-20c3af99  http://192.168.0.103:8788  last_seen=2026-11-08T12:08:24  status=null
```

同一时刻 `/api/cluster/state` 对该节点回填的是当前时间。T-0288 的体检工具因此
报出 `leader_record_stale`，持续十几个小时，看起来像主节点早已死亡。

## 二、证据锚

- `hive_cluster.py#L1507-L1513`：`_self_node()` 生成的自身记录里**没有 `last_seen`**。
- `hive_cluster.py#L1561-L1569`：`_node_status_locked()` 对 `id == self.node_id`
  直接返回 `alive`，所以本机永远「活着」，但对外暴露的 `last_seen` 字段仍是旧值。
- 刷新只发生在 `_update_node_locked(..., touch=True)`，而该函数只在收到**别人**的
  投票/心跳时被调用；leader 不会收到自己的心跳。
- 现场：`last_seen` 停在 11-08 12:08:24（进程启动时刻），而 `uptime_s` 已 >112000。

## 三、为什么是缺陷

`last_seen` 是看板、体检脚本与外部监控判断节点活性的公开字段。leader 的记录永远
不更新，等于对外长期宣告「主节点已失联」，既干扰排障，也会掩盖真实的
「1/1 当选后无人可达」状态（见 T-0294）。

## 四、修复方向（只改 `hive_cluster.py`）

1. 在快照/心跳生成路径里刷新自身记录：维护循环每 tick 写
   `self.nodes[self.node_id]["last_seen"]` 与 `last_seen_epoch`，或在
   `_public_node_locked()` 对 self 使用 `now` 回填。
2. 两处只能选一处作为唯一事实源，避免磁盘与 API 两个值继续分叉；
   建议落盘刷新（`state.json` 可见且与其它节点一致）。
3. 保持 `_node_status_locked()` 对 self 的 `alive` 语义不变，不改阈值。

## 五、验证方式（修复后应全绿）

```bash
python -m pytest -q tests/test_leader_self_last_seen.py
python -m pytest -q tests/test_dashboard_cluster.py
```

新增测试至少覆盖：leader 快照里自身 `last_seen` 与当前时间差 <1s；
`state.json` 落盘值同样被刷新；非 leader 节点行为不变。

## 六、风险与边界

- 只刷新自身记录，不改变任何节点状态判定（`peer_timeout`/`dead_timeout`）与 quorum。
- 不改 `state.json` 文件格式、不改看板代码、不改体检脚本。
- 与 T-0293 的地址校准互不依赖：本卡只改 `last_seen`，不碰 `url`。
- 不动其它卡面与 agent 配置；不重写历史节点记录。
