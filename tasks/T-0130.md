## 背景

`retries` 字段目前**只增不停**：`_reenqueue_ready`（看门狗自动回收）和 `cmd_retry`（显式重试）
都会 `retries + 1`，但全仓没有任何一处会因它停下。

后果：一张注定失败的卡（比如 verify 恒红、或 agent 一领就崩）会被看门狗判死 → 退回 ready →
dispatch 重新分派 → 再判死 → 再退回……**无限循环**。`hive orchestrate` 是常驻进程，这个循环会
7×24 小时不停烧 agent 时间（exec agent 还是真花钱的 LLM 调用），而 `hive doctor` / `digest`
只能事后看到 retries 数字在涨，阻止不了。

看门狗（T-0125）和总控（T-0126）把「自动推进」做出来了，但缺一道**熔断**。本卡补上。

## 目标

1. 卡面新增 `max_retries` 字段（`TASK_FIELDS` + `cmd_task` 建卡 + `cmd_draft` adopt 三处），
   默认 `DEFAULT_MAX_RETRIES = 3`。
2. **熔断只卡自动路径**：看门狗回收（`_reenqueue_ready`）前先判
   `retries >= max_retries` —— 已达上限就不再退回 ready，改用现有 `_set_state(tid,"blocked",...)`
   转成 `blocked` 并写明原因（"自动回收已达上限 N 次，停止自动重派，需人工介入"）。
   `blocked` 会被 `dispatch`、worker、`orchestrate` 全部跳过，等于自动退出流水线。
3. **人工显式 `hive retry` 不拦**，但超过上限时 log 一条告警——尊重"人在上"，
   人明确要求重跑就照做。
4. `cmd_watchdog` 的候选里把这类卡的 `action` 从 `reclaim` 标成 `block`，
   dry-run 日志和 JSON 输出都能看出"这张是要回收 / 还是要判死转 blocked"。
5. `hive doctor` 对"已达重试上限"的 blocked 卡单独点名（现在只笼统说 blocked 等资源，
   看不出是烧光了重试次数）。
6. 测试（新建 `tests/test_retry_cap.py`）：
   - 未达上限 → 回收后仍是 `ready`、`retries+1`；
   - 已达上限 → 回收后变 `blocked`、**不再回到 ready**、`retries` 不再涨；
   - `blocked` 卡被 `dispatch` 跳过（验证真的退出了流水线）；
   - watchdog JSON/日志里 action 是 `block`；
   - 显式 `hive retry` 超过上限仍能跑（只是告警）。

## 红线

- **不改** `retries` 的累加语义与位置（仍记在卡上、仍由 retry/回收各自 +1）。
- **不拦** 人工显式 `hive retry` —— 上限只作用于自动回收路径。
- **不改** `blocked` 的既有语义（dispatch/worker/orchestrate 照旧跳过它）。
- **不引入** 任何第三方依赖。
- `max_retries = 0` 要能表示"一次都不许自动重派"（首次判死就转 blocked），别把它当成"不限"。
