## 背景

排查「草稿内容被还原」时抓到的真凶，已用实锤实验确认：

`Worker.__init__`（hive.py:1937）和 `Worker.loop()`（hive.py:2337）都是**无条件**执行
`git fetch` + `git reset --hard origin/main`，没有任何安全检查。

实锤：把 `drafts/T-0128.md` 改脏（611 字节、` M`）→ 只构造一个
`Worker('/home/skywalk/dswork/hive','workbuddy')`、不跑任何业务 → 文件立刻变回 668 字节骨架、
`git status` 变干净。**任何构造 Worker 的命令（`hive take` / `work` / `submit`、MCP claim…）
都会静默抹掉协调仓里未提交的已跟踪改动**，包括正在写的草稿。

设计上其实早知道这个坑：`HiveMcp.worker()` 的注释写着「worker 初始化时会 reset --hard；
共用主工作区会把人未提交的改动冲掉」，所以 MCP server 专门用独占 clone 规避。但
`hive take` / `hive work` 跑在**主工作区**上，就直接暴露了。
`Worker.loop()` 更糟——轮询期间每一轮都抹一次。

## 目标

把这两处裸 reset 换成现成的 `Hive.sync_main()`（hive.py:412），它已有正确守卫：
- 本地与 `origin/main` 对齐、或本地领先 → **直接 return，不动工作区**（本次要修的核心场景）；
- 落后且工作区干净 → `reset --hard origin/main`（保持原同步能力）；
- 落后且有已跟踪改动 → **raise HiveError 报错**，绝不静默丢人的改动。

具体改动：
1. `Worker.__init__`：`self.h.fetch()` + `git reset --hard` → `self.h.sync_main()`，
   注释说明为什么不能直接 reset。
2. `Worker.loop()`：轮询里的 `self.h.fetch()` + `git reset --hard` → `self.h.sync_main()`。
   `loop()` 本来就 catch `HiveError` 并继续下一轮，所以落后+脏只会记 log，不会崩。
3. **不动** `mcp_server.py:338`（`HiveMcp.hive()`）和 `mcp_server.py:1021`（启动探测）：
   这两处作用在 MCP 独占 clone 上，reset 是其「每次调用都读到最新卡」的设计前提，
   且文档已明确 MCP 必须用独占 clone。
4. **不动** `hive.py:440`——那就是 `sync_main` 自己的（有守卫的）reset。

测试（新建 `tests/test_worker_guard.py`，接 `world` 夹具）：
- 构造 Worker 后，协调仓里一个被改脏的已跟踪文件**必须还在**（回归守卫）；
- `hive work --once` 跑一轮后同样必须还在；
- 顺带断言 `sync_main` 在「落后且脏」时是 raise 而不是静默 reset（保住既有契约）。

## 红线

- **不改** `sync_main` 本身的语义与守卫逻辑。
- **不改** MCP 两处 reset 的行为（`HiveMcp.hive()` / 启动探测），否则 MCP 读到旧卡。
- **不引入** 任何第三方依赖。
- 不能让「已对齐时」反而多出一次 reset —— 那正是要消除的破坏点。
- 落后+脏必须是**报错**，不能退化成静默丢弃，也不能退化成直接继续（会读到旧卡/旧 agent 配置）。
