## 背景

2026-11-25 的 T-0489 现场，把 `hive_submit` 的结构性问题暴露得很彻底：

- `cmd_submit` 是同步的：commit → push `task/<tid>` → 逐条跑 verify → 才写 `results/<tid>.json`（`hive.py` 5530–5733）；
- `run_verify` 单条默认上限 1800 秒（`hive.py` 1617）；
- MCP 服务是单线程逐行读 stdin（`mcp_server.py` 1322–1337），submit 在跑 verify 的整段时间里，服务端什么也不回。

结果就是：客户端等到超时，报 `LocalHub returned an invalid raw MCP result`；紧接着 `hive_get_task` 也报同一个错（服务端还堵在那次 submit 里）。分支和 commit 早就推上去了，但结果没写，卡停在 running，谁也确认不了状态。T-0489 最后只能人工 retry + 换机重跑。

顺带暴露第二处冲突：verify 可能跑 30 分钟以上，而租约默认 10 分钟。租约到期后再写 store，会被 `lease lost` 拒收——就算客户端不超时，结果照样落不下来。

## 目标（可验收）

1. MCP `hive_submit` 的同步段只做「commit + push 任务分支」，耗时只随 git 操作增长（本机（Windows 沙箱盘）实测 9–10 秒，远小于一次 verify 的分钟级），返回 `status="submitting"`、`branch`、`head`、`job`、`log`、下一步提示。
2. verify 放到**独立后台进程**里跑；客户端断开、MCP server 退出都不影响它把结果写完。
3. 后台 job 在 verify 期间**持续续租**，写完结果前租约必须有效。
4. `hive_get_task` / `hive_result` 能看到提交阶段：`pushing | verifying(i/n) | writing | done | failed | timed_out | lease_lost | lost`。
5. 三种异常都有终态、都不悬挂：verify 失败 → `status=failed`；verify 超时 → `timed_out=true` 的 failed 结果；后台进程被杀 → `phase=lost`，**不伪造结果**，提示 `hive retry`。
6. CLI `hive submit` 默认行为不变（同步、返回 0/1）；新增 `--async` 可选，供人或脚本使用。
7. 同一条卡重复 submit 幂等：已有活 job 就返回现状，不重复起进程；已有结果则按原逻辑拒绝。

## 设计约束（必须照做，评审会逐条看）

1. **只抽一套产结果逻辑**：把 `cmd_submit` 后半段（verify 汇总 → 结果闸门 → 组 result → 写 res 分支 → store_result → 释放租约）抽成 `finish_submit(...)`，同步路径与后台 job 共用。禁止复制粘贴出第二套 result 构造——字段不一致会让 land/看板再次踩坑。
2. **后台必须是独立进程，不是线程**：MCP 是单线程 stdio，线程里再跑 30 分钟一样会占住 handler，而且 server 退出线程就没了。用 `subprocess.Popen` 起 `hive.py submit <tid> --run-job <jobfile>`：
   - POSIX：`start_new_session=True`；
   - Windows：`creationflags=DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`；
   - `stdin=DEVNULL`，stdout/stderr 全部重定向到 job 日志文件。**后台代码任何一行都不许写 stdout**（会污染 JSON-RPC 流）。
3. **job 状态文件**：`$HIVE_STATE/agents/<agent>/jobs/<tid>.json`（无 `HIVE_STATE` 时用默认 state 根），原子写（tmp + `os.replace`）。字段至少：
   `task, agent, phase, pid, started_at, updated, branch, head, verify_total, verify_index, log, lease_id, error`。
4. **跨平台**：Windows 与 FreeBSD 都要能跑。文件锁不要无条件 `import fcntl`——POSIX 用 `fcntl.flock`，Windows 用 `msvcrt.locking` 或 `O_EXCL` + pid 存活校验；锁文件 `<tid>.lock` 放同目录。
5. **租约**：job 从 job 文件/租约留底取 `lease_id`；verify 期间每 `max(120s, lease_minutes*60/3)` 续一次（store 模式走 `store_renew`，git 模式走 cluster 续租）。续租失败 → `phase=lease_lost`，不写结果，日志写清原因。写结果前再校验一次租约未过期。
6. **快返回的边界**：commit/push 失败仍然同步报错，不进入后台——「已推送分支」这句话必须是真的。响应里的 `head` 就是 job 之后写结果用的 head，job 不许再取一次 HEAD。
7. **verify 超时归 job 管**：继续用 `run_verify` 的上限，但 job 必须把超时收敛成 failed 结果（`timed_out=true`、`error` 写明命令与上限），不能让卡停在 running。上限允许用 `HIVE_VERIFY_TIMEOUT` 覆盖，测试用。
8. **不做的事**：不改 store 协议、不加新的 MCP 工具；不改 `hive_submit` 现有的入口校验（owner、租约 fencing、越界、严格模式）——这些必须留在同步段，否则调用方拿不到即时反馈。
9. **跨机可见性**：job 文件只在 owner 那台机器上，owner 的 `hive_get_task` 读它并附 `submit` 块（`phase/pid/verify_index/log_tail` 最多 20 行）；主控端读不到时返回 `submit_remote=true`、不报错，只看 claim/result。这是本卡接受的范围，不要求扩 store schema。
10. **worktree 保留**：MCP 提交一直用 `keep=True`；job 结束后不删 worktree，留给 agent 复查，沿用现有 `gc` 清理。

## 验收判据（测试必须覆盖，缺一条不算过）

1. 快返回：卡上 verify 为 `python -c "import time;time.sleep(3)"`，`t_submit` 返回耗时 < 2s，`status=submitting`，branch/head 与远端一致。
2. 不阻塞（核心回归）：submit 返回后、后台 verify 仍在跑（测试里是 6 秒）时，连续两次 `hive_get_task` 都在 4 秒内返回合法 JSON——直接对应 T-0489 的 `invalid raw MCP result`（旧实现会一直等到 verify 结束）。
3. 后台落库：verify 结束后 10s 内 `results/<tid>.json` 出现，`status=done`、`verify[0].code=0`；`store_result` 恰好被调用一次。
4. 失败：verify 返回 1 → 结果 `status=failed`，带 verify tail；job `phase=failed`。
5. 超时：`HIVE_VERIFY_TIMEOUT=1` + `sleep 5` → 结果 `timed_out=true`，不悬挂。
6. 续租：fake store 记录到 `renew >= 1`（测试里把续租间隔调小）。
7. 进程丢失：kill 掉 job pid → `hive_get_task` 的 `submit.phase=lost`，且**没有**生成伪造结果。
8. 幂等：同一 tid 再次 submit → 返回已有 job，不起第二个进程。
9. 同步路径回归：`cmd_submit` 返回 0/1 语义不变，`tests/test_store_result_signal.py` 全绿。
