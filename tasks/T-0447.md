# 光明：T-0445 的「内存错误」取证——抓原始失败快照 + 同机连跑统计与内存曲线

> 来源：T-0445 收口时唯一没结论的一条。当年报的是「内存错误 / 栈溢出」，但修复后
> 一切复现手段都不红，于是只能写「不可复现」，既不能判宿主、也不能判已修好，
> 该分支因此一直悬着。**本卡只做取证，不改编译器行为**，目标是把这条线落成
> 「有硬证据的三分结论」之一，或者明确列出还缺哪些环境条件。

## 现状（T-0445 实测，供本卡对齐口径）

- 264 个 lightharness `.light` 模块，单进程连编：RSS 22MB → 27MB，无累积趋势。
- 最大模块 `web服务器.light`（140253B）：峰值 62.9MB。
- 人为放大：5MB 单字符串 / 10 万元素列表：峰值 132MB，仍不报错。
- T-0445 修的 codegen 递归是确定性问题（已在 R225 迭代化），与「偶发内存错误」不是同一处。
- 结论现状：**无原始失败快照 → 无法归因**。所以 T-0445 的内存分支至今未关闭。

## 这一轮要交付什么

### 1. 采集器 `tools/r225_mem_capture.py`（新增，纯 Python，不许用 POSIX 工具）

- 参数：`--modules DIR --rounds N --workers W --out DIR --timeout-s S`
- 每个模块独立编译（优先子进程，保证内存可归零），逐条记录：
  文件、字节数、行数、编译耗时 ms、编译前后 RSS、峰值工作集、私有字节、
  rc、异常类型、异常尾部 200 字符。
- 取内存的两条分支（本卡核心，必须都实测过）：
  - Windows：`ctypes` + `psapi.GetProcessMemoryInfo`（WorkingSetSize / PeakWorkingSetSize /
    PrivateUsage），系统级可用内存用 `GlobalMemoryStatusEx`。
  - FreeBSD / POSIX：`resource.getrusage(RUSAGE_SELF).ru_maxrss`（KB），
    可用内存走 `sysctl hw.realmem / vm.stats.vm.v_free_count`（拿不到就降级为「不可用」，不许崩）。
- 产物：`runs.csv`（每模块每轮一行）+ `summary.json`（每轮首/末/峰值 RSS、增长百分比、
  失败清单、机器信息、Python 版本、参数快照）。
- 失败即抓快照：traceback 全文、当时 RSS、系统可用物理内存、进程句柄数、
  `tracemalloc` top10（按行号聚合）、Python 版本、主机名、开始/结束时间、并发数。
  Windows 的 `MemoryError` 有时不带 traceback，此时必须落「当时内存快照 + 模块路径 + rc」，
  并标明「traceback 缺失」——不许静默吞掉。
- 多进程模式（`--workers>1`）：子进程崩溃/被 OOM 杀掉必须落盘成一条 `crash` 记录，
  父进程不得静默继续。

### 2. 同机连跑统计（判宿主的硬证据本体）

- ≥10 轮 × 264 模块，单进程与 8 并发各一组。
- 每轮给：首轮 RSS、末轮 RSS、峰值、增长百分比、失败数；再给「轮间斜率」与「轮内斜率」。
- 三态判定函数（进 `summary.json` 且被判据覆盖）：
  - `leak`：轮间 RSS 单调上升且总增长 > 5%，或单轮内出现单向爬升；
  - `stable`：增长 ≤ 5% 且无失败；
  - `flaky`：同输入不同轮结果不一致（某轮失败、下一轮通过）。
- 内存曲线要**能给人看**：CSV 之外再输出一份 ASCII/文本表（每轮一行）方便贴进 summary。

### 3. 放大触达矩阵（至少 3 条，全部给数字）

1. 单进程 264 模块 × 10 轮；
2. 8 worker 并发同量（看是否只在并发/内存压力下才红）；
3. 大模块 + 深嵌套/长链叠加（借 T-0445 的 1200 项链与 ≥200KB 模块），
   并在旁边起一个「内存占用气球」进程把可用内存压到 ~10% 再跑一轮（模拟内存紧张）。

### 4. 双平台对照

FreeBSD 15.1（`ssh workbuddy@192.168.0.88`，密码取 `.env` 的 `SSH_PASS_WORKBUDDY`；
免密可用时直接 `BatchMode=yes`）跑同一个采集器，产出 Windows / FreeBSD 双平台曲线对比表。
注意：该机无 pytest-xdist，需 `-o addopts=''`；跑完清理远端临时目录。

### 5. 结论三分（必须带硬证据，禁止只写结论）

- **代码问题**：最小复现 + 定位到文件:行 + 触发阈值；
- **宿主问题**：同机连跑统计表 + 内存曲线 + 与 FreeBSD 的对照（同代码不同平台，一边红一边绿才算硬证据）；
- **证据不足**：列出已试矩阵每格数字，并明确写出要总控补哪些条件才能复现——
  机器名/CPU/物理内存、Windows 版本与补丁、Python 精确 patch 版本、
  当时 pytest 参数与插件、是否 xdist 与并发数、lightharness 当时的 commit、
  失败时刻的 rc 与 stderr 原文。

若全矩阵双平台皆绿：**明确写「当前环境下不可复现，本卡不关闭 T-0445 内存分支，
需要原始失败快照才能继续」**，不许硬凑「宿主问题」。

### 6. 判据 `tests/test_R227_mem_snapshot.py`（要快，全文件 < 60s）

- fixture 自带（`tmp_path` 现生成 3 个小 `.light`），不依赖 lightharness、外网、目录残留。
- 断言：CSV 字段齐全且行数 = 模块数 × 轮数；summary 的斜率/增长百分比计算正确
  （用手算期望值对拍）；三态判定对 3 组构造数据分别给出 leak/stable/flaky；
  失败快照路径被真实触发一次（注入一个必抛异常的模块，断言快照字段齐全）；
  Windows 与 POSIX 两条取内存分支都能各自跑通（不满足的分支记 skip **只允许**用于
  「当前平台没有该分支」，且必须在 summary 里说明）；
  退出码语义（有失败 → 非 0，全绿 → 0）正确。
- 不许把任何断言改 skip / xfail 来「变绿」。
