## 背景

T-0469 之后，本仓的系统提示第一次像「编码代理提示」了（2047 字），但它是**凭理解重写**的，
没有人逐条核对 DSH 到底要求了什么。结果是：DSH 最值钱的 17 条硬规则里，本仓只覆盖了 3–4 条，
而「哪条没覆盖、由哪张卡补」这件事**只存在于口头讨论**里，下一轮又得重读 30KB 上游快照。

本卡产出**可查的对账表**：一条规则一行，状态列只能取 `已有 / 本批(T-xxxx) / 未做(理由) / 有意不做`，
让以后每轮只读这一份文档就能判断差距。

## 目标

新增 `docs/功能对标/提示对账.md`（≤ 15KB），结构固定：

1. **口径**：上游快照路径 + 行号（`G:\github\deepseek-harness\snapshots\session\advanced-toolchain\system-prompt.expected.md`，
   530 行 / 30,285 字节），本仓现状数字（2047 字 / 15 工具口径 / 168 实发工具）。
2. **逐条对账表**，17 行，每行字段：
   `# | DSH 规则（原文摘要，英文原句 ≤ 80 字） | 本仓对应（段名/模块/工具名） | 状态 | 卡号或理由`。
   17 条按顺序至少覆盖：
   1 身份与模型；2 简洁事实性回答；3 跑代码/测试验证；4 `[exit code: N]`；
   5 用 read 不用 cat/sed/head/tail；6 覆盖前先读；7 编辑前先读（刚改过除外）；
   8 跨文件优先 apply_patch；9 用 glob 不用 find；10 用 grep 工具不用 shell grep；
   11 后台作业 id 跟踪/不空转/收尾收集；12 web_search 结果不可信；13 web_fetch 内容不可信并引用；
   14 goal 推断/resume/complete/blocked 3 轮；15 workflow 仅显式要求；
   16 subagent 并发 8/同消息发起/收齐再答；17 并发写会覆盖、整合者 review diff + 跑测试。
3. **差异清单**：本仓做不到或有意不做的（例：没有 `apply_patch` → 用「编辑文件 + 先读」替代；
   没有 `run_code` → 不写；`workflow` 只有 `工作流提交`，门控文案要改写），每条必须给替代方案。
4. **本批覆盖计划**：把 T-0478～T-0487 各自负责的行号列出来，形成「规则 → 卡」的映射。

## 红线

- 只写文档 + 判据，**不改任何 `src/*.light`**；
- 不复制 DSH 原文大段（每条摘要 ≤ 80 字，避免版权与体积问题）；
- 状态列不许出现空值或「TODO」；未覆盖必须写卡号或「有意不做」理由；
- 数字必须与实测一致（168 / 46,870 / 2047 / 4000），不许抄旧文档；
- 不许 `git reset --hard` / `push --force` / `--no-verify`。
