## 背景

外部评审（DeepSeek，2026-11）把「报错质量」列为 AI 友好与人类友好的共同第一道门槛：AI 最怕模糊报错，而一个「错误码 + 原因 + 候选修复」三元组，比任何语法糖对 AI 友好性的提升都大。

现状：`src/errors.py` 的 `ErrorEntry`（第 686 行）已有 `stage/message/line/column/fix_suggestions`，但**没有稳定错误码**，也没有机器可读的候选修复；`src/enhanced_errors.py` 的提示是散落的字符串。`docs/AI编程指南.md` 与 `docs/STDLIB_REFERENCE.md` 里记录了 14 个高频坑（缺导入、关键字冲突、类系统后端不兼容、列表索引赋值、`?:`、`&&/||`、段落实参数量、单行段落空跑等），但都只是自然语言。

本卡只做**框架与码表**，不改 CLI、不改渲染器——那两张卡（T-0317 定位、T-0318 JSON 输出）并行做。

## 要做什么

1. 新建 `src/diagnostics/__init__.py`、`model.py`、`registry.py`，纯标准库。
2. `model.py`：`Diagnostic` dataclass，字段固定为
   `code / severity(error|warning|info) / stage / line / column / message / hint / fixes(list[str], ≤3) / candidates(list[str]) / provisional(bool) / docs`。
   - `to_dict()` 字段顺序稳定（JSON 可直接 diff）；`from_dict()` 可往返；
   - `line` 为 0 时表示「位置未知」，序列化时保留 0，**不许编造行号**。
3. `registry.py`：
   - `Rule(code, title, pattern, stage, hint, fixes, candidates)`；
   - 内置 **≥14 条**，覆盖 AI 编程指南与 STDLIB_REFERENCE 的高频坑，码段约定：
     `L1xxx` 词法/语法、`L2xxx` 类型、`L3xxx` 运行时、`L4xxx` 模块/导入、`L5xxx` 后端差异；
   - `explain(message, stage=None) -> Diagnostic | None`：按正则命中返回；**未命中返回 None，不造兜底假码**；
   - `get(code) -> Rule | None`；
   - `to_legacy_entry(diag) -> ErrorEntry`，保证 `src/errors.py` 现有文本输出逐字不变（不改那个文件）。
4. `docs/错误码规范.md`：码段划分、字段语义、新增一条码的流程、兼容承诺（**码一旦发布不复用、不改变含义**）。
5. `tests/test_diagnostics_registry.py`：
   - ≥14 条规则，每条至少一组正例（命中）与反例（不命中）；
   - `explain()` 未命中返回 None；
   - `to_dict`/`from_dict` 往返相等；
   - 同一错误码在两条规则里重复 → 测试失败；
   - `to_legacy_entry` 转换后 `format()` 输出与直接构造 `ErrorEntry` 一致。

## 不要做什么

- 不改 `cli/light.py`（T-0318 负责）、不改 `src/enhanced_errors.py`（T-0317 负责）——避免并行冲突。
- 不引入第三方依赖；不联网。
- 不为「凑够 14 条」编造语言里不存在的问题；每条都要能在 docs 或代码里找到出处，并在 `Rule` 里留 `source` 注释。
- 不把 warning 升级成 error。

## 完成标准

- `python -m pytest -q tests/test_diagnostics_registry.py` 全绿。
- summary 里贴出：条数统计、码段分布、`explain()` 对 3 个真实报错的命中示例（含 code 与 fixes）。
