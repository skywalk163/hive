# T-0351 控制面装配修复与组播下行接 H-LSA

## 背景

交办方要求「总控有责任隔一段时间就通过组播把更新信息发给子节点，
这样可以节省 git 去 gitea pull 的时间和流量」。

**关键事实：这套组播控制面已经写好了，只是没装上。**
`hive_control/` 目录里有 `plane.py`(56KB) / `downlink.py` / `uplink.py` / `pull.py` /
`election.py` / `config.py`，已经实现：组播 `239.255.42.1:47899`、
`dynamic_multicast_interval(active)`、`Limits.max_packet_bytes=1400`、
200ms 聚合窗口、增量/全量拉取、fallback 逐节点单播、Hello / LeaderHeartbeat、
只有 Leader 组播（I3）。`docs/集群服务.md` §6 甚至已经列了「和 RIP / OSPF 的对应关系」。

但 `docs/控制面v0.5-运维.md:43-50` 写得很清楚：

> `hive_control/adapter.py` 组装 `ControlPlane` 时没有传入
> `node` / `address` / `listen_port` / `config`，构造函数会抛 `TypeError`
> 并被适配器降级吞掉。因此 `plane_available:false`、`degraded:true`、
> `multicast_mode:"off"` —— **控制面实际没有工作**。该装配缺陷属 T-0311 范围。

所以本卡是「**修装配 + 把 H-LSA 摘要接进下行 + 在 dev 环境证明它真的通了**」，
不是新写一套组播。装配缺陷位置：`hive_control/adapter.py:91-95`；
目标构造签名见 `hive_control/plane.py:286`。

规范见 `H-LSA-协议设计-借鉴OSPF.md` §2（T1 组播摘要）、§3（复用清单）、§4 第 1 道闸。

## 要做什么

1. **修装配缺陷**：在 `hive_control/adapter.py` 组装 `ControlPlane` 时补齐
   `node` / `address` / `listen_port` / `config` 四个参数，来源从
   `cluster serve` 已有的 `--name` / `--advertise` / `--port` / 配置对象取，
   不新增必填 CLI 参数、不改旧 HTTP 面的选主与租约语义（D1 / D14 不变）。
   异常仍按现有「降级吞掉 + 记日志」处理，不许因控制面失败拖垮集群启动。
2. **证明装配通了**：在 **dev 隔离实例**上 `GET /api/cluster/status` 必须返回
   `plane_available:true`、`degraded:false`、`multicast_mode:"multicast"`。
   这是 T-0356 集成验收的硬前置，截图/JSON 写进验收证据。
3. **下行接 H-LSA 摘要**（`hive_control/downlink.py` + `config.py`）：
   - 新增一种下行报文 `{"type":"lsa_digest", ...}`，字段
     `(leader_epoch, seq, digest, head_sha, n_changes, area, project_tag, sent_at)`，
     **不带状态体**，单包 ≤1400B；
   - 走 **T1 60s 摘要节奏**（调用 T-0350 `hive_lsa.tick()` / `build_digest()`），
     与 `dynamic_multicast_interval()` 管的高频实时提示节奏**分层并存**，
     不改后者的 2.0/1.0/0.5s 语义；
   - 只有控制面 Leader 发（I3）；follower 只听不发。
4. **切主防重复泛洪**（呼应 `幽灵leader根治-104操作手册.md`）：
   - 切主后设 `suppress_window ≥ 2 × hello_interval`（`Limits.hello_interval=2.0s`）；
   - 接收端校验 `leader_epoch` 单调递增 + `project_tag` + `cluster_id`，
     旧主 / 幽灵 leader / 开发实例误入的包**直接丢**，并计数到 `status()` 指标；
   - 组播不可用时沿用既有 `fallback_after=30.0s` 逐节点单播降级，语义不变。
5. **网络隔离可配**（配合 T-0349）：`hive_control/config.py` 的组播组/端口改为可覆盖
   （开发用 `239.255.42.2:47900`），报文加 `project_tag` 与 HMAC 校验；
   **dev 实例不得向生产 `239.255.42.1:47899` 发包**。
6. **`tests/test_control_plane_attach.py`**：用注入的 fake transport（不真发 UDP 包），
   断言装配参数齐全、`plane_available:true`、摘要报文 ≤1400B 且不含状态体、
   只有 leader 发、切主抑制窗口内不重复泛洪、旧 epoch 包被丢、
   fallback 语义不变、`project_tag`/cluster_id 不匹配被拒。

## 不要做什么

- **不重写 `hive_control/plane.py` 主体**，不改选举 / 租约 / 拉取协议的既有语义；
  只改 `adapter.py`（装配）、`downlink.py`（新报文类型）、`config.py`（可配组播 + 常量）；
- 不改 `hive_cluster.py`（T-0352 持有）、不改 `hive.py`（T-0353 持有）；
- 不把全量状态体塞进任何下行报文或心跳；
- 不在生产实例上验证装配，**只在 dev 隔离实例**上跑；不向生产组播组发包；
- 不重启生产 `cluster serve`，不改 `config.json` / `.env`；
- 不因为「组播不方便测」就改成定时全量单播——那等于把流量问题放回去。

## 完成标准

1. dev 实例 `/api/cluster/status` 的 `plane_available:true` / `degraded:false`，
   `multicast_mode` 为 `"multicast"`（或明确标注的 `"fallback"` 且原因可查）。
2. 单次 T1 摘要包 ≤1400B，字段与设计文档 §2 一致，不含任何 `progress`/`leases`/卡面全量。
3. 切主仿真中组播源恒 ≤1，旧 epoch 包丢弃计数 >0，抑制窗口内不产生重复泛洪。
4. fake transport 单测全绿，且不产生真实网络流量。
5. 0.16.03 / 0.16.05 的旧 HTTP 面行为零改动（回归由 T-0356 统一复核）。
