# T-0144 背景

外部 reviewer（DeepSeek 官网 agent）读完仓库给出一份评审，里面有**两条判断是错的**，
而错因都在我们自己身上：

1. **「hive.py 是 1550 行单文件」** —— 这个数字是它从 README 第 3 行抄的。
   实际 `hive.py` 已经 **3144 行**，而且 MCP server 早在 T-0123 前后就拆出去了
   （`mcp_server.py` 1038 行 + `llm_controller.py` 471 行）。
   README 自己就过时了，怪不得别人。
2. **「项目可能已停止开发，功能合并至光明（Light）项目」** —— 这条更伤。
   光明（LightLang）是一门**独立的中文编程语言**，跟 hive 毫无继承关系；
   hive 里的 `light` 只是**曾经登记过的代码仓**，T-0133 已经做了隔离、
   `agents/*.json` 现在只登记 `hive`。但 README 的 `agent add` 示例
   （56-58、67、87、172、188 行）至今还在写 `--repo light=...`，
   任何一个新读者都会顺着得出「这项目围着 light 转」的结论。
   **评审里最伤人的那条，是这份 README 自己招来的。**

## 要做的三件事

1. **README 规模描述改成现状**：不再写死一个会腐烂的行数。改成说清楚
   实际构成（hive.py 主程序 + mcp_server.py + llm_controller.py 已拆出），
   或者干脆不提行数。**别再留一个会过时的具体数字**——这是第二次踩了。
2. **README 的 `light` 示例全部换成 `hive`**：现在的现实是「现阶段只登记 hive 仓」，
   示例必须跟 `agents/*.json` 的真实内容一致。顺手把 `docs/` 里残留的
   light 示例一并清掉（操作手册 T-0140 已经清过，README 漏了）。
3. **README 顶部加一行项目状态**：说清「活跃开发中」，避免再被当成归档项目。
   这条是开源礼仪，成本一行。

## 顺带：ci.yml 那处硬编码（本次只加注释，不改代码）

`.gitea/workflows/ci.yml:28` 写死了 `uses: http://192.168.1.5:3000/actions/checkout@v4`。
判断下来**不改成可配置**，理由是：

- 它在 `.gitea/` 下，**GitHub 只认 `.github/workflows/`、GitCode 也不认这个目录**，
  推到两个公开平台根本不会触发，零影响；
- 真正会踩的只有「自建 Gitea 上 fork」这个很窄的场景；
- 那行注释写明它是为绕开 Gitea 裸 `uses` 回落到 github.com——而这台机器上
  github.com 是被封的，**改成官方 `actions/checkout@v4` 反而会弄坏自己的 CI**；
- 换成 `${{ vars.xxx }}` 有风险：Gitea runner 未必在 `uses:` 上做表达式求值，
  为了一个窄场景去赌一个可能让现有 CI 挂掉的行为，不划算。

所以只加醒目注释，告诉换机器的人该改哪一行。**代码零改动，可发现性问题解决。**
