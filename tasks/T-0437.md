> 第一次接 hive？先读 `docs/AGENT快速上手.md`。
> 本卡修的是 **hive 自身的可用性缺陷**（不是 light 仓的问题），症状极具误导性。

## 背景：`hive land` 在大仓上崩 `MemoryError`，且报错完全不指向真实原因

2026-11-21 合 T-0434（light 仓）时实测：

```
$ python hive.py land T-0434
MemoryError
```

连续两次稳定复现。换一种调用方式（带 traceback）直接**进程级崩溃**：

```
Error: subprocess-local: Windows Job runner exited with exit code 3221226505
```

（`0xC0000409` = STATUS_STACK_BUFFER_OVERRUN，Windows 上常见的「进程被内存问题直接干掉」）

### 真实原因（已定位）

`land_one()` → `_pick_remote()`（`hive.py:3083`）在**没有显式给 `--remote`** 时，
会把 `code_remotes(repo)` 里的**每个远端**都 `git fetch --prune` 一遍，再逐个探测分支。
这一步在下面这个仓上内存失控：

| 因素 | light 仓实测值 | lightmem 仓（对照，没出问题） |
|---|---|---|
| 远端数 | **3**（gitea / gitcode / origin） | 3 |
| worktree 数 | **32** | 4 |
| 对象规模 | packs 6 个 / 101.71 MiB / in-pack 79377 | 明显更小 |
| 可用内存 | 本机当时 **8.17 GB / 18.55 GB** | 同机 |

### 决定性证据：加 `--remote` 就立刻好了

```
$ python hive.py land T-0434                       # 崩：MemoryError
$ python hive.py land T-0434 --remote gitea        # 成功：可以合入（dry-run）
$ python hive.py land T-0434 --remote gitea --apply # 成功合入
```

`--remote` 的作用就是**跳过 `_pick_remote` 的探测循环**（`hive.py:3098-3103`
只 `fetch` 指定的那一个）。所以问题范围锁定在 `_pick_remote`，不在 land 的其它步骤。

### 为什么这个 bug 很坏

1. **报错完全误导**：`MemoryError` 三个字既不说是哪一步、也不说和远端有关，
   排查者第一反应会是「机器内存不够」或「light 仓坏了」，实际上和仓库数据无关；
2. **进程级崩溃**（带 traceback 时）连 Python 的异常栈都拿不到，只剩一个 Windows 退出码；
3. **有 workaround 但没人知道**：`--remote` 能绕过，但报错里一个字没提；
4. **大仓必然踩**：worktree 多、远端多、对象多，正好是活跃仓库的常态。

## 目标（按优先级）

### 1) 让失败可诊断（**最低成本、收益最大，必做**）

现在 `MemoryError` 是裸抛。至少要捕获它，并给出**指向 workaround 的提示**：

```
合入失败：内存不足（探测远端时耗尽）。这条仓有 N 个远端 /
M 个 worktree。请改用 --remote <名字> 指定远端以跳过多远端探测，
例如：hive land T-0434 --remote gitea（现有远端：gitea, gitcode, origin）
```

要求：
- 捕获 `MemoryError`（以及它可能派生的 `RecursionError`/进程崩溃前的信号）；
- 提示里**必须**列出可用远端名（让人能直接抄）；
- 在 `docs/` 或 `CHANGELOG.md` 里记一条，让下一个踩到的人能搜到。

### 2) 让 `_pick_remote` 不再做全量探测（**治本**）

当前逻辑：`for name in remotes: fetch(name); if rev_parse(...): return name`
——**每个远端都 fetch 一次**，即使第一个就命中。

改进方向（择一或组合，**在 summary 里说明选了哪个、为什么**）：

- **方案甲（惰性探测，推荐）**：按优先级逐个探测，**一旦命中立即返回**，
  不再 fetch 后续远端。当前代码其实已经是「命中即 return」，但 `fetch` 是逐个做的，
  真正的问题是**每个远端都 fetch 全量对象**。所以关键是：
  - 探测前先用 `git ls-remote --heads <remote> refs/heads/<branch>`（**只取引用，不拉对象**）
    判断分支在不在，命中后再对这个远端做一次真正的 `fetch`；
  - 这样未命中的远端只承担一次 `ls-remote`，不承担对象传输。

- **方案乙（缓存远端归属）**：把「分支 → 远端」的映射记在本地状态里，
  下次直接命中，不重复探测。需要处理缓存失效（分支被删/换远端）。

- **方案丙（限制探测预算）**：给 `_pick_remote` 设总时长/总对象预算，超了就降级为
  「用首选远端 + 提示 `--remote`」。

### 3) 回归测试

至少覆盖两条：
- **不复现崩溃**：mock 一个「有 3 个远端、第一个就命中」的场景，断言只对
  **1 个**远端做了重操作（fetch），对其余只做 `ls-remote`（或干脆不碰）；
- **`--remote` 仍然有效**：显式指定时完全不进探测循环（这是现有行为，别改坏）。

若测试环境不好造 git 仓，可用 mock 替换 `git()` / `git_net()` 记录调用序列，
**只要断言的是「调用了哪些远端、各调几次」即可**，不必真跑大仓。

## 红线

- **不改 land 的合并/推送语义**：`_pick_remote` 改的只是「怎么选出远端」，
  选出之后的行为（取分支、算 base、推 main、close）一个字不能变。
- **不降低安全性**：`_pick_remote` 现在的「显式给了 `--remote` 就只认它，找不到直接报错、
  不静默回落」是刻意设计（`hive.py:3085-3086` 注释写明「手滑打错远端名却『成功了』，
  比失败更可怕」）。**不许为了省事把它改成静默回落。**
- 不动 `.git`、不动任何业务仓（light / lightmem / lightharness）。
- 不引入第三方依赖（hive 是纯标准库）。
- 判据不得弱化：不许把「能跑完」当唯一判据（旧行为本来就能跑完，只是会崩）。

## 验收要点

- 复现路径写清楚：哪个仓、几个远端几个 worktree、什么命令崩的。
  若你能在本机复现（light 仓 3 远端 / 32 worktree），**贴出复现输出**；
  若换机器后不再复现（内存变宽裕），也要**如实说明无法复现的原因**，
  并改用 mock 测试证明修复有效（不要假装复现了）。
- 改后 `hive land T-0434 --remote gitea` 与 `hive land <某卡>`（不指定 remote）
  **两种走法都能正常工作**，各贴一次输出。
- 新加的回归测试贴输出，并**故意改坏实现**（例如让探测对所有远端都 fetch）
  验证测试**确实变红**（反跑记录写进 summary）。
- 错误提示的改法要贴出来（原文），并确认里面**有可用远端名**。
