## 背景

今晚连踩两次（T-0133、T-0135）：`land --apply` 的合并在临时 worktree 里**成功推入
origin/main**，但收尾的 `cmd_close` 在主工作区跑 `sync_main()`，而主仓工作区
「落后 + 有未提交改动」（raccoon 正在主仓改文档没提交——多 agent 共用一台机器时的
日常），守卫抛「不敢自动 reset」→ land 半途而废：

- 代码已合入、卡片却停在 `assigned`，没关闭；
- 操作者只看到一句 sync_main 的原始报错，**完全看不出合并已经成功**，容易误判成
  整个 land 失败；
- 两次都靠人工 `git merge --ff-only origin/main`（先核验指纹确认传入改动与
  raccoon 的文件无重叠）+ `hive close` 补救。人肉兜底不是机制。

根因：`cmd_close` 只需要提交 `tasks/<tid>.md` + `results/<tid>.json` 并推送，却
要求整个协调仓工作区「对齐且干净」——过度保守。land 的合并步骤本来就在临时
worktree 里做、不碰主工作区，收尾却退回主工作区，自相矛盾。

## 目标

0. **方案调整（实施时定的，理由记此备查）**：初稿设想「关卡也放进 land 的临时
   worktree 做」，实现时否决——那个 worktree 是**代码仓**的，而卡片文件在**协调仓**；
   自举卡（repo=hive）两者恰好同目录，但 light 那样的卡会把 `tasks/<tid>.md` 提交进
   错误的仓。改为：关卡仍在协调仓主工作区做，但把对齐方式从 `sync_main`（落后且脏
   就报错）换成新的 `_sync_for_commit`（落后就试 `merge --ff-only`；git 保证 ff 只
   碰真正变化的文件，未提交改动不在其中就原样保留，真在其中 git 自己会拒绝）。
   对全部卡型都成立，且顺带修好独立 `hive close` / MCP `hive_close` 的同一处卡点。
1. `land_one` 推完合并后若关卡失败，输出必须说清「**合并已成功、只是关卡失败**」
   并给出收尾命令（新状态 `merged-not-closed`），不许裸抛同步错误让人以为全盘失败。
2. 回归测试：构造「协调仓主工作区落后 origin/main 且有未提交改动」的场景，
   `land --apply` 必须一次成功（合并 + 关卡都完成），且那些未提交改动原样保留。
   再构造「未提交改动与传入改动重叠」的场景：ff 被 git 拒绝 → land 报
   `merged-not-closed` + 明确原因，不崩、不丢改动。

## 红线

- **不改 `sync_main` 本身**（T-0129 的守卫是防数据丢失的底线，动它要单开卡论证）；
  新逻辑放在并行的方法 `_sync_for_commit` 里，它同样绝不丢弃任何改动。
- 独立 `hive close` / MCP `hive_close` 也换用 `_sync_for_commit`（同一处卡点，
  顺带修好）：从「落后且脏就拒绝」变为「能安全 ff 就 ff、不能才报错」，
  **仍走主工作区、仍不丢任何未提交改动**。
- land 的合并策略不变（ff 优先、冲突不 force、临时 worktree 机制不变）。
- 不碰 `docs/`（raccoon 在主仓改文档未提交）。

## 验收

- 新测试绿；全量 pytest 无回归（当前 139）。
- 手工复核：主仓工作区留一个未提交改动 → `hive land <tid> --apply` 一条命令完成
  合并 + 关卡 → `git status` 那个改动还在。
