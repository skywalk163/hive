## 背景

Linux 上 lightmem 的日志去哪、由谁回收，目前**两条线各说各话**：

- A 线 `deploy/lightmem.service` / `deploy/lightmem-mcp.service` **都没有** `StandardOutput=` /
  `StandardError=` / `SyslogIdentifier=`，也就是走 systemd 默认 → 全部进 **journald**。
  （实测：`grep -E 'StandardOutput|StandardError|SyslogIdentifier' deploy/lightmem*.service` 无输出。）
- C 线 T-0413 交付的 `deploy/logrotate.d/lightmem` 轮转的是 `/var/log/lightmem.log`、
  `/var/log/lightmem-mcp.log` —— 在真实 systemd 部署里**这两个文件不存在**。

T-0417 真机验收确认：logrotate 靠 `missingok` 静默跳过，**对真实日志是空转**；
`journalctl --disk-usage` = 8.0M，`SystemMaxUse` 还是注释默认。
也就是说：**日志确实在被自动回收（靠 journald 的默认策略），但不是我们配的那套，也没人量过上限。**

## 目标

1) **先量清事实**（无论最后选哪边，这一步都要做）：
   - systemd 部署下真实日志落在哪：`journalctl -u lightmem.service -u lightmem-mcp.service --no-pager | head`、
     `journalctl --disk-usage`、`/var/log/lightmem*.log` 是否存在；
   - 跑一段时间（或造量）后 journald 的实际占用与默认上限（`journalctl --vacuum-size` 前先只看不删）；
   - 记录 unit 里 `User=` / `ProtectSystem=` 等是否会让 `append:` 目标不可写。
2) **定夺并落地**二选一（在卡里写清选了哪个、为什么、代价是什么）：
   - **方案甲（推荐给「运维要可预期」的部署）**：给两个 unit 加
     `StandardOutput=append:/var/log/lightmem.log` + `StandardError=append:/var/log/lightmem.log`，
     `SyslogIdentifier=lightmem`。这样 C 线的 logrotate 才真正生效。
     必须同时处理：日志目录属主/权限（`User=lightmem` 要能写）、`copytruncate` 与 append 模式是否打架
     （systemd `append:` 是 O_APPEND 打开的，轮转后进程继续写旧 inode —— 这点要实测，不能靠猜）。
   - **方案乙（推荐给「少一个失败点」的部署）**：明确走 journald，
     把 `deploy/logrotate.d/lightmem` 的口径改成/补成 journald 回收（文档化 `SystemMaxUse`、
     `MaxRetentionSec` 的建议值与修改方法），并在配置头注明「本文件只对显式落文件的部署有效」。
3) 不管选哪个，都要在 `deploy/README.md` 与 `deploy/logrotate.d/README.md` 写清
   **「日志去哪 / 谁回收 / 怎么量」** 三行答案，让运维不用读代码。
4) 若发现 `append:` 与 `copytruncate` 真的打架，方案甲必须换成
   `StandardOutput=file:`（不带 O_APPEND）或改用 journald，并在 summary 写实测结论。

## 红线

- **不改 kernel 语义、不改端口口径、不动 FreeBSD rc.d**。
- 不得为了让 logrotate「看起来生效」而去 `touch` 一个空日志文件糊弄 —— 那会把空转藏得更深。
- 涉及 unit 语义的改动必须在 summary 里给出**重启后实测**（`systemctl daemon-reload && restart`，
  贴日志文件增长与轮转结果）；只改文档/注释的提交不要碰 unit 文件。
- 两个 unit 的日志口径必须一致（不能一个 append 一个 journald）。

## 验收要点

- `systemd-analyze verify deploy/lightmem.service deploy/lightmem-mcp.service` 无新增 error（有 systemd 的机器上）。
- 方案甲：`logrotate -f` 后**日志文件真的滚动**（`.1` 生成、活动文件变小），且轮转后服务继续往新文件写
  （不能卡在旧 inode 丢日志）—— 贴前后 `ls -l`、`wc -l`、`journalctl` 对照。
- 方案乙：贴 journald 实际占用、默认上限查询结果、以及按文档改上限后的复测。
- 两种方案都必须回答一句话：「**我这条部署，日志 30 天后还在不在、占多大、被谁删**」。
