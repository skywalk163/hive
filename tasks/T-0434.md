## 背景

`src/code_generator.py` 的 `_method_def_name_map` 注释里写着（约 224-226 行）：

```python
# 冲突复核（2026-10-15）：全仓 .light 中 `.调用(`/`.缺失(`/`.取属性(` 调用 0 处、
# `段落 调用/缺失/取属性` 定义 0 处（同名不同词的 调用函数/调用AI/调用处理器 属
# 不同键，不受影响），故本批映射零既有语义迁移。
```

**这条现在是错的。** 实测扫描（本卡开卡前核实，范围：全仓 `*.light`，排除 `.git`/`node_modules`/`__pycache__`/`_*_scratch` 等）：

| 项 | 注释声称 | 实际 |
|---|---|---|
| `.调用(` / `.缺失(` / `.取属性(` 调用 | 0 处 | **0 处（仍成立）** |
| `段落 调用/缺失/取属性` 定义 | 0 处 | **3 处（不成立）** |

3 处定义全部在 `stdlib/集合工具.light`：

- `stdlib/集合工具.light:33`  `段落 缺失(键):`
- `stdlib/集合工具.light:191` `段落 取属性(名):`
- `stdlib/集合工具.light:209` `段落 调用(*值们):`

**时间线（这就是为什么会过期，不是当初写错）**：

- 注释的复核日期是 **2026-10-15**；
- 这 3 处定义是 **2026-10-16** 由 `af3783192`（R152 收口）引入的 —— **复核完第二天**。

也就是说：复核当时是对的，之后另一条线加了这三处定义，注释就没人更新了。

## 为什么值得单独开卡

T-0431 的排查被这条注释带偏过：因为注释说「定义 0 处」，排查者一开始认为
「测试桩少写了 `调用` 方法」，而真相是 `段落 调用` 会被编译成 `__call__`，
所以根本不存在名为 `调用` 的属性。这条注释的存在直接增加了那次排查的成本。

## 目标

1) **订正注释**（`src/code_generator.py`，只改注释，不动任何代码）：
   - 说明「复核日期」与「现状」会漂移，把结论改成**带条件**的说法，而不是绝对断言；
   - 明确写出：`.调用(` 这类**调用**确实 0 处，但 `段落 调用/缺失/取属性` **定义**在
     `stdlib/集合工具.light` 里有 3 处（R152 引入），它们正是本映射的**使用者/受益者**，
     是「按设计生效」而不是「意外命中」；
   - 补一句**最关键的坑**：类内 `段落 调用` 编译成 `__call__` 后，实例上**不存在**
     名为 `调用` 的属性，`实例.调用` 取属性会 `AttributeError`。要当回调传就得传
     **实例本身**（这是 T-0431 的结论，务必写进注释，防止后人再踩）。

2) **加一条可复跑的核实依据**：把「怎么重新扫这三类符号」写进注释或紧邻的文档，
   免得下次又没人知道复核该怎么做。只要一行命令即可，例如：
