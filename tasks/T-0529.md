## 一句话

Windows 侧的光明编译器把 `如果 (甲 或 乙) == 假:` 编译成了 `甲 或 (乙 == 假)`——**括号组在 `==` 左侧时被丢掉了**，于是条件静默判反。同一份源码在 0.88（FreeBSD 15.1 / python 3.12.13 / Clang）上正常。

## 最小复现（`repro.light`）

```
设 甲 为 真
设 乙 为 假
如果 (甲 或 乙) == 假:
  打印("走了真分支")
否则:
  打印("走了假分支")
如果 (假 且 甲) == 假:
  打印("走了真分支")
否则:
  打印("走了假分支")
设 组 为 (甲 或 乙)
如果 组 == 假:
  打印("走了真分支")
否则:
  打印("走了假分支")
```

正确结果：`走了假分支` / `走了真分支` / `走了假分支`。

实测：

| 环境 | `(真 或 假)==假` | `(假 且 真)==假` | 先赋值 `组==假` |
|---|---|---|---|
| Windows 10，python 3.13.18（MSC v.1944），`light-merge` @`700eb12b0`（main，含 T-0446/T-0447 括号/单参调用迭代化） | 走了真分支 **（错）** | 走了假分支 **（错）** | 走了假分支（对） |
| 0.88 FreeBSD 15.1，python 3.12.13（Clang 19.1.7），`~/light-merge` 副本（非 git 树，版本待确认） | 走了假分支（对） | 走了真分支（对） | 走了假分支（对） |

补充形态（Windows）：`(真 或 真) == 假` 也判成真（错）；`((甲 或 乙) == 假)` 加一层括号仍错；先赋给变量再比较则正确 —— 说明问题在「括号组直接出现在比较左侧」这一条生成路径，不是 `或` 本身算错。

推测：比较/`或`/`且` 的优先级在 codegen 阶段被摊平（`或`、`且` 的结合优先级被排到 `==` 之上），T-0446「括号/单参调用迭代化」很可能就是引入点（0.88 的编译器副本版本较旧，未复现）。

## 影响（为什么是 P0）

- 这是**静默错判**：不报错、不抛异常，条件直接反了；`如果 X == 假:` 这种写法天然就是「守卫」，写反等于守卫失效。
- lightharness 里 `src/*.light` + `stdlib/*.light` 命中 `(…或/且…) == 假` 形态约 **92 处**（`Select-String -Pattern "\(.*或.*\) *== *假"` 粗计数，含误命中）。
- 已确定的连锁红：`src/设置生效.light:76-79` 的 `解析字号` 用 `如果 (是整数(值) 或 是浮点(值)) == 假:`，Windows 上 `解析字号(14)` 抛「字号必须是数字: 14」→ lightharness 的 `examples/test_web路由.light` 在 Windows 上**必红**（T-0526 验证时踩到，与线程无关）。
