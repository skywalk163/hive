## 背景

状态机只有 `ready / assigned / running / done` 四个状态。异常卡没有去处，只能靠
`retry` 反复空跑 —— git log 里那 6 次「chore: 复位 ready」就是这么来的。

活例子：`T-0102`（Windows 接入）`needs: windows + gui`，但现存的 4 个 agent
（`fb88-dsh` / `fb88-verify` / `raccoon` / `workbuddy`）没有一个带 `windows`。
它会**永远躺在 ready 列表里**，每次 dispatch 都报一次「能力缺失」，变成僵尸卡。

## 目标

给状态机补三个状态，让异常卡有地方待：

1. **`blocked`** —— 等外部资源，不是出错。比如等 Windows 真机、等某个 runner 修好。
   - `hive block T-xxxx --reason "等 Win10 VM 装好 Python"` 把卡置为 blocked；
   - `hive unblock T-xxxx` 退回 ready；
   - **dispatch 和 worker 都跳过 blocked 的卡**（现在 worker 的 `pending()` 只看
     inbox，但 dispatch 的 `ready` 过滤要显式排除，别让它反复出现在跳过原因里）；
   - `hive status` 里单独列出来，`doctor` 里统计数量。

2. **`conflict`** —— 合并冲突，等人或 agent 来解。T-0110 的 `hive land` 会在合并不上时
   需要这个状态；本卡先把它加进状态机，让 T-0110 有地方落。
   - 同样：dispatch / worker 跳过；
   - `doctor` 必须把 conflict 的卡报成**错误**（不是警告）—— 有卡冲突不解决，后面全堵着。

3. **`needs_review`** —— 等人确认。给「agent 写卡草稿」那种流程预留（后面会有
   `hive plan`），本卡只要状态机支持，不需要实现 plan。

统一约定（这三条是重点，别漏）：
- `TASK_FIELDS` 加不加新字段随意，但 `state` 的合法值要有一个集中的常量，
  别散落在各处字符串比较；
- **所有「在飞」判断**现在写的是 `state in ("assigned", "running")`，
  要改成从一个统一的 `IN_FLIGHT_STATES` 取，避免以后加状态又漏一处。
  已知位置：`_load_counts`、`_repo_loads`、`cmd_prune` 的 `busy`、`cmd_stats`、
  `cmd_status` 的推导、`cmd_doctor`；
- `cmd_status` 里已经有 `state not in ("done", "blocked")` 这种写法（说明当初想过），
  正好收口。

4. 顺手做掉：**把 T-0102 置为 blocked**，理由写「等待 Windows 10 VM（192.168.0.86）
   接入；当前 4 个 agent 均无 windows 能力」。改 `tasks/T-0102.md` 的 state 字段即可，
   **不要删卡、不要改它的目标和验收**。

5. MCP：给 `mcp_server.py` 加一个 `hive_block` / `hive_unblock`（或让 `hive_abort` 支持
   `requeue=False, mark="blocked"`），让 GUI agent 遇到环境问题能自己把卡挂起。
   至少要让「blocked 的卡不会出现在 `hive_next` 的推荐里」这件事成立。
