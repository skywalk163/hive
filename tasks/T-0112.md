## 背景

hive 现在用 hive 开发自己，**代码仓和协调仓库是同一个目录**。这带来一个别的仓没有的风险：

1. worker 提交时是 `git add -A`（hive.py 里 exec 分支和 `cmd_submit` 都是），
   agent 顺手改了 `tasks/*.md`、`results/*.json`、`agents/*.json` 也照样提交上去。
   任务卡就是「考卷」，agent 能改自己的考卷。
2. 好消息：verify 命令是从 `origin/main` 的任务卡读的（`self.h.card(tid)`），
   所以**改卡骗不了当次验收** —— 但会污染 retry 的记录和历史审计。
3. 还有一个更现实的问题：**verify 强度参差**。T-0101 的验收是
   `grep -q abilities agents/*.json && grep -q "同仓" hive.py && pytest`，
   前两条 grep 一个字符串就能过。而且那张卡的 summary 里 agent 自己坦白
   「本机 sandbox 后端不可用，没能跑测试」，却照样判 done ——
   **summary 说了什么和 diff 里有什么，没人交叉核对**。

## 目标

两件事：越界拦得住，成果对得上。

### A. paths 越界检测

1. 提交前算一次 diff：任务卡声明了 `paths` 时，检查改动文件是否都落在白名单里
   （同样的前缀匹配规则，和 T-0111 的 `_paths_conflict` 共用一段逻辑）。
2. 行为分级，**默认只警告不阻断**（别一上来就把正常流程卡死）：
   - 默认：把越界文件列表写进结果的 `out_of_paths` 字段、打到日志里，任务照常完成；
   - `hive.py` 加一个开关（环境变量 `HIVE_STRICT_PATHS=1` 或 agent 配置
     `"strict_paths": true`），打开后越界就判 `failed`，错误信息列出越界文件。
3. `paths` 为空的卡不检查（未声明 = 不约束），但要记一笔。

### B. `hive audit T-xxxx`

比对「agent 说做了什么」和「diff 里真有什么」：

1. 输出结构（人看，也便于以后机器判）：
   - 卡片声明的 `paths` vs 实际改动文件；
   - 改动文件的增删行数；
   - verify 每条命令的退出码（从 result 里取）；
   - result 的 `summary` 全文（人来判断有没有吹牛）；
   - 一个 `risk` 标记：出现「paths 越界」「verify 里有 grep 但没有真实测试命令」
     「summary 里出现『没能跑/无法验证/未测试』之类措辞」时置为 `warn` 并列出原因。
2. 支持 `hive audit --all`：把所有待合并（`result=done` 但 `state != done`）的卡过一遍，
   给总控一个合并前的一页纸清单。

## 红线

- 不改 light 等仓；不引入新依赖。
- **不要动 verify 的执行逻辑本身**（verify 怎么跑是另一张卡的事，本卡只做「审计」不做事）。
- 默认行为必须向后兼容：现有 32 个测试不能因为加了检查就挂。
- 别改 `tasks/*.md`、`results/*.json`。

## 验收

`git show --stat HEAD` 覆盖 `hive.py` + `tests/` + `docs/`；verify 全过。
