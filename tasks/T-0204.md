> 来源：2026-10-29 给 light 仓出语言缺陷修复卡时**当场踩到**的两个 worker 缺陷。两个都让一批卡白跑，属于「基础设施静默失效」。

## 一、worker 进程缓存在启动时的 agent 配置，新增仓库后必须重启才看得见（P1）

`agents/<name>.json` 的 `repos` 是在 `Worker.__init__` 里读一次存到 `self.cfg` 的。
之后往配置里加一个新仓（本次：2026-10-27 给 `fb88-dsh` 加 `light=/home/skywalk/dswork/light`），
**正在跑的 worker 完全看不到**——它启动于 10-25，内存里还是旧配置。

表现：每一张该仓的卡都**瞬间失败**（0 秒），结果里只有一句

```
agent fb88-dsh 没有配置仓库 'light' 的本地路径
```

而且 dispatch 认为卡已经派出去、worker 认为卡已经跑完，**双方都不觉得异常**。
本次连废 T-0194、T-0195 两张卡才由人肉发现。

**期望**（二选一，推荐前者）：
1. 每次领卡前**重读** `agents/<name>.json`（文件很小，代价可忽略）；
2. 或至少在派发/领取时校验「卡片的 repo 在 agent 配置里」，不在就**明确拒绝派发**，
   而不是让 worker 领下来再秒败。

顺带：同一症状也会发生在「agent 能力标签更新」上（`needs` 匹配用的是 dispatch 侧的配置，
worker 侧是另一份），值得一起检查口径。

## 二、卡片的 worktree 被回收后，worker 尝试 resume 直接崩进程（P1）

T-0193 失败后 worktree 被清掉，但卡仍是 `assigned`（有结果、还没 land）。worker 下一轮想 resume：

```
FileNotFoundError: [Errno 2] No such file or directory: '/home/skywalk/.hive/wt/T-0193'
```

**未捕获**，整个 worker 进程退出。也就是说：**一张状态不一致的卡能打死整台机器上的 worker**，
而且日志里只有 traceback，没有「哪张卡、该怎么办」。

**期望**：
1. resume 前检查 worktree 是否存在，不存在就**重建**（`git worktree add` + 拉到卡的 base），
   而不是拿旧 cwd 去 `subprocess.run`；
2. 重建失败则把这张卡标 `blocked` 并写明原因，**继续处理下一张**，绝不整进程退出；
3. 主循环对单张卡的异常做兜底（try/except 包住单卡处理），一张卡的意外不能停掉整条流水线。

## 验收

新增 `tests/test_worker_recovery.py`：

1. **配置热更新**：worker 起来后修改 `agents/<name>.json` 增加一个仓库，不重启，
   `pending()` / 领卡流程能看到新仓库（或至少报出「配置已变更，请重启」而不是静默秒败）
2. **worktree 缺失**：造一张 `assigned` + 有结果 + worktree 目录不存在的卡，跑一轮 worker，
   断言：进程**没退**、该卡被重建或转 `blocked`、且后续的卡仍被处理
3. **异常兜底**：让单卡处理抛任意异常，断言主循环继续

## 边界

只动 worker 侧（`Worker.__init__` / `pending` / `claim` / 单卡处理的外层）。别改 dispatch 的
能力匹配算法（那是另一条线）。改完跑 `python3 -m pytest -q tests/test_core.py` 确认 69 项仍全绿。
