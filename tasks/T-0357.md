# T-0357 生产合入闸门与灰度回退（默认 shelved，人工闸门）

## 背景

**本卡默认 `shelved`，不进派发池。** 它存在的意义是把「开发验证完」与
「动生产」之间钉一道人工闸门——交办方明确说过：

> 当前的 hive 集群里有任务，一不小心，就会导致整个开发工作的停滞。

前 8 张卡全部只在隔离开发副本里工作，生产 `~/dswork/hive/` 一个字节都没改
（除了本批发布写入的 `tasks/T-034x.md`）。**只有本卡允许碰生产，
且必须由交办方 `unshelve` 后才可执行。**

历史纪律参照：

- `hive-优化报告-2026-11-13.md:5,176`「不改任何卡面状态、结果台账、分支，
  不 push、不重启常驻进程」；
- `docs/集群升级.md:30-37,132-137` `upgrade publish|check|apply|rollout` 灰度、
  回滚点 `~/.hive/upgrade/last.json`、只做 `merge --ff-only`、脏工作区拒绝；
- `CSDN-hive-派单接单-发布任务新功能.md:213-225` 改代码 ≠ 生效，
  常驻进程加载旧 `hive.py`，重启有固定顺序。

## 要做什么（unshelve 之后才执行）

1. **前置检查清单**（一条不满足就停，不许带病上线）：
   - `python3 hive.py status --json` 确认**没有 ready / assigned 在飞卡**、没有进行中租约；
     在途任务全部收口；
   - T-0356 的 `docs/H-LSA-验收报告.md` 8 项 SLA 全通过、隔离清单 5 条有证据；
   - **生产协调仓那批未提交改动（判据与漂移 / T-0342/T-0344 相关）已由改动主人处理完毕**，
     或已明确 rebase 方案；**绝不代表他们提交 / stash / 丢弃**；
   - 备份：看板 `status.json`、`~/.hive/cluster/state.json`、
     升级回滚点 `~/.hive/upgrade/last.json`，并记录备份路径与校验和；
   - 明确变更窗口、执行人、回退执行人。
2. **代码合入**：把开发副本的实现按 T-0356 报告列出的文件清单，
   与生产在途改动 rebase 对齐后合入；逐文件核对 §四文件锁，
   确认没有覆盖别人的改动。**有冲突就停，人工裁决。**
3. **灰度顺序**（不许跳步）：
   ```
   python3 hive.py upgrade publish            # 先发布版本
   python3 hive.py upgrade check              # 校验
   python3 hive.py upgrade apply --node <单节点>   # 单节点灰度
   # 观察 ≥30min：plane_available、心跳字节、Gitea 请求数、看板横幅、SLA
   python3 hive.py upgrade rollout            # 全量
   ```
   灰度期间若空闲带宽回到 0.16.05 之前量级、或出现同步风暴，立即回退。
4. **重启顺序**（只有确实需要时才重启，且严格按序）：
   `master.sh stop → cluster stop → 确认无残留进程 → cluster start →
   自检 → store 探活 → master.sh start`（引自既有文档）。
5. **回退预案**：`upgrade` 回滚点 + `merge --ff-only` + 脏工作区拒绝；
   回退后复跑 `tests/test_hlsa_integration.py` 与 0.16.03/0.16.05 六项回归，
   确认旧面完好。
6. **`docs/H-LSA-上线与回退.md`**：记录实际执行时间、每步命令与输出、
   灰度观察数据、备份路径、回退演练结果。
7. **`tests/test_rollout_gate.py`**：把前置检查做成可自动判定的门禁
   （在飞卡数、SLA 报告存在性、备份存在性、脏工作区拒绝、灰度步骤顺序），
   供执行前一键预检；**默认 `--dry-run`，不产生任何写操作**。

## 不要做什么

- **不要自动执行本卡**：`shelved` 状态是刻意设的，任何 agent 不得自行 `unshelve`；
- 集群有在途任务、没有 T-0356 验收报告、没有备份、没有变更窗口 → 一律不执行；
- 不跳过单节点灰度直接 `rollout`，不跳过 `upgrade check`；
- 不 stash / checkout / reset / clean 别人的未提交改动，不擅自代表改动主人提交；
- 不改判据口径、不放宽 SLA、不把 `unavailable` 写成 `pass`；
- 不在灰度观察期内同时做其他生产变更。

## 完成标准

1. 前置门禁 `python3 tools/check_rollout_gate.py --dry-run` 全绿，
   且输出里明确列出备份路径与变更窗口。
2. 灰度单节点观察 ≥30min，`plane_available:true`、空闲带宽 ≤ 0.16.05 基线、
   Gitea 请求 ≤1 次/30min、看板不再出现「请执行 git pull」。
3. 全量 rollout 后生产 `term` 收敛正常、无幽灵 leader、无重复组播源，
   在途任务与卡面状态零损伤。
4. 上线文档含完整命令留痕与可执行的回退步骤；回退演练有结果。
