## 背景

webui/app.js 当前在流式输出期间**禁止切换会话**：

- `selectSession(id)` 第 774 行：`if (streaming) { addSystem("正在流式输出中，请稍后再切换会话。", true); return; }`
- `new-session-btn` 的点击处理（约 1441 行）：streaming 时提示「请稍后再新建会话」并 return。

用户诉求：流式输出时切换会话**应当被允许**，而不是被拦住。现在的拦法让用户在模型还在吐字时无法去看别的会话，体验很差。

## 目标（选定语义：中止当前流 → 切换到目标会话）

采用「**先中止当前流，再切换**」的语义（与现有「停止」按钮 `stopStreaming()` 一致：abort 后 `finalizeTurn()` 保留已渲染内容，不丢已收到的文本）。理由：一个流绑定在发起时的 `sessionId` 上，切到别的会话后继续把 token 追加到新会话 UI 会串味；所以切换 = 停老流 + 进新会话，最安全也最符合直觉。

1) 修改 `selectSession(id)`：把「streaming 就弹提示 return」改成：
   - 若 `streaming`：调 `stopStreaming()`（abort controller），并把 `currentBubble` 的 `streaming` class 去掉、结束本地计时（`setStreaming(false)` 的收口语义），提示一句中文「已停止当前输出并切换会话」。
   - **处理 abort 异步竞态**：`controller.abort()` 触发的 `catch`（1155 行 `if err.name === "AbortError" → finalizeTurn()`）会在切换之后异步执行。必须保证它不会污染目标会话——可采用：切换前把当前会话的渲染引用快照化/置空，或给 abort catch 加「epoch/token 校验」：只有仍是当前会话才 finalize UI；或在 abort 后同步调用一次收口并让 catch 变成幂等 no-op。具体实现由你定，但**必须在 summary 里说明竞态处理方式**。
   - 然后正常走原来的 fetch 历史 + 回放路径。
2) 同样修改 `new-session-btn` 的 streaming 分支：streaming 时先停流再进空状态（与 selectSession 同一套收口，建议抽一个 `abortActiveTurnForSwitch()` 复用，避免两处漂移）。
3) 本轮用户主动中止 → 仍走 `AbortError` 分支（保留已渲染内容），**不要**走 rollbackTurn（那是发送失败回滚用的）。
4) 队列：`setStreaming(false)` 会触发 `flushLocalQueue()` 把排队消息发出去。切会话后若本地队列里还有**属于老会话**的排队消息，不应发到新会话——请评估并在切换时清空 `localQueue`（或给队列项打 sessionId 标记），在 summary 说明取舍。
