## 现象（2026-11-10 现场，FreeBSD fb98）

- 看板 http://192.168.0.88:8787/ 每 40~45 秒显示一次「集群：未启动」，
  而集群进程明明在跑。
- `hive cluster start` 报「集群进程已拉起，但 15s 内尚未响应 health」；
  `hive cluster stop` / `start` 反复重启都不管用。
- `cluster.log` 里 term 一天涨了 1289 次，`leader_lost` 反复报「主节点租约过期」，
  `本轮选举未获多数` 358 次。
- 实测 `/api/cluster/state` 每 40s 卡 20s；而看板 `load_cluster_state()` 的探测
  超时只有 **0.6s**，一次卡顿就足以判定「没起来」并回退到 `state.json`
  （`running=false`）。

## 根因：两把锁互等

1. `_persist_locked()` 在 `self.lock` **里面**直接 `_write_json`。state.json 实测
   521KB，一次写入（`json.dumps` + 临时文件 + `os.replace`）40ms 起步，ZFS 上还会
   撞 `zil_commit` 的 fsync。选举路径 `_start_election()` 持锁调它。
2. `_self_node()` / 心跳响应 / 选票闸门在**持主锁**时调 `store.commit_seq()`，
   而 `commit_seq()` 要拿 `store._lock`。
3. `_ingest_store_cards()` 补卡时长时间占用 `store._lock`。连接是
   `isolation_level=None`（autocommit）+ `PRAGMA synchronous=FULL`，
   逐行 execute 等于逐行 fsync：194 张卡要 **18 秒**。

三者串起来就是雪崩：补卡线程占住 store 锁 → 持主锁的线程排队 → 心跳发不出 →
租约过期 → 重选 → 重选又要持锁落盘 → 循环加剧。

## 改法

1. **`_persist_locked()` 只在锁内打脏标记**，写盘统一由 `_persist()` 在锁外完成
   （锁内只取快照）。停机路径补 `_persist(force=True)`，否则 `cluster status`
   离线视图会停在旧任期（回归用例已覆盖）。
2. **新增 `_store_seq()` / `_refresh_store_seq()` 位点缓存**：持主锁的路径只读
   缓存值，绝不跨到 `store._lock` 上排队；缓存由 `_loop_health_cache` 在锁外每秒
   刷新。`handle_vote` / `handle_store` 本来就在锁外，仍取实时值（严格模式靠它
   判「落后」）。
3. **`Store.ingest_cards()` 改单事务批量提交**（`batch=200` 分段，每段释放一次
   store 锁）。
4. 停机前 `_persist(force=True)`，保证离线快照是最新任期。

## 附带修复：节点换 IP 被误判为「伪造身份」

`DESKTOP-IC6RTQ4` 的地址从 `192.168.0.109` 变成 `192.168.0.100`，进程没重启，
自述 url 还停在旧 IP，于是每一跳都被身份校验拒掉：该节点再也回不了成员表，
且每 30 秒往 `cluster.log` 丢一条「忽略伪造身份心跳」。

判据刻意从严，只认**同一个进程实例**（node_id 在册 + `incarnation` 完全相等），
命中只把登记地址改写成请求来源 IP，不改身份；册上地址已是新值后静默放行
（幂等），避免「迁移日志」自己变成新噪音源。换了实例或未知 id 仍按伪造处理。
