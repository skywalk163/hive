## 现象

`examples/test_会话模型选择.light` ⑤ 必红（0.88 基线树同样红，与 T-0490/T-0526 的线程退出、与 T-0529 编译器修复都无关）：

```
断言失败[对话_不带模型_200]：实际=202 期望=200     # test_会话模型选择.light:136
```

## 现场

同一会话连发两条 `/v1/chat/completions`，**都没有真正消费流**：

- ④ `test_会话模型选择.light:127`：`聊天体(会话标识, "buddy/hy3")`，`聊天体` 里写死 `"stream": true`（第 56 行）；
  代码只断言 `响应["状态"] == 200`，返回体（`"流响应"`）从头到尾没被迭代；
- ⑤ 第 135 行紧接着发第二条（`model` 为空），期望 200，实际 202 → 走 `src/web服务器.light:1111` 的 `队入队` 分支。

## 机理（两条候选，必须先取证再动手）

`src/web服务器.light:1095-1124` 的口径是「同一会话一次只跑一轮」：入口 `队尝试占用`，抢不到就 202/409；
流式请求把占用所有权**转交后台线程**，由它在本轮真正跑完时释放（`造流式响应` 尾部 `队释放占用`，约 3209-3217）。
T-0453 注释明确写了「直调处理器且不消费流的自测不受影响：占用由后台线程在本轮结束时释放」——
现在这条前提在 ⑤ 上不成立，候选原因：

1. **时序竞态**：④ 的后台线程还没跑到释放点（本轮还在跑），⑤ 就抢占用 → 202。若属此类，说明例子本身缺"等上一轮结束"。
2. **真的释放不到**：后台线程把帧投进 `实时队列`，无人消费时队列满则阻塞在投递上，走不到释放（3213 `队列.关闭()` 之前）→
   会话被**永久**占住，后续同会话请求**全都** 202。若属此类，是产品侧健壮性缺陷（直调/断连客户端会把会话钉死）。

取证要求（写进 summary，不要猜）：在 ⑤ 前打印 `队是否忙(己.队列闸门, 会话标识)`、`队排队深度(...)`，
并在 ④ 之后按 10ms 间隔轮询这个忙标志的翻转时刻；另外抓一次后台线程栈（faulthandler 或 `threading.enumerate()` +
`sys._current_frames()`）看它卡在 `队列.投递` 还是正在 `跑一轮`。

## 修法（按取证结论二选一，不许用 sleep 掩盖）

- **结论=竞态**：改 `examples/test_会话模型选择.light`，在 ⑤ 之前加一个辅助段落
  `等本轮结束(上限秒)`：轮询「该会话不再忙」（口径用 `src/会话队列.light` 的 `队是否忙`，不要自造标志），
  超上限就 `断言失败`（**不许**无限等、也不许 `sleep 固定秒` 蒙过去）。这属于补上"上一轮何时结束"这个判据前提，
  不是放宽断言：④ 的 200、⑤ 的 200、模型落盘三条断言一个字都不动。
- **结论=释放不到**：改 `src/web服务器.light` 的 `造流式响应`：无人消费时也必须跑完并释放占用
  （例如队列满/客户端断开时降级为丢弃帧而不是阻塞投递；或对直调（无 HTTP 发送侧）的载具走"每块即时丢弃"）。
  这条动的是服务端，必须在 summary 里写清"断开连接 / 直调不消费"两种入口都不再钉死会话，并补判据。

## 判据

新增 `tests/unit/test_会话占用释放.py`（允许走 `运行.py` 子进程，按仓库既有单例的 import 口径）：

- 直接调 `路由处理器` 发一条 `stream=true` 请求、**完全不消费**返回体；
- 轮询同会话的 `队是否忙`，要求 **≤ 5s 内翻回不忙**（现在实测永远忙）；
- 之后同会话再发一条 `stream=false`，要求 200（不是 202）。

既有 `examples/test_会话模型选择.light` 本身保持断言不变即可（它已被上面的等待覆盖）。
