# spec 门禁对检出形态敏感：`stdlib_汇总` 指纹不归一 CRLF，非 Windows 检出必红

## 背景

T-0383（R222 M 线收口）在 0.88 上跑全量，发现 `tests/test_spec_lockstep.py::test_spec_is_rebuildable_byte_for_byte`
三轮全量都红（M2/M3/M4），但**同一份提交在 Windows 上是绿的**。

现场：`192.168.0.88:/tmp/lp-ci/run-20261118-010730-T-0383-M4`

根因：`spec/build_spec.py::_stdlib_digest()` 对 `stdlib/*.light` + `stdlib/*.py`
**按磁盘原始字节**算 sha256，没有做行尾归一：

```python
def _stdlib_digest() -> str:
    h = hashlib.sha256()
    for p in sorted(...glob("*.light") + ...glob("*.py")):
        h.update(_rel(p).encode("utf-8"))
        h.update(b"\0")
        h.update(_sha256(p).encode("ascii"))   # ← 原始字节，CRLF/LF 结果不同
        h.update(b"\n")
    return h.hexdigest()
```

而 `test_spec_is_rebuildable_byte_for_byte` 只归一了 spec JSON **自身**的行尾：

```python
current = f.read().replace("\r\n", "\n")   # 归一了 spec 文件
rebuilt = build_spec.render(build_spec.build())  # 但 build() 里的 digest 用的是输入文件原始字节
```

归一的对象错了：该归一的是**输入文件**，不是输出 JSON。

## 同一棵树、四种检出、四个指纹（实测）

| 检出形态 | `stdlib_汇总` |
| --- | --- |
| spec 里记录的 / T-0383 工作树（158 文件全 CRLF） | `5168681cc08ed6d5` ← 生成时的形态 |
| `light-merge` 主工作树（153 CRLF + 5 LF 混合） | `eb5613aa62fa7302` |
| 从 git blob 取（全 LF = 干净检出） | `d2318dc662cbb1aa` |
| 0.88 FreeBSD 快照（tar 保留 LF） | `7e7d995923a0a937` |

结论：Windows（`core.autocrlf=true`，检出 CRLF）绿；**0.88 / Linux / 任何干净检出必红**；
本机主工作树因为恰好有 5 个文件是 LF，也红（`python -m spec.build_spec --check` rc=1）。

这不是"合并没刷新指纹"的一次性事故，而是**门禁本身对检出形态敏感**——换一台机器就红，
所以每次合并后"重新生成一遍"只是把红推到下一个非 Windows 环境。

`FINGERPRINT_FILES` 里的 11 个源文件（`src/keywords.py`、`src/lexer.py`、`src/code_generator.py`、
`src/version.py`、`src/diagnostics/registry.py`、`docs/language/*.md`、`tests/unit/test_spec_docs_sync.py`）
有同样的问题——从 git blob 取全 LF 时，只有 `src/keywords.py` 一个对得上，其余 10 个全不匹配。

## 目标

让指纹对行尾**不敏感**，使同一份提交在任何检出形态下算出的值相同。

首选（改一处、覆盖全部）：

- 新增一个 `_sha256_normalized(path)`，先 `read_bytes().replace(b"\r\n", b"\n")` 再 sha256；
- `_stdlib_digest()` 与 `build()` 里 `FINGERPRINT_FILES` 的 `_sha256(ROOT / rel)[:16]` 全部改用它；
- 重新生成一次 `spec/light.spec.json`（`PYTHONPATH=src python -m spec.build_spec`），并在
  **非 Windows 检出**（0.88 或 Linux）上验证 `--check` 仍绿。

备选（更彻底，但要评估影响面）：`.gitattributes` 给 `stdlib/*.light` 与上述 11 个源文件加 `-text`
（禁止行尾转换），让磁盘内容永远等于 blob。缺点：已有 153 个 CRLF 工作树文件会显示为"全文件改动"，
且 Windows 编辑器保存仍可能转回 CRLF，治标不治本。除非同时加 `check-attr` 门禁，否则推荐首选方案。

顺带修（同一函数附近，一并做掉）：

- `spec/build_spec.py` 的 diff 输出标签**写反了**：

  ```python
  print(f"不一致：第 {i} 行\n  仓内: {a[:160]}\n  现状: {b[:160]}", ...)
  #   a 是 current（仓内文件）  b 是 text（重建值）—— 顺序对，但文案方向让排查时误判
  ```

  T-0383 排查时就被这两个词带偏过一次。建议改成 `文件:` / `重建:`，或直接把值标出来。

## 红线

- 不要为了让 0.88 变绿而**删掉或弱化** `test_spec_is_rebuildable_byte_for_byte`——它是 A 线的核心门禁。
- 不要用"跑一遍 `build_spec` 覆盖 spec 文件"当成修复：那只是把红推给下一个非 Windows 检出。
- `spec/light.spec.json` 被仓根 `.gitignore` 的 `*.json` 忽略，改动需 `git add -f`。

## 验收

```bash
# 1) Windows（CRLF 检出）
PYTHONPATH=src python -m spec.build_spec --check          # rc=0
PYTHONPATH=src python -m pytest -q -o addopts= tests/test_spec_lockstep.py   # 28+ passed

# 2) 0.88（LF 检出）—— 这是本次的判据环境
python tools/remote_ci.py --repo . --tag T-xxxx-spec -- tests/test_spec_lockstep.py
#   期望：全绿；且与 Windows 算出的 stdlib_汇总 **逐字相同**

# 3) 反证：人为把某个 stdlib 文件改成 CRLF，指纹必须不变
#    （归一后行尾不参与，这个断言应成立）
```

第 2 条是关键：**同一份 spec 在 0.88 上 `--check` 必须 rc=0**。T-0383 判它新增红，就是因为这条不成立。
