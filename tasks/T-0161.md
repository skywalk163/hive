## 背景

总控在群里提了一条提升方向：

> 可以考虑在 worker 内部引入轻量级的多进程/线程池，在 worktree 隔离的前提下
> 安全地并行执行多个 exec 任务。

当前 `hive.py` 的 `Worker`（约 2328 行）**一次只跑一张卡**：worker 从 `inbox/<name>/`
里挑出可领的卡，逐张 `claim → prepare(worktree) → 执行 → submit`。每张卡天然有独立的
git worktree（`prepare`/`run_task` 里 `git worktree add -B task/<tid>`），所以"物理隔离"
已经具备。瓶颈在 worker 自身是串行的，单台机器上的 exec agent 吞吐被卡成 1。

`agent` 配置里已经有 `max_concurrency`（默认 1，见 `cmd_dispatch` 1216/1240/1263 行、
`mcp_server.py:435`），但它是**分派侧**的并发上限，worker 内部并没有真正并发跑。

本卡只出设计，不动代码。目标是给 T-0162（实现）一份可直接照着写的蓝图。

## 要做什么

在 `docs/design-worker-parallel.md` 写一份设计文档，**必须包含以下小节（verify 会校验）**：

- `## 模型`：线程池 vs 进程池的取舍；一个任务一个 worker 线程，每个线程独占自己的 worktree；
  建议默认用 `concurrent.futures.ThreadPoolExecutor`（I/O 密集的 LLM 调用，GIL 不是瓶颈），
  并说明何时该用进程池。
- `## 租约与心跳`：现有 `lease_heartbeat` 上下文管理器（在 `run_task` 2622 行被使用，
  `_heartbeat_loop` 在 2503 行）是按"一个 worker 一个任务"写的。设计要说明如何改成
  **每任务一条心跳线程**，保证并发多任务时每张卡各自续租、互不干扰，且 worker 主进程退出时
  全部心跳正确停止。
- `## 隔离保证`：重申 worktree 物理隔离如何让并发任务看不到彼此未提交改动；说明并发改
  同一文件时仍靠 `paths`/`land` 串行兜底（引用 `docs/多机并行开发.md` §5 的三层保障）。
- `## 错误隔离`：一张任务线程崩溃/超时/被 kill，不能拖垮池里其他任务；日志按 `task`
  分文件（`state/logs/<tid>.log`）互不串。
- `## 与 dispatch 的关系`：worker 内部并发后，`max_concurrency` 的语义从"分派侧上限"
  收敛为"worker 自身上限"；说明 `dispatch` 与 worker 各自的职责边界，避免重复限流。
- `## 落地建议`：给出 T-0162 的实现步骤清单（新增 `Worker.run_tasks(tids)`、
  `start-worker.sh` 加 `--max-concurrency`、每任务心跳、回归测试），并标注风险点。

要给出**明确的最终推荐方案**（线程池 + 每任务心跳 + 上限取 `max_concurrency`），不要停留在
罗列选项。
