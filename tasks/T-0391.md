# `test_linter_canonical._run_cli` 没给 encoding：Windows 上 2 条用例必红（假红）

## 背景

T-0380（R222 D 线）的 `tests/test_linter_canonical.py` 里有 2 条用例在 **Windows 本机必红**，
但在 0.88（FreeBSD，UTF-8 locale）上是绿的：

```
FAILED tests/test_linter_canonical.py::test_report_only_keeps_file_and_mtime
FAILED tests/test_linter_canonical.py::test_cli_help_lists_canonical
```

失败形状：

```
    assert 'L5001' in proc.stdout
E   TypeError: argument of type 'NoneType' is not a container or iterable
```

根因在 `_run_cli()`：

```python
def _run_cli(args, cwd=ROOT):
    env = dict(os.environ)
    env['PYTHONPATH'] = str(SRC_DIR)
    return subprocess.run(
        [sys.executable, '-X', 'utf8', '-m', 'src.linter.cli', *args],
        cwd=str(cwd),
        env=env,
        capture_output=True,
        text=True,          # ← 没给 encoding，父进程用 locale 默认（Windows = GBK）
    )
```

子进程被 `-X utf8` 强制用 UTF-8 输出中文，父进程却按 GBK 解码：

```
UnicodeDecodeError: 'gbk' codec can't decode byte 0x93 in position 100: illegal multibyte sequence
```

这个异常发生在 `subprocess` 内部的读线程里，被 pytest 记为
`PytestUnhandledThreadExceptionWarning`；主线程拿到的是 `proc.stdout = None`，
于是下一条 `assert 'L5001' in proc.stdout` 抛 `TypeError` —— 真正的原因（编码）被这个
`TypeError` 盖住了，排查时很容易误判成"linter 没输出"。

## 证据链

| 环境 | 命令 | 结果 |
| --- | --- | --- |
| Windows 本机（默认） | `python -m pytest ... tests/test_linter_canonical.py` | **2 failed / 17 passed** |
| Windows 本机 + `PYTHONUTF8=1` | 同上 | **19 passed** ✅ |
| 0.88（FreeBSD，UTF-8 locale） | 同上 | 19 passed ✅ |

也就是说：**不是产物坏了，是测试装置对 locale 敏感**。

hive 的 verify 用 `sys.executable`（`C:\Python314\python.exe`）跑，且不带 `PYTHONUTF8`，
所以任何在 Windows 上验 T-0380 及其后继卡的 verify 都会撞到这 2 条红。
T-0383（R222 M 线收口）就是被这 2 条卡住、hive 判 `failed` 的。

## 目标

让 `_run_cli` 的父子进程编码口径一致，不再依赖宿主 locale。

最小改动（一处）：

```python
    return subprocess.run(
        [sys.executable, '-X', 'utf8', '-m', 'src.linter.cli', *args],
        cwd=str(cwd),
        env=env,
        capture_output=True,
        text=True,
        encoding='utf-8',        # ← 与子进程的 -X utf8 对齐
        errors='replace',        # ← 兜底：真出现坏字节也不让断言变成 None
    )
```

`errors='replace'` 之后 `proc.stdout` 永远不是 `None`，断言失败时会给出真实的输出差异，
而不是被 `TypeError` 掩盖。

建议顺手做（同一文件、同类问题）：

- 检查 `tests/` 下**其它**用 `subprocess.run(..., text=True)` 且**没有** `encoding=` 的 helper。
  `tests/test_cli_json.py`、`tests/test_patch_engine.py` 等 R222 新增测试都有 `_run_cli` 类似物，
  逐个确认是否需要同样处理。可以先用一条 grep 找出来再判断（注意别把已经显式给了 encoding 的算进来）：

  ```bash
  grep -rn "text=True" tests/ --include=*.py | grep -v "encoding="
  ```

  > 注意：Windows 上 `grep` 要在 Git Bash 里跑；本仓有 hive_compat 垫片的话也可用
  > `python -c` 代替。别直接照抄 POSIX 判据当 verify。

- 如果这个模式很普遍，考虑在 `tests/conftest.py` 里加一个统一的小工具函数
  `run_py(args, **kw)`，内部强制 `encoding='utf-8', errors='replace'`，让后续测试别再各写一遍。

## 红线

- 不要用"verify 命令前面加 `PYTHONUTF8=1`"当修复。那是**绕过**：`hive_compat` 只对声明了
  `VAR=value` 前缀的命令生效，而卡面 verify 是 `PYTHONPATH=src python3 -m pytest ...`，
  加前缀等于改所有卡的卡面，且本机手工跑（不带前缀）仍然红。修 `_run_cli` 才是治本。
- 不要删这 2 条用例或给它加 skip。它们测的是真实契约（`--canonical --dry-run` 必须报 L5001、
  `--help` 必须列出 `--canonical`/`--apply`），在 0.88 上是真跑的。
- 不要改成 `errors='ignore'`——会把真正的差异吞掉，断言变成永远通过。

## 验收

```bash
# 1) Windows 本机，不加任何环境变量（关键：模拟 hive verify 的默认口径）
python -m pytest -q -o addopts= tests/test_linter_canonical.py
#   期望：19 passed（现在 2 failed / 17 passed）

# 2) 0.88 上不变（不能为了 Windows 绿而把远端弄红）
python tools/remote_ci.py --repo . --tag T-xxxx-lint -- tests/test_linter_canonical.py
#   期望：19 passed

# 3) 若顺手改了其它 helper，对应文件也要双跑
python -m pytest -q -o addopts= tests/test_cli_json.py tests/test_patch_engine.py
```

第 1 条是核心：**不带 `PYTHONUTF8` 也必须绿**。
