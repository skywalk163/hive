# 对外地址启动后不再校准：IP 漂移 → 主节点被全群判死 → 选举风暴

## 一、现象（2026-11-09 19:20 实测）

- 本机 `ipconfig getifaddr en0` = **192.168.0.110**，但节点表里本机仍写着
  `http://192.168.0.103:8788`；本机自连 `.103` 直接超时（2s），连 `.110` 才是 200。
- 其他节点 `curl http://192.168.0.103:8788/api/cluster/health` 全部失败，
  于是每 5 秒判定「主节点租约过期 / 心跳超时」，进而在
  `1/3 → 1/2 → 1/1` 之间反复重选。
- 日志特征：`失联：主节点租约过期`、`失联：心跳超时`、`本轮选举未获多数：term=N（1/3 票）`
  在同一分钟内反复出现；10 分钟窗口内 101 次 `election_started`、136 次 `term_advanced`。

## 二、证据锚

- `hive_cluster.py#L341-L343`：`advertise` 只取构造参数 / `HIVE_CLUSTER_ADVERTISE` / 磁盘旧值。
- `hive_cluster.py#L1100`、`#L1141-L1142`：`advertise_host = config.advertise or _guess_lan_ip()`，
  **只在进程启动时算一次**，之后没有任何刷新路径。
- `hive_cluster.py#L1507-L1513`：`_self_node()` 的 `url` 固定用启动时算出的值。
- 对照：`ipconfig getifaddr en0` = `192.168.0.110`；`state.json` 本机 `url` = `.103`。

## 三、为什么是缺陷

节点的 `url` 是集群内唯一的可达性契约：心跳、投票、租约全按它发包。
DHCP 换址、Wi-Fi 切网、笔记本睡眠唤醒都会让 IP 变化，而 hived 不会察觉，
于是「自己认为一切正常、全群认为它已死」。这不是配置问题，是缺少自校准逻辑：
进程生命周期远长于一次 DHCP 租期。

## 四、修复方向（本卡只改 `hive_cluster.py`）

1. 新增 `_refresh_advertise_locked()`：每隔 `advertise_refresh_s`（默认 30s，可被
   构造参数/环境变量覆盖）比较 `_guess_lan_ip()` 与当前 `advertise_host`。
2. 仅在**未显式指定** `advertise` 且 IP 连续两次探测一致时切换，避免多网卡抖动；
   更新 `advertise_host` 与自身节点记录的 `url`，并 emit `advertise_changed` 事件留痕。
3. 若本机是 leader，地址变化后立即广播一次快照让同伴更新自己的记录；
   不要让同伴继续打旧地址直到租约过期。
4. 显式 `--advertise` / `HIVE_CLUSTER_ADVERTISE` 时保持现状（人明确指定的不自动改）。

## 五、验证方式（修复后应全绿）

```bash
python -m pytest -q tests/test_cluster_advertise_refresh.py
python -c "import pathlib; s=pathlib.Path('hive_cluster.py').read_text(encoding='utf-8'); assert '_refresh_advertise_locked' in s; assert 'advertise_changed' in s; print('advertise-refresh-present')"
python -m pytest -q tests/test_cluster_topology_check.py
```

新增测试至少覆盖：IP 变化后 `self.url` 更新、事件只发一次（不刷屏）、
连续两次探测不一致时不切换、显式 advertise 不被覆盖。

## 六、风险与边界

- **不改** `_guess_lan_ip()` 的选网卡规则；不改 `config.json` 默认值；不引入第三方依赖。
- 多网卡机器可能挑错网卡：因此只做「变化才更新 + 去抖」，且显式 advertise 优先。
- **不改** 选举/租约/quorum 逻辑（另见 T-0294）；不碰 `state.json` 手工编辑。
- 本卡不改 `hive.py`，不动其它卡面与 agent 配置。
