签名（win 3.10/3.11/3.12，日志原文）：

```
AssertionError: Lists differ: ['?', '?'] != ['甲', '乙']
L-262 未销账：原生腿=['AL=2', 'A0=?', 'A1=?', 'UL=2', 'U0=?', 'U1=?']
            转译腿=['AL=2', 'A0=甲', 'A1=乙', 'UL=2', 'U0=甲', 'U1=乙']
```

边界实参那条更进一步，把形参**引号**都改写了：

```
['a b', '??', '?"??"'] != ['a b', '中文', '带"引号"']
```

`?"??"` = `带"引号"` 里的 `"` 按 OEM 码页前置字节（0x81）落成 `?`——典型的
「命令行是 Unicode → CRT 按 ANSI/OEM 解成字节 → 再被当 UTF-8 读」两跳转码。

## 二、已定位到的断因（L-262 只落了一半）

T-0234 那批改动确实落了**两条**：

- `src/llvm/runtime_typed.c:dv_get_args` 已从 `i = 1` 起（对齐 `sys.argv[1:]`，不含 argv[0]）；
- `src/llvm/codegen_typed.py` 已把 `用户参数` 登记（`UL=`/`U=` 行能打出来，说明确实走到这条腿）。

但 argv **本身的编码**还在裸奔：

- `_dv_arg_to_str`（runtime_typed.c）把 Windows argv 当 ANSI 处理：`MultiByteToWideChar(CP_ACP, ...)`
  → `WideCharToMultiByte(CP_UTF8, ...)`。本机（zh-CN，ACP=936/GBK）实测能过，
  但 **GitHub runner 是 en-US，ACP=1252，编码全部落空**；
- 2026-10-30 那批 `codegen_typed` 的 `用户参数` 增量**没带 argv 编码处理**——
  这正是「本机绿、runner 红」的差别。

另有一条同源候选：**python 那半边的 argv 也不一定是 UTF-8**。`sys.argv`（CLI 侧）在
Windows 上由 CRT 按 ACP/OEM 解码，为 cp1252 时中文可能回不去——需要探针验证，别先假设。

## 三、交付

1. **原生腿取参改成宽字符入口**（推荐）：
   `runtime_typed.c` 里不要再用 `argv`，改在启动早期调 `GetCommandLineW()`
   + `CommandLineToArgvW()`（Windows 分支限定），把结果按 UTF-8 落进
   `dv_init_args` 的替代路径；`_dv_arg_to_str` 直接吐 UTF-8，不再做 ACP 猜测。
   旧的 `dv_init_args(argc, argv)` 保留给非 Windows。
   ⚠️ 用了 `CommandLineToArgvW` 要链 `shell32`——`src/llvm/compiler.py` 的链接参数
   对 Windows 分支要同步加，否则整条 clang 腿链接失败。
2. **CLI 侧对齐**：`cli/light.py` 真传实参给产物（`subprocess.run([exe, *实参])`）时，
   src 腿的 `sys.argv` 口径要么同样按 UTF-8 重建，要么在测试里显式钉住
   `PYTHONUTF8=1`（CI 已有全局 `PYTHONUTF8=1`/`PYTHONIOENCODING=utf-8`，但
   `sys.argv` 的获得走的是 `CommandLineToArgvW` 之前的 CRT，未必受影响——以探针为准）。
3. **看 3.11/3.13 那条单版本红的连带**：
   `test_原生腿_T6C_向量复数颜色参数编码.py::test_O0_编码解码_URL_对拍` 只在
   win 3.11 露头一次，签名是 `实际=9 期望=10`、**缺的是
   `URL查询串解码("a=hello+world&b=x%2Fy&c=中")` 的 `a=hello world` 一行**。
   它与「`+` 号解码/字段顺序」有关，可能与本卡的 argv 无关，属于独立偶发——
   **本卡只负责复现一次并给出继续或另开卡的结论**，不硬修；修不了就写"待证"。

## 四、还有一条待你验的前提（重要）

**mac 侧的红是"非 arm64 物理机"解释不了的残余**，已另立 T-0250。但你这条链路上有个

## 六、假绿条件（必须写进交付说明）

- `gh run list` 不带 `-w CI` 会取到 Deploy Docs / Quality Gate（本会话实测：不加时
  limit 1 拿到 `Deploy Docs to GitHub Pages`），那轮里根本没有这 4 条 job，
  `fail=0` 也会成立——所以判据里必须带 `-w CI` 并且断言 `win=4`。
- `gh run view --json jobs` 返回的是**这一轮最新 attempt**；若该 attempt 还在跑，
  `conclusion` 是空串，不是失败。要么先确认 run 已 completed，要么把"空串"当未决而不是绿。
- 本机（Windows worker）绿 **推不出** runner 绿：runner 的 ACP 不是 936。
  本机只能证明"没回归"，runner 那 4 条 job 才是判据。
- `--timeout=300` 的原因见测试文件头：原生腿每例真编译真跑（~4s/例），
  xdist 并发下 clang 争抢会破全局 `--timeout=60`。
