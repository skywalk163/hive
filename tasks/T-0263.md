# CI 里克隆失败只是打个 warning，测试就「跳过」了

## 问题原文

`.github/workflows/ci.yml:29`：

```yaml
- name: 检出 light-merge 编译器
  run: |
    REPO="${{ vars.LIGHT_MERGE_REPO }}"
    if [ -z "$REPO" ]; then
      echo "::warning::LIGHT_MERGE_REPO 未配置，尝试默认地址"
      REPO="https://gitcode.com/skywalk163/light.git"
    fi
    git clone --depth 1 "$REPO" ../light-merge || echo "::warning::light-merge 检出失败，测试将跳过"
```

`|| echo "::warning::..."` 意味着：**克隆失败 → 退出码被吞 → 后续步骤照跑 → job 可能绿**。

后面还有一段硬编码：

```yaml
EXPECT=5610f44a2b7d6970a9a185bccba578e13b9a7657
if ! git -C ../light-merge cat-file -e ${EXPECT}^{commit} 2>/dev/null; then
  echo "::warning::克隆的 light-merge 不含 L-013/L-021 修复（缺 commit ${EXPECT}），回退 canonical gitcode main"
  rm -rf ../light-merge
  git clone --depth 1 https://gitcode.com/skywalk163/light.git ../light-merge
fi
```

两个问题：
1. 克隆失败被吞，测试「跳过」而 job 绿 —— 这是**假绿**
2. `EXPECT` 钉死一个 SHA。`--depth 1` 的浅克隆里，老 commit 通常**根本不存在**
   （`git cat-file -e` 会失败），于是每次都走「回退」分支重新克隆一次 —— 白白多一次网络往返；
   而如果哪天这个 SHA 被 force-push 掉，判断就永远为假。

## 起点线索

- 仓库只有一个 workflow：`.github/workflows/ci.yml`（30 分钟 `timeout-minutes` 已设，这点是好的）
- `lightharness/smoke.sh` 存在且可执行（8104 字节）
- `lightharness/tests/` 有 32 个条目、74 个入库文件

## 目标

### 1) 克隆失败直接红，不留假绿

```yaml
- name: 检出 light 编译器（语言本体）
  run: |
    REPO="${{ vars.LIGHT_MERGE_REPO }}"
    if [ -z "$REPO" ]; then
      echo "::notice::LIGHT_MERGE_REPO 未配置，使用默认地址"
      REPO="https://gitcode.com/skywalk163/light.git"
    fi
    if ! git clone --depth 1 "$REPO" ../light-merge; then
      echo "::error title=light 编译器检出失败::无法克隆 $REPO。lightharness 的测试依赖同级目录的 light 仓，缺它整批用例没有意义。请检查网络/仓库地址/vars.LIGHT_MERGE_REPO。"
      exit 1
    fi
```

关键点：`::error` + `exit 1`，让失败**显式红**，且日志里一句话说清「为什么这件事重要」。
不要用 `continue-on-error: true`。

### 2) 把「commit 存在性」换成「能力探针」

删掉 `EXPECT=5610f44a...` 那段。改成验能力：

```yaml
- name: 校验 light 编译器可用（能力探针，替代硬编码 commit）
  run: |
    set -e
    cd ../light-merge
    # 光明确认能跑起来
    python -m cli.light_unified --version
    # 能编一个最小程序（这是所有 .light 用例的前置能力）
    cat > /tmp/_lh_hello.light <<'LIGHT'
打印("hello")
LIGHT
    python -m cli.light_unified run /tmp/_lh_hello.light
```

判据从「某个特定 commit 在不在」变成「编译器到底能不能用」——
这才是测试真正依赖的东西，也不怕上游演进。

> ⚠️ 先用本机验证这两条命令真的能跑通：
> ```bash
> cd /home/skywalk/dswork/light && python -m cli.light_unified --version   # 光明 v0.4.1
> ```
> 我本机跑过 `--version` 是通的。`run` 那条请你在交付前自己也验一次。

### 3) 补一个「sibling 缺失」的显式报错

`light` 仓的 CI（`.github/workflows/ci.yml:131-150`）已经有一套很成熟的做法：
sibling 缺失时 `pytest.skip` 并把 reason 打进 SKIPPED 汇总，「绝不 collect error」。
lightharness 这边是反过来的——它**需要** sibling，所以应该**缺了就红**，而不是 skip。

在 job 开头加一步前置检查，把「为什么必须红」写在日志里：

```yaml
- name: 前置：确认测试对 light 编译器的依赖是硬依赖
  run: |
    echo "本仓测试依赖 ../light-merge（语言本体编译器）。"
    echo "克隆失败/编译器不可用 → 整批用例无意义 → 必须红，不得 skip。"
```
