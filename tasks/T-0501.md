## 背景

现有工具名多为 `tool_NN`（如 tool_20/21/22/23、tool_66/67/68）无语义编号，模型只能靠 description 反推用途，路由准确率低、思考开销大。W1/T1.1 已为全部工具打上 `domain` 元数据，本卡基于 domain 设计语义化命名。

## 目标

1. 制定命名规范：`<域>.<动作>` 形式（如 `ctx.select_blocks`、`workflow.query_status`、`file.search`），域取值与 T-0496 的 domain 对齐；
2. 为全部 `tool_NN` 工具产出一张 **tool_NN → 语义名** 映射表，作为后续改名的唯一依据；
3. 明确**向后兼容策略**：中文名工具（如 `搜索文件`）是否保留别名，避免破坏既有会话/脚本。

## 关键设计取舍

- 命名规范要落在 `docs/工具命名规范.light.md`，作为 W2/T2.2 改名的输入；
- 映射表须可被校验：每个 tool_NN 都有唯一语义名，无冲突、无遗漏；
- 旧名兼容：通过工具别名机制保留旧名一段时间（具体机制在 T-0463 别名实现），映射表需标注每个工具「保留别名 / 直接改名」。

## 交付物

- `docs/工具命名规范.light.md`
- tool_NN → 语义名 映射表（随规范或独立数据文件）
- `tests/test_T0501_命名映射表.py`：校验映射表完整性、唯一性、域对齐

## 验收判据

1. 映射表覆盖全部 tool_NN，无遗漏、无重名冲突；
2. 每个语义名的域前缀与 T-0496 的 domain 一致；
3. 兼容策略对每个工具都有明确标注（保留别名 / 直接改名）；
4. 命名规范文档可被 T-0502 直接消费。

## 红线

- 本卡**只产出方案与映射表，不动 registry**（改名在 T-0502）；
- 命名不得与现有中文名/英文工具名冲突；
- 域前缀必须复用 T-0496 的 domain 枚举，不得另造一套。
