## 背景

经验现在是会丢的。举几个真实例子：

- T-0101 的 agent 在 summary 里坦白「本机 sandbox 后端不可用，没能跑测试」，但结果照样
  判 done —— 这条情报只躺在那张卡的 result json 里，下一次派卡时 dispatch 完全不知道；
- fb88-dsh 的 worker 死过一次（没用 setsid 启动会随父 shell 回收），日志停在半路；
- `dsh-exec` 无条件 `sudo chroot`，从 WorkBuddy 的工具环境起 worker 必挂；
- 历史上反复出现「复位 ready」「retry」的人工清场。

这些本来都该在以后的建卡时被避免，但它们没有回流的地方。`docs/` 里没有 lessons 文件，
`hive stats` 只给数字不给归因。

## 目标

让 hive 能自己产出「复盘摘要」，把失败原因聚成类，落到 `docs/lessons.md`。

1. **`hive digest [--days N] [--out FILE] [--json]`**：
   - 扫 `results/*.json`（归档的）+ 在飞的 `res/*` 分支；
   - `--days N` 按 `finished_at` 过滤（默认 7 天）；
   - 输出 markdown：
     - 总览：完成 / 失败 / 成功率 / 中位与 P90 耗时；
     - **失败归因**（重点）：从 `result.error` 聚类 ——
       `超时` / `verify 未通过`（并把挂掉的那条命令附上）/ `agent 退出码 N` / 其它。
       每类列出卡号，让人一眼看出是「卡写得太难」还是「环境不稳」；
     - 按 agent 的成功率与耗时；
     - 耗时最长的 5 张卡（往往是「卡拆得不够小」的信号）；
     - 反复重跑的卡（同一 id 出现多次结果 —— 意味着第一版验收就没过）。
   - `--out FILE` 写到文件，`--json` 给机器读（看板以后可以用）。
2. **`docs/lessons.md`**：本卡顺手写第一版，把这些真实教训沉淀进去（至少包含上面
   背景里的四条）。它不是流水账，是「以后建卡/配环境时该注意什么」。
   格式：`## 类别` + 一条条 `- **现象** → **原因** → **以后怎么做**`。
3. **周期性复盘卡怎么跑**：在 `docs/操作手册.md` 里写清楚用法 ——
   总控每天用 `hive digest --days 1` 看一眼；或者建一张卡让 agent 读 digest
   + `hive doctor` 产出「本周 lessons 增补 + 候选改进卡草稿」（草稿走 T-0120 的路子）。
4. **给后面留接口**：`hive digest --json` 的输出结构要在文档里写死 ——
   T-0120 的 `draft lint`（判定 `needs` 有没有 agent 能满足）和看板都打算消费它。

## 红线

- 不改 light 等仓；不引入新依赖。
- `hive digest` 是**只读**的，绝不写任务卡、不推分支（`--out` 只写普通文件）。
- 结果里可能缺字段（老卡、失败卡），代码要容错，别 KeyError。
- 别动 `tasks/*.md`、`results/*.json`。

## 备注

写测试用例时注意：hive 的日志走 stderr，断言要把 stdout+stderr 合并看；
`status --json` 返回的是 list 不是 dict。夹具在 `tests/conftest.py`，
`world.add_task(...)` 之后再跑一次 worker 就有 result 了。
