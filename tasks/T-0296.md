# submit 假成功：结果写 store 失败被吞掉，命令仍打印成功

## 一、现象

集群选举风暴期间（见 T-0293 / T-0294），`cluster.log` 可见
`POST /api/cluster/store/result ... 409`。但 agent 侧的 `hive submit` 仍然输出
`T-xxxx done by ...` 并返回成功；store 里没有结果行，卡随后因租约过期被重新派发，
表现就是「结果静默丢失」——此前 **T-0250 / T-0252** 都踩过。

## 二、证据锚

- `hive.py#L990-L999`：

  ```python
  def store_result(tid, agent, lease_id, result):
      try:
          return store_call("result", {...})
      except HiveError:
          return None          # ← 异常被吞，调用方无法区分成功/失败
  ```

- `hive.py#L3749-L3761`：`cmd_submit` 直接调用 `store_result(...)`，
  **不检查返回值**，随后照常 `print` 成功并返回 0。

  ```python
  store_result(tid, owner, str(claim.get("lease_id") or ""), result)
  ...
  print(f"{tid} {result['status']} by {owner}（{result['duration_s']}s）...")
  ```

- 次生路径：新 leader 上任会 `store.truncate_uncommitted()`（`hive_cluster.py#L2313`），
  旧 leader 已接受但未复制到多数的 result 会被截断丢弃。

## 三、为什么是缺陷

`submit` 是 agent 交付的唯一收口动作。结果写不进 store 却不报错，会让
「卡已 done」与「store 无结果」长期不一致：看板看不到、`close/land` 不执行、
租约过期后重复派发同一张卡。这不是容错，是**假成功**。

## 四、修复方向（只改 `hive.py`）

1. `store_result()` 不再吞异常：返回 `(ok, err)` 或直接抛出可识别的
   `ResultWriteError`，保留原始错误码（409/无主/超时）。
2. `cmd_submit()` 必须检查结果写入状态：
   - 失败时**保留** worktree 与 `res/<tid>` 分支（已有 git 侧结果不丢）；
   - 按 `ctx` 里的退避重试 N 次（默认 3，间隔 2s/4s/8s），每次失败 emit 明确日志；
   - 最终仍失败则返回非 0，并在 `.hive/summary.md` 写清「git 已写、store 未写」的状态。
3. 成功路径的 stdout 保持现有格式（避免破坏既有解析），只在失败路径新增错误输出。
4. `store_release(requeue=True)` 只在实际写入成功后才执行，避免「未落库还被释放」。

## 五、验证方式（修复后应全绿）

```bash
python -m pytest -q tests/test_store_result_signal.py
python -m pytest -q tests/test_store_claim_errors.py tests/test_submit_summary.py
```

新增测试至少覆盖：`store_call` 抛 `HiveError` 时 `cmd_submit` 返回非 0 且不打印成功；
重试次数符合预期；重试成功后正常返回 0；失败时 worktree 与 `res/<tid>` 保留。

## 六、风险与边界

- 失败返回非 0 会改变现有「永远成功」的调用方预期，需同步检查 `hive_worker` 对
  submit 返回码的处理（本卡允许改调用点，但仍只限 `hive.py`）。
- **不改** git 提交语义、`res/<tid>` 分支命名、verify 判定逻辑。
- 不改 `hive_cluster.py`（选举侧见 T-0293/T-0294/T-0295）、不改 `state.json`、不动其它卡面。
