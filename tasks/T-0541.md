## 背景

2026-11-28 排查"开机后控制台窗口弹出几十次"时确认：

- 当天开机（08:20:48）后集群日志只有 2 次 git 同步：08:22:44 light、08:23:10 lightharness，间隔 26 秒且是不同仓；`sync_cursor.json` 印证。没有"几秒后又同步"。
- 但历史日志（前一天 20:51:48–20:53:48）有 43 条密集 sync，每 2–3 秒一次、lightharness/hive 交替、每条 target sha 都不同——用户记忆中"几秒之后又进行了同步"确有其事。
- 本次 pull（1a0333e..ba01eef）没有改动同步/窗口逻辑；T-0538 的 conhost 修复早已在本地。

## 根因

`hive_cluster.py` 的 `RepoSyncAgent` 有两条触发 git 的路径：

1. 看板刷新 → `hive status --json --sync-health` → `_sync_gate` / `SyncThrottle`（T2 1800s ±20% jitter + T0/T1 提前触发 + `fetch_if_changed` 10s TTL），绝大多数轮次直接跳过，已有节流。
2. `repo.updated` 事件消费 → `_consume_events()`（每 15 秒 tick）→ 对每条事件里的每个 repo **立即**调用 `_sync_repo()` → `h._sync_one_repo()` 跑 git ls-remote / fetch / merge。这条路径**没有最小间隔、没有"上一轮未结束就跳过"的在飞标志**，是 43 条密集同步的来源。

`_reconcile()` 本身有 300 秒周期并对 ahead/diverged 终态跳过，但事件消费路径绕过了它。

## 目标

给事件消费路径加 per-repo 节流，避免事件风暴时几秒一轮地打 git；保留事件驱动的实时性和安全快进语义。

## 要做什么

1. 在 `hive_cluster.py::RepoSyncAgent` 增加 per-repo 的最小同步间隔（默认 180–300 秒，可由环境变量覆盖，与既有节流口径一致），基于 `self._state["repos"][name]` 的 `synced_at` / `updated_at` 判断；未到间隔则跳过该事件。
2. 加"在飞"标志：同一 repo 上一轮 `_sync_repo` 未结束时不重复启动（`self._lock` 已串行，但只防并发、不防连续触发）。
3. 对 `target` 与已记录 sha 相同、或状态为 ahead/diverged 终态的仓库，事件消费同样跳过（复用 `_reconcile` 的终态判定口径）。
4. 补回归测试 `tests/test_cluster_sync.py`：
   - 同一 repo 连续多条 repo.updated 事件在最小间隔内只触发 1 次 git；
   - 不同 repo 的事件互不阻塞；
   - 在飞标志阻止重入；
   - 终态（ahead/diverged）事件被跳过。
5. 保持 `RepoSyncAgent.status()` 输出字段兼容（看板/API 依赖）。
