# test_vote_store_behind 一条用例与 T-0299「不抢占在位主控」冲突

## 一、现象

`python -m pytest -q tests/test_vote_store_behind.py` 在 main 上确定性 1 failed：

```
FAILED tests/test_vote_store_behind.py::test_lagging_candidate_wins_election_without_force
E  assert False is True
E  AssertionError: 落后候选默认应能当选，而不是等到 quorum 退化
```

日志：`选举前侦听到在位主控，本轮不发 CLAIM`。

## 二、根因

该用例在 `a` 仍是**在位主控、租约有效**时直接调用
`b._start_election(force=False)`，期望 b 以更高 term 抢下主控。

但 T-0299（已 land）把「不抢占在位主控」写成硬规则：
`_start_election` 在 `leader_id != self and leader_lease_until > now` 时直接
返回 False，并且发 CLAIM 前还有 `_carrier_sense()` 询问成员 `/health`，
发现有效主控就放弃本轮。这正是 T-0299 卡里的红线之一。

所以这是**用例旧口径**（T-0295 时期没有这条抢占禁令），不是实现回归。

## 三、目标

只改 `tests/test_vote_store_behind.py` 这一条用例，保留它真正要钉的语义
（**数据新鲜度不是选举资格**：落后的 b 不需要 force 也能当选），同时遵守
T-0299 的不抢占规则：

1. 先让在位主控**正常下野**：`a.handle_resign({"node_id": a.node_id})`；
2. 等 `b` 自己把过期租约清掉（`wait_until(lambda: b.leader_id is None)`）；
3. 再 `b._start_election(force=False)` —— `a` 仍是成员、仍是活着的投票人，
   默认模式（非严格）下会给落后的 b 投赞成票，b 以 2/2 票当选。

这样 `a.store=99` / `b.store=None`（last_store_seq=0）的落差仍在，storch 闸门
仍被真实走到（a 会 emit `vote_store_lag`），只是把「抢在位主控」换成「正常切主」。

## 四、红线

- 只改 `tests/test_vote_store_behind.py` 的这一条，不改其它用例；
- 不改 `hive_cluster.py`、不改 T-0299 的不抢占规则、不改默认值；
- 不动其它测试与卡面。

## 五、验收

```
python -m pytest -q tests/test_vote_store_behind.py
python -m pytest -q tests/test_cluster.py
```

两个都全绿。
