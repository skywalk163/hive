# 光明：parser 深嵌套 ≥80 层就 RecursionError——修到 150 层可编可跑，且不许靠抬递归上限

> 来源：T-0445（Windows「内存错误 / 栈溢出」假红）收口时如实登记的两条残留之一。
> 同卡第二残留是 `/` 链的 `_light_trunc_div` 逐层调用（>150 项仍受 CPython 嵌套上限），
> 本轮不要求修，只需在 summary 里复测一次并写明现状。

## 现象（2026-11-24 实测，Win10 / CPython 3.13.18；FreeBSD 15.1 / 3.12.13 同)

`段落 主程序:\n  设 甲 为 ((((…1…)))).\n  写(转字符串(甲))。`

- **60 层括号**：绿，能编能跑。
- **80 层括号**：`RecursionError: maximum recursion depth exceeded`（parser 阶段直接红）。
- 每层约 12 个 Python 帧：`src/parser_expr.py` 的 10 级优先级阶梯
  （logical_or → logical_and → comparison → bitor → bitxor → bitand → shift →
  add → mul → power → factor/primary）每级都要下钻一次。
- 嵌套调用同形：`f(f(f(…1…)))` 到 ~80 层同样红。
- 与操作系统无关，与 T-0445 修的 codegen 递归不是同一处（那条链已迭代化）。

影响：机器生成的长表达式、深嵌套配置/JSON 字面量、工具参数 schema 这类**语义完全合法**
的光明源码在编译期直接失败，下游判据拿到 rc≠0 就打成红。

对照（同一台机实测 CPython 自身）：嵌套括号 200 层可编、300 层报
`too many nested parentheses`。所以目标不是"无限深"，而是把光明的可用区间拉到
**宿主 Python 上限附近**，同时不改变任何语义。

## 这一轮要交付什么

1. **最小复现**：≥80 层括号 与 ≥80 层嵌套调用 两个最小 `.light`（脚本自带 fixture，
   不依赖 lightharness、外网、特定目录残留），现状必须能稳定红（写进 summary）。
2. **修复**：表达式解析不再"每层括号递归一轮"。允许两条路线，做哪条由执行者按实测选：
   - (a) 括号层迭代化：遇到 `(` 显式压栈并按深度循环解析，或把 10 级阶梯改成
     显式算子栈（优先级爬升）；
   - (b) 解析期"深度预算"：递归前先按 token 流算最大括号深度，超过宿主安全层数时
     给出**明确的 ParseError**（带层数与建议），而不是 RecursionError —— 但这条路
     只能算"把崩溃换成可读报错"，**不能算修好**，需在 summary 里明确标注未达 150 层。
   首选 (a)，判据按 150 层给。
3. **codegen 冗余括号收敛**：纯括号层（`((((1))))`）生成 Python 时不得继续叠括号
   （否则 150 层括号会在 `compile()` 阶段撞 CPython 的嵌套上限，白修）。嵌套调用
   无法扁平，按宿主上限为界即可。
4. **判据** `tests/test_R226_deep_nest.py`：
   - 150 层括号、150 层嵌套调用：`parse → generate → compile → exec` 全过，输出正确；
   - **不许靠抬上限**：把 `sys.setrecursionlimit` 压到 500 后，同一 150 层夹具仍可编可跑
     （证明栈深度与层数解耦）；
   - **反证**：把新路径退回旧逐层递归（保留一个内部开关，如
     `_iterative_paren_parse = True`，测试里置 False），同一夹具必须真红；
   - **大模块回归**：≥200KB / ≥4000 行模块仍绿，编译耗时与峰值内存在卡内实测后设上限；
   - **语义对拍**：`((((1+2)*3))))`、混优先级、比较链、`包含`、除法等形态，结果与
     旧实现逐字一致（不允许"修了深嵌套、改了优先级"）；
   - **FreeBSD 15.1（192.168.0.88，`ssh workbuddy@192.168.0.88`，密码取 .env 的
     SSH_PASS_WORKBUDDY）同文件全绿**，防止把 Windows 侧修成 POSIX 回归。
5. **不改契约**：L0 核心字、语法表、AST 形状（`ast_nodes_v3.BinaryOp` 等）一律不动；
   只许改实现与新增测试。

## 红线

- 不许把红用例改 skip / xfail 变绿；
- 不许用 `sys.setrecursionlimit(...)` / `threading.stack_size(...)` 的"调大"当修复
  （Windows 线程栈更小，抬上限只会把可捕获的 RecursionError 换成打穿 C 栈的硬崩溃）；
  测试里压**小**上限是判据手段，不算违规；
- 不依赖外网、真实凭证、特定目录残留；复现脚本自带 fixture；
- 不做无关重构；不顺手改 T-0445 的判据文件（`tests/test_R225_win_memory.py` 不许动）；
- 150 层做不到就把**实际可达层数 + 硬证据**（哪一层红、栈帧数、宿主上限、每个候选
  方案的实测数字）写进 `.hive/summary.md`，不许硬凑"修好了"。

## 已知线索

- 递归点：`src/parser_expr.py` 的 10 级优先级阶梯 + `src/parser_core.py` 的语句/表达式入口；
  括号在 `factor/primary` 处回落到最低优先级，于是每层括号 = 一整轮 12 帧。
- T-0445 的 codegen 迭代折叠可直接复用：`_left_spine` / `_fold_binary_spine` /
  `_generate_binary_chain`（`src/code_generator.py`，R225 小节）。
- 深嵌套**块缩进**（>100 层）是 CPython `MAXINDENT` 的硬限制，属宿主边界，不在本卡范围；
  别把它和括号深嵌套混为一谈。
- 判据文件命名沿用 `tests/test_R226_deep_nest.py`，不要与 R225 的用例混在一个文件里。
