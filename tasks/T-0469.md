# lightharness 系统提示与工具面升级：从 4 工具提升到可用编码代理

## 背景（来自 2026-11-24/25 实测与 0461 交接文档）
生产会话只有 4 个工具（`bash,读文件,写文件,搜索文件`）；`默认系统提示文本()`（总入口.light:306）只有三条工具实参契约，注释明写"只钉工具调用契约，不写业务人格"。对比 DSH：核心工具 20+（fs/fs-search/str-replace-editor/todo/goal/subagent/jobs/web/workflow/schedule/skill/cordis/present/LSP/session-query 等），system-prompt 是 30+ 节顺序槽位的组装系统（HARNESS_IDENTITY/PLAN_POLICY/TOOL_*/FILE_REFERENCE/PTC 等），由各插件贡献内容。结果：模型缺规划/工具选择/文件引用引导，复杂任务全靠 bash 试探——T-0461 交接文档里代理把大量精力花在 `cd $W` 绕 cd 守卫、bash heredoc 写文件、手工 subprocess 编码等工具摩擦上，而非实现 light-mcp。

## 要做什么
1. 把已有的 `系统提示.light` 组装框架真正接进 Web/CLI 主路径：在 `跑一轮` 组提示时，除工具契约外，加入身份、规划策略、何时用何种工具、文件引用/路径规范、目标/todo 使用引导等 section（可复用 `src/智能体指令.light` 已有的 AGENTS.md 发现能力，避免重复造轮子）。
2. 工具面：在 standard 预设下至少补上结构化编辑（str-replace-editor 风格）、todo 规划、目标管理三类工具（可基于已有 `src/工具_*.light` 或 `核心工具.light` 现成模块；优先复用，缺的再补最小实现），并保证与 MCP 工具挂载（T-0468）共存不互相过滤。
3. 保持向后兼容：工具线名规则（中文名合名 read_file/write_file/search_files）不变；T-0443/0456 关于 standard 恰 4 工具的旧判据需要同步更新到新基线，并在 summary 里说明为什么改。
4. 提示词长度受控：新增 section 总量有上限（如 4k tokens），避免把上下文撑爆（关联 T-0466）。

## 验收
- 新增 `tests/test_T0469_提示与工具面.py`：断言默认系统提示含规划/工具选择/文件引用引导（文本关键词）；standard 注册表含新增工具且 `mcp__*` 共存（配合 T-0468）；提示词总长有上限断言。
- `python -m pytest -q tests/test_T0469_提示与工具面.py` 全绿。
- 手工：跑一次多步编码任务，观察 bash 占比是否下降（截图/日志证据贴 summary）。

## 不做什么
- 不引第三方依赖；不改模型端点/密钥逻辑。
- 不重复实现 AGENTS.md 发现（复用 智能体指令.light）。
