## 症状

`试: … 最终: …`（**没有 `捕`**）时异常被完全吞掉，而且异常点之后、**同一段落内**的代码继续执行；
外层 `捕` 收不到。Python 的 `try/finally` 是传播异常的，这里语义被静默改写了。

## 复现（可直接存成 .light 跑，实测输出见下）

```light
段落 冒炮():
  抛出 "我是一个异常"

段落 探():
  试:
    冒炮()
    打印 "抛出之后（不该出现）"
  最终:
    打印 "最终块执行"
  打印 "异常之后仍然继续执行了"

段落 主():
  试:
    探()
    打印 "外层: 没抛"
  捕 错误 为 e2:
    打印 "外层捕获到"

主()
```

实际输出：

```
最终块执行
异常之后仍然继续执行了
外层: 没抛
```

期望：打印 `最终块执行` 之后异常向外传播，进入外层 `捕` → 打印「外层捕获到」；
「异常之后仍然继续执行了」永远不该出现。

## 根因（初判）

无 `捕` 的 `试` 被生成为 `try/except: pass` + `finally`，应为 `try/finally`。
这是「假绿制造机」：失败被吞，报错最终指向别处（lighthive 的原子提交就因此把错误指到了 `git push` 参数上）。

## 落点

- `src/code_generator.py`：`TryStatement` 生成分支（约 :975 附近；`finally` 相关另见 :3675）
- `src/code_generator_unified.py`：同名分支
- `antlrparser/`：若该后端也生成 try，一并核

## 验收（`--verify` 会真跑，请让新用例有牙）

新增 `tests/unit/test_LH10_最终块异常传播.py`，至少 4 例：

1. **无捕 + 最终**：异常穿透到外层 `捕`；断言「不该出现」那行 **没有** 输出
2. **有捕**：本层 `捕` 吃掉，`最终` 仍执行
3. **捕 + 最终** 同时存在：先 `捕` 再 `最终`，顺序正确
4. **`返回` 在 `试` 内 + `最终`**：return 路径也要走 finally（返回值不被 finally 覆盖）

建议用 `subprocess` 起 `python3 -m cli.light run <临时.light>` 断言 stdout 全等，
而不是 import 内部函数——这个缺陷的表现层就是「程序没崩但结果错了」。

## 边界

- 只改「无 `捕`」这条路径的生成；**不要**顺手改 `捕` 的既有语义（大量存量代码依赖）。
- **不要动 `builtin_map` 区域**（另一张卡在同一文件里改它，hive 会按 paths 串行，别抢区域）。
