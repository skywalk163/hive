# P0：压缩后任务停住、再发「继续」也没反应——定位根因并修复

## 现象（用户现场）

在 lightharness Web UI 里跑长任务，界面出现

```
已触发上下文压缩，旧消息可能被省略。
```

之后**任务停住**；此时在输入框再发「继续」，**没有任何反应**（不是报错，是像没发出去）。

## 已取到的现场证据（先看这个，别重复踩）

1. **压缩帧是流的最后几帧之一**（`src/web服务器.light:2723-2728` 推流实现、`471-473` 同步路径）；
   用户看到提示时，这一轮其实已经结束了 → 提示与「停止」在视觉上重合。
2. 真实会话 `sessions/--G-...--/web_1794959184.4618163/session.jsonl` 的 `turn/end` 原因：
   - turn 4：`max-tokens`（18 步、输入 37869 token）
   - turn 6：`max-steps`（25 步、输入 60974 token）
   也就是说「停住」的两种现场分别是撞输出上限与撞步数上限，而**这两个原因没有进统计帧**。
3. `src/会话细节.light:时补统计字段` 只补 `开始时刻/完成时刻/耗时秒/速率`，
   **没有结束原因**；前端 `renderStats` 自然无从解释为什么停。
4. 服务端有 `{"error": {...}}` / `["error": {...}]` 帧（`web服务器.light:2617/2624/2676`），
   但前端 `webui/app.js` 的 `readStream.handleFrame` **没有 error 分支**（全文件只有 HTTP 错误路径用到 `.error`），
   所以驱动失败在界面上完全不可见。
5. 会话占用（`src/会话队列.light`）：
   - 流式请求的占用由 `推流实现` 拿（`web服务器.light:2698`）、`最终` 释放（`2753`）；
   - 忙判定在 `处理对话:831`，**检查与真正拿锁之间没有原子性**；
   - 202 排队的项**只由「正在跑的那一轮」的 `当` 循环消费**（`2650-2663`），
     若入队时那一轮已经跳出循环，队列里这条就永远没人消费 → 后续每条消息都 202 且不执行。
6. 自动压缩发生在 `src/代理.light:683-685`（每步前），压缩动作是
   `src/会话.light:压缩替换`：把 `[低界,高界]` 打遮蔽、新检查点插在遮蔽段之后、**后段之前**，
   于是 `事件表` 不再按序号单调；而多处 `保存序号 = 长(事件表)` 把它当**序号**用
   （`web服务器.light:817/1008/2625`，`代理.light:576`）。压缩后两者可能不再等值。

## 要做什么

1. **先复现**（不要改代码就下结论）：照抄 `tests/test_T0407_收口接线.py` 的
   「真起服务 + 脚本化 mock LLM」手法，新写 `tests/test_T0453_压缩后续跑.py`：
   - 环境里把 `HARNESS_MODEL_CONTEXT_WINDOW` 调到很小（例如 2000）、`HARNESS_WEB_MOCK` 关掉，
     让 mock LLM 产生足够多工具结果触发**自动压缩**；
   - 断言第一轮 SSE 里出现「压缩」帧；
   - **同一会话**再发一条「继续」，断言 30s 内必须跑出新的 `assistant/message`
     （现在是 202/静默，这就是要修的红）。
2. **二选一定根因，并给出反跑证据**（在 summary 里写清楚是哪条）：
   - A. 占用/排队滞留（第 5 条线索）→ 修法：占用的「检查+获取」原子化；
     释放时若待办队列非空，必须由释放方重新拉起一次消费（或交给常驻 drainer），
     保证「入队必有人取」；对 202 项加超时兜底（超时后转 409/明确失败，不静默烂在队列里）。
   - B. 压缩后事件序号/保存序号错位（第 6 条线索）→ 修法：把「长度」与「最大序号」分开，
     新增 `最大序号(会话对象)`；压缩替换后重排事件表时保证 lookup/增量保存都按序号口径；
     补纯逻辑判据：压缩替换后「读回消息数 == 内存消息数」「增量保存不丢事件」。
   （两条都命中也修两条。）
3. **结束原因必须传出去**：`时补统计字段` 增补 `结束原因`（取 `轮次结果["种类"]`：
   `completed/max-steps/max-tokens/aborted/error`），并在流式收尾帧里带上；
   同时保证「压缩」帧之后一定有统计帧与 `[DONE]`，压缩帧不能是最后一帧。
4. **超长轮次要能续**：`max-steps`/`max-tokens` 结束时，服务端不得把会话留在「忙」状态；
   下一次请求必须能正常开新一轮（判据 1 覆盖）。

## 判据（verify 全绿才交，当前必须红）

`tests/test_T0453_压缩后续跑.py`：

1. 小窗口触发自动压缩 → SSE 出现 `种类=压缩`；
2. 压缩后同一会话发「继续」→ 30s 内出现新的 `assistant/message`，且 HTTP 200（不是 202/409/空）；
3. 统计帧新增字段 `结束原因`，取值在四值闭集内；
4. 压缩帧后仍收到 `[DONE]`（顺序断言）；
5. 纯逻辑：`压缩替换` 后 `最大序号 == 事件表长度` 的等价关系**不要求恒成立**，但
   `增量保存(起始序号=压缩前长度)` 后读回的消息条数必须等于内存消息条数（不许丢/不许重）；
6. **反跑**：把释放时的「待办非空→重新拉起」删掉，用例 2 立红（贴记录）。

## 红线

- 不伪造 `[DONE]`；不许用「catch 掉异常」当修复。
