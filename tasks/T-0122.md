## 背景

verify 是任务卡自带的，强度完全取决于写卡人的良心。现实情况：

- T-0101 的验收是 `grep -q abilities agents/*.json && grep -q "同仓" hive.py && pytest`
  —— 前两条 **grep 一个字符串就能过**，第三条 pytest 才是真验收。整条命令绑在一起，
  看板只看最终退出码，看不出「到底是哪条在把关」。
- 更糟的一条：那张卡的 agent 在 summary 里自己写了「本机 sandbox 后端不可用，
  没能跑测试」，结果照样 `status: done`。**测试到底跑没跑，没人知道。**
- T-0110 那次失败反而证明机制是有效的：agent 什么都没产出，`grep cmd_land` 立刻判红。

所以问题不是「要不要验收」，而是「**怎么知道这张卡的验收是真的**」。

## 目标

给 verify 做强度分级，并把评估结果挂到结果和 list 流程里。

1. **分类函数 `_verify_strength(cmd) -> "strong" | "weak"`**（放在 hive.py，两边共用）：
   - `strong`：真的会执行被测对象 —— `pytest` / `python -m pytest` / `npm test` /
     `go test` / `cargo test` / `make test` / `make check` / 任何带 `-m pytest` 或
     `python -m unittest` 的组合；
   - `weak`：只检查痕迹 —— `grep` / `test -f` / `test -d` / `which` / `echo` /
     `[ -f ... ]` / `wc -l` / `cat`；
   - 判断要**保守**：拿不准就算 weak。完整的 shell 管线（`&&`、`;`）按「最弱的一环」算
     —— T-0101 那条 `grep && grep && pytest` 因此会被判成 weak，这正是我们想要的信号。
2. **`hive result`**：结果视图里给每条 verify 标出强弱，并给整张卡一个结论：
   - 至少一条 `strong` 且全绿 → `strong-pass`；
   - 有绿但没有 strong → `weak-pass`（**要显式提醒**：这张卡的成果没有被真正执行验证）；
   - 有红 → `fail`。
   `--json` 里同样带上。
3. **`hive doctor`**：「已有结果但只有 weak 验收」的卡算 warning 列出来 ——
   总控合并前就该看到。
4. **`hive plan-lint` / `draft lint`**（T-0120）：草稿没有 strong verify 就报 error 阻挡转正。
5. **MCP**：`hive_result` 的返回里带上 `verify_strength`，让 agent 自己也看得见。
6. 测试：至少覆盖 strong/weak 的判定（含 `grep && pytest` 这种混合管线），
   以及 `weak-pass` 卡会被 doctor 点名。

## 红线

- 不改 light 等仓；不引入新依赖；**不要真的去跑额外的命令**（只是静态分类，不是沙箱）。
- 不改变 verify 的执行行为：现在怎么跑还怎么跑，本卡只加「评估」这一层。
- `_verify_strength` 必须是纯函数、好测试，别塞进别的方法里。
- 别动 `tasks/*.md`、`results/*.json`。
