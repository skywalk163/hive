## 背景

环境：Tesla V100S-PCIE-32GB、compute_capability 7.0、`torch 2.10.0+cu128`、`amp=float16`
（Volta 无 bf16 tensorcore，`torch.is_bf16_supported()` 返回 True 但不可用）。
数据规模两轮不变：371 样本 / 37,448 token / 决策 token 36 / 验证 token 260 / vocab 2902，
模型 3,214,272 参数（non-embedding 2,657,088）。

基线数字（实测，**不要重算**）：

| 项 | 首跑（默认 `--max-new-tokens 384`） | A 组（`--max-new-tokens 512`） |
|---|---|---|
| ③ 无约束结构合法率 | fail **0.8077**（42/52，截断 6） | fail **0.9091**（50/55，截断 3） |
| ③ 非截断裸合法率 | 42/46 = 91.3% | 50/52 = **96.2%（已过 95%）** |
| ② C vs B 精确匹配 | C=0.204 / B=0.159，差 2 条 | C=0.213 / B=0.170，差 2 条（无改善） |
| ① 探针（`EDIT` 点） | 与多数类基线持平（等价恒预测多数类） | **0.6667**（多数类 0.2222、随机 0.3333）；A 组 0.8889 |
| ④ 密度 / 速度 | pass：0.0018 / 0.000 | pass：0.0019 / 0.001 |
| 负对照 shuffle | 0.3333 | 0.3333（`< leak_threshold 0.7`，无泄漏） |
| 数据门禁三项 | 1/7 决策点（`EDIT`）、test 9 条、模板簇重合 27 | **完全相同，未动** |

由此得到四条可执行判断：

1. **③ 的 fail 已基本是解码预算问题，不是模型问题。** 截断 6→3，非截断裸合法率 91.3%→96.2% 已过线。
   但 v3 的 `counted_toward_structure_rate` 就是计入截断，所以小数仍是 0.9091。要让它自证，
   只能把截断压到 0（继续加生成预算或改早停），**不许改分母**。
2. **② 两轮都没动**（C/B 各涨 0.01，差距始终 2 条 < 要求 3 条）。"加评估样本数"这个变量还没验证过——
   B 组 `--eval-gen-samples 140` 尚未跑。
3. **① 第一次有数，且是坏消息：C 0.667 < A 0.889。** 门禁一旦放开、按现有数据直接判，① 会 **fail**。
   说明"1 个决策点 + 36 训练/9 测试条"根本支撑不了"统一序列可替代外挂分类器"这个论点。
   补样本（T-0370）不只是为了解锁可测，很可能直接把论点测死；补的时候必须按模板簇分组切分，
   让 A 组也面对跨模板泛化，否则会被"27 簇重合"一句话否掉。
4. **④ 口径仍待定**：1.9‰ 按 `reports/零模型系统报告.md` 的"1–2% 区间"仍未达下限，
   而偏低根因与门禁第一条同源（只注入 `EDIT` 一点），不能拿 ④ pass 当机制验证成功的证据。

## 要做的事

### 1. 脚本加固（`scripts/openi_run.sh`，只改这一处范围）

- `bg` / `run` 启动前**强制预检 CUDA**：不可用时直接中止并打印三条排查提示；
  确实要纯 CPU 跑必须显式 `LP_ALLOW_CPU=1`。现状是无提示回落 `--device cpu`，
  本次就是这么误判成"没跑起来"（显存 0 = CPU 在啃）。
- 新增 `status` 子命令，一条命令给全：进程是否存活（`pgrep -af train_openi.py`）、
  `nvidia-smi` 显存占用、最新日志头 3 行与末 5 行、`metrics.json` 是否生成。

### 2. 三次运行（A 已完成，B/C 待跑）

在仓库根目录执行，均不改预设、不改数据：

| 运行 | 命令 | 状态 | 结果 |
|---|---|---|---|
| A | `LP_EXTRA="--max-new-tokens 512" LP_BUDGET_MIN=210 bash scripts/openi_run.sh bg` | **已完成** | 截断 6→3，③ 0.8077→0.9091，非截断 96.2% |
| B | `LP_EXTRA="--max-new-tokens 512 --eval-gen-samples 140" LP_BUDGET_MIN=210 bash scripts/openi_run.sh bg` | 待跑 | 唯一未验证变量：让 ② 的"差 2 条"具备判别力 |
| C | 同 B，加 `LP_PRESET=small` | 待跑（可选） | 若 B 仍 <95%，区分容量问题与解码问题 |

A 已证明 512 不够把截断清零：还剩 3 条。B 若截断仍非 0，先加预算到 640 再谈容量。

每次跑完必须记录 `metrics.json` 里的 `n_counted` / `n_truncated`，不要只看 0.8x/0.9x 这个小数。

### 3. 失败归因（本地做，不需要 GPU）

解包 `lightprism_out/generated_samples.jsonl`，按 `truncated` 与 `structure_problems` 分两类统计：

- 截断样本（A 组剩 3 条）：命中哪些任务类型、生成到第几个 token 断；
- 真非法样本（A 组 **2 条**，首跑约 4 条）：缺哪个段（`<CODE>` 未闭合？`<V:…>` 缺失？），
  逐条列出任务原文片段（≤40 字）。2 条就是 ②③ 全部剩余差距，必须逐条落到具体任务上。

### 4. 判据 ④ 口径定调（二者之一，必须写进报告）

- **方案甲（改判据）**：`judge` 把 ④ 改成区间 `[0.01, 0.02]`，并同步 `tests/test_openi_v3_judge.py`
  的用例；本次运行按新口径会变 `unknown`（密度过低），报告里如实写。
- **方案乙（不改代码）**：明确声明 ④ 只卡上限，同时在报告注明"密度 0.19% 低于方案 1–2% 区间，
  属机制覆盖不足，不构成机制验证"。

不允许两个都不做、继续让 ④ pass 兼职"机制已验证"。
