## 背景

`integration` 是 light 时代的批量合入层。现行模型（v0.9.x）是 task 分支
**直接 land 到 main**（ff 优先、no-ff 兜底、冲突置 conflict 卡交回），代码里
根本没有 integration/release 概念（`grep integration hive.py` 零命中），但文档
还在教旧模型，新 agent 会被误导去找一个不存在的分支。CHANGELOG 的历史记载
不改（那是档案）。

## 目标

1. **操作手册 §5 分支图**（186 行）：
   `task/T-0101 ─┐ ┼─▶ integration ──CI 绿 + 人 review──▶ main（批量）`
   改为现行模型：task 分支 submit（verify 绿 + 结果落 `res/<tid>`）→
   `hive land --apply` 直接合入 main（ff 优先、非 ff 走合并提交、冲突置 conflict）。
2. **§5 冲突规则**（192 行）：「冲突回给 owner 作为新卡，不要在 integration 上
   手工解半天」→ 现行：land 检出冲突会把卡置 `conflict` 状态并说明冲突文件，
   总控解决后重跑 `land --apply`。
3. **§4 验收段**（136 行）「绿了再合 `integration`」→「绿了就
   `hive land T-0101 --apply`（见 §5.1）」。
4. **close 示例 note**（70、141 行，README 149 行）：「已并入 integration」类
   →「已 land 合入」类。
5. **§3 prune 规则**（93 行）：「只认 `task/*` 和 `verify/*` 两种前缀，
   `main` / `integration` / `release/*` 永远不碰」→ 前半句是代码事实保留，
   后半句名单改为「其它分支一概不碰（结构性保护：只枚举这两个前缀）」。
6. **docs/迁移指南.md:21**：「合并仍手工：`task/T-xxxx` → `integration` → `main`」
   →「合入已自动化：`hive land T-xxxx --apply`（见操作手册 §5.1）」。
