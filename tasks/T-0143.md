# T-0143 背景

raccoon-win（Windows 真机，192.168.0.86）提交 T-0142 的结果后，本机的
`hive status` / `hive doctor` **整条命令崩掉**，直接抛 `UnicodeDecodeError`
（不是警告，是 traceback，退出码非 0）：

```
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xbf in position 419
```

崩的位置是 `result_info()` → `read_ref_file()` → `run()` 里的
`subprocess.run(..., text=True)`。

## 根因：run() 的编码跟着 locale 跑

`run()` 是 hive 唯一的外部命令出口，它写成
`subprocess.run(cmd, text=True, ...)`，**没有指定 encoding**。
`text=True` 的隐含语义是「stdin/stdout 都用 locale 编码」，于是：

- **写入侧（Windows 上）**：`commit_file_to_ref()` 用
  `git hash-object -w --stdin`（`input=content`）把结果 JSON 送进 git。
  中文字符串在 Windows 上被按 **cp936（GBK）** 编码进 blob。
  实测 `results/T-0142.json` 里 `verify[].cmd` 与 `tail[]` 全是 GBK 字节
  （`\xbf\xcd\xbb\xa7\xb6\xcb\xbd\xd3\xc8\xeb`），文件开头的
  `"task": "T-0142"` 因为是纯 ASCII 才看不出问题。
- **读取侧（Linux 上）**：同一个 blob 被 `git show` 取回、按 UTF-8 解码 →
  非法字节 → `read_ref_file()` 直接抛异常，调用它的 `status` / `doctor`
  没有任何兜底，整条命令死掉。

也就是说：**Windows 上写得越认真、中文越多，Linux 上越容易崩**。
这不是数据问题，是 hive 自己的编码纪律缺失。

## 影响面

不只是 T-0142 这一张卡。`run()` 是全局出口，所有走它的路径都受影响：

- 结果 JSON（res 引用）：写入污染 + 读取崩溃；
- 卡面 / 文档提交（同样的 `commit_file_to_ref` 路径）：在 Windows 上会把
  卡面写成 GBK，Linux 侧读卡面时同样会炸；
- verify 命令输出捕获：Windows 控制台是 GBK，`tail` 字段同样带非法字节。

## 修法

在 `run()` 这一个出口上钉死编码，**一次修掉两侧**：

- `encoding="utf-8"`：写入侧无论 locale 是什么，进 git 的字节永远是 UTF-8，
  从此 Windows 写出来的结果和 Linux 写出来的是同一份编码（治本）；
- `errors="replace"`：读取侧遇到非法字节只替换不抛异常，保证 hive 的
  只读命令永远不会被外部数据打死，最坏是显示 `�` 而不是整个看板消失（兜底）。

不做的事：不改 `commit_file_to_ref` / `read_ref_file` 的签名，不做
per-callsite 的 encoding 补漏——散落各处迟早会漏，收口在最底层。

## 验收

- 造一个含 GBK 字节的 `res/<tid>` blob，修完读它不崩、能解析出字段；
- 有回归测试钉住：模拟 locale 非法字节，断言 `run()` 与 `read_ref_file()`
  不抛异常；
- 全量 pytest 通过。
