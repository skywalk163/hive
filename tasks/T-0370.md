# 补监督信号：决策点 7/7 → 单位点 ≥30 条，test ≥30，ERR 类 test 正样本

> 来源：`reports/训练报告_v2.md` §九-3「决策密度未达 1%，受 29 条真实日志限制，扩日志比调重复更有效」；
> `reports/零模型系统报告.md` §四（选项级分布）、§五；`reports/ERR样本覆盖.md`；
> `任务书-20261114-LightPrism-v2整合/T-0348` 的完成标准（本卡是它的数据前置）。
> **本卡只补数据，不训练、不调参、不动验收口径。**

## 一、为什么开这张卡（实测事实，不是推测）

| 事实 | 当前值 | 门禁要求 | 证据 |
|---|---|---|---|
| test 侧决策样本数 | **9—13** | ≥30 | `train_openi.py --self-check` 实跑（v2 整合稿 §2.1） |
| 决策点 test 覆盖 | **1/7（仅 EDIT）** | 7/7 | 同上 |
| 决策 token 密度 | **0.083%—0.096%** | 1—2% | 同上 |
| `err_tasks` 条数 | **8** | 需含 test 正样本 | `data/unified/manifest.json` |
| 真实日志条数 | **29** | 受此限制 | `data/runtime/decisions.jsonl` |

零模型系统的 29 条日志已经把 **7/7 个决策点**都打出过，但**选项级极偏**：
`PLAN=DIRECT` 29/29、`SAFE=L0` 29/29、`EDIT=RW` 28/29、`NEXT=TEST` 25/29。
另有 7 个选项**从未出现**：`EDIT=PATCH`、`SAFE=L1`、`SAFE=L2`、`FIX=ADD_TYPE`、
`FIX=RENAME`、`CTX=DROP`、`PLAN=DECOMPOSE`。

所以现在的病灶不是「决策点覆盖」，而是**选项分布塌成常量 + 总量太小**：
模型只要学会「照抄多数类」就能拿高准确率（这正是 `train_openi.py` v3.2 加
`majority_baseline` 要防的假绿）。**卡片的核心工作是把选项分布拉开，不是把 29 条复制成 300 条。**

## 二、要做的四件事

### 2.1 扩真实任务量（让日志自然变多）

在 `src/lightprism/runtime/` 的模板集与任务集上**扩充任务**，目标是产出
**≥150 条真实 attempt 日志**（每次 attempt 一条，含重试），全部走真实链路：
真实展开 `.light` → 真实 `light ai check` → 真实运行比对。

- 任务类型要覆盖到能**自然触发**下列路径（不是硬塞标签）：
  - 需要子任务分解的复合任务 → `PLAN=DECOMPOSE`；
  - 需要多次尝试才能过的任务（`retry≥1`）→ `RETRY=YES` 与 `FIX=*`；
  - 局部改动而非整段重写 → `EDIT=FR` / `EDIT=PATCH`；
  - 需要丢弃错误检索结果的场景 → `CTX=DROP`。
- **做不到的选项如实记「未观测 + 原因」**，例如 `SAFE=L1/L2` 需要有人工确认节点，
  零模型系统当前没有；`FIX=ADD_TYPE/RENAME` 需要 repair 动作真的实现那两类编辑。
  **禁止为了凑覆盖去伪造动作**——决策 token 必须来自系统当下真实执行的动作。

### 2.2 把弹性的选项做出真实分歧

`PLAN=DIRECT` 29/29 说明任务全被单模板直接展开。要让 `DECOMPOSE` 出现，
就得让系统面对**真的需要拆分的复合任务**（例：先算再格式化再输出），
并且在实现上真的走子任务路径。同理 `EDIT=PATCH` 要求 repair 真的支持补丁式编辑。

> 允许的实现范围：可以改模板集、任务集、repair 动作、retrieval 策略。
> **不允许**改「决策 token 由什么映射」的映射表来把标签换个名字。

### 2.3 按 test 侧重算覆盖，并保证 test ≥30

- 新增一个「覆盖核算」入口（建议 `scripts/runtime_eval.py` 增子命令或
  `src/lightprism/runtime/coverage.py`），产出 JSON：
  每决策点 × 每选项的 **train/test 条数**，以及 **test 侧**决策样本总数。
- **切分口径**：同一模板/同一源码变体不得跨 train/test（对齐 `--group-split` 的思路，
  `train/test 模板重合` 必须为 0）。
- 判据是 **test 侧** ≥30 条决策样本、**test 侧** 7 个决策点全覆盖；
  train 侧再多也不算数。

### 2.4 补 ERR 类 test 正样本（先定因，再补样）

`reports/ERR样本覆盖.md` 实测：8 类验证码里 7 类不可达，全部回落 `L0000`。
**不要重跑同一个探针指望结果变化**，先做定因：

1. `light` 的 `src/diagnostics/registry.py` 里 `L1001/L1005/L1007/L2001/L2002/L4001/L4002`
   都已登记，但 `light ai check` 实测全回落 `L0000`。查清是**规则未接线**、
   **priority 被兜底规则吃掉**，还是 **check 只跑某一 stage**。
2. 定因结论写进报告，并在**本仓**加回归用例：给每个已登记码至少一条
   「输入片段 → 期望具体码（不是 L0000）」的断言。
3. 修在 `light` 仓的部分**不在本卡 paths，另开卡**（本卡只在 `lightprism` 侧
   记录依赖与阻塞）；若定因确认是 `light` 侧缺陷，本卡按 `blocked` 交，
   写清是哪一条规则、哪一行。
4. 能在 `lightprism` 侧解决的（映射表/样本构造）就地解决，并把
   `data/unified/err_tasks.jsonl` 扩到**每可达码 ≥10 条，且 test 侧至少有 1 条非 PASS**。
