> 背景：T-0428（R30 三项真机验证）收口时发现 `scripts/gate.sh` **本身不绿**：
> PASS 8 / FAIL 7。经核对，7 条 FAIL **无一由该卡引入**（基线上同样 7 条、原因逐条相同）。
> 本卡就是把这条「长期红着的门禁」修绿，别再让每张卡都靠人工判断「是不是新增红」。

## 背景：两个根因，其实是同一件事的两种表现

`gate.sh` 会**自动发现仓库里所有 `go.mod` 并逐个跑**（`scripts/gate.sh:138-143`）：

```sh
MODS="$(cd "$ROOT" && find . -name go.mod -not -path './vendor/*' -exec dirname {} \; ...)"
```

而本仓库有**两个 module**：根 module（`lightmem`）和 `kernel/`（`github.com/lightmem/kernel`）。
根 module 的 `go.mod` 里写着：

```
require github.com/lightmem/kernel v0.0.0
```

但 **既没有 `replace` 指向本地 `kernel/`，`go.sum` 里也没有该模块的条目**（已实测确认）。
于是根 module 的 `go build` / `go vet` / `go test` 都会去网络找 `v0.0.0` 并失败：
`missing go.sum entry for github.com/lightmem/kernel`。

`.github/workflows/ci.yml` **已经绕开了**这个问题（所有 go 命令都 `working-directory: kernel`，
文件头注释也写明了原因），但 `gate.sh` 没有绕，所以本地门禁和 CI 的口径不一致。

## 目标

### 1) 修根 module 的 kernel 依赖（主因）

二选一，**必须在卡里说明选了哪个、为什么**：

- **方案甲（推荐）：给根 `go.mod` 加 `replace` 指向本地**
  ```
  replace github.com/lightmem/kernel => ./kernel
  ```
  理由：这是 monorepo 的标准做法；`v0.0.0` 本来就是个占位版本号，永远不可能从网络拉到。
  加了 replace 后根 module 的 build/vet/test 都能真正跑起来，**这本身就是价值**——
  现在根 module 里的 `eval/` 那批代码（约 12 个文件 import kernel）从来没被 `go test` 真正验证过。
  - 风险：根 module 的 test 一旦真跑起来，**可能暴露出之前被掩盖的失败**。
    这是好事（本来就是技术债），但会让本卡工作量不可控。若如此，**先如实记录**，
    把「修那些测试」拆成后续卡，不要在本卡里硬扛。

- **方案乙：让 `gate.sh` 与 CI 口径一致，跳过根 module**
  在 `MODS` 发现逻辑里排除根 module（或加白名单只跑 `kernel`）。
  理由：CI 已经这么做，本地门禁对齐 CI 即可。
  - 风险：这是**掩盖**而非修复——根 module 的代码将永远不被验证。
  - 若选乙，必须同时加一条**显式的 INFO 行**说明「根 module 未纳入门禁，原因 X」，
    不许静默跳过。

### 2) 修 gofmt

先确认到底是哪个文件、哪一行。**本机无 gofmt，无法确证**，但已定位到高度可疑处：
`kernel/auth_loopback_guard_test.go` 的 `非回环` 切片里，行尾注释的对齐列不一致
（L20/L21/L24/L25 注释在第 21 列，L28 在第 22 列）。gofmt 对同组行尾注释会按 tab 重排。

**修法**：`gofmt -w kernel/auth_loopback_guard_test.go`，然后 `git diff` 看它到底改了什么，
把改动贴进 summary。**不要手改对齐**（手算 tab 宽度几乎必错）。

### 3) 收口标准

本卡完成后，`sh scripts/gate.sh` 必须满足其一：

- **首选**：`FAIL 0`（真正全绿）；
- **次选**：若方案甲暴露出大量既有测试失败，允许 `FAIL > 0` 但**必须在 summary 里逐条列出**
  剩余 FAIL 的原因与后续卡号，并确保 `[1b] gofmt` 与根 module 的 build **至少是绿的**。

无论哪种，都要在 `deploy/README.md` 或 `CONTRIBUTING.md`（择一）写清
**「本地跑门禁前要知道的两个 module 事实」**：谁依赖谁、哪些命令要在 `kernel/` 下跑。
现在这个信息只存在于 `ci.yml` 的注释里，人不会去看。

## 红线

- **不改 kernel 业务代码**、不改任何 `*.go` 的逻辑，只做依赖/格式/脚本层面的修复。
- `go.mod` / `go.sum` 的改动必须最小：只加 `replace`（方案甲）或什么都不加（方案乙）。
  **不许**为了让它编过而删依赖、升级/降级已有依赖、或把 `require` 整个删掉。
- 不许用 `GATE_STRICT_FMT=0` 或调大 `GATE_FMT_MAX` 来「让门禁变绿」——
  那是把红线改成橡皮筋，属于本卡明令禁止的作弊路径。
- 不许改 `gate.sh` 的**判定逻辑**（只在方案乙下允许改 module 发现范围，且需显式 INFO）。
- 不动 FreeBSD 0.88 现网。
