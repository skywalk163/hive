# 0.88 全量不可复现：10 条用例卡在 `--timeout=60` 边界，负载一高就随机红

## 背景

T-0383（R222 M 线收口）在 0.88 上跑了三轮全量，**同一份提交**三次的失败集合都不一样：

| 轮次 | failed | 现场 |
| --- | --- | --- |
| M2 | 21 | `run-20261117-235551-T-0383-M2` |
| M3 | 19 | `run-20261118-003704-T-0383-M3` |
| M4 | 14 | `run-20261118-010730-T-0383-M4` |

M2 与 M3 之间有 10 条来回翻。逐个串行复跑（`-o addopts=`，无 timeout、无并行）**10/10 全绿**：

| 用例 | 单跑耗时 | 红在哪轮 |
| --- | --- | --- |
| `test_duan_run[test_L075.light]` | 4.38s | M2 |
| `test_duan_run[test_L076.light]` | — | M3 |
| `test_a25_泛型外层含嵌套类` | 8.34s | M2 |
| `test_A5_类内0参与模块2参共存` | 4.56s | M2 |
| `test_双腿对拍2参追加一致` | 28.19s | M3 |
| `test_B5_连续两个单行段落体` | 4.37s | M2 |
| `test_B7_多行段落体含嵌套分支不受影响` | — | M3 |
| `test_断言工具_对拍Python` | 14.04s | M2 |
| `test_中文分词_O0对拍` | 7.71s | M2 |
| `test_拼音转换_O0对拍` | — | M3 |

根因不是"单跑 4 秒为什么全量会超 60 秒"这么简单——看全量输出的 slowest 列表：

```
60.71s call     tests/unit/test_原生腿_R11B_中文工具.py::test_中文分词_O0对拍
59.81s call     tests/e2e/test_e2e_chain.py::test_duan_run[test_L076.light]
59.24s call     tests/unit/test_R220_归约与段落体.py::TestB单行段落体::test_B5_...
```

这些用例在 `-n 6` 并行 + 原生腿真编译的场景下本来就跑到 **59–60s**，而仓库 `pyproject.toml`：

```toml
addopts = "--tb=short --durations=15 --ignore=tests/archive --timeout=60 -n 4 --dist=loadscope"
```

`--timeout=60` 正好压在它们头上。跑测期间 0.88 的 `load average ≈ 15`（12 vCPU，有别的 agent 在跑），
再挤一点就超时。

**直接证据**：把 timeout 压到 1s 复现，失败文案与全量里出现的完全同一形状：

```
/usr/local/lib/python3.12/selectors.py:415: Failed: Timeout (>1.0s) from pytest-timeout.
```

## 目标

让 0.88 全量的结论**可复现**：同样的提交、同样的 tag，跑两遍失败集合应当一致。

推荐做法（按优先级）：

1. **给 slow 用例单独放宽 timeout**。pytest-timeout 支持按 marker 覆盖：

   ```toml
   markers = [
       "slow: 慢测试（e2e / 编译大项目 / 长耗时），PR 触发时跳过，main 推送时全量运行",
   ]
   # 在 conftest.py 里用 hook 给 slow 标记的项放大超时，或用 @pytest.mark.timeout(180)
   ```

   已经注册了 `slow` marker（见 `pyproject.toml`），但上面这 10 条**没有标 slow**。
   所以第一步是给它们补 `@pytest.mark.slow`，第二步再谈超时。

2. 或者把全局 `--timeout=60` 提到 `--timeout=120`。副作用：真卡死的用例要多等 60s 才被掐，
   全量最坏情况变长。但如果只放宽到 90–120s，实际影响很小（现在最快 60s 那批只是因为踩线）。

3. **跑测纪律（不改代码也能先做）**：`tools/remote_ci.py` 起全量前检查远端 load，
   超过阈值就在 `[3/4]` 行打警告或排队等待。0.88 只有 12 vCPU，两条线同时跑必然互相挤。

建议 1 + 3 一起做，2 作为兜底。

## 红线

- 不要为了让全量"稳定绿"而直接删掉 `--timeout=60`——没有超时的话，真卡死的用例会把整轮拖到
  `remote_ci.py` 的 `--timeout 5400` 才失败，更难定位。
- 不要用"多跑几遍取交集"当结论（T-0383 就是这么做的，但那只是**绕过**问题，不是修好）。
  判据应当一次可复现。
- 标 `slow` 的用例在 `-m "not slow"` 的 PR 流程里会被跳过，确认这是想要的取舍（现在 main 推送跑全量，OK）。

## 验收

```bash
# 1) 同一提交连跑两轮，失败集合应完全一致
python tools/remote_ci.py --repo . --tag T-xxxx-r1 -- --ignore=tests/dogfood -rf --tb=no
python tools/remote_ci.py --repo . --tag T-xxxx-r2 -- --ignore=tests/dogfood -rf --tb=no
#   期望：failed 列表逐条相同（diff 为空）

# 2) 校验 10 条边界用例在负载下不再随机红
#    （可配合在 0.88 上制造 load，例如同时跑另一轮）

# 3) 全量耗时没有显著恶化
#    基线 ~28–30 分钟（-n 6），放宽后不应超过 35 分钟
```

第 1 条是核心：**可复现性**才是本卡要买的东西。
