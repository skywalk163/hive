> 来源：known_issues.md「缺陷 R13B-TLS」。POSIX（FreeBSD/Linux）专属死锁，Windows Schannel 正常。

## 背景

POSIX 下 HTTPS 握手永远阻塞（直到服务器超时断开 EOF）；Windows Schannel 正常。

- **根因**：`dv_tls_bio_send` 把 mbedTLS 加密产物（ClientHello 等）追加进 `out_pending` 队列但**不直接写 socket**；`dv_tls_bio_recv` 直接调用阻塞 `recv()` 等服务器响应——但 ClientHello 从未上线，服务器不发响应，死锁。
- 反跑证据：移除 bio_recv 中的 flush → POSIX HTTPS 握手立即自锁（阻塞至 EOF）。

## 要做什么

1. **先读 known_issues.md 的 R13B-TLS 条目**，确认根因描述与现状代码是否仍吻合（HEAD 可能已有变动，先 grep `dv_tls_bio_send` / `dv_tls_bio_recv` 定位）。
2. **修法方向**（状态机对齐 Schannel 做法）：bio_send 入队后**触发一次 flush**（把 out_pending 里的字节真写 socket）；bio_recv 改非阻塞/状态机驱动（WANT_READ/WANT_WRITE 透传，喂 `dv_coro_await_io` 不阻塞事件循环）。
   - 这是 C runtime 改动（`src/llvm/runtime_typed.c`），需在 FreeBSD 0.88 编译验证。
3. **最小复现探针**：在 FreeBSD 0.88 用光明代码真起一个 HTTPS 客户端请求（如 `https://example.com`），修前阻塞/超时，修后能拿到响应。
4. **配回归用例**：`tests/unit/test_R13B_TLS_POSIX握手.py`，POSIX 真跑（Windows 上 skip，标注平台）。

## 红线

- ⛔ 不改 Windows Schannel 路径（已正常）。

- ⛔ 不动握手之外的已工作 TLS 逻辑。
- ⛔ C runtime 改动 ⇒ FreeBSD 0.88 编译 + 全量门 new_reds=0。
