# 主控与分发：谁决定，谁执行

> 这份文档回答一个问题：**任务卡是怎么跑到某一台机器的某个 AI 手上的**，
> 以及一台新机器要怎么挂进来。
>
> 适用对象：想让多台机器（Windows 上的 WorkBuddy / Trae / CodeArts、
> FreeBSD/Linux 上的 dsh）自动接活，而不是每次人工 `hive prompt` 再复制粘贴。

---

## 1. 两个角色，别混在一起

| 角色 | 进程 | 职责 | 跑几份 |
|---|---|---|---|
| 主控（脑） | `scripts/master.sh`（= `hive orchestrate`） | 决定**哪张卡给谁**：回收死卡、派活、合入绿卡、快进主线 | 全局一份 |
| worker（手脚） | `scripts/worker.sh`（= `hive work`） | 从自己的收件箱取卡，在独立 worktree 里干活，把结果推回 | 每台机器一份 |

主控**不碰任何代码仓的工作区**，它只写协调仓的卡面和 `inbox/`。
这样主控挂掉不会丢任何人的活，重启后接着派。

```
master ──dispatch──> 协调仓 tasks/T-xxxx.md (owner)
                    协调仓 inbox/<agent>/T-xxxx.md
                              │  git pull（worker 每轮 fetch + reset）
                              ▼
                          worker <agent>
                     claim 租约 → git worktree add
                              │
                     ┌────────┴────────┐
                exec 模式          manual 模式
           prompt 走 stdin     写好 .hive/task.md
           agent 自己改文件     弹 IDE / 剪贴板
                     └────────┬────────┘
                              ▼
                 commit → push task/<tid>
                 verify → 写 results/T-xxxx.json
                              │
                     master land：合入 main + close
```

## 2. 五种接入形态，按「机器上有什么」选

| 形态 | agent 配置 | 那台机器需要 | 人的参与 |
|---|---|---|---|
| **exec（推荐）** | `--mode exec --command "python …/scripts/agent-exec.py"` | 任一 AI 的 headless CLI | 无 |
| **manual + launch** | `--mode manual --dispatchable --launch "<ide> {worktree}"` | 只有 GUI IDE | 在 IDE 里让它干活 |
| **verify** | `--mode verify` | 只要能跑命令 | 无（不调 agent） |
| **MCP 拉** | 不配 worker | IDE 支持 MCP | 无（AI 自己来领） |
| **accept（派单—接单）** | `--mode accept --accept-window-minutes 180` | 一个能定时唤起 AI 的计划任务 | 无（AI 定时来接单） |

**关键判据只有一条**：主控能不能把 prompt 送进那个 AI。
- 有 CLI → `exec`，主控派卡后 AI 自己跑完、自己交结果；
- 只有 GUI → 送不进去，只能把 worktree 和任务卡准备好、把 IDE 弹出来，人点一下；
- 支持 MCP → 反向：AI 自己来拉（见 `docs/MCP接入.md`），主控仍然决定派给谁；
- **只有定时任务、没有常驻 worker / CLI / MCP** → `accept`：主控派单，AI 被定时唤起后自己
  `hive accept` 接单（见 §4.6）。这是「主控发布任务、agent 定时领取」的标准形态。

`exec` 是「主控分配 → AI 立刻完成」最自动的形态；`accept` 是同一个人做派单决策、
但**允许接单方按自己的节奏醒来**的形态。下面这一节讲怎么把任意一台机器变成 `exec`。

## 2.5 `scripts/agent-exec.py`：一处收口所有 CLI 差异

每台机器上的 AI 入口都不一样：

```
Windows + WorkBuddy   codebuddy -p "…" -y --output-format text
Windows + Trae        traecli   -p "…" -y --allowed-tool … --output-format text
Linux/FreeBSD         scripts/dsh-headless --profile headless -
```

如果为每台机器手写一条 `command`，配置会散成一地，换台机器就得重来一遍。
`scripts/agent-exec.py` 把差异收在一处：**所有机器上 `command` 长得完全一样**。

```sh
# 先自检：这台机器能走哪条路
python scripts/agent-exec.py --probe
```

```
  codebuddy    ✓ C:\Users\skywalk\AppData\Roaming\npm\codebuddy.cmd
  traecli      · 未找到
  dsh-exec     · 未找到
结论：可用，将使用 codebuddy（…）
```

探测顺序是 `codebuddy` → `cbc` → `traecli` → `dsh-exec` → `dsh-headless` → `dsh`，
先查 `PATH`，再查脚本同目录（hive 自带的 `dsh-exec` 从不进 `PATH`）。
也可以用 `HIVE_AGENT_CLI=traecli` 强制指定，指定了就**只**认它，探测不到直接失败——
宁可明确失败，也不要「以为在跑 A、其实是 B」。

### 为什么不把 prompt 拼进命令行

这是这个适配器唯一需要解释的设计。Windows 的 cmd 命令行上限是 8191 字符，一张正常任务卡
（含验收命令、上下文、依赖）很容易超；中文还要过 cp936 编码，引号嵌套更容易出事。

所以适配器给 CLI 的永远是一句**固定的短指令**：

> 你是 hive 协同开发集群中的一个 worker。当前目录是一张任务卡的独立 git worktree。
> 请先完整读取 `.hive/task.md`，然后严格按它完成任务。
> 硬约束：只改允许路径 / 不要 git commit、git push / 完成后写 `.hive/summary.md` …

而 `.hive/task.md` 是 worker 早就渲染好放在 worktree 里的，内容与卡面完全一致。
既绕开长度限制，也保证 AI 拿到的不是你手工转述的二手需求。

`dsh` 类 CLI 是整段吃 stdin 的，适配器会把卡面内容直接喂进去（`stdin` 为空时退回读
`.hive/task.md`），不会出现「a task is required」那种看起来像没派任务的假故障。

### 相关环境变量

| 变量 | 作用 |
|---|---|
| `HIVE_AGENT_CLI` | 强制指定 CLI（`codebuddy` / `traecli` / `dsh` / 绝对路径） |
| `HIVE_AGENT_ARGS` | 追加参数，空格分隔，例如 `--model gpt-5` |
| `HIVE_AGENT_MODEL` | 传给 `--model` |

## 3. `dispatchable`：为什么 manual 也能被自动派

2026-11-06 之前 `dispatch` 里有一行：

```python
if mode == "manual":
    blocked.append(f"人工优先（{name} 是 manual 模式）")
    continue
```

当时 16 个 agent 里 15 个是 `manual`，唯一的 `fb88-dsh` 也标了 manual。
结果是 `dispatch --apply` 恒输出「没有可分派的任务」，人只能手工
`hive prompt T-xxxx | clip` 再粘到 IDE 里 —— 这正是「全是手工领取」的由来。

现在改成：**manual 默认仍不派，但 agent 配置里显式写了 `dispatchable: true` 就参与候选**。
语义是「这台机器上有常驻 worker 会在收件箱里接活，派过去有人接」。

> 2026-11-07 新增第四种模式 **`accept`**：它**天然参与派发**，既不需要 `dispatchable`，
> 也不需要 `command` / 常驻 worker —— 那台机器上有定时任务唤起 AI 来接单即可（见 §4.6）。

```sh
# 打开
python3 hive.py agent add --name trae-win --mode manual --dispatchable ...
# 关闭（不传 --dispatchable 不会关掉已开的开关，得显式写 false）
```

重新登记时**不传 `--dispatchable` 视为保持原状** —— 避免脚本里复制粘贴旧命令
把某台机器的自动分派悄悄关掉，而现象只是「它再也不接卡了」。

`agent list` 会在这种 agent 后面标 `[可派]`：

```
trae-win         host=win10    ...  manual  [可派]
doubao-win       host=win10    ...  manual
```

## 4. 接入一台 Windows 机器：一条命令

在那台机器的 hive 仓根执行，普通用户即可，不需要管理员：

```powershell
# 第一步：自检（只报告，不登记、不改任何东西）
powershell -ExecutionPolicy Bypass -File scripts\join-agent.ps1 -Probe

# 第二步：接入。-Mode 默认 auto：脚本自己判断这台机器该走哪条路
powershell -ExecutionPolicy Bypass -File scripts\join-agent.ps1 `
    -Agent trae-win `
    -Repo "hive=G:\dswork\duan-light-merge\hive"
```

`-Mode auto` 的判断：

- 探测到 headless CLI → 切 `exec`，生成 `agent-exec.cmd` 包装并登记。
  **主控派下来的卡，这台机器自己就跑完了，不需要人。**
- 探测不到 → 切 `manual`，在常见安装路径里找 Trae / WorkBuddy 自动填进 `launch`。
  worker 会建好 worktree、弹出 IDE、把 prompt 放进剪贴板，人点一下粘贴。

它做四件事：校验 python/git → 决定模式 → 生成
`%USERPROFILE%\.hive\agents\<agent>\` 下的 `run-worker.cmd` 与 `agent-exec.cmd` →
注册 `hive-worker-<agent>` 计划任务（登录触发）并立刻拉起。

**为什么是计划任务不是服务**：worker 要在**用户会话**里跑 —— manual 模式靠它弹 IDE、
写剪贴板，SYSTEM 账户看不到用户桌面，起来也没用。

### Trae 要装哪个 CLI（容易踩错）

不要把 IDE 自带的 `trae` 当成 CLI。它是 VSCode fork 的窗口管理壳
（`--diff` / `--goto` / `--list-extensions`），**没有任何 headless 执行能力**。
能干活的是独立安装的 **TraeCode CLI**：

```powershell
irm https://trae.cn/trae-cli/install.ps1 | iex
traecli --help
```

常见参数：`-p` 非交互、`-y` 跳过权限确认、`--allowed-tool Bash,Edit,Write`
预先授权、`--json` 结构化输出。注意它目前是「TRAE 企业版旗舰版套餐」才可用；
没有这个套餐，Trae 那台只能走 manual。

WorkBuddy / CodeBuddy 的 CLI 是 `codebuddy`（别名 `cbc`），文档见
<https://www.codebuddy.cn/docs/cli/headless>。`-p` 模式下 **`-y` 是必需的** ——
否则文件读写、命令执行全被权限检查挡下来，AI 会在「要不要允许」那儿空转，
现象是卡住不动而不是报错。

### 4.5 定时领取：不需要 OpenSSH，也不需要常驻 worker

hive 从设计上就是**拉取式**的（`hive.py` 文件头第 11 行）：worker 只要能
`git fetch/push` 协调仓就能领卡、交结果，**主控不需要 SSH 进任何一台 agent 机器**。
`join-agent.ps1` 的常驻 worker 只是拉取的一种实现；换成本地计划任务定时把
worker 叫醒，同样成立，而且更皮实：机器重启、休眠、worker 崩了，下一个周期
自己就回来，不用人去救进程。

`scripts/win-scheduled-work.ps1` 就是这个模式。每轮依次做：

1. `git pull --ff-only` 同步 **hive 工具仓** —— 顺带把「远端机器代码旧」也解决了；
   工作区有本地改动时跳过，不撞车。
2. `hive work --once --no-cluster` 领一轮卡就退出。`--no-cluster` 很关键：
   定时领取走纯 git 通道，不需要拉起 8788 集群服务，也就不会被选主、端口、
   冷启动自检这些事牵连。

```powershell
cd <hive工具仓>\scripts

# 体检（只报告；会顺带指出 agent 未登记 / 未标 dispatchable / manual 无 command）
powershell -ExecutionPolicy Bypass -File .\win-scheduled-work.ps1 -Agent trae-win

# 立刻跑一轮验证（不需要先注册）
powershell -ExecutionPolicy Bypass -File .\win-scheduled-work.ps1 -Agent trae-win -RunNow

# 注册：每 30 分钟一轮；想要一小时就 -Minutes 60
powershell -ExecutionPolicy Bypass -File .\win-scheduled-work.ps1 -Agent trae-win -Minutes 30 -Apply

# 看状态 / 卸载
powershell -ExecutionPolicy Bypass -File .\win-scheduled-work.ps1 -Agent trae-win -Status
powershell -ExecutionPolicy Bypass -File .\win-scheduled-work.ps1 -Agent trae-win -Uninstall
```

`-Minutes` 可选 15 / 30 / 60 / 120。**半小时是默认推荐**：一小时也完全可用，
代价是主控派卡后最坏等 60 分钟才开工。用命名 Mutex 防重入 —— 上一轮没跑完时
新触发直接跳过（卡还在 inbox 里，下一轮会捡到，不会丢）。

**它解决什么、不解决什么**（分清楚才不会配错）：

| 诉求 | 定时领取能解决吗 | 说明 |
|---|---|---|
| 定时把派给自己的卡领走 | ✅ | `work --once`，纯 git，无需任何入站端口 |
| 让 agent 机器跟上 hive 新代码 | ✅ | 每轮开头 `git pull --ff-only` |
| 主控主动远程排障 / 改配置 / 看服务日志 | ❌ | 那才需要 SSH；但可以用「派一张运维卡」让 agent 自己做 |
| 自动把卡**派给**这台机器 | ⚠️ | 传统形态取决于主控 `dispatch` 与 `dispatchable`；**`accept` 模式天然可派**（§4.6） |
| 让卡自动干完（不配 CLI） | ✅ | `accept` 模式下定时任务唤起 AI：`hive accept` → 干活 → `submit`；`manual` 仍需人点，全自动得配 `exec` 的 `command` |

所以 OpenSSH Server **不是必需的**：只有当人确实需要从主控反向登录进那台机器时
才值得开。日常「派卡 → agent 干活 → 交结果」这条链路，定时任务就够了。

### 4.6 `accept`：派单—接单（2026-11-07 新增第四种 agent 模式）

**这是给「主控发布任务 → agent 通过定时任务自己去 hive 接单」用的正式语义。**

#### 为什么必须有它（现场）

2026-11-07 07:38 主控把 9 张卡 `assign` 给三台 Windows agent，07:48–07:50
**watchdog 全部按 `dispatch_unclaimed` 回收**：`state` 从 `assigned` 打回 `ready`、
owner 清空、`dispatch_miss=1`，`dispatched_to` 保留。根因是
`HIVE_DISPATCH_UNCLAIMED_MINUTES` 默认 **10 分钟**（为常驻 worker 设计），
而 Windows 定时任务**每小时才醒一轮** —— 卡在接单方醒来之前就被收走了；
回收后还有 60 分钟推送 TTL 压着不重派，累计 2 次 `dispatch_miss` 就转 `blocked`
锁死。**这与 `mode: manual` 无关，改 mode 也修不了**；`dispatch-mark` 不校验 mode，
`dispatch --apply` 也只是另一条入口。缺的是「派单」和「接单」之间的独立语义
与足够长的等待窗口。

#### 语义与状态流转

```
ready ──assign / dispatch──> assigned 且 dispatched_to=X、inbox/X/T-xxxx.md
                              │  （已派单，未接单；此时看板 STAGE 是「已推送」）
                              │  ← accept 窗口内 watchdog 不回收、不记 dispatch_miss
                              ▼
                    hive accept T-xxxx --agent X
                    校验派单对象 → 抢 claim 租约 → 备 worktree → 写 accepted_at
                              │
                              ▼  干活、写 .hive/summary.md
                    hive submit T-xxxx → result → land
```

- **`accept` 天然参与 `dispatch --apply`**，不需要 `dispatchable: true`；
  也不需要 `command` / `launch` / 常驻 worker。
- **接单窗口**：agent 配置 `accept_window_minutes`（默认 180 分钟，也可用
  `HIVE_ACCEPT_WINDOW_MINUTES` 覆盖），必须 ≥ 定时任务的唤醒周期。
  watchdog 按派单对象查配置，逐卡使用这个窗口，其它模式仍是 10 分钟。
- **超时不等于派发失败**：窗口用尽只把卡退回 `ready`、保留 `dispatched_to` 与
  inbox 便条，**不累加 `dispatch_miss`、不转 `blocked`**；下一轮定时任务照样能接。
- **接单校验**：`hive accept` 只认 `dispatched_to`（或 `owner`）是自己的单，
  不抢无主单、不碰别人的单；`state=ready` 但派单对象仍是自己也允许接
  （正是超时退回后的形态）。MCP 侧有同名工具 `hive_accept`，
  `hive_next` 对 accept agent 只推荐派给它的单。

#### 怎么用

```sh
# 登记（repos / worktrees 别漏：agent add 会重建整份配置）
python3 hive.py --dir . agent add --name trae-win --mode accept \
  --accept-window-minutes 180 --repo hive=G:/dswork/hive \
  --repo light=G:/dswork/light --worktrees C:/Users/skywalk/.hive/wt/trae-win

# 主控派单（store 后端下 assign 只写 store，读 Git 卡面的领取者仍要双写，见 §9）
HIVE_CLAIM_BACKEND=git python3 hive.py --dir . assign T-0260 --agent trae-win
python3 hive.py --dir . assign T-0260 --agent trae-win

# 定时任务里的 AI 接单（完整 prompt 见 docs/子agent定时领取-prompt.md）
python3 hive.py --dir . accept T-0260 --agent trae-win
python3 hive.py --dir . submit  T-0260
```

| | `exec` | `manual` + `dispatchable` | `accept` |
|---|---|---|---|
| 派单后谁接 | 常驻 worker 立刻调 CLI | 常驻 worker 建 worktree 等人 | 定时任务唤起 AI 自己接 |
| 需要 `command` | 必须 | 不必（但 worker 不干活） | 不必 |
| 需要常驻进程 | 是 | 是 | **否** |
| 回收窗口 | 10 分钟 | 10 分钟 | `accept_window_minutes`（默认 180） |
| 派单与接单是否分开 | 否（派过去就跑） | 否 | **是（`accepted_at` 留痕）** |

#### 部署生效边界（必须做，否则新代码不生效）

`orchestrate` / `cluster serve` 是**常驻进程**，加载的是启动那一刻的 `hive.py`。
2026-11-07 13:13 提交 accept 模式后，旧 orchestrate（11-06 05:22 启动，PID 53801）仍在跑，
13:29–13:30 又按 10 分钟窗口把 8 张卡回收了一遍（卡面 `dispatch_miss=1`）。
改完 `hive.py` / `hive_cluster.py` 后必须重启：

```sh
python3 hive.py --dir . cluster restart          # 重启 hived（8788）
scripts/master.sh restart                       # orchestrate 由 master.sh 托管时
ps -eo pid,lstart,args | grep orchestrate       # 核对新进程启动时间
```

重启后 `hive watchdog --json` dry-run 应不再列出派给 accept agent 的卡（候选数 0）。
**未重启前，本节所有窗口语义都只存在于代码里，不生效。**

## 6. 启动主控

在**一台**有 git 写权限的机器上：

```sh
scripts/master.sh start              # 后台常驻，每 60s 一轮
INTERVAL=30 scripts/master.sh start  # 更勤快
scripts/master.sh status
scripts/master.sh stop
```

每一轮 tick 做四件事：

1. `watchdog --apply` 回收过期租约 / 孤儿卡 / 僵尸卡；
2. `dispatch --apply` 把 ready 卡按能力、仓库、负载、paths 冲突、依赖派出去；
3. `land --all --apply` 把 verify 全绿、依赖就绪的 done 卡合入主线并 close；
4. `sync-repos` 把本机代码仓快进到 origin（只快进，不强制）。

**只跑一份**。两个主控同时派卡会把同一张卡派给两个 agent（claim 那层最终只有
一个抢到，但另一个白跑一轮）；`master.sh` 用 PID 文件挡住第二次启动。

**主控必须是集群 leader**。有集群但本机是 follower 时，orchestrate 会打印
`本机 follower，跳过写动作` 并空转 —— 这是防两个节点同时写的保护，不是故障。
单机 / 应急时用 `HIVE_CLUSTER_AUTOSTART=0` 或 `hive cluster status` 确认角色。

---

## 7. manual 卡怎么算「干完了」

旧逻辑只有一条路：人在 worktree 里写 `.hive/summary.md`。GUI agent 干完活忘了写
summary 是常态，于是 worker 一路死等到 `timeout_minutes`（默认 120）才判超时，
**把已经改完的卡判成失败**。

现在三种信号任一成立就收工：

1. `summary.md` 非空 —— 最明确，agent 自己写的自述；
2. `HEAD` 变了 —— agent 自己 commit 过；
3. 工作区有改动 —— 只改了文件没提交（worker 会兜底 commit）。

第 2/3 条只是「可以收工」的判据，**不放松任何质量闸门**：越界检查、verify、
结果闸门照旧全跑，判不过照样 `failed`。
为了防止「改到一半」被误判，改动快照必须连续两次相同（默认间隔 20 秒，
`HIVE_MANUAL_SETTLE_SECONDS` 可调）才认完成。

## 8. 排障：卡住时按这个顺序看

| 现象 | 先查什么 |
|---|---|
| 主控说「没有可分派的任务」 | `agent list` 看有没有 `[可派]`；`dispatch` 的 skip 原因会直接写「人工优先（X 是 manual 模式）」 |
| 派了但没机器接 | 那台机器 `worker.sh status`；`inbox/<agent>/` 有没有新文件；worker 日志 |
| 接了但一直不动 | 日志里 `手动模式：请在 ... 里让 GUI agent 完成` —— 说明在等人。看 IDE 有没有被弹出来（`--launch` 配了没） |
| 干完了却判超时 | 应该是老版本；现在有 settle 检测。若是老版本，先升到含 T-0259 的版本 |
| exec agent 一启动就失败 | `--command` 里那条命令行手动跑一遍，确认它能从 stdin 读 prompt |
| 结果写了但没合入 | 主控的 `land` 只在 leader 上跑；`hive status` 看卡是不是 done 但未 close |
| 同一张卡被派给两台机器 | 有两个主控在跑。`master.sh status` 各机器都查一遍 |

## 9. 和「`hive prompt` + 手工 copy」的关系

那条老路**没有废**，它适合：

- 临时排查一张卡的指令长什么样：`python3 hive.py prompt T-0231`；
- 想手动指定人：`python3 hive.py assign T-0231 --agent trae-win`（assign 不受
  manual 限制，直接就写）；
- 集群彻底不通时的应急。

它只是不该是**日常流程**。日常应该是：**主控派 → worker 接 → agent 自己跑完交活**。
只有那台机器确实没有 headless CLI 时，人才会出现在「在 IDE 里点一下粘贴」这一步 ——
而且那是能力缺口，不是流程设计。
