## 架构总览

### 一张图

```
                        ┌──────────────────────────────────────────────┐
                        │           中心仓（Gitea）＝ 唯一真相          │
                        │                                              │
                        │  tasks/T-xxxx.md      ← 卡面（state/owner/   │
                        │                          paths/verify/...）  │
                        │  claim/<tid> 分支     ← claims/<tid>.json    │
                        │                          （谁持有 + 租约）    │
                        │  res/<tid>   分支     ← results/<tid>.json   │
                        │                          （结果 + verify 码） │
                        │  agents/<name>.json   ← 谁在哪台机器、会什么  │
                        │  inbox/<agent>/<tid>.md ← "该你干了"的便条    │
                        └───────────────┬──────────────────────────────┘
                                        │ git push / fetch（无数据库、无调度中心、无 SSH）
        ┌───────────────────────────────┼───────────────────────────────┐
        │                               │                               │
┌───────┴────────┐            ┌─────────┴────────┐            ┌─────────┴────────┐
│ FreeBSD worker │            │ Win10 worker     │            │ Win10 手工 GUI    │
│ fb88-dsh       │            │ raccoon-win      │            │ workbuddyai-win   │
│ exec 模式      │            │ exec 模式        │            │ manual 模式       │
│ 独立 worktree  │            │ 独立 worktree    │            │ 独立 worktree     │
└───────┬────────┘            └─────────┬────────┘            └─────────┬────────┘
        │                               │                               │
        └───────────────► 代码仓（自举阶段 = 同一个 hive 仓）◄────────────┘
                     task/<tid> 分支 ──► land ──► main
```

四根支柱（多机之所以成立全靠这四条，详述见 [多机并行开发](多机并行开发.md) §1）：

| 支柱 | 机制 | 一句话 |
|---|---|---|
| **中心仓唯一真相** | `tasks/` + `claim/` + `res/` 都在 git 里 | 任何"谁在干什么"都能 `git fetch` 出来，不靠某个进程的内存 |
| **claim 原子锁** | `claim/<tid>` 分支 + 普通 `git push` | 非快进被服务端拒绝 = 抢锁失败，天然互斥，不需要额外锁服务 |
| **worktree 隔离** | 一卡一 worktree、一卡一分支 `task/<tid>` | agent 之间物理上看不到对方未提交的改动 |
| **land 串行合流** | `hive land` 一次合一张，冲突显式暴露 | 最后一步不并发，冲突只报不猜 |

### 三套 git ref，别混

自举阶段协调仓和代码仓是**同一个目录**，但语义上是三套互不相干的引用：

| ref | 装什么 | 谁写 | 生命周期 |
|---|---|---|---|
| `refs/heads/claim/<tid>` | `claims/<tid>.json`（agent、`claimed_at`、`lease_until`、`host`） | worker / `take` / `assign` 抢锁时 | 租约过期或 close 时删除 |
| `refs/heads/res/<tid>` | `results/<tid>.json`（status、每条 verify 的退出码、summary、改动清单） | `submit` / worker 跑完 | close 时归档进 main 的 `results/`，分支删除 |
| `refs/heads/task/<tid>` | 这张卡改出来的代码 | worker 执行完 `git push --force` | land 合入 main 后由 `prune` 清 |

`claim`/`res` 的写法和普通分支不同：`commit_file_to_ref()` 用 `commit-tree` 造一个
「parent=origin/main、只含一个文件」的 commit 再 push，并用临时 `GIT_INDEX_FILE`，
所以**多个 worker 共用同一个 clone 也不会互相踩 index**。`claim` 保持非快进（这就是原子性的来源），
`res` 用 `--force-with-lease`（重跑必须能顶掉上一次结果，否则结果永远落不进去）。

### 一条卡的一生

```
写卡                      dispatch                     worker                       总控
─────────────────────────────────────────────────────────────────────────────────────────────
tasks/T-xxxx.md
  state=ready
        │
        ├─► inbox/<agent>/T-xxxx.md      （便条，不是真相）
        │   state=assigned, owner=<agent>
        │                        │
        │                        ├─► claim/<tid> 抢锁成功，租约开始（lease_minutes，默认 180）
        │                        │        │
        │                        │        ├─► worktree 建好（~/.hive/wt/<agent>/<tid>）
        │                        │        │   state=running
        │                        │        │        │
        │                        │        │        ├─► agent 改代码 → 提交 task/<tid>
        │                        │        │        ├─► 跑 verify（退出码进结果）
        │                        │        │        └─► res/<tid> 写入 results/<tid>.json
        │                        │        │                 │
        │                        │        │                 ├─► hive audit（summary vs 真实 diff）
        │                        │        │                 └─► hive land --apply
        │                        │        │                          │
        │                        │        │                          ├─► 临时 worktree 真 merge
        │                        │        │                          ├─► push main
        │                        │        │                          └─► close：state=done
        │                        │        │                               归档 results/、删 claim/res
        │                        │        │
        │                        └────────┴─► 中途死掉？watchdog 回收 → ready（或熔断成 blocked）
```

状态机（7 个状态，代码里是 `STATES` 常量，改状态必须同步改三个集合）：

| 状态 | 含义 | 谁推进 | dispatch/worker 会碰吗 |
|---|---|---|---|
| `ready` | 可领 | 人写卡 / watchdog 回收 / `unblock` / `retry` | 会派 |
| `assigned` | 已分派，等人或 worker 来 claim | `dispatch --apply` / `take` / `assign` | 会派（算负载） |
| `running` | 正在执行（worker 已 claim） | worker | 算负载，不重派 |
| `needs_review` | 等人看 | 人 / 总控 | **跳过**（HANDOFF） |
| `conflict` | land 撞冲突，必须尽快解 | `land` | **跳过**，`doctor` 按 error 报 |
| `blocked` | 等外部资源，或自动回收额度烧光 | `block` / watchdog 熔断 | **跳过** |
| `done` | 已合入并 close | `close`（land 里自动调） | 终态 |

## dispatch

职责一句话：**在"能干的"和"现在不忙的"之间做匹配，并保证两张在飞的卡不抢同一片文件。**
它只写两样东西：卡面的 `state/owner` 和 `inbox/<agent>/<tid>.md`。

### 决策链（八道闸，按代码顺序）

`hive.py` 的 `Hive.cmd_dispatch()` 对每张 `ready` 且无 owner 的卡（按 `P0<P1<P2<P3` 排序）
依次过闸，任一不过就进 `skipped` 并带上原因：

| # | 闸 | 判据 | 不过时的提示 |
|---|---|---|---|
| 1 | 本次上限 | 已达 `--limit` | `超出本次 --limit N` |
| 2 | 仓库 | 现阶段**只派 `repo: hive`** | `非 hive 仓任务暂不派发` |
| 3 | 依赖 | `depends_on` 的卡结果都是 `done` | `依赖未就绪: T-xxxx` |
| 4 | 能力 | 卡面 `needs` ⊆ agent 的 `abilities ∪ capabilities` | `能力缺失（xxx 缺 yyy）` |
| 5 | 仓库登记 | `repo` 在该 agent 的 `repos` 里 | `仓不匹配（未登记 hive）` |
| 6 | 模式 | `manual` 一律人工优先；`verify` 模式不接带 `paths` 的卡 | `人工优先（是 manual 模式）` |
| 7 | 负载 | 该 agent 在飞卡数 < `max_concurrency`（默认 1） | `负载已满（2/1）` |
| 8 | paths 冲突 | 与**在飞卡**的 paths 重叠数 < `HIVE_MAX_PER_REPO`（默认 1） | `paths 冲突：与在飞的 T-xxxx 抢同一片文件` |

两个容易误解的点：

- **并发粒度是 paths，不是 repo。** 同一仓里改互不相干目录的卡可以同时跑；否则自举阶段
  （hive 是唯一在开发的仓）等于全串行。细节与目录前缀匹配规则见 [锁与冲突模型](锁与冲突模型.md)。
- **"负载"包含已分派但还没 claim 的卡**（`_load_counts`），否则同一台机器会被塞爆。
  `paths` 冲突检测同理会把本次刚排进 plan 的卡也算进 `occupied`。

匹配到多个候选时按 `(当前负载, 是否卡面指定的 agent, 名字)` 排序取第一个 —— 也就是**先摊平负载**。

### dry-run 与 --apply

```sh
python hive.py dispatch                 # dry-run：打印每张卡「派给谁 / 为什么不派」
python hive.py dispatch --apply         # 真写：改卡面 + 写 inbox + 一次 commit 推上去
python hive.py dispatch --apply --host win10    # 多机时最常用
python hive.py dispatch --apply --agent fb88-dsh
python hive.py dispatch --json          # 给脚本/总控用
```

`--dry-run` 优先级高于 `--apply`（同时给也不会写）。**日常先 dry-run 再 apply**：
dry-run 的 `skip` 行就是最好的体检报告，能直接看出是卡写得不对还是机器没登记。
命令细节见 [多机并行开发](多机并行开发.md) §4.2。

### 与 worker 的边界

- dispatch 只决定"派给谁"，**不启动任何进程**；真正干活的是那台机器上的 worker（§3）。
- 分派后卡是 `assigned`，如果那台机器的 worker 没在跑，卡会一直躺着 → 见 §6 `orphan_assigned` 和 §7 排障表。
- 手工路径（`take` / MCP `hive_claim`）与 dispatch 写的是同一套字段，所以两条路可以混用。

## worker

worker 是"那台机器上的常驻执行者"，`hive work --agent <name>` 启动。它只认 `inbox/<自己>/`
里的便条，也只碰自己能 claim 的卡。

### 三种模式（`agents/<name>.json` 的 `mode`）

| 模式 | 谁干活 | 适合 | 关键行为 |
|---|---|---|---|
| `exec` | 命令行 LLM（`command` 字段） | FreeBSD / 有 CLI agent 的机器 | 全自动：轮询 → claim → 建 worktree → 调 LLM → verify → push 结果 |
| `manual` | 人 + GUI agent（小浣熊 / WorkBuddy） | 只有聊天窗口的机器 | worker 只备好 worktree 并打印提示（Windows 还会把 prompt 复制到剪贴板），等人写 `summary.md`；也可完全不靠 worker，人 `take` + agent 走 MCP |
| `verify` | 无 agent | 只做验收的机器 | 检出 `verify/<tid>` 分支（只读，不产出代码分支），只跑 verify |

`exec` 模式必须配 `command`，否则启动即报错；`verify` 模式要求卡面至少有一条 `verify`。

### 单卡执行链路

```
loop（每 interval 秒）                       ← hive.py Worker.loop()
  └─ sync_main()                            ← 对齐 main；脏且落后就报错，绝不裸 reset
  └─ pending()                              ← 扫 inbox，过滤：已完成 / 别人持有 / 依赖未就绪 / handoff 状态
      └─ claim(tid)                         ← 抢 claim/<tid>（§4）
          └─ run_task(tid)
              ├─ fetch + 清旧 worktree
              ├─ git worktree add -B task/<tid>   （verify 模式用 verify/<tid>）
              │    续跑：卡面 fresh=false 且远端已有 task/<tid> 时，base 取它，而不是 main
              ├─ 写 <wt>/.hive/task.md（含硬性规则）与 .hive/summary.md 位置
              ├─ 起心跳（lease_heartbeat）→ 按模式执行（LLM / 等人 / 只跑 verify）
              ├─ 越界检查：changed_files vs 卡面 paths（默认只告警，严格模式判失败）
              ├─ commit + push --force 到 task/<tid>
              ├─ 跑 verify，逐条记退出码
              └─ 写 res/<tid> 的结果（status=done/failed + summary + 改动清单）
```

几个必须知道的点：

- **`.hive/` 不进 git**：worker 会往 worktree 的 `info/exclude` 里补 `.hive/`，`summary.md`
  和 `progress.md` 因此不污染 diff。
- **日志按卡分文件**：`~/.hive/agents/<agent>/logs/<tid>.log`，一张卡的执行输出不会串到别的卡。
- **超时是硬杀**：卡面 `timeout_minutes`（缺省 60；manual 等人时缺省 120），`--keep` 可保留
  worktree 供事后排查。
- **`sync_main()` 不是裸 `reset --hard`**：worker 常跑在主工作区上，裸 reset 会静默抹掉人未提交
  的改动（T-0129 的教训）。落后且脏时它会直接报错 —— 报错是设计，不是故障。

### 内部并发（现状 + 规划）

现状：**一个 worker 一次只跑一张卡**。`max_concurrency` 目前只作用于分派侧（§2 第 7 道闸），
worker 自己仍是串行的，单机吞吐上限为 1。

规划：T-0161 出设计（`docs/design-worker-parallel.md`，线程池 + 每任务一条心跳 + 上限取
`max_concurrency`）、T-0162 实现。落地后 `max_concurrency` 的语义会从"分派侧上限"收敛为
"worker 自身上限"，dispatch 与 worker 的职责边界需要重新划一次。
**在那之前别指望单机跑并发**，要提速就加机器或加 agent。

## claim 与租约

### 原子性从哪来

`claim/<tid>` 是一条普通分支，抢锁就是一次**普通** `git push`：

```
两个 agent 同时 push refs/heads/claim/T-0123
   ├─ A 成功（远端没有这条 ref，快进成立）
   └─ B 被服务端拒绝（非快进）→ 抢锁失败
```

没有 `--force`，没有额外锁服务，**"非快进被拒"就是锁**。push 的内容是
`claims/<tid>.json`：`{task, agent, claimed_at, lease_until, host}`。

### 三个入口，一条铁律

| 入口 | 写什么 | 适用 |
|---|---|---|
| `dispatch --apply` / `hive assign` | 卡面 `assigned+owner` + `inbox`（**不抢锁**） | 分派给 exec worker，锁由 worker 自己去抢 |
| `hive take <tid> --agent X` | 先抢锁，成功后才 `assign` + 建 worktree | manual agent / 贴 prompt 路径 |
| MCP `hive_claim` | 同 `take`（先抢锁后 assign） | GUI agent 自助闭环 |
| `hive claim <tid> --agent X` | **只抢锁，不写 owner** | 几乎不该直接用，见下 |

铁律：**先抢锁，抢到才 assign。** 旧顺序（先 assign 再 claim）在抢锁失败时会留下
「owner=A、租约却在 B 手上」的半 assigned 状态，之后 submit 必然报错。

这条铁律踩过三次，是本文最值得记住的历史：

- T-0146：给抢锁失败加了**带抖动的指数退避**（`HIVE_CLAIM_BACKOFF_BASE/MAX/JITTER`、
  `HIVE_CLAIM_MAX_RETRIES`，默认 0.5s/8s/0.5/3 次）。重试次数有上限、每次 push 还有
  `HIVE_NET_TIMEOUT`（默认 120s）兜底，所以最坏耗时是有界的，不会退避到天荒地老；
  能确认"已被别人持有"时**不重试**，直接报持有者。
- T-0147：MCP 的 `hive_claim` 改成先抢锁后 assign，与 CLI `take` 对齐。
- T-0160：实测踩到 CLI `hive claim` 只抢锁不写 owner，`submit` 报「没有 owner」。
  现在 CLI 会明确提示改用 `take`，但**别用 `claim` 起步**这条没变。

### 租约与心跳

- 租约时长取卡面 `lease_minutes`（缺省 180），写进 claim 的 `lease_until`。
- worker 执行期间起一条守护线程，间隔 `max(5, lease_minutes // 3) * 60` 秒把 `lease_until`
  往前推（`refreshed_at` 记录刷新时间）。**活着的 worker 会自己续租**，所以
  「租约过期」可以放心判成「人/进程真的死了」，不会误杀长任务。
- 手工路径（`take` 之后自己慢慢干）**没有心跳**：CLI 没有续租命令，只有 MCP 的
  `hive_extend_lease`；不挂 MCP 的话就得赶在租约到期前 `submit`，否则会被 `watchdog` 判 `stale` 回收。
- 续租是 best-effort：刷新失败只写日志，不打断任务。

## land 与合流

### 合入条件（四道，任一不过就 `blocked` 并列出原因）

1. 有结果，且结果 `status == done`；
2. 结果里**每条** verify 退出码都是 0；
3. 卡还没 close（`state != done`）；
4. `depends_on` 的卡全部已 close。

### 它到底做了什么

```
hive land T-xxxx            # 预演：真做一次 merge，然后拆掉
hive land T-xxxx --apply    # 真合：推 main + close
hive land --all --apply     # 批量：把当前所有满足条件的卡逐张合（`landable()` 按任务号排序）
hive land T-xxxx --json
```

1. `code_repo()` 解析代码仓路径（**优先取本机 host 匹配且真实存在的那个**，多机最容易踩的点，
   见 [多机并行开发](多机并行开发.md) §2）；
2. 在临时 worktree `~/.hive/land/<tid>` 里合并（用完就拆，不碰主 checkout，不用 clone）；
3. 先试 `merge --ff-only`，不行再 `merge --no-ff`；merge 命令显式带 `-c user.name/email`，
   不依赖机器有没有配 git 身份；
4. 冲突 → 卡置 `conflict` 并列出冲突文件；非冲突失败 → `failed` 并把 git 原话带出来；
5. 只有 `--apply` 才 `push <head>:refs/heads/main`，然后调 `close`（归档结果、删 claim/res 分支）。

**预演不是猜的**：它真的把 merge 跑了一遍，所以报冲突就是真冲突。

### 输出怎么读

| status | 含义 | 你该做什么 |
|---|---|---|
| `would-merge` | 预演通过 | 加 `--apply` |
| `landed` | 已合入并 close | 无 |
| `conflict` | 真冲突，看 `conflicts` 字段 | **不手工在 main 上解**，按 §5 规矩回给 owner 开新卡 |
| `failed` | 不是文件冲突（身份缺失、目标被锁、push 超时等） | 看 `problems` 原文 |
| `blocked` | 不满足四道条件 | 看 `problems`，多半是结果没 done 或依赖没 close |
| `merged-not-closed` | 代码已进 main，**只是关卡失败**（协调仓有未提交改动等） | 处理干净后跑 `hive close <tid>`，别重跑 land |

三条红线：**冲突一律不自动解、不 force push、失败的卡原样留着等人。** `--all` 是逐张尝试，
某张撞冲突不会中止整批（后面的卡若依赖它，会因「依赖未 close」被 `blocked`，等于自然停下）。

> 口径差异（本文核对 `hive.py` `cmd_land()` 的结果）：`操作手册` §5.1 写「`--all` 遇到冲突就
> **停下**」，现行代码是逐张尝试、不 `break`。以代码为准；两处描述待统一。

命令与审计细节见 [多机并行开发](多机并行开发.md) §4.4 与 [操作手册](操作手册.md) §5.1–5.3。

合流前务必先跑 `hive audit <tid>`：它比对"agent 说做了什么"和"diff 里真有什么"，
`paths` 越界、verify 恒过、summary 里出现「没能跑 / 无法验证 / 未测试」这类口供，都会在这里被点名。

## watchdog 与 gc

两者常被混为一谈，其实**分工完全不同**：

| | `hive gc` | `hive watchdog` |
|---|---|---|
| 动什么 | 只删**过期的 claim 分支** | 改**卡面状态**（退回 ready 或转 blocked） |
| 判龄依据 | `claimed_at`（领取时刻） | `lease_until`（心跳续期后的到期时刻） |
| 默认阈值 | `--minutes 180` | `--minutes 0`（只看是否已过期）、`--orphan-grace 30` |
| 什么时候用 | 手工清理残留租约 | 常驻（`orchestrate` 每轮都跑） |

### watchdog 的五种判定

都以「卡还在 in-flight（assigned/running）且没有结果」为前提：

| 判定 | 现象 | 处理 |
|---|---|---|
| `orphan_running` | `running` 但 claim 分支没了（崩溃 / 被 gc 清掉） | 回收 |
| `orphan_assigned` | `assigned` 但一直没人来 claim，且分派时间早于 `now - orphan_grace` | 回收（grace 内的新卡不碰，留给 worker） |
| `zombie` | claim 的 agent 没在 `agents/` 登记 | 回收 |
| `stale` | `lease_until` 已过期（活着的 worker 有心跳，不会触发） | 回收 |
| `land_lag` | 已经有结果却还停在 in-flight | **只提示不回收**，那是 land 的活 |

`orphan_assigned` 的分派时间从 `inbox/<owner>/<tid>.md` 里读 `assigned_at` —— 所以
**别手工删 inbox 便条**，删了 watchdog 就失去判据。

### 重试熔断

回收 = 卡退回 `ready` + 清 owner + `retries+1` + 删归档结果 + 在卡尾留一条备注。
一张注定失败的卡会「判死 → 重派 → 再判死」，常驻的 `orchestrate` 会 7×24 烧 agent 时间
（exec 还是真花钱的 LLM 调用）。所以：

- 额度 = 卡面 `max_retries`（默认 **3**，`0` = 一次都不许自动重派）；
- 额度用尽后**不再退回 ready，改判 `blocked`**，`action` 从 `reclaim` 变成 `block`；
- `blocked` 被 dispatch / worker / orchestrate 全部跳过，等于自动退出流水线；
- 人工 `hive retry` **不受此限**（人在明确要求重跑），但会提醒你额度已超。

### block 还是 abort

| | `hive block` | `hive abort` |
|---|---|---|
| 适用 | 等外部资源（真机没装好、依赖卡没完成） | 这活我干不了 / 不该我干 |
| 卡的归宿 | `blocked`，不重派，直到 `unblock` | 退回 `ready`，别人立刻能接 |
| 会不会触发熔断 | 不会（不是自动回收） | 不会 |

判据一句话：**"不是这活的问题，是条件还没到" → block；"这活我干不了" → abort。**
两者都释放租约。`blocked` 会在 `hive doctor` 里点名，不会被静默遗忘。
详见 [AGENT快速上手](AGENT快速上手.md) §8。

### 总控进程：把它们串起来

`hive orchestrate` 每轮固定四步（任一阶段抛错都 catch 住继续下一轮）：
`watchdog --apply` → `dispatch --apply` → `land --all --apply` → `doctor`。
它只负责"脑"，worker 仍是各机器独立进程，两者解耦；manual agent 的卡它不碰。

## 排障表

先跑这三条拿事实，再查表：

```sh
python hive.py status          # 谁在跑什么（一屏全览）
python hive.py doctor          # 卡面/租约/结果/agent 配置的体检
python hive.py dispatch        # dry-run，skip 行就是"为什么没派"
```

| 现象 | 原因 | 处理 |
|---|---|---|
| **`dispatch` 不派某张卡** | ① `repo` 不是 `hive`（现阶段只派 hive 仓）② `needs` 有 agent 不会的能力 ③ 依赖没 `done` ④ 目标 agent 是 `manual`（人工优先）⑤ 负载满 ⑥ 与在飞卡 `paths` 冲突 | 看 dry-run 的 `skip` 原因逐条对；能力不足就 `agent add` 补 `--abilities`，冲突就拆细 `paths` 或加 `depends_on` |
| **`dispatch --host X` 一个都不派** | agent 没写 `host` 或写错（大小写/机器名不一致） | `hive agent list` 看 host；`agent_host()` 会小写化，别写成 `Win10-Office` |
| **`land` 报「本地代码仓不可用: G:/...」** | 拿到了**别的机器**的 `repos` 路径 | 已修（`1dd373b`，按 host 优先取本机存在的路径）；确认本机 agent 的 `repos` 路径真实存在 |
| **卡一直 `assigned` 没人干** | 那台机器没跑 worker / worker 挂了 / 机器关机 | 看 `ps` 与 `~/.hive/agents/<agent>/logs/`；确认后 `hive watchdog --apply` 回收，或 `hive retry <tid> --agent 别的agent` |
| **`claimable: []` / 「现在没有我能接的卡」** | ① 真没卡 ② 能力不匹配 ③ 已被别人领走 | 依次 `hive_list_tasks` → `hive_stats` → `hive_doctor`；别一上来就以为坏了 |
| **`T-xxx 已被 yyy 领取，抢不到`** | 并发抢锁输了（非快进被拒） | 换一张卡，或等 yyy 交；退避已内置（T-0146），不用手抖着重试 |
| **`submit` 报「没有 owner」** | 用了 CLI `hive claim`（只抢锁不写 owner） | 改用 `hive take <tid> --agent X`；或先 `hive assign` 再 submit |
| **验收恒过（verify 永远 0）** | verify 命令本身有问题：空命令、`true`、只 echo、或命令没 `import` 就 `sys.exit` | 先手动跑一遍，**确认它该红的时候会红**；`hive audit` 会点名弱 verify |
| **verify 红了但代码看起来对** | 验收命令自己写错了（`lessons` 第一条就是这个） | 手跑命令区分「代码错」还是「命令错」；命令错找总控改卡 |
| **两台机器同时改同一文件** | `paths` 没写或写得太粗（写 `docs/` 就等于占整个目录） | 拆细 `paths`；或用文件级 `locks`（规划中，见 [锁与冲突模型](锁与冲突模型.md)）；或加 `depends_on` 串行 |
| **land 报 `conflict`** | 两张卡改到同一片文件，分支隔离挡不住合流冲突 | 不手工在 main 上解；把 `conflicts` 清单回给 owner 开新卡重做 |
| **land 报 `merged-not-closed`** | 代码已进 main，但 `close` 被协调仓未提交改动拦住 | 处理干净后 `hive close <tid>`，**不要重跑 land** |
| **`paths 越界`** | 改了卡面声明外的文件（自举阶段代码仓=协调仓，很容易顺手改到 `tasks/`） | 回退越界改动；确需改动就找总控改卡面 `paths` |
| **中心仓不可达** | 网络 / Gitea 挂了 | 修网络；worker 每轮会重试，长任务靠心跳续租不会被误判死。`HIVE_NET_TIMEOUT`（默认 120s）保证不会无限挂起 |
| **`unable to read sha1 file`** | 服务端自动 gc 与并发 `fetch` 撞了 | 重试一次；夜间空闲时手工 `hive gc`，见 [操作手册](操作手册.md) §8 |
| **长任务跑到一半被回收** | `hive gc` 按 `claimed_at` 判龄、**不看心跳**；默认 180 分钟一刀切 | 长任务别用默认阈值：`hive gc --minutes 1440`，或把卡面 `lease_minutes` 调大（心跳间隔随之变长） |
| **卡变 `blocked` 且写着"回收额度用尽"** | 自动回收达 `max_retries`（默认 3），熔断 | 确认根因后 `hive retry <tid>`，或调大卡面 `max_retries` |
| **`worktree` 已存在 / 「已经检出到」** | 上次异常退出留下残留 | `git -C <代码仓> worktree remove --force <路径>` 后 `git worktree prune` |
| **MCP 读到的还是旧卡** | `--dir` 写在 `mcp` 前面被静默忽略，回退到默认 clone | 写成 `hive.py mcp --agent X --dir <仓>`，看启动行 `dir=` 确认 |
| **MCP 一启动就把我的改动抹了** | MCP 每次调用都 `fetch + reset --hard`（有意保留），且 `--dir` 指向了主工作区 | 用默认独占 clone `~/.hive/clones/mcp-<agent>`，别指到正在改的仓 |
| **`tools/list` 里没有 `hive_block`** | 客户端连的是旧 clone（T-0135 修过 schema 漏括号） | 重启 MCP server / 更新 clone |

排障的共同套路：**先把"事实"和"说法"分开**。事实只有三样 —— 卡面（`tasks/`）、租约（`claim/`）、
结果（`res/`）；其它（summary、日志、聊天记录）都只是说法。`hive status` / `doctor` / `dispatch --dry-run`
是拿事实最便宜的三条命令。

## 一页自检（新人接手的第一个小时）

```sh
# 1. 我在哪、我是谁、我能领什么
python hive.py doctor
python hive.py agent list

# 2. 总线现在什么状态
python hive.py status
python hive.py stats

# 3. 有卡可派吗？为什么不派？（dry-run，不改任何东西）
python hive.py dispatch

# 4. 有死卡吗？（dry-run，不改任何东西）
python hive.py watchdog

# 5. 有该合没合的卡吗？
python hive.py audit --all

# 6. 真要动手时
python hive.py dispatch --apply --limit 2
```

六条命令跑完，链路图里哪一环断了就一目了然：`doctor` 管配置、`status` 管状态、
`dispatch` 管入口、`watchdog` 管出口、`audit`/`land` 管合流。
