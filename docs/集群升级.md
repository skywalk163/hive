# 集群升级：主控发布，子节点检索后升级

> 2026-11-11 起，hive 自带集群升级：主控把当前版本发布到协调仓，子节点检索到新版本后
> 一键升级（默认听从主控）。不新增任何服务，仍然「git 即通道」。

## 一、版本号规范

- 格式 **`MAJOR.MINOR.PATCH`**，其中 **PATCH 固定两位**：`0.16.00`、`0.16.01`、`0.17.10`。
- 比较一律按**数值三元组**（`parse_version` / `compare_versions`），不做字符串比较——
  否则 `"0.16.10" < "0.16.9"` 会判错。
- 真源仍是 `hive.py` 的 `VERSION`，`pyproject.toml` 必须与它一致
  （`tests/test_version_consistency.py` 守着）。
- 升级完成后**当前进程的 VERSION 还是旧值**，所以 `upgrade` 一律从
  `hive.py` 文件里读版本（`version_from_file`），不用内存常量。

## 二、它是怎么工作的

发布信息写在协调仓 `main` 根目录的 `release.json`：

```json
{
  "version": "0.16.00",
  "commit": "<发布前那份代码的 commit>",
  "published_at": "2026-11-11T13:00:00+08:00",
  "published_by": "fb98",
  "notes": "集群升级功能"
}
```

- 主控 `upgrade publish` → 写 `release.json` 并 push 到 `origin/main`，顺带广播
  `upgrade.published` 集群事件。
- 子节点 `upgrade check` → `git fetch` 后读 `origin/main:release.json`，和本地
  `hive.py` 的 `VERSION` 比。
- 子节点 `upgrade apply` → **只做 `git merge --ff-only origin/main`**，不做变基、
  不强推；成功后把回滚点写进 `~/.hive/upgrade/last.json`。

「可升级」的判定：远端版本更高，**或** 版本相同但本地 HEAD 落后（同版本热修复）。

## 三、命令

```sh
# 主控：发布（要求本地 HEAD == origin/main，先把代码推上去）
hive upgrade publish --notes "本批：集群升级 + 时间预算"
hive upgrade publish --json

# 任意节点：看本地 / 主控版本、是否可升级
hive upgrade status
hive upgrade check            # 同 status，额外提示本地是否落后 origin/main
hive upgrade check --json     # 给脚本 / 看板用

# 子节点：升级（默认策略 follow，直接升）
hive upgrade apply
hive upgrade apply --dry-run  # 只预演，不动 HEAD
hive upgrade apply --yes      # 策略是 manual 时确认

# 主控：一键节点升级（把当前发布版本下发到每台落后节点）
hive upgrade rollout --dry-run            # 预演：只看会动谁
hive upgrade rollout                      # 下发（只换代码）
hive upgrade rollout --restart            # 下发并让各节点自动重启 hived
hive upgrade rollout --node fb98 --node win10   # 只动指定节点
```

### 一键节点升级（0.16.02）

主控把 `/api/cluster/upgrade` 逐台下发到节点表里**版本落后且在线**的机器，
每台的落地端就是 `Cluster.handle_upgrade_trigger` → 与 `hive upgrade apply`
**完全同一套实现**（脏工作区 / 非快进 / policy 三道闸门一个不少）。

- **只动落后的**：版本一致或离线的节点跳过，且不算失败。
- **只有主控能发起**：落地端会核对发起方是不是本机当前认可的主控，否则 403
  —— 否则任何集群成员都能远程改写别人的代码仓。
- **`--restart`**：升级只换代码，进程还跑着旧代码，集群面板的「版本」列不会
  变，人就会以为「点了没反应」。加这个开关会让节点在响应发出后安排一次
  `cluster restart`（独立会话的 helper，延迟 3 秒，避免把自己杀在写响应途中的时机）。
- **看板**：顶栏「一键节点升级」按钮（仅 controller 可见），默认带自动重启。

### 版本列为什么可能一直显示 `1.0`

节点自述的 `version` 取自**该进程启动那一刻** `hive.py` 的 `VERSION`。跑着
2026-11-10 之前代码的进程（`CLUSTER_VERSION` 当时还是写死的 `1.0`）不会因为
升级了代码就变 —— 它对「该重启了」这件事说得没错，只是**老进程本身**报不出
真实版本。升级并重启后，这一列才会显示实际版本。

## 四、升级策略（默认听从主控）

读取顺序：环境变量 `HIVE_UPGRADE_POLICY` → `~/.hive/cluster/config.json` 的
`upgrade_policy` → 默认 `follow`。

| 策略 | 行为 |
|---|---|
| `follow`（默认） | 检索到新版本后 `apply` 直接执行 —— 听从主控 |
| `manual` | `apply` 必须带 `--yes`（看板上会弹确认框） |
| `never` | 拒绝升级（本机想钉在某个版本时用） |

```json
// ~/.hive/cluster/config.json
{ "upgrade_policy": "manual" }
```

## 五、看板

顶栏版本条（`v0.16.00`）右侧：

- **检查升级**：向主控检索；有新版本时提示「发现新版本 vX」。
- **升级到 vX**：只在可升级时出现，点击二次确认后执行（等价 `apply --yes`）。
- **发布升级**：只在 **controller 角色**（或本机回环免鉴权）时出现，
  点击后可填一句变更说明，等价 `publish --notes`。

后端接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/upgrade` | 本地/主控版本、是否可升级、`can_publish`（只读免鉴权） |
| POST | `/api/upgrade` | `{action: "check"\|"apply"\|"publish", yes?, notes?}`；需写权限，`publish` 另需 controller |

升级动作会写审计日志（`dashboard/audit.log`），超时 300 秒。

### 集群页的「版本」列

「集群」面板的节点表里有一列**版本**，它来自节点自述的 `version` 字段：

- 取值是**该节点进程启动那一刻** `hive.py` 里的 `VERSION`（`hive_cluster.py`
  的 `CLUSTER_VERSION` 由 `_detect_hive_version()` 读文件得出）。
- 所以它跟顶栏版本条是**同一口径**，不再是以前写死的 `1.0`。
- 升级完成后进程没重启的节点，这一列仍显示**旧版本**——这不是 bug，而是提示：
  代码换了、跑的还是旧进程，**该重启了**。重启 hived / 看板后这一列才会变成新版本。

判断「集群里谁还没升级」直接看这一列与主控版本是否一致即可。

## 六、安全边界

1. **脏工作区拒绝**：协调仓有已跟踪文件改动就不升级，避免 `merge` 覆盖手头改动。
   未跟踪文件不拦（不会被 merge 碰到）。
2. **只快进**：`--ff-only`，非快进直接失败，绝不 `reset --hard` / 强推。
3. **可回滚**：`~/.hive/upgrade/last.json` 记录 `from_commit` / `to_commit` /
   `from_version` / `to_version`，回退就是 `git reset --hard <from_commit>`。
4. **发布前校验**：`publish` 要求本地 HEAD == `origin/main`，避免发布一个别人
   拿不到的提交；版本格式非法直接报错。
5. **不自动重启**：升级只换代码，`hived` / 看板进程仍跑旧代码，需要重启后生效
   （刻意不自动杀进程，避免打断正在跑的任务）。

## 七、验证

`tests/test_upgrade.py` 12 条：版本解析/比较/非法格式、当前版本两位小数、
发布写入与可见性、未推送 HEAD 拒绝发布、check → apply 全链路、dry-run 不动 HEAD、
脏工作区拒绝、`never` / `manual` 策略、默认策略是 follow、看板接口接线。

真实链路演练（测试里用 bare 仓模拟）：

```
hive1（主控）: VERSION 0.15.00 → 0.16.00 → upgrade publish
hive2（子节点）: reset 到 0.15.00 → upgrade check（可升级）→ upgrade apply（ff 到主控 HEAD）
```

## 八、已知边界

- 升级的是**协调仓里的 hive 代码**（`hive.py` 及其兄弟模块）。各节点自己的
  代码仓（light 等）不在升级范围内，仍由 `hive land` 管。
- 不做版本降级：只有远端更高（或同版本但有新提交）才会升级。
- 集群事件只是加速通知，真正的真相仍是 `origin/main:release.json`——集群没起也能升级。
