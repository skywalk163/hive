# 租约与摄入须知

> 2026-11-20 立（T-0423）。起因：卡面写着 `lease_minutes: 300`，首领却拿到
> **10 分钟**租约，十分钟后被看板判成「跑飞」，而 leader 侧那张卡其实一切正常。
> 这份文档给的是「租约到底谁说了算」「怎么查」「怎么不踩」的操作口径。

---

## 一、一句话结论

**store 后端的租约时长以 Git 卡面的 `lease_minutes` 为准；卡面确实没写才退回
`STORE_LEASE_MINUTES = 10`。** 卡面写了却拿到 10 分钟，说明首领那一刻读到的卡面
**不是最新那一版**，不是 leader 算错。

---

## 二、两个后端，两种真相源

| 后端 | claim 锁存在哪 | 租约时长取自 | 缺省值 |
|---|---|---|---|
| `claim_backend=git` | `claim/<tid>` 分支 | 卡面 `lease_minutes` | 180 分钟 |
| `claim_backend=store` | leader 的 SQLite `claims` 表 | 卡面 `lease_minutes` | 10 分钟 |

store 后端的取值顺序（`hive.store_lease_minutes_for`）：

1. 本机工作区 `tasks/<tid>.md` 里的 `lease_minutes`；
2. 本机卡面没写 → **回读 `origin/main:tasks/<tid>.md`** 再取一次；
3. 两处都没写 → `STORE_LEASE_MINUTES`（10 分钟）兜底。

> store 的 `tasks` 表**没有** `lease_minutes` 列（只有 `id/state/owner/retries/
> payload_json/def_hash/updated`），`store/claim` 的时长也不从表里取 —— 它由
> follower 随请求带上来的 `lease_minutes` 决定（`hive_cluster._store_op_for`：
> `int(body.get("lease_minutes") or 10)`），leader 只负责按这个数写
> `claims.lease_until`。所以「store 里缺这个字段」不可能是 10 分钟的原因，真正
> 缺字段的是**首领本机那份 Git 卡面**。

---

## 三、为什么「卡面写了 300」还会拿到 10（T-0410 现场）

修复前的三组取证（隔离 db + 临时 git 仓，不碰线上 0.88）：

| 局面 | 本地卡面 | origin/main | 拿到的租约 |
|---|---|---|---|
| A | `lease_minutes: 300` | 同左 | 300 分钟 ✅ |
| B | **没有**该字段（旧版） | `lease_minutes: 300` | **10 分钟** ❌ |
| C | 没有该字段 | 没有该字段 | 10 分钟 ✅（兜底生效） |

B 就是现场：`Worker.claim` 取的是 `Hive.card(tid)`，而它读的是**工作区文件**。
`sync_main` 为了不抹掉人未提交的改动，有两条「原地不动」的路径：

- 本地领先 origin/main → 直接返回，不 reset；
- 落后但工作区有已跟踪改动 → 报错或不动（`--untracked-files=no` 之外都算脏）。

再加上 fetch 失败是被吞掉的（只 log），于是「main 上卡面已是 300、工作区还是
上一版没有 `lease_minutes`」完全成立 —— 取到空 → 退回 10 分钟。

**这类卡随后会怎样**：10 分钟一到，`lease_until` 过期，看板把状态推成
stale/running，而 leader 侧其实还是 ready —— 本机看板留下一份假的「跑飞」快照。
看板只是受害者，别去改看板。

---

## 四、修复后仍然要守的规矩

- **卡面有值以卡面为准**（T-0387 的主逻辑）—— 这条一个字都没动。
- **`STORE_LEASE_MINUTES = 10` 保留**：卡面确实没写时才用它。
- **Git 后端租约语义不变**（还是 180 缺省、还是 `claim/<tid>` 分支）。
- **不要在 leader 上手工改 store 数据**去「修」一张卡的租约：下一次心跳/续租
  会按卡面重算，手工改只会制造第二份不一致。要改就改卡面。

## 五、怎么查（现场三步）

```sh
# 1) 这张卡的卡面到底写了多少
hive show T-0410 --json | grep -E 'lease_minutes|timeout_minutes'

# 2) 首领拿到的租约是不是同一个数（claimed_at → lease_until 的差）
hive status --json | python3 -c "import json,sys; \
  r=[x for x in json.load(sys.stdin)['rows'] if x['id']=='T-0410']; \
  print(r[0]['claimed_at'], r[0]['lease_until'])"

# 3) 本机协调仓是否落后（落后就是上面 B 局面的温床）
hive status --json | grep -E 'sync_health|local_stale'
git -C <协调仓> log --oneline -1 origin/main
git -C <协调仓> log --oneline -1 HEAD
```

领卡成功时日志里会有一行 `T-xxxx store 领取成功（lease <8位>）`；如果租约与卡面
**明显不一致**（短了 10% 以上），修复后的代码会打：

```
[hive ...] T-0410 租约不一致：卡面 300 分钟，store 实际 10 分钟；按卡面补 290 分钟
```

看到这行就说明 leader 侧或旧版节点把时长截短了，但**已经自动补回**，不必人工介入；
要根治则升级对应节点。

## 六、怎么规避（派发侧 / 运维侧）

1. **新卡 push 后别急着让别的机器首领**：`hive dispatch` 之后给 follower 一次
   `hive fetch`/`hive status` 的时间窗（通常几秒），让协调仓追上 main。
2. **协调仓别长期「脏着」**：主工作区有未提交的已跟踪改动时，`sync_main` 会
   拒绝 reset，卡面就一直停在旧版。跑 `hive doctor` 看 `local_stale`，该提交就提交。
3. **leader 启动后新增的卡必须摄入**：store 只在 leader 启动时全量摄入一次。
   领卡遇到 `E_NO_TASK` 时 follower 会自动补登记（`_ingest_missing_card`，优先送
   `origin/main` 的完整卡面，含 `lease_minutes`/`timeout_minutes`）。补登记失败
   会在日志里留 `补登记失败`，看到就查 leader 是否在线、是否旧版不支持 `ingest`。
4. **长任务卡必须写 `lease_minutes`**（且 ≥ 预估时长），别指望 10 分钟兜底。
   没有常驻心跳的 GUI/manual agent 尤其如此。
