# hive 常驻集群：像 OSPF 一样在线，像 git 一样可信

> 面向：要在多台机器上长期跑 agent 的人。
> 读完你应该能回答三个问题：**为什么还要一层集群？它什么时候说话算数？主节点挂了怎么办？**

---

## 0. 一句话定位

**git 仍然是任务状态的唯一真相；集群是「在线状态 + 进度通知」的快速控制面。**

- `claim/<tid>` 的原子性、`res/<tid>` 的审计、`land` 的合流，全部不动。
- 集群负责：谁在线、谁在跑哪张卡、进度到哪一步、谁是主节点。
- **建议每台跑 agent 的机器都起一个节点；不起也能用**——只是跨机信息回到
  「等下一次 `git fetch`」的旧速度，且失去主节点故障时的自动接管。
- 分布式能**消除单点**（一台机器关机/重启，其他节点继续提供服务），但不是物理意义上的
  「永不宕机」：所有节点同时断电、网络全断、或 Git 中心仓不可达时，服务仍会降级。

这条边界很重要：集群里的租约是**建议性**的，不是第二套锁。真正决定「这张卡归谁」的仍然是 git 分支。

## 1. 拓扑

```
       ┌──────────────────────────── 局域网 / VPN ────────────────────────────┐
       │                                                                      │
┌──────┴───────┐        HTTP 8788 (状态/心跳/投票/进度)        ┌──────────────┴──┐
│  fb88         │◄────────────────────────────────────────────►│  win10          │
│  hive cluster │        UDP 8789 (广播发现，可选)              │  hive cluster   │
│  serve        │                                              │  serve          │
│  role=leader  │◄────────────── 注册/心跳/转发 ───────────────►│  role=follower  │
└──────┬───────┘                                              └────────┬─────────┘
       │                                                               │
   agent 进度 / 租约                                            agent 进度 / 租约
       │                                                               │
       └────────────────────────► git 中心仓 ◄─────────────────────────┘
                              （claim / res / tasks，唯一真相）
```

每台跑 agent 的机器各起一个 `hive cluster serve`。它们彼此发现、注册、心跳；
其中一台是主节点（leader），其余是跟随者（follower）。主节点只做协调，不做代码合并。

## 2. 启动与接入

### 2.1 每台机器

```sh
# 前台跑（调试用）
python3 hive.py --dir ~/dswork/hive cluster serve

# 后台常驻（推荐）
python3 hive.py --dir ~/dswork/hive cluster start

python3 hive.py --dir ~/dswork/hive cluster status
python3 hive.py --dir ~/dswork/hive cluster peers
python3 hive.py --dir ~/dswork/hive cluster watch      # 持续打印事件（给脚本/人看）
python3 hive.py --dir ~/dswork/hive cluster sync       # 本机代码同步游标/状态

# verify-only / GUI 机器：只观察，不参选、不投票
python3 hive.py --dir ~/dswork/hive cluster start --no-elect
```

`hive work` 和 `hive orchestrate` 启动时会顺手 `cluster ensure`：本机没起就后台拉起。
不想自动起：`HIVE_CLUSTER_AUTOSTART=0`。

### 2.2 新机器加入

同一广播域内**什么都不用配**：新节点启动后发 UDP 发现，收到 announce 就向主节点注册。

跨网段、广播被禁、或机器在不同 VLAN 时，用静态 seed：

```sh
python3 hive.py --dir ~/dswork/hive cluster start --seed 192.168.1.5:8788
# 或先记录，等本机集群起来后自动重试
python3 hive.py --dir ~/dswork/hive cluster join 192.168.1.5:8788
```

seed 会写进 `~/.hive/cluster/config.json`，下次启动继续用。

### 2.3 端口与防火墙

| 端口 | 协议 | 用途 | 默认 |
|---|---|---|---|
| 8788 | TCP | 集群 HTTP API | `HIVE_CLUSTER_PORT` |
| 8789 | UDP | 广播发现 | `HIVE_CLUSTER_DISCOVERY_PORT` |

只开 TCP 8788 也能工作（静态 seed 或手动 join）；UDP 只是省掉手填地址。

端口默认值只在 [hive_ports.py](../hive_ports.py) 定义一次；完整分配、预留段、
防火墙和冲突排查见 [端口与服务规划](端口与服务规划.md)。现场查看/体检：

```sh
python3 hive.py --dir ~/hive ports
python3 hive.py --dir ~/hive ports --check
```

### 2.4 共享 token（跨机建议必配）

```sh
export HIVE_CLUSTER_TOKEN='换成你自己的长随机串'
# 所有机器的值必须一致；也可写进 ~/.hive/cluster/config.json 的 "token"
```

设置后，`/api/cluster/state`、注册、心跳、投票、进度写入都要求
`X-Hive-Cluster-Token` 或 `Authorization: Bearer ...`。`/api/cluster/health`
保持公开，方便探活。

## 3. 发现与注册流程

```
新节点启动
  │
  ├─ 读 ~/.hive/cluster/state.json / config.json（上次的 term、leader、seed）
  │
  ├─ UDP 广播 discover ──► 已有节点回 announce（带自己的 leader 信息）
  │
  ├─ 逐个尝试 seed：POST /api/cluster/register
  │        │
  │        ├─ 200 → 主节点收下，返回完整 state（term/leader/nodes/events）
  │        └─ 409 → 对方不是主节点，返回它知道的主节点 URL → 再注册一次
  │
  └─ 没找到任何主节点 → 进入选举等待
```

注册成功后：

- 新节点每 `HIVE_CLUSTER_HEARTBEAT` 秒（默认 1s）向主节点发心跳；
- 主节点把成员变化、进度、租约、事件通过心跳响应/广播带回来；
- 其他节点通过主节点或彼此的心跳逐步收敛到同一份视图。

## 4. 选主、任期、化身号、宽限期

### 4.1 任期（term）= fencing token

每次选举 `term + 1`。所有写入（进度、租约、投票）都带 term：

- 旧主节点/旧进程带着旧 term 写入，新主节点返回 `409 stale`；
- 节点看到更高 term，立即让位并把 `voted_for` 清空；
- 同 term 的双主（网络分区恢复后）按 node id 大者优先，另一个主动降级。

这解决的是「僵尸主节点复活后继续发号施令」——仅靠心跳超时解决不了。

### 4.2 化身号（incarnation）

节点每次启动把 `incarnation` 推到 `max(上次+1, 当前毫秒)`，持久化在
`~/.hive/cluster/node.json`。其他节点只接受**更高或相等**化身号的记录：

- 重启后的节点能干净覆盖关于自己的「已经死了」的旧传闻；
- 旧进程即使还能发包，低化身号会被忽略，不会把新进程的状态顶掉。

### 4.3 选举规则

- 跟随者超过 `leader_lease`（默认 5s）没收到主节点心跳 → 清空 leader；
- 等一个错开的选举超时（`election_min` + rank × `election_jitter`，默认 3s 起）；
- 候选者 `term+1`，向**当前可见的活节点**拉票；
- 多数门槛 = `floor(活节点数/2)+1`，单节点集群为 1；
- 拿到多数 → 成为主节点，立即广播心跳。
- 跟随者之间也会互发轻量心跳：主节点死后，B/C 仍能确认对方活着，多数门槛才是 2；
  否则双方都可能把对方判死，各自以「1 节点多数」当选（早期实现踩过这个双主坑）。

> **取舍**：多数按「当前可见的活节点」算，而不是固定配置成员数。
> 2 节点集群里主节点退出后，剩下那台自己就是多数，所以能接管；
> 代价是网络分区时两边可能各自选出主节点。恢复后由 term 收敛。
> 这是家用/小团队局域网「可用性优先」的选择，不是 Raft 的强一致承诺。

### 4.4 主节点退出

- **优雅停止**（`hive cluster stop` / Ctrl-C）：先向同伴发 `resign`，同伴立即进入选举，
  通常 1~2 秒内出新主。
- **崩溃/断电**：同伴靠 `leader_lease` 超时发现，通常 5~8 秒内出新主。
- 新主上任会发 `leader_elected` 事件，`hive cluster watch` / 看板徽标能看到。

### 4.5 租约恢复宽限期

新主节点上任后，会把已知的、未释放的租约标记 `grace_until = now + 120s`
（`--lease-grace` 可调）。宽限期内：

- 集群不会因为「换主了」就建议重派；
- 原 worker 若还在跑，继续续租即可；
- 宽限期过后租约才按正常 TTL 判过期。

真正的回收仍然由 `hive watchdog` 根据 git 里的 claim 决定，集群只提供更早的提示。

## 5. 集群里有什么

`GET /api/cluster/state`（带 token）返回：

| 字段 | 含义 |
|---|---|
| `term` / `role` / `leader` | 当前任期、本机角色、主节点记录 |
| `nodes[]` | 已知节点：id/name/host/port/url/incarnation/last_seen/status(role) |
| `alive` / `known` / `quorum` | 在线数、已知数、当前多数门槛 |
| `events[]` | 最近 500 条事件（join/leave/elected/progress/lease/repo.updated…） |
| `progress{}` | 每张卡的实时进度（state/progress/step/message/updated_at/term/gen） |
| `leases{}` | 建议性租约（agent/lease_until/term/gen/grace_until/released） |
| `generation` | 单调递增的状态代数，供长轮询判断「有没有新东西」 |

### 5.1 HTTP API

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/cluster/health` | 探活（免 token） |
| GET | `/api/cluster/state` | 完整快照 |
| GET | `/api/cluster/task-status` | 只取 progress + leases |
| GET | `/api/cluster/events?since=N` | 事件增量 |
| GET | `/api/cluster/wait?since=N&timeout=20` | 长轮询，状态变了就返回 |
| GET | `/api/cluster/sync` | 本机 SyncAgent 游标/最近同步状态 |
| POST | `/api/cluster/register` | 注册节点 |
| POST | `/api/cluster/heartbeat` | 心跳 / 状态交换 |
| POST | `/api/cluster/vote` | 拉票 |
| POST | `/api/cluster/resign` | 主节点主动让位 |
| POST | `/api/cluster/leave` | 节点退出 |
| POST | `/api/cluster/push` | 上报任务进度 |
| POST | `/api/cluster/lease` | 上报/续租建议性租约 |
| POST | `/api/cluster/release` | 释放租约 |
| POST | `/api/cluster/seed` | 动态加 seed 并尝试注册 |
| POST | `/api/cluster/discover` | 立即触发一轮发现 |
| POST | `/api/cluster/event` | 控制面事件（P0：`repo.updated`） |

### 5.2 与 worker 的接线

- `Worker.claim` 抢到 git 锁后，向本机集群发 `lease`；
- `_refresh_lease` 续租时同步刷新集群租约；
- `run_task` 结束（成功/失败/异常）撤销集群租约；
- agent 每次 `push_status`：先试 `HIVE_PUSH_URL`（老看板直推），再退到本机集群
  `/api/cluster/push`；
- **P0 起 `status/<tid>` 默认不再 force push**：`HIVE_STATUS_GIT=auto`（默认）只在
  里程碑且集群不可用时兜底；`always` 恢复旧行为；`never` 永不写 Git；
- 看板 `/api/status` 会把集群进度合并进任务行（`push_source=cluster`）；
- `hive cluster status/peers/events/watch` 给人和脚本用；
- **orchestrate leader gate**：有集群时只有 leader 跑 watchdog/dispatch/land；
  follower/no-leader 跳过写动作；`--no-elect` 的节点只做 observer。

### 5.3 代码同步（P0）

- `land` 成功后向本机集群发 `repo.updated`，事件带代码仓和协调仓的 sha；
- 每台机器的 `RepoSyncAgent`（在 `cluster serve` 进程里）消费事件，按本机 `repos`
  映射做 `fetch + merge --ff-only`；dirty/diverged 跳过并记录，绝不 reset；
- 游标在 `~/.hive/cluster/sync_cursor.json`；每 5 分钟用 `git ls-remote` 补偿漏掉的事件；
- `hive cluster sync` 或 `GET /api/cluster/sync` 查看最近同步状态；land 那台自己也会
  立即快进主检出。

## 6. 和 RIP / OSPF 的对应关系

| 网络协议里的机制 | hive 集群里的对应 | 说明 |
|---|---|---|
| Hello / 邻居保活 | 1s 心跳 + `last_seen` | 软状态：超时即 suspect/dead |
| 路由器 ID / 化身号 | node_id + incarnation | 重启后严格递增，覆盖旧记录 |
| 选举 / DR-BDR | term + vote | 有确定性的 fencing token，不只是优先级 |
| LSA 泛洪 | 事件列表 + 心跳响应/长轮询 | 事件驱动增量，不靠全量快照 |
| 区域（Area） | 按 `cluster_id` 隔离 | 不同项目/团队可用不同 cluster_id / 端口 |
| Split Horizon | 只从主节点向跟随者广播，写入单跳转发 | 避免「A 等 B、B 等 A」的循环 |

没有照搬路由算法：任务协调不是求最短路径，核心模型是任务状态机 + 租约。
RIP/OSPF 提供的是**状态传播纪律**，不是可直接套用的代码。

## 7. 排障

| 现象 | 先看什么 | 常见原因 |
|---|---|---|
| 看板徽标「未启动」 | `hive cluster status` | 本机没起；`HIVE_CLUSTER_AUTOSTART=0`；缺 `hive_cluster.py` |
| 有进程但 status 显示「状态文件」 | `curl 127.0.0.1:8788/api/cluster/health` | 端口不一致（`--port`/config）、进程崩了、防火墙只放 UDP |
| 新机器一直不注册 | `hive cluster discover`；对端 `cluster peers` | UDP 8789 被禁、跨网段、token 不一致、`cluster_id` 不同 |
| 两台都显示自己是主节点 | 各自 `cluster term/peers` | 网络分区；恢复后 term 大的赢，等 1~2 个心跳周期 |
| 主节点挂了不切换 | `cluster watch`；`leader_lease` | 跟随者仍能连到旧主（半死）、系统时间偏差、UDP/HTTP 都被挡 |
| 进度看板不更新 | `hive cluster events`；`/api/status` 的 `push_source` | worker 没起集群、token 不一致、git 快照比集群新（被正确忽略） |
| 租约一直显示宽限 | `cluster status` 的 `lease_grace_until` | 新主刚上任（120s 内正常）；旧租约没人释放 |

日志：`~/.hive/cluster/cluster.log`（`hive cluster start` 自动轮转到 `.log.1`）。
状态：`~/.hive/cluster/state.json`（进程不在时 `status` 也读它）。

## 9. 已知边界

1. **不是强一致存储**：集群状态是软状态，最终一致；不要拿它替代 git claim。
2. **不加密**：HTTP 明文 + token。只建议在可信局域网/VPN 内使用；跨公网请套 TLS 反向代理。
3. **2 节点分区的双主**：可用性优先的取舍，靠 term 收敛；需要严格 CP 就上 3 节点。
4. **UDP 广播不跨网段**：跨网段用 seed；容器/云主机通常也要 seed。
5. **事件与进度有上限**：事件最多 500 条，progress/leases 不做历史归档；审计仍看 git。
