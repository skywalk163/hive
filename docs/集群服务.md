# hive 常驻集群：像 OSPF 一样在线，像 git 一样可信

> 面向：要在多台机器上长期跑 agent 的人。
> 读完你应该能回答三个问题：**为什么还要一层集群？它什么时候说话算数？主节点挂了怎么办？**

---

## 0. 一句话定位

**git 仍然是任务状态的唯一真相；集群是「在线状态 + 进度通知」的快速控制面。**

- `claim/<tid>` 的原子性、`res/<tid>` 的审计、`land` 的合流，全部不动。
- 集群负责：谁在线、谁在跑哪张卡、进度到哪一步、谁是主节点。
- **建议每台跑 agent 的机器都起一个节点；不起也能用**——只是跨机信息回到
  「等下一次 `git fetch`」的旧速度，且失去主节点故障时的自动接管。
- 分布式能**消除单点**（一台机器关机/重启，其他节点继续提供服务），但不是物理意义上的
  「永不宕机」：所有节点同时断电、网络全断、或 Git 中心仓不可达时，服务仍会降级。

这条边界很重要：集群里的租约是**建议性**的，不是第二套锁。真正决定「这张卡归谁」的仍然是 git 分支。

## 1. 拓扑

```
       ┌──────────────────────────── 局域网 / VPN ────────────────────────────┐
       │                                                                      │
┌──────┴───────┐        HTTP 8788 (状态/心跳/投票/进度)        ┌──────────────┴──┐
│  fb88         │◄────────────────────────────────────────────►│  win10          │
│  hive cluster │        UDP 8789 (广播发现，可选)              │  hive cluster   │
│  serve        │                                              │  serve          │
│  role=leader  │◄────────────── 注册/心跳/转发 ───────────────►│  role=follower  │
└──────┬───────┘                                              └────────┬─────────┘
       │                                                               │
   agent 进度 / 租约                                            agent 进度 / 租约
       │                                                               │
       └────────────────────────► git 中心仓 ◄─────────────────────────┘
                              （claim / res / tasks，唯一真相）
```

每台跑 agent 的机器各起一个 `hive cluster serve`。它们彼此发现、注册、心跳；
其中一台是主节点（leader），其余是跟随者（follower）。主节点只做协调，不做代码合并。

## 2. 启动与接入

### 2.1 每台机器

> 以下命令在 hive 工作目录里跑（hive 仓 = `./hive`）；Windows 把 `/` 换成 `\`。

```sh
# 前台跑（调试用）
python3 hive/hive.py --dir hive cluster serve

# 后台常驻（推荐；daemon 是 cluster 的别名，默认带 MCP HTTP）
python3 hive/hive.py --dir hive daemon start
# 或者显式给 cluster 开 MCP
python3 hive/hive.py --dir hive cluster start --mcp

python3 hive/hive.py --dir hive cluster status
python3 hive/hive.py --dir hive cluster peers
python3 hive/hive.py --dir hive cluster watch      # 持续打印事件（给脚本/人看）
python3 hive/hive.py --dir hive cluster sync       # 本机代码同步游标/状态

# verify-only / GUI 机器：只观察，不参选、不投票
python3 hive/hive.py --dir hive cluster start --no-elect
```

`hive work` 和 `hive orchestrate` 启动时会顺手 `cluster ensure`：本机没起就后台拉起。
不想自动起：`HIVE_CLUSTER_AUTOSTART=0`。

### 2.2 新机器加入

同一广播域内**什么都不用配**：新节点启动后发 UDP 发现，收到 announce 就向主节点注册。

跨网段、广播被禁、或机器在不同 VLAN 时，用静态 seed：

```sh
python3 hive/hive.py --dir hive cluster start --seed 192.168.1.5:8788
# 或先记录，等本机集群起来后自动重试
python3 hive/hive.py --dir hive cluster join 192.168.1.5:8788
```

seed 会写进 `~/.hive/cluster/config.json`，下次启动继续用。

### 2.3 端口与防火墙

| 端口 | 协议 | 用途 | 默认 |
|---|---|---|---|
| 8788 | TCP | 集群 HTTP API | `HIVE_CLUSTER_PORT` |
| 8789 | UDP | 广播发现 | `HIVE_CLUSTER_DISCOVERY_PORT` |

只开 TCP 8788 也能工作（静态 seed 或手动 join）；UDP 只是省掉手填地址。

端口默认值只在 [hive_ports.py](../hive_ports.py) 定义一次；完整分配、预留段、
防火墙和冲突排查见 [端口与服务规划](端口与服务规划.md)。现场查看/体检：

```sh
python3 hive/hive.py --dir hive ports
python3 hive/hive.py --dir hive ports --check
```

### 2.4 共享 token（跨机建议必配）

```sh
export HIVE_CLUSTER_TOKEN='换成你自己的长随机串'
# 所有机器的值必须一致；也可写进 ~/.hive/cluster/config.json 的 "token"
```

设置后，`/api/cluster/state`、注册、心跳、投票、进度写入都要求
`X-Hive-Cluster-Token` 或 `Authorization: Bearer ...`。`/api/cluster/health`
保持公开，方便探活。

## 3. 发现与注册流程

```
新节点启动
  │
  ├─ 读 ~/.hive/cluster/state.json / config.json（上次的 term、leader、seed）
  │
  ├─ UDP 广播 discover ──► 已有节点回 announce（带自己的 leader 信息）
  │
  ├─ 逐个尝试 seed：POST /api/cluster/register
  │        │
  │        ├─ 200 → 主节点收下，返回完整 state（term/leader/nodes/events）
  │        └─ 409 → 对方不是主节点，返回它知道的主节点 URL → 再注册一次
  │
  └─ 没找到任何主节点 → 进入选举等待
```

注册成功后：

- 新节点每 `HIVE_CLUSTER_HEARTBEAT` 秒（默认 1s）向主节点发心跳；
- 主节点把成员变化、进度、租约、事件通过心跳响应/广播带回来；
- 其他节点通过主节点或彼此的心跳逐步收敛到同一份视图。

## 4. 选主、任期、化身号、宽限期

### 4.1 任期（term）= fencing token

每次选举 `term + 1`。所有写入（进度、租约、投票）都带 term：

- 旧主节点/旧进程带着旧 term 写入，新主节点返回 `409 stale`；
- 节点看到更高 term，立即让位并把 `voted_for` 清空；
- 同 term 的双主（网络分区恢复后）按 node id 大者优先，另一个主动降级。

这解决的是「僵尸主节点复活后继续发号施令」——仅靠心跳超时解决不了。

### 4.2 化身号（incarnation）

节点每次启动把 `incarnation` 推到 `max(上次+1, 当前毫秒)`，持久化在
`~/.hive/cluster/node.json`。其他节点只接受**更高或相等**化身号的记录：

- 重启后的节点能干净覆盖关于自己的「已经死了」的旧传闻；
- 旧进程即使还能发包，低化身号会被忽略，不会把新进程的状态顶掉。

### 4.3 选举规则

- 跟随者超过 `leader_lease`（默认 5s）没收到主节点心跳 → 清空 leader；
- 等一个错开的选举超时（`election_min` + rank × `election_jitter`，默认 3s 起）；
- 候选者 `term+1`，向**当前可见的活节点**拉票；
- 多数门槛 = `floor(活节点数/2)+1`，单节点集群为 1；
- 拿到多数 → 成为主节点，立即广播心跳。
- 跟随者之间也会互发轻量心跳：主节点死后，B/C 仍能确认对方活着，多数门槛才是 2；
  否则双方都可能把对方判死，各自以「1 节点多数」当选（早期实现踩过这个双主坑）。

> **取舍**：多数按「当前可见的活节点」算，而不是固定配置成员数。
> 2 节点集群里主节点退出后，剩下那台自己就是多数，所以能接管；
> 代价是网络分区时两边可能各自选出主节点。恢复后由 term 收敛。
> 这是家用/小团队局域网「可用性优先」的选择，不是 Raft 的强一致承诺。

### 4.3.1 人工指定主控（谁当家由人说了算）

自动选主看的是「谁先发起 + 谁的 term 高」，和「谁该当主控」无关。家里那台
常年开机的机器被笔记本抢走主控、之后再也回不去，是很常见的困扰。所以留了两条
人工通道 —— **偏好**管长期，**夺权**管当下。

```sh
# ① 立刻切换：把某台推上主控（不传 --node 就是本机）
hive cluster promote
hive cluster promote --node fb98

# ② 长期偏好：这台重启后，只要没有主控，它最先发起选举
hive cluster prefer            # 把自己设为首选
hive cluster prefer --clear    # 清除

# ③ 启动时的手动开关
hive cluster start --leader    # 启动同时把本机记为首选

# 看当前谁当家
hive cluster leader
```

**偏好（preferred_leader）的作用范围要说清楚**：它是**本机配置**，只影响本机的
选举延迟 —— 被偏好的节点延迟为 0，其它节点让出一个选举窗口。所以想让 0.88
稳定当主控，就在 0.88 上配（或 `start --leader`）。它只在「当前没有主控」时生效：
主控还活着的时候，偏好不会把它顶下去。

**夺权（promote）做了什么**，按顺序：

1. 先请现任主控 `resign` 主动下台 —— 它自己降级，比等它被更高任期压下去干净，
   中间不会出现两边都以为自己是主控的窗口；
2. 把本机 term 追到集群最高（`/api/cluster/health` 免 token 且带 term）。
   这一步容易被忽略但很关键：**重启过的节点 term 往往落后一整截**，
   直接 `term+1` 仍然比在位主控小，投票会被 `stale_term` 拒掉，
   现象是「敲了 promote 什么也没发生」；
3. `term+1` 发起选举，投票请求带 `force: true`。

**`force` 放开了什么**：原本 `handle_vote` 里有一道闸 —— 候选人的 store
落后于我就拒绝投票（防止选出数据落后的主节点）。人工夺权时这道闸会挡路，
因为重启节点的 store 几乎必然落后。放开它的依据是：**hive 的 store 只是缓存，
git 才是事实账**，落后会在当上主控后由 `StoreReconciler` 从卡面补回来。
放行时会写一条 `leader_forced` 事件，注明落后多少条 —— 事后能分辨这次任期切换
是「按规矩选的」还是「人硬点的」。

不想放开的话：`HIVE_CLUSTER_ALLOW_FORCE_PROMOTE=0`（或 config.json 里
`allow_forced_promote: false`），语义变成「宁可没主控，也不接受落后节点」。

> **注意 promote 会打断当前主控**：它有几百毫秒的不应期，正在跑的
> `orchestrate` 那一轮可能落空（下一轮会重来）。别在关键任务收口时切。

### 4.3.2 主控优先级（OSPF 式，值大者优先）

`preferred_leader` 有个别扭的地方：它是**本机配置**，想让 0.88 当主控，
就得在 0.88 上单独配一条，换一台机器又要重配，而且别的节点看不见这个偏好。

所以照 OSPF 的 DR 选举补了一层**优先级**：每台节点在自己配置里声明「我该排第几」，
这个值随节点自述（`_self_node()["priority"]`）**广播给全集群**，谁都能看到。
不用再在每台机器上互相约定「谁是首选」。

```sh
hive cluster priority                 # 看本机优先级 + 全集群按优先级排序
hive cluster priority --priority 2    # 本机改成 2（改完自动重启本机节点生效）
hive cluster priority --priority 2 --no-restart   # 只改配置，下次重启生效
hive cluster peers                    # 表格里有 PRIO 列
```

取值范围 **0-255**（OSPF 的接口优先级是 8bit），默认 1 —— 不改的话行为和以前
完全一致（谁先发起谁当）。命令行输越界值会直接报错；从 `config.json` / 环境变量 /
别的节点广播来的越界值会被规整到边界，避免一个填错的 999 把排序搅乱。

**六条语义，全部照抄 OSPF 的 DR/BDR 选举**：

| 规则 | 行为 | 为什么这么定 |
|---|---|---|
| 取值范围 0-255 | 默认 1；CLI 越界报错，其它来源 clamp | OSPF 的 DR priority 是 8bit 无符号值 |
| 值大者优先 | 优先级高的选举延迟更短，先发起、先当选 | 这才是「设定优先级」的本意 |
| 同值按 node_id 定序 | 相当于 OSPF 用 Router ID 打平手 | 保证顺序确定，避免同轮打平后反复重选 |
| **不抢占在位主控** | 高优先级节点后加入，不会把现任主控挤下来 | 否则设了 2 的机器每次重启都抢一次主控，而重启往往正发生在排障时 |
| **0 = 放弃竞选资格** | 不主动发起选举；其它节点也会拒投它；`promote` 同样不越过 | OSPF 里 priority 0 的接口是 DRother，永远不会成为 DR/BDR；给「只读副本 / 弱机器」用 |
| 0 是硬资格，集群侧也拦 | `handle_vote` 见候选人为 0 且自己为正优先级就拒票 | 原先只靠本机 `delay=inf` 自觉，跑老代码 / 配错的节点抢跑仍可能凑够多数当上主控 |

> **全集群都是 0 时会退化成人人 1**。这一点和 OSPF 不同（OSPF 全 0 就没有 DR，
> 广播网络直接不通），是刻意的可用性取舍：hive 没有主控就派不了卡，而不这么兜底
> 的话没有任何节点愿意发起选举。「把优先级理解成越小越优先、全填 0」这种事一定会
> 发生，死锁比不理解更难查。退化期间 0 不再是禁赛标志，拒票保护也同步放开。

优先级只在**当前没有主控**时才起作用。想立刻换人，还是用 `promote`（但本机若设了 0，
要先 `cluster priority --priority 1` 把资格拿回来）：

```sh
hive cluster priority --priority 2   # 长期：我应该优先当家
hive cluster promote                 # 当下：现在就换我
```

三者分工：`priority` 是默认机制（谁都能声明）、`preferred_leader` 是人工硬指定
（压过一切优先级，delay=0）、`promote` 是立刻动手。优先级排在 preferred 之后，
即被 preferred 指定的那台仍然最先；但若被指定的那台自己设了 0，这个偏好会被忽略
（否则全集群一起给它让路，而它永远不开口，就没人能当选）。

配置持久化在 `~/.hive/cluster/config.json` 的 `leader_priority`，也可以用环境变量
`HIVE_CLUSTER_PRIORITY` 或启动参数 `--priority N` 给。生效优先级是
**启动参数 > 环境变量 > config.json > 默认值 1**。

**配置文件是每台机器本地一份**，路径 `~/.hive/cluster/config.json`（Windows 是
`%USERPROFILE%\.hive\cluster\config.json`）。仓库里的
[`config.example.json`](../config.example.json) 是模板，按需复制过去改：

```json
{
  "name": "fb98",
  "electable": true,
  "leader_priority": 2,
  "preferred_leader": ""
}
```

不写 `leader_priority` 就是默认 1（大家平等）；想让某台优先当家，只在**那一台**
写 2 即可，其余节点保持 1 —— 值会随心跳广播，别的节点自己会看到，不需要在别人
机器上代设。逐机设置可以用 `hive cluster priority --priority 2`（它会自动写
config.json 并重启本机节点），`hive cluster priority` 不带参数则列出全集群的
优先级排序。

> 为什么不放进 git 仓库共享一份：协调仓是各节点 `git pull` 同步的，若配置跟着
> 仓库走，所有机器会读到同一个 `leader_priority`，「某台 2、其余 1」的差异化
> 就不存在了。所以配置必须是**节点本地**的，仓库里只放模板。同理 `name`、
> `advertise`、`seeds` 这类逐机参数也不该共享。

**和 OSPF 剩下的三点差异（有意保留，不是漏实现）**：

1. **接口级 → 节点级**：OSPF 是「每个广播网段选一个 DR」，一台路由器在不同网段
   可以有不同优先级；hive 是「整个集群一个主控」，所以优先级是节点级配置。
2. **没有 BDR**：OSPF 会同时选出次高优先级的 BDR，DR 挂了由 BDR 立即接手；
   hive 只有一个 leader，挂了要重新走一轮选举 + 追 term（通常 5~8 秒）。
   要 BDR 就得维护一份随时可接管的 store 副本，当前架构用 git 当事实账，
   新主上任后从卡面追平即可，不值得为省这几秒再养一个热备。
3. **人工通道是 OSPF 没有的**：`preferred_leader` / `promote` 是为「人指定谁当家」
   加的，OSPF 的 DR 选举没有管理员手动夺权这个动作。优先级排在它们之后。

另外 `election_jitter` 被设成 0 时，名次之间仍有 0.05s 的最小间隔，
避免所有节点同一刻开跑、让优先级退化成「谁网络快谁当」。

### 4.4 主节点退出

- **优雅停止**（`hive cluster stop` / Ctrl-C）：先向同伴发 `resign`，同伴立即进入选举，
  通常 1~2 秒内出新主。
- **崩溃/断电**：同伴靠 `leader_lease` 超时发现，通常 5~8 秒内出新主。
- 新主上任会发 `leader_elected` 事件，`hive cluster watch` / 看板徽标能看到。

### 4.5 租约恢复宽限期

新主节点上任后，会把已知的、未释放的租约标记 `grace_until = now + 120s`
（`--lease-grace` 可调）。宽限期内：

- 集群不会因为「换主了」就建议重派；
- 原 worker 若还在跑，继续续租即可；
- 宽限期过后租约才按正常 TTL 判过期。

真正的回收仍然由 `hive watchdog` 根据 git 里的 claim 决定，集群只提供更早的提示。

## 5. 集群里有什么

`GET /api/cluster/state`（带 token）返回：

| 字段 | 含义 |
|---|---|
| `term` / `role` / `leader` | 当前任期、本机角色、主节点记录 |
| `nodes[]` | 已知节点：id/name/host/port/url/incarnation/last_seen/status(role) |
| `alive` / `known` / `quorum` | 在线数、已知数、当前多数门槛 |
| `events[]` | 最近 500 条事件（join/leave/elected/progress/lease/repo.updated…） |
| `progress{}` | 每张卡的实时进度（state/progress/step/message/updated_at/term/gen） |
| `leases{}` | 建议性租约（agent/lease_until/term/gen/grace_until/released） |
| `generation` | 单调递增的状态代数，供长轮询判断「有没有新东西」 |

### 5.1 HTTP API

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/cluster/health` | 探活（免 token） |
| GET | `/api/cluster/state` | 完整快照 |
| GET | `/api/cluster/task-status` | 只取 progress + leases |
| GET | `/api/cluster/events?since=N` | 事件增量 |
| GET | `/api/cluster/wait?since=N&timeout=20` | 长轮询，状态变了就返回 |
| GET | `/api/cluster/sync` | 本机 SyncAgent 游标/最近同步状态 |

### 5.2 与 worker 的接线

- `Worker.claim` 抢到 git 锁后，向本机集群发 `lease`；
- `_refresh_lease` 续租时同步刷新集群租约；
- `run_task` 结束（成功/失败/异常）撤销集群租约；
- agent 每次 `push_status`：先试 `HIVE_PUSH_URL`（老看板直推），再退到本机集群
  `/api/cluster/push`；
- **P0 起 `status/<tid>` 默认不再 force push**：`HIVE_STATUS_GIT=auto`（默认）只在
  里程碑且集群不可用时兜底；`always` 恢复旧行为；`never` 永不写 Git；
- 看板 `/api/status` 会把集群进度合并进任务行（`push_source=cluster`）；
- `hive cluster status/peers/events/watch` 给人和脚本用；
- **orchestrate leader gate**：有集群时只有 leader 跑 watchdog/dispatch/land；
  follower/no-leader 跳过写动作；`--no-elect` 的节点只做 observer。

### 5.3 代码同步（P0）

- `land` 成功后向本机集群发 `repo.updated`，事件带代码仓和协调仓的 sha；
- 每台机器的 `RepoSyncAgent`（在 `cluster serve` 进程里）消费事件，按本机 `repos`
  映射做 `fetch + merge --ff-only`；dirty/diverged 跳过并记录，绝不 reset；
- 游标在 `~/.hive/cluster/sync_cursor.json`；每 5 分钟用 `git ls-remote` 补偿漏掉的事件；
- `hive cluster sync` 或 `GET /api/cluster/sync` 查看最近同步状态；land 那台自己也会
  立即快进主检出。

## 6. 和 RIP / OSPF 的对应关系

| 网络协议里的机制 | hive 集群里的对应 | 说明 |
|---|---|---|
| Hello / 邻居保活 | 1s 心跳 + `last_seen` | 软状态：超时即 suspect/dead |
| 路由器 ID / 化身号 | node_id + incarnation | 重启后严格递增，覆盖旧记录 |
| 选举 / DR-BDR | term + vote + 优先级 | 优先级定顺序（0-255，值大者先，0=弃权），term 定权威（fencing token）；**都不抢占在位主控**；hive 只借了 DR 选举规则，没有实现 BDR 热备 |
| LSA 泛洪 | 事件列表 + 心跳响应/长轮询 | 事件驱动增量，不靠全量快照 |
| 区域（Area） | 按 `cluster_id` 隔离 | 不同项目/团队可用不同 cluster_id / 端口 |
| Split Horizon | 只从主节点向跟随者广播，写入单跳转发 | 避免「A 等 B、B 等 A」的循环 |

没有照搬路由算法：任务协调不是求最短路径，核心模型是任务状态机 + 租约。
RIP/OSPF 提供的是**状态传播纪律**，不是可直接套用的代码。

## 7. 排障

| 现象 | 先看什么 | 常见原因 |
|---|---|---|
| 看板徽标「未启动」 | `hive cluster status` | 本机没起；`HIVE_CLUSTER_AUTOSTART=0`；缺 `hive_cluster.py` |
| 有进程但 status 显示「状态文件」 | `curl 127.0.0.1:8788/api/cluster/health` | 端口不一致（`--port`/config）、进程崩了、防火墙只放 UDP |
| 新机器一直不注册 | `hive cluster discover`；对端 `cluster peers` | UDP 8789 被禁、跨网段、token 不一致、`cluster_id` 不同 |
| 两台都显示自己是主节点 | 各自 `cluster term/peers` | 网络分区；恢复后 term 大的赢，等 1~2 个心跳周期 |
| 主节点挂了不切换 | `cluster watch`；`leader_lease` | 跟随者仍能连到旧主（半死）、系统时间偏差、UDP/HTTP 都被挡 |
| 进度看板不更新 | `hive cluster events`；`/api/status` 的 `push_source` | worker 没起集群、token 不一致、git 快照比集群新（被正确忽略） |
| 租约一直显示宽限 | `cluster status` 的 `lease_grace_until` | 新主刚上任（120s 内正常）；旧租约没人释放 |
| 主控是一台早就不在的机器 / 两个身份指向同一个 URL | `cluster peers` 看 URL 列是否重复 | 幽灵节点：见下 |
| `cluster restart` 报「集群未能就绪」但 8788 能探活 | 先 `curl 127.0.0.1:8788/api/cluster/health` | Windows 冷启动超过自检窗口，误报；见 §7.2 |
| 日志刷 `ConnectionResetError: [WinError 10054]` | 不用管 | 探活/旧连接被重置，服务正常；新版本已静默 |

### 7.1 幽灵节点（僵尸 leader 记录）

症状：`cluster peers` 里有个节点指向**和别的节点完全一样的 URL**（曾出现
`laiweilideMacBook-Air` 与 `DESKTOP-6LFQUO8` 都写 `192.168.0.104:8788`），
而那台机器早就不在线；它还被显示成 leader、`term=0`，写请求全被 follower 拒。

根因不在「机器重复登记」，而在 `_adopt_leader_locked()`：节点收到「leader 是 X」
的快照时会 `_update_node_locked(rec, touch=True)`，把 leader 记录写回节点表并刷新
`last_seen`。只要 `leader_id` 还指向 X，每次心跳就给 X 续一次命 —— **单删节点表
没用，下一拍必复活**。所以必须同时清掉所有节点上的 `leader_id`：

```bash
GHOST=laiweilideMacBook-Air-20c3af99      # 从 cluster peers / state.json 取 id
for u in http://127.0.0.1:8788 http://192.168.0.104:8788; do
  curl -sX POST "$u/api/cluster/resign" -H 'Content-Type: application/json' \
       -d "{\"node_id\":\"$GHOST\"}"
  curl -sX POST "$u/api/cluster/leave"  -H 'Content-Type: application/json' \
       -d "{\"node_id\":\"$GHOST\"}"
done
python3 hive.py cluster promote           # 或等自动选举：preferred/priority 会让本机先发起
python3 hive.py cluster peers             # 应只剩 2 个节点、URL 各不相同
```

顺序不能反：先 `resign`（断掉 leader 指向）→ 再 `leave`（删记录）→ 最后 `promote`
产生更高 term 的新 leader。**每个节点都要做**，漏一个它就会把幽灵广播回来。

**重启会让它从磁盘回来**：`state.json` 里如果还留着「同一 URL、两个 node_id」
的记录，重启时 `_load_state()` 会原样读回，随后心跳又把它续活（2026-11-06
重启 104 后复发就是这条链）。当前版本已加两道防护：加载时
`_dedupe_node_urls_locked()` 按 URL 去重（本机自己优先，其余按 incarnation
取最新），`_update_node_locked()` 拒绝同 URL 的旧身份续命。**升级代码并重启
一次后，幽灵就不会再靠重启复活**；在这之前，重启过节点就再跑一遍上面的
resign → leave → promote。

### 7.1.1 幽灵 leader 死循环（follower 互相喂租约，2026-11-09）

和上面「重复 URL 的僵尸记录」不同，这次**节点表是干净的**：每台 follower 都把
`leader_id` 指向同一台其实也是 follower 的机器（现场是 `192.168.0.103`），
`state.json` 里 `leader_lease_until` 却一直往后走，term 从 2110 一路涨到
2150，日志刷满 `leader_seen` 和「本轮选举未获多数」，集群长期无主。

根因是**租约可以被跟随者重新签发**：

1. `_follower_heartbeat()` 无条件把自己发往 `leader_url` 的那次回复当成
   「主控本人心跳」（`from_leader=True`），并对回复里的 leader 记录调用
   `_adopt_leader_locked(..., refresh_lease=True)`，把租约重签成 `now + lease`；
2. 每台 follower 又在自己的心跳回复里广播这份「新鲜」租约；
3. 同伴收到后走 `refresh_lease=False`，但旧实现仍用
   `min(remote_lease, now + lease)` 参与计算，于是每转一跳租约就续一次；
4. 租约永不过期 → `_maintenance_once()` 永远不触发 `_clear_leader_locked()`
   → `leader_id` 永远非空 → 谁都不发起选举。

修复后加了四道防线，都在 `hive_cluster.py`：

| 防线 | 做法 |
|---|---|
| 只有主控本人能签租约 | `handle_heartbeat()` 仅在 `body.leader is True` 时 `refresh_lease=True`；回复新增 `is_leader` / `node_id` 供请求方核验，老版本用顶层 `role` 兜底。跟随者互探、`_peer_heartbeat`、更高任期传闻、vote 回复一律改为 `refresh_lease=False` |
| 跟随者不传播主控身份 | `_merge_snapshot_locked()` 只在 `from_leader=True` 时采纳 leader 记录，且要求 `leader.id == sender_id`（**主控记录必须由本人签发**）。一台机器「自己 `role=leader`、却把 `leader_id` 指向幽灵」的不一致快照一律拒收 |
| 主控心跳核对来源 IP | `handle_heartbeat(..., peer_ip=...)` 要求自述 `url` 的主机就是请求来源 IP（自述为域名时不校验）。最终取证：**幽灵是 `leader: True` 心跳写进来的** —— 现场 `192.168.0.110` 那台机器沿用旧 `node.json` 里的 Mac 身份，声明已下线的 `192.168.0.103`。身份对不上的请求**只读不写**：不合并节点、不推进 term、不采纳主控、不签租约 —— 否则它注入的高 term 会把本机选举一遍遍打断（term 2170→2234 就是这么来的） |
| 转述不再重新签发 | `_adopt_leader_locked()` 的 False 分支只沿用远端给出的**绝对到期时间**，不参与 `now + lease` 的续期计算 |
| 主控地址拨不通即撤销 | `_follower_heartbeat` 连续失败超过 2 个租约窗口就清 leader；再加「超过 `max(3 × leader_lease, 2s)` 没收到主控本人心跳」的兜底。两条都能在同伴还在撑租约时把幽灵清掉 |
| 重启不继承主控身份 | `_load_state()` 一律丢弃磁盘里的 `leader_id` / `leader_url` / 租约，等真主控心跳（1 秒内）或重新选举确认 |

**运维含义**：升级**一台**就能破环，不必再「所有节点同时停服 + 手工改
state.json」—— 升级过的节点不再被喂租约，会按 `leader_priority` 最先发起
选举；它拿到更高 term 后，旧版本节点会接受它的主控心跳。旧节点之间仍会互相
喂，但影响不到新主。**仍建议全集群尽快同步代码**，混合版本期间旧节点自身的
主控视图可能滞后。`state.json` 里的旧 `leader_id` 不用手工清，重启时自动丢弃。

现场 2026-11-09 收敛结果：本机 `fb98` 以 leader 身份稳定，`.101` / `.109` /
`.110` 三台 follower 的 term 与 leader 指向全部对齐到 `fb98`；`.103` 确认
**没有任何机器**（`Host is down`），只是 `.110` 上旧 `node.json` 里留下的
身份与 URL。要除根，在那台机器上删掉 `~/.hive/cluster/node.json` 让程序按
当前主机名重建身份，再重启节点即可 —— 否则它仍会以幽灵身份发心跳，只是
升级过的节点不再理会。

### 7.2 Windows 节点：同步代码 + 重启服务

Windows 节点只开 445 / 8788，没有 SSH / WinRM / RDP，hive 的 HTTP 也没有任意
命令执行接口 —— 所以**必须有一次人工 bootstrap**。在目标机器上：

```powershell
cd <hive 仓库>\scripts
powershell -ExecutionPolicy Bypass -File .\win-sync-restart.ps1                 # 先体检
powershell -ExecutionPolicy Bypass -File .\win-sync-restart.ps1 -Apply          # 同步 + 重启
powershell -ExecutionPolicy Bypass -File .\win-sync-restart.ps1 -Apply -EnableRemote
```

脚本自动定位 `hive.py` 与协调仓，`git pull --ff-only` 后用官方
`hive.py cluster restart` 重启（detached 拉起、自带健康自检），最后探活。

> **多数情况不需要这个脚本，也不需要 `-EnableRemote`。** 领任务是拉取式的，
> 用 `scripts/win-scheduled-work.ps1` 设个定时计划任务，每轮自动 `git pull`
> 同步代码 + `work --once --no-cluster` 领卡即可，全程不碰集群服务、不用开
> 22 端口。见 `docs/主控与分发.md` §4.5。只有确实需要主控反向 ssh 进来
> 排障时，才值得 `-EnableRemote`（装 OpenSSH Server、只放行 `192.168.0.0/24`，
> 公钥追加到 `C:\ProgramData\ssh\administrators_authorized_keys`）。

#### 「集群未能就绪」多半是误报

`cluster restart` 的自检窗口原先写死 8 秒。Windows 上 Microsoft Store 版
Python 冷启动 + 打开 store（上百张卡）+ 起 MCP/发现线程很容易超过它，于是
父进程打印「未能就绪」并返回 1，**但子进程没有被杀、随后照样启动完成**。
日志尾部还常有一段 `ConnectionResetError: [WinError 10054]`，那是探活或旧
连接被重置时 HTTP handler 抛的，纯噪音，不是崩溃原因。

正确判据是**实际探活**，不是 restart 的退出码：

```powershell
curl.exe -s http://127.0.0.1:8788/api/cluster/health
python hive.py cluster status
```

`win-sync-restart.ps1` 已改成：restart 非零只记警告，继续探活 30 秒，探活成功
就算成功。核心侧也修了三处：启动窗口改为 `HIVE_CLUSTER_STARTUP_TIMEOUT`
（Windows 默认 30s、其它 15s）；窗口用尽但进程仍活着时返回 0 并提示「启动较慢」，
不再误判失败；`Handler.handle()` 就地吞掉连接重置，避免 traceback 污染日志。

日志：`~/.hive/cluster/cluster.log`（`hive cluster start` 自动轮转到 `.log.1`）。
状态：`~/.hive/cluster/state.json`（进程不在时 `status` 也读它）。

## 9. 已知边界

1. **不是强一致存储**：集群状态是软状态，最终一致；不要拿它替代 git claim。
2. **不加密**：HTTP 明文 + token。只建议在可信局域网/VPN 内使用；跨公网请套 TLS 反向代理。
3. **2 节点分区的双主**：可用性优先的取舍，靠 term 收敛；需要严格 CP 就上 3 节点。
4. **UDP 广播不跨网段**：跨网段用 seed；容器/云主机通常也要 seed。
5. **事件与进度有上限**：事件最多 500 条，progress/leases 不做历史归档；审计仍看 git。
