## 二、查出的 5 个问题

### T-0327　主锁饥饿：整集群周期性「假死」

**根因是两把锁互等**，三个环节叠加：

1. `_persist_locked()` 在 `self.lock` 里直接 `_write_json`
   —— state.json 521KB，一次 40ms+，ZFS 上还撞 `zil_commit` 的 fsync
2. `_self_node()` / 心跳响应 / 选票闸门在**持主锁**时调 `store.commit_seq()`
   —— 而它要拿 `store._lock`
3. `ingest_cards()` 在 autocommit + `synchronous=FULL` 下逐行 fsync
   —— **194 张卡要 18 秒**，整条 store 锁被占死

连锁反应：

```
补卡线程占 store 锁 → 持主锁线程排队 → 心跳发不出 → 租约过期
   → 重选 → 重选又持锁落盘 → 雪崩
```

**修法**：

- `_persist_locked` 只打脏标记，写盘由 `_persist()` 在锁外做（停机补 `force=True`）
- 新增 `_store_seq()` 位点缓存：持锁路径只读缓存，由 `_loop_health_cache` 每秒在锁外刷新
- `ingest_cards` 改单事务批量提交（`batch=200` 分段，每段释放 store 锁）

**效果**：194 张卡 `18037ms → 47.6ms`（379 倍）；state 接口 60 次采样**0 次超过 0.6s**。

> 排查手法：`curl -m 5 -w '%{time_total}'` 反复采样看周期性卡秒级；
> `procstat -kk <pid>` 抓线程栈，看到 `zfs_fsync` / `_cv_wait` 即可佐证。

### T-0328　选主改「择优」：摘掉 Raft 的一致性关卡

**这个问题需要你重新设计方向。** 我最初在旧框架里打补丁，用户指出：

> 「主必须选出来啊，除非是单台机器，况且单台机器自己就是主啊！
> 其它机器再并进来，根据协议，就应该尊它为主！」
> 「竞争得主后，不手工关闭，几乎不会丢失主啊！」

**根因**：当选条件是 `len(votes) >= quorum`，那是 Raft 防网络分区双主的**一致性**约束。
而 hive 的 store 只是缓存、**git 才是事实账**，卡在这条等于自愿放弃可用性。

```
3 台真机 + 2 条僵尸记录 → quorum 抬到 4 → 永远凑不够 → 长期无主
```

且选举失败会退避，期间僵尸仍在票池（`membership_ttl=300s`），形成死循环，
直到 TTL 过期才突然自愈。**一天 382 次「本轮选举未获多数」**。

**修法 —— 四级择优链**（照 OSPF 的 DR 语义）：

```
preferred_leader（人工硬指定）
  → leader_priority（0-255，值大者胜）
    → link_speed（Mbit/s，同优先级比速率）
      → node_id 字典序（确定性兜底 —— 关键！）
```

第 4 层是关键：没有它，两台同优先级机器会算出「一样强」，只能随机抢、撞车、重选。
有了它，**全集群对「谁更强」得出同一个答案**，可以直接让位。

配套语义：

- **票数降级为记录/告警**，不再是当选前提
- **单机立刻当主**（返回 0，不等 `election_min`）
- **non-preemptive**：在位主控活着时，更高优先级节点后加入也不抢占
- **尊重已投的票**：比我强的节点若明确投了我，说明它承认该我当主，此时不再让位
  —— 否则出现「2/2 全票当选却让位、谁都不当主」的死循环（实现中真实踩到）
- **票池照 OSPF 邻居表**：alive/suspect 才算票；dead 出池；转述来的陌生 id 不算票
  （原 `known is None` 时给 `_now()` 是复活幽灵的病灶）；被删节点立墓碑 1 小时

**效果**：5 分钟 55 次采样**无主 0 次**，term 稳在 3802；单机 0.25s 当选；
主控挂掉立刻接手；5 个僵尸 + 主控挂掉仍能正常选主。

### T-0329　生产守护 + 开发隔离

起因：fb98 既是生产主控又是开发机 —— **改代码重启集群 = 全团队停摆**。
且生产集群原本是 `nohup` 拉起的**孤儿进程（PPID=1）、无守护**，进程一退就永久无主。

**守护**：`scripts/freebsd/hive_cluster.rc` + `hive-cluster-run.sh`，交给 `daemon(8)`：

- 崩溃 **5 秒**自动拉起（实测 `kill -9` 后恢复并重新当选）
- 开机自启
- `status` 用「端口监听 + 进程存在」组合判断，不依赖 pidfile

**隔离**：`scripts/dev-cluster.sh`

| | 生产 | 开发 |
|---|---|---|
| state_dir | `~/.hive/cluster` | `~/.hive/dev-cluster` |
| 端口 | 8788/8789/8790 | 8888/8889/— |
| cluster_id | `hive` | `hive-dev` |
| store/MCP/同步 | 启用 | **全关** |

**实测**：连续 restart 开发集群 3 次，生产 `term` 不变、`peers=4` 完好。

> **两个坑（已写进脚本注释与文档）**
> 1. 启动包装路径在 `scripts/freebsd/`，不是仓库根 `freebsd/` —— 写错会刷屏 `No such file`
> 2. `rc.subr` 的 `su -m` 继承 root 的 `HOME`，`$HOME/.hive` 展开成 `//.hive` → `Permission denied`

### 没搬成 192.168.1.5：网络单向不通

原计划把主控迁到 fb5（`leader_priority=115`），让开发机彻底不参与生产。

**排查结论**：

| 方向 | 结果 |
|---|---|
| fb98(`0.88`) → fb5(`1.5`) | 通（经 `192.168.0.1` 一跳） |
| fb5 → fb98 | **不通**（`192.168.1.1 → 100.120.0.1`，`100.64/10` 是运营商 CGNAT） |

fb5 上没有到 `192.168.0.0/24` 的回程路由；手动加 `route add -net 192.168.0.0/24 192.168.1.1`
后仍不通（traceroute 显示流量直接进公网），**该路由已撤销**。

节点间要互发心跳/拉票/同步 store，全部要求**双向可达**。单向通组不成集群。

**要迁的话，先解决网络（二选一）**：
1. 路由器给 `192.168.1.0/24` 加一条指向 `192.168.0.1` 的回程路由（最省事）
2. 两机上装 Tailscale / ZeroTier 走 overlay

### T-0332　术语分层：工作流用「合入」，git 用「合并」

用户反馈：在 agent chat 说「合并」上百次，有几次被理解成「把两个任务合并到一起」。

**查证（非凭语感）**：

- **Git 官方中文文档用「合并」**：快进合并 / 真正合并 / 合并冲突 / 合并策略
- **Gitee 官方帮助也用「合并」**：「合并 Pull Request」「合并到目标分支」
- **但企业研发流程普遍用「合入」**：华为云 HCIP 教材、阿里云代码评审文档

**业内并不统一**，区别在语义：

| 词 | 指什么 |
|---|---|
| 合并 | git 的 `merge` 动作，**无方向** |
| 合入 | 工作流概念，把改动并入主线，**带方向** |

`land` 是「并入 main + verify + 关卡」的**工作流操作**，有方向性，故用「合入」。

**歧义源头**就是这句缺宾语的话：

```
改前：任务 T-0001 已完成，请合并（land）。      ← 能理解成"把两个任务合并"
改后：任务 T-0001 已完成，请把它合入（land）。  ← 方向明确
```

**分层改法**（不做全盘替换）：

- 改「合入」：看板列名（待合入）、按钮（复制合入指令）、给主控的指令、
  MCP 工具描述、CLI 汇总、TUI 分组名、land 状态标签
- 保留「合并」：合并冲突、快进合并、合并策略、配置/数据结构合并

**防回潮**：`CONTRIBUTING.md` 新增 §3.5，写清权威出处、语义区别、哪些地方用哪个。

## 四、方法论沉淀（五条）

1. **抄协议先分清它为什么存在：一致性 ≠ 可用性**
   引入外部协议语义前先问：它解决哪个问题？我们是同一个问题吗？

2. **两把锁互等，症状是「整集群周期性无响应」**
   把「任何锁内的 IO / 网络 / sqlite 都当 bug」当纪律；日志里 `lock_wait=136ms` 是体检指标。

3. **修「偶发」前先量化基线**
   曾把写盘改成后台线程，用例失败率 20%→40%；回退原版跑 10 次确认本来就 20%，
   才知道是写盘线程抢 GIL 导致，于是换掉方案。

4. **测试里的期望值会固化错误语义**
   失败 ≠ 改坏了。要看它钉的是「保护目的」还是「旧实现细节」：
   前者保留（改写成「更强的可达节点在就不得自封」），后者跟着改。

5. **文档写着「实现基线」但代码里根本没有，比没有更危险**
   标注「设计意图」还是「现状」必须显式；改机制后 grep 旧名词，连代码注释一起改。
