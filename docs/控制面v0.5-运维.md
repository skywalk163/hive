# Hive 韧性控制面 v0.5 · 运维手册

> 面向：在一组机器上长期跑 `hive cluster serve` 的人。
> 一句话：控制面是**附加在旧 HTTP 集群面上的提示通道**；Git 仍是唯一事实账。
>
> 相关文档：[实现约定](控制面v0.5-实现约定.md)（接口与裁定）、
> [端口与服务规划](端口与服务规划.md)（全局端口表）、
> [集群服务](集群服务.md)（旧 HTTP 面）、
> [架构与排障全景](架构与排障全景.md)（全局排障入口）。

## 1. 它是什么，和旧 HTTP 面什么关系

控制面（`hive_control/`）解决的是旧 HTTP 面在高频状态变化下的两个问题：
每秒几十次心跳/进度轮询会把主控和网络打满；跨机状态在 Leader 切换后收敛慢。
它把「谁在跑哪张卡」做成一条**可丢、可重放、只做提示**的通道：

- 上行：Worker 上报 → 本地聚合 → TCP 发给控制面 Leader；
- 下行：Leader 组播（失败时逐节点单播）最新条目；
- 拉取：节点发现水位缺口时向 Leader 增量/全量拉取；
- 租约：只在内存里判断过期并下发 `expiring` 提示，不改 Git。

### 1.1 双面并存（D1 / D14）

| | 旧 HTTP 面 | 控制面 v0.5 |
|---|---|---|
| 代码 | `hive_cluster.py` | `hive_control/` |
| 端口 | HTTP 8788 | 上行/拉取 TCP 8789、UDP 47899 |
| Leader | 旧面自己选（`/api/cluster/state` 的 `leader`） | 控制面独立选（`/api/cluster/status` 的 `control_leader`） |
| 谁是权威 | 提示 + 部分协调 | **只是提示**；Git 才是权威（I1） |
| 何时开启 | 一直有 | 只有 `hive cluster serve` 入口开启（D14） |

要点：

1. 两个 Leader 并列存在，本期**不合并**；旧面的选主、租约、store 语义一行都没改。
2. 只有控制面 Leader 向组播地址发消息（I3）；旧面 Leader 不发。
3. 程序化构造 `Cluster(...)`（单测、嵌入式）默认**不**装配控制面，
   所以 `/api/cluster/status` 的 `control` 段会返回 `{"enabled": false, ...}`；
   这不是故障。
4. 控制面任何失败都不能拖垮集群启动：适配器启动异常只记日志，旧面照常服务。

> **上线前必读（当前 main 的真实状态）**
> `hive cluster serve` 会挂上适配器，但 `hive_control/adapter.py` 组装
> `ControlPlane` 时没有传入 `node` / `address` / `listen_port` / `config`，
> 构造函数会抛 `TypeError` 并被适配器降级吞掉。因此现在
> `GET /api/cluster/status` 稳定返回 `plane_available:false`、`degraded:true`、
> `multicast_mode:"off"`：控制面**实际没有工作**，旧 HTTP 面不受影响。
> 下文描述的是契约规定的目标行为；灰度前请先用 §5 的判据确认这一项已修复
> （`plane_available:true`）。该装配缺陷属于 T-0311 的范围，不在本文档卡内。

## 2. 端口与套接字

| 端口 | 协议 | 用途 | 默认绑定 | 谁能访问 | 备注 |
|---|---|---|---|---|---|
| **8788** | TCP | 集群 HTTP（旧面 + 新增 status/pull 路由） | `0.0.0.0`（`--host`） | 局域网 | 配了 token 时写/读接口都要 token |
| **8789** | TCP | 控制面上行 + 拉取 | 节点的对外地址（`--advertise`） | 局域网节点 | **= HTTP 端口 + 1**；改 `--port` 后跟着变 |
| **47899** | UDP | 控制面：组播 `239.255.42.1` + Hello/回退单播 | 同上 | 同一网段 | 只有控制面 Leader 往组播地址发 |
| **8789** | UDP | 旧面的广播发现（与上面的 TCP 8789 同名不同协议） | `0.0.0.0` | 同一网段 | 可 `--no-discover` 关闭 |
| — | Unix socket | Worker ↔ serve 上报/通知 | `/tmp/hive-control.sock`（Windows：`%TEMP%\hive-control.sock`） | 本机 | 不经过网络，不受 token 保护 |

查看占用（POSIX）：

```bash
lsof -nP -iTCP:8788 -sTCP:LISTEN
lsof -nP -iTCP:8789 -sTCP:LISTEN
lsof -nP -iUDP:47899
# FreeBSD 没有 lsof 时
sockstat -4l | grep -E '8788|8789|47899'
```

Windows：

```bat
netstat -ano | findstr /R "8788 8789 47899"
```

防火墙至少放行：节点之间 **TCP 8789** 与 **UDP 47899**；HTTP 8788 按原规则。
组播还需要交换机/主机允许 IGMP（见 §4）。

## 3. 状态 API

### 3.1 `GET /api/cluster/status`

未配置集群 token 时可直接访问；配置了 token 时二选一：

```bash
curl -s http://192.168.0.88:8788/api/cluster/status

# 配了 token 的集群
curl -s -H "X-Hive-Cluster-Token: $HIVE_CLUSTER_TOKEN" \
     http://192.168.0.88:8788/api/cluster/status
# 等价写法： -H "Authorization: Bearer $HIVE_CLUSTER_TOKEN"
```

当前 main 实测（降级态，已省略 `local_agents` 明细）：

```json
{
  "ok": true,
  "control": {
    "enabled": true,
    "running": true,
    "plane_available": false,
    "degraded": true,
    "multicast_mode": "off",
    "control_leader": null,
    "control_epoch": 0,
    "control_port": 47899,
    "peers": [{"host": "127.0.0.1", "port": 47899, "node_id": "t0314-doc-0c55ede6"}],
    "queues": {"pull": 0, "uplink": 0, "downlink": 0, "notify": 0},
    "counters": {"pull_requests": 0, "pull_completed": 0, "pull_failed": 0}
  }
}
```

字段解释：

| 字段 | 含义 | 运维判读 |
|---|---|---|
| `enabled` | 该 `Cluster` 是否装配了控制面 | `false` 表示不是 `serve` 入口（或程序化构造），不是故障 |
| `running` | 适配器是否已 `start()` | `false` 且 `enabled:true` → 启动就失败，看日志 |
| `plane_available` | 编排器是否真的装配成功 | **`false` 就是控制面没工作**；旧面不受影响 |
| `degraded` | `plane_available` 的反面 | `true` 时下面所有控制面指标都不可信 |
| `multicast_mode` | `multicast` / `fallback` / `off` | `fallback` 说明组播不可用，已逐节点单播；`off` 是没装配 |
| `control_leader` | 控制面 Leader 的 router_id（整数） | `null` = 还没选出；与旧面 `leader` 是两回事 |
| `control_epoch` | 控制面 Leader 任期 | 一直涨说明在反复切主（§4） |
| `control_port` | **控制面 UDP 端口**，默认 47899 | 不是上行 TCP；上行 TCP 是 HTTP 端口 + 1 |
| `peers` | 从旧集群节点表算出的控制面邻居（host + 47899） | 为空多半是节点表/发现没起来 |
| `queues` | 拉取/上行/下行/通知队列长度 | 持续只增不减 → 对端不收或线程卡住 |
| `counters` | 控制面累计计数（拉取请求/完成/失败等） | 与 `pull.status` 对照看 |

> 说明：适配器对外只汇总上述字段。`ttl_violations`、`fallback_sends` 这类细粒度
> 计数器目前只在编排器内存里，没有并进 HTTP 摘要；排障时以进程日志为准。

### 3.2 `POST /api/cluster/pull` 与结果查询

拉取是异步的：HTTP 只回 202 + `request_id`，结果靠第二个接口查（D15）。

```bash
# 触发一次增量拉取
curl -s -X POST http://127.0.0.1:8788/api/cluster/pull \
     -H 'Content-Type: application/json' \
     -d '{"project":"hive","mode":"incremental"}'

# => 202
# {"ok":true,"request_id":"27ee1d9f...","state":"pending",
#  "mode":"incremental","project":"hive","delegated":false,"degraded":true}

# 查结果（running / done / error）
curl -s "http://127.0.0.1:8788/api/cluster/pull/status?id=27ee1d9f..."
```

| 项 | 说明 |
|---|---|
| `mode` | `incremental`（默认）或 `full`；其它值直接 400 |
| `project` | 空字符串表示按本地 agent 涉及的项目自动挑 |
| `state` | `pending` / `running` / `done` / `error` / `failed` / `rejected` |
| `delegated` | `true` 表示真的交给了编排器；`false` 说明是降级/未装配 |
| HTTP 码 | 202 已受理；200 已结束；400 参数错；404 未知 id；503 控制面未启用（非 serve 入口） |
| 配额 | 增量每 project 10 次/秒；全量每 project 1 次/60 秒；超限由拉取协议回 `retry` + `after_ms` |

注意事项：

- 人工拉取走独立队列与线程池（容量 64），**不触发下行**（G5），也不改 Git。
- `full` 会按页（默认每页 100 条）拉全量，比增量贵得多，别当健康检查用。

## 4. 回退模式：组播发不出去时

这里的「回退」是**传输回退**（组播 → 逐节点单播），不是版本回滚（版本回滚见 §5）。

**触发条件（D9）**，满足任一条：

1. 接收端 `IP_ADD_MEMBERSHIP` 失败（网卡不支持、容器无组播、被内核策略禁掉）；
2. 连续 30 秒没有收到任何有效下行，但上行 TCP 仍能确认 Leader 存活。

**如何确认**：

```bash
curl -s http://127.0.0.1:8788/api/cluster/status \
  | python3 -c 'import json,sys; c=json.load(sys.stdin)["control"]; print(c["multicast_mode"], c["control_leader"], c["control_epoch"])'
```

`multicast_mode` 变成 `fallback` 即已回退；`off` 不是回退，是控制面没装配（§1 的上线前必读）。

**行为差异**：语义不变（同样的条目、同样的 TTL=1 校验），只是 Leader 改成给每个
已知节点单独发 UDP。成本和延迟随节点数线性增长，但不会丢正确性。

**如何恢复**：

- 回退**不会自动切回组播**（避免在两种模式间抖动）；修好网络后**重启进程**，
  启动时会重新尝试加入组播组。
- 排查顺序：`ip maddr show` / `netstat -g` 看组播组是否加入 → 交换机 IGMP snooping
  是否把端口裁掉 → 主机防火墙是否放行 UDP 47899 → 容器/虚拟网卡是否支持组播。
- 单节点集群本来就没有邻居，`fallback` 与 `multicast` 对业务没有区别，不用处理。

## 5. 灰度、关闭与回滚

### 5.1 灰度顺序

控制面是**加法**：旧面的路由、选主、租约、store 都不变，所以可以按节点灰度。

1. 先升级**一台非关键节点**（不要先动生产 Leader），重启 `hive cluster serve`；
2. 等过 `waiting_interval`（默认 40 秒）和 `heartbeat_timeout`（6 秒），看目标态；
3. 观察至少 15 分钟（覆盖 30 秒组播回退窗口和一次租约续约周期）；
4. 再逐台铺开；任何一台出现 §5.3 的回滚信号就停下。

灰度通过的判据（全部满足）：

| 判据 | 期望 |
|---|---|
| `control.enabled` / `running` | `true` / `true` |
| `control.plane_available` / `degraded` | `true` / `false` |
| `control.control_leader` | 非 `null`，且全网看到同一个值 |
| `control.control_epoch` | 稳定，不持续递增 |
| `control.multicast_mode` | `multicast`（或单节点 `fallback`） |
| `control.queues` | 有界，不持续增长 |
| 旧面 `/api/cluster/state` / `/api/cluster/health` | 与升级前一致 |

### 5.2 如何关闭控制面

**当前版本没有运行时开关**：D14 规定只有 `hive cluster serve` 入口把
`Config.control_plane` 置 `True`，没有 CLI 参数、环境变量或 `config.json` 键可以关它。
能关的只有两种场景：

- **程序化嵌入**（单测、脚本里直接 `Cluster(...)`）：默认就是关闭的，不要手动置位即可；
- **已部署节点**：只能做版本回退（下一节），或者在启动入口去掉置位那行（属于改代码，需走评审）。

不要试图用 `config.json` 里的字段关控制面：那个文件不是运行时配置来源，
写了也不会生效。

### 5.3 版本回滚

触发条件（出现任一条就回滚，不要边观察边硬扛）：

- `plane_available:false` 且重启后依旧（装配失败）；
- 控制面反复切主：`control_epoch` 每分钟涨多次；
- `8789` 端口起不来，或控制面异常把 `serve` 启动拖慢/拖挂；
- 旧面 `/api/cluster/health` 超时、看板掉线等**旧面**回归；
- 节点 CPU/网络被控制面明显挤占，且关不掉。

回滚步骤（在出问题的节点上）：

```bash
# 1. 找到升级前的提交（示例：升级提交是 abc1234）
cd ~/dswork/hive
git log --oneline -10

# 2. 退到升级前（不要动 main 分支；部署目录用自己的方式）
git checkout <升级前的提交>

# 3. 重启节点（沿用原来的端口/状态目录/种子参数）
python3 hive.py cluster restart --port 8788 --state-dir ~/.hive/cluster

# 4. 确认旧面恢复
curl -s http://127.0.0.1:8788/api/cluster/health
curl -s http://127.0.0.1:8788/api/cluster/state | head -c 300
```

回滚后：

- 控制面相关路由会退回旧实现：`/api/cluster/status` 可能 404 或不再有 `control` 段，
  以回滚到的版本为准；
- `/tmp/hive-control.sock` 与 `/tmp/hive-incarnation` 可以留着，不影响旧面；
  确认不再升级再删；
- Git、store、租约都不受控制面回滚影响（控制面从不写它们）。

## 6. 常见故障

| 现象 | 先看什么 | 处置 |
|---|---|---|
| `degraded:true`、`plane_available:false` | 启动日志里有没有 `control: 启动失败`；是否为 `serve` 入口 | 当前 main 的已知装配缺陷（§1）；旧面可用，先不要把它当生产依赖 |
| `multicast_mode:"fallback"` | 组播组是否加入、交换机 IGMP、UDP 47899 防火墙 | 修网络后**重启**才回组播；不修也能跑，只是逐节点单播 |
| `8789` 端口起不来 | `lsof -nP -iTCP:8789`；是否被别的服务/旧进程占着 | 杀掉旧进程或改 `--port`（上行端口跟着变成 N+1）；端口冲突会让控制面整体降级 |
| `control_leader` 一直是 `null` | 邻居 `peers` 是否为空；UDP 47899 双向是否通；是否还在 40 秒等待期 | 先等过 `waiting_interval`；再查防火墙/网段；控制面无投票，不需要凑多数 |
| `control_epoch` 一直涨 | 是否有人频繁重启、网络是否抖动；旧面 Leader 是否同时在抖 | 控制面 6 秒收不到心跳就重选；先稳住网络与进程，再谈调参 |
| 下行包被丢（TTL 告警） | 编排器内存计数 `ttl_violations`（当前未并进 HTTP 摘要，看日志/自检） | TTL≠1 的包按 I4 直接丢弃；检查中间设备是否改写 TTL、是否有代理/中继把包转进来 |
| 拉取一直 `retry` | `pull.status` 与 `counters.pull_rejected/pull_failed`；`after_ms` | 配额是增量 10 次/秒/project、全量 1 次/60 秒/project；按 `after_ms` 退避，别连点 |
| Worker 不上报 | `/tmp/hive-control.sock` 是否存在；`worker_sock.connections`；agent 名是否本机登记 | 删掉残留 socket 后重启 serve；Windows 看 `%TEMP%\hive-control.sock`；同机多用户时检查 socket 权限 |
| `/api/cluster/pull` 返回 503 | 该节点是不是 `serve` 入口 | 程序化/嵌入式实例默认不开控制面（D14），不是故障 |
| `/api/cluster/status` 返回 500 | 适配器 `status()` 异常，`error` 字段有类型和信息 | 旧面不受影响；按错误信息修配置或回滚版本 |

日志位置：`<state_dir>/cluster.log`（默认 `~/.hive/cluster/cluster.log`），
控制面的启动/切主日志都在这；单个文件超过 5 MB 会滚动成 `cluster.log.1`。

## 7. 安全边界

1. **假设局域网可信**。控制面的 TCP 8789、UDP 47899、Unix socket **都没有认证、
   没有加密**：任何能连上这些端口的人都能上报/收走状态。请用网段隔离、主机防火墙
   和 VLAN 划边界，不要把 8789/47899 暴露到公网或不可信办公网。
2. **token 只保护 HTTP 面（8788）**。`--token` / `HIVE_CLUSTER_TOKEN` 只作用于 HTTP
   路由；给控制面端口配 token 没有任何效果。token 建议用环境变量传，
   不要写在命令行（`ps` 能看到）。
3. **控制面不替代 Git（I1）**。控制面里的状态、`expiring` 提示都只是缓存/提示：
   - 判断一张卡归谁，仍然以 Git 分支与 claim 为准；
   - `expiring` 只是「租约可能过期」的提醒（D4），不会自动回收、不会写回 Git；
   - 控制面整层挂掉，集群仍能靠旧面和 Git 工作，只是跨机状态收敛变慢。
4. **Unix socket 是本机信任边界**。`/tmp/hive-control.sock` 在共享主机上受 umask
   约束；多用户机器请收紧 `/tmp` 权限或改用隔离的运行用户。
5. **不要用控制面状态做审计**。它是可丢的提示通道（队列满会丢 steady、通知会丢），
   审计看 Git 的结果与 `results/`。
