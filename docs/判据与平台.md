# 判据与执行平台

> 2026-11-02 立。起因：T-0221 / T-0222 两张卡**产物完全合格**，却各被判 failed、各浪费一轮。
> 原因不在代码，在判据的写法与执行平台不匹配。这份文档是给领卡的 agent 看的操作口径。

---

## 一、问题是什么

卡上的 `verify`（执行契约里的「预期输出」）常写成 POSIX 风格：

```sh
head -1 LICENSE | grep -qi mit
! grep -qiE '\(bsd|apache-2\)' README.md
test -z "$(git ls-files | grep '\.docx$')"
```

这些在 Linux / FreeBSD / macOS 上没问题。但 **Windows worker 用 `cmd.exe` + `shell=True`**：

| 写法 | Windows 结果 |
|---|---|
| `head` / `grep` / `awk` / `sed` / `wc` | 不在 PATH（在 `C:\Program Files\Git\usr\bin`，未导出）→ **exit 255** |
| `!` 取反 | `!` 不是 cmd 语法 → **exit 255** |
| `$(...)` 命令替换 | cmd 不支持 → 失败 |
| `test -f x` | ✅ `hive_compat` 垫片会改写成 Python 判断 |
| `! test -f x` | ✅ 同上，垫片认识 |
| `a -eq b` | ✅ 垫片认识 |

`hive_compat.py` 只覆盖 `test -f/-e/-d/-r/-s`、`! test`、`-eq/-ne/-lt/-gt/-le/-ge`、`true`。
**其它一律原样丢给 cmd.exe。**

后果：判据 exit 255 → 结果记 `failed` → 卡变 `blocked`，而产物其实是好的。

---

## 二、写判据：优先用跨平台写法

`git` 是 hive 的硬依赖，Windows 上一定装了（hive 自己要 push）。所以把 grep 换成 `git grep`：

| 目的 | 不要写 | 改写成 |
|---|---|---|
| 文件里有某串 | `grep -q X f` | `git grep -q X -- f` |
| 文件里**没有**某串 | `! grep -q X f` | `git grep -L X -- f` |
| 文件存在 | `test -f f` | 不变（垫片支持） |
| tag 存在 | `git tag \| grep -qx v1` | `git rev-parse -q --verify refs/tags/v1` |
| 正则交替 | `git grep -qE 'a\|b' -- f` | `git grep -q -e a -e b -- f`（**别用单引号包竖线**） |

**`git grep -L` 是关键**：它列出「**不含**匹配」的文件，没找到就输出文件名并 **exit 0**——
正好等价于 `! grep -q`，而且不需要 `!`。这是本次事故里最有用的一条。

> ⚠️ **单引号在 cmd.exe 里不是引号**。`'a|b'` 会被劈成
> `git grep -qE 'a` 管道给 `b' -- f`，实测报「'b'' 不是内部或外部命令」，exit 255。
> 这是 T-0225 的失败原因（T-0221/T-0222 之后第三个）。
> 现版 hive 已在 `verify_command` 里做了 Windows 专有补救：把「含 `|` / `&` 的单引号片段」
> 自动换成双引号。**但这只是兜底**——写卡时请直接用 `-e a -e b` 或双引号，别依赖它。

> 坑：`git grep` 只搜**已跟踪**文件。新增的文件（例如刚写的 `LICENSE`）必须先 `git add`，
> 否则判据会 exit 1（文件明明在，库里的看不见）。

## 三、判据确实跑不了：换台机器跑，不要改判据

**不要为了让 Windows 过而把判据改弱**（比如 `head|grep` 改成 `test -f`）——那等于丢掉验收强度，
以后没人知道文件内容对不对。

正确做法：**到 192.168.0.88 上跑**。

| 项 | 值 |
|---|---|
| 主机 | `192.168.0.88` |
| 系统 | FreeBSD 15.1-RELEASE-p1（`head`/`grep`/`awk`/`sed`/`test` 都在 `/usr/bin`） |
| 用户 | `workbuddy` |
| 密码 | 工作目录 `.env` 里的 **`SSH_PASS_WORKBUDDY`** |

> ⚠️ **`.env` 里这个密码值尾部带空格**（录入残留）。取值必须先 strip，
> 否则认证会以「Permission denied」失败，而你会以为是密码错。

### POSIX 上一行跑通的做法

```sh
PW=$(sed -n 's/^SSH_PASS_WORKBUDDY=//p' .env | tr -d '\r\n' | sed 's/[[:space:]]*$//')
printf '#!/bin/sh\necho "%s"\n' "$PW" > /tmp/ap.sh && chmod 700 /tmp/ap.sh
SSH_ASKPASS_REQUIRE=force SSH_ASKPASS=/tmp/ap.sh setsid -w \
  ssh -o PreferredAuthentications=keyboard-interactive,password \
      -o PubkeyAuthentication=no -o NumberOfPasswordPrompts=1 \
      workbuddy@192.168.0.88 '<把判据原样放这里>'
rm -f /tmp/ap.sh
```

注意 `-o PreferredAuthentications=keyboard-interactive,password` 和 `PubkeyAuthentication=no`：
0.88 只开 `publickey` 与 `keyboard-interactive`，没有纯 `password`，不指定会拿不到密码提示。

### Windows worker 上

Windows 10+ 自带 `ssh.exe`，但 `SSH_ASKPASS` 支持不全。按可用性依次尝试：

1. `plink -batch -pw "<密码>" workbuddy@192.168.0.88 "<命令>"`（装了 PuTTY 就有）
2. Python + `paramiko`（`pip show paramiko` 有就用）
3. 都不行：**如实写进 `.hive/summary.md`**，说明「判据需要 POSIX 环境，本机无法执行」，
   然后 `hive_submit` 时附上手动复核的证据（例如把文件内容贴出来）。**不要伪造 exit 0。**

## 三之二、不产出文件改动的卡（打 tag / 纯验收）

hive 有一道「零改动」闸门：一次提交如果 `changed_files` 为空就判 failed，
防的是「agent 没干活却报完成」。但它会误伤两类卡：

- **只打 tag**（T-0227）：tag 在 `refs/tags`，不是文件改动；
- **纯验收 / 台账卡**：`paths: []`，卡面本就写着「不改代码」。

两种解法（现版 hive 都已覆盖）：

| 情形 | 做法 |
|---|---|
| `paths: []`（验收/台账卡） | **自动放行**，无需任何声明 |
| 有 paths 但确实只打 tag | 卡面 frontmatter 加 `allow_empty_diff: true` |

> ⚠️ 历史坑：`allow_empty_diff` 曾会被 `retry` / `take` 重写卡片时**丢掉**
> （`write_card` 只输出 `TASK_FIELDS` 里的键），于是出现「加开关 → retry → 开关消失 →
> 又判零改动」的死循环。现已修：`write_card` 会保留所有非内部字段，
> 并把这个性质写成单测。

## 四、提交前自查

- [ ] 判据里没有裸 `grep` / `head` / `awk` / `sed` / `!` / `$(...)`
- [ ] 新增文件已经 `git add`（否则 `git grep` 判不到）
- [ ] 判据在本机真跑过一遍，看到 exit 0，而不是「应该能过」
- [ ] 跑不了的话，在 summary 里写明去了 0.88、命令是什么、输出是什么

## 五、这件事的教训（写给下次写卡的人）

1. **判据是契约，不是注释**。它会在目标平台上真实执行；写的时候要问「这台机器认识这个命令吗」。
2. **失败要先分清是产物错还是判据错**。T-0221/T-0222 的产物两次都是对的，
   但两次都因为判据被判 failed——如果不看 `results/<id>.json` 里的 `verify[].code`，
   会误以为 agent 没干活。
3. **改判据属于「卡外改动」**，agent 不该自己动（会把验收强度改弱）。所以正确的顺序是：
   agent 报「判据跑不了」→ 人修判据 → 重跑。这条链路现在由本文件的第二节兜住大部分情况。
