# 从「聊天里手工分发」迁移到蜂巢

> 适用：现在是一台 Windows 开多个 agent，一个 AI 列任务、你复制粘贴分发。
> 目标：两周内把「分发」和「收结果」交给任务总线，人只做拆卡和合并。

## 第 0 周：并行跑，不切

旧流程不变，只做三件事：

1. Gitea 建 `skywalk/hive`，把工作目录下的 `hive/` 推上去；
2. 在 fb88 登记 `fb88-dsh`，跑一张**文档卡**（改 `docs/` 一段）；
3. 不要求别人用，只观察：任务卡信息够不够、verify 会不会误判。

验收：从建卡到结果落库 < 10 分钟，且你能只看 `hive status` 就知道做到哪。

## 第 1 周：一个仓库、两类卡

- 只接 `light`，只开 `fb88-dsh` 一个 worker；
- 只写两种卡：**代码卡**（exec）和**验收卡**（verify）；
- 每天最多 3 张并行，路径必须互斥；
- 合入已自动化：`hive land T-xxxx --apply`（见操作手册 §5.1）。

验收：一周 5–8 张卡，没有一次「两个 agent 改同一文件」。

## 第 2 周：Windows 接入 + 看板

- `windows/bootstrap.ps1` 把 Win10 登记成 `verify` 验收机；
- 跑通「诊断卡 → 修复卡 → 验收卡」三卡闭环；
- 开看板（`hive status --json` → dashboard），每天早上看一次；
- 开始记四个数：周期时间、一次通过率、人工介入、冲突次数。

验收：Windows 挂一次，任务能自动回收重派，不需要你去 VM 里收拾。

## 旧 → 新 对照

| 旧动作 | 新动作 |
|---|---|
| 在聊天里列 TODO | `hive task new` 写卡 |
| 复制粘贴给某个 agent | `hive dispatch --apply` 或 `assign` |
| 问「做到哪了」 | `hive status` / `hive result` |
| agent 说「做完了」 | `results/T-xxxx.json` + `verify` 退出码 |
| 人肉记谁在做什么 | `claim/T-xxxx` 租约 |
| 合并前翻聊天记录 | `git diff main...task/T-xxxx` |

## 先拿哪张卡试

优先选满足这四条的：

1. 只改一个目录；
2. 有现成测试命令；
3. 失败不会造成数据损坏；
4. 半天内能做完。

推荐：文档修订、单个测试补例、一个已知小 bug、CI 脚本调整。
不要拿「重构编译器」「跨三个仓的接口变更」当第一张卡。

## 常见失败模式

| 现象 | 原因 | 处理 |
|---|---|---|
| 卡分不出去 | agent 没声明 `repo`/`needs` | `hive doctor` 看警告；补 `capabilities` |
| 两张卡改同一文件 | `paths` 没写或重叠 | 加 `depends_on` 串行，或拆路径 |
| worker 说没任务 | 没 assign / 依赖没过 | `status` 看 state；`result` 看依赖 |
| 一直 running | VM 死机/agent 卡住 | `gc` + `retry`，缩短租约 |
| 结果推不上去 | 分支保护/token 权限 | 允许 `task/*`、`claim/*`、`res/*` |
| 合并冲突多 | 并行度太高 | 降到 3 张，路径互斥 |

## 成功标准（两周后回看）

- 80% 的卡不需要你复制粘贴；
- 你能在 10 秒内回答「现在有几张卡在跑、谁在跑」；
- 合并前的 diff 和测试结果是自动附带的，不靠回忆；
- Windows 挂掉不影响 FreeBSD 的进度；
- 你每天花在「分发/追问」上的时间 < 20 分钟。
