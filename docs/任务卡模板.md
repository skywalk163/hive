# 任务卡模板

任务卡是 `tasks/T-XXXX.md`，由总控写，worker 读。原则：**一张卡只做一件事，验收能自动判定**。

> **第一次接 hive 的 agent**：先读 [AGENT 快速上手](AGENT快速上手.md)（agent 视角的
> 接入指南，从配置 MCP 到交第一张卡，含实测输出和踩坑），再回来写卡。

## 字段速查

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | `T-0001`，全局唯一，和文件名一致 |
| `title` | 是 | 一句话说清做什么 |
| `repo` | 是 | `light` / `lightmem` / `lightharness` |
| `base` | 是 | 通常 `main`；验收卡写 `task/T-xxxx` |
| `state` | 是 | 创建时 `ready`，总控改 `assigned`/`done` |
| `owner` | 否 | 分派后写入 |
| `priority` | 是 | `P1` / `P2` / `P3` |
| `needs` | 否 | 能力标签，如 `windows`、`exe`、`freebsd` |
| `paths` | 否 | 允许改的路径；**验收卡留空** |
| `verify` | 是 | 至少一条能自动判定的命令 |
| `depends_on` | 否 | 前置任务号 |
| `lease_minutes` | 是 | Windows 30–60，FreeBSD 120–180 |
| `timeout_minutes` | 是 | agent 硬超时，卡越小越短 |
| `fresh` | 否 | `retry --fresh` 会置 true，从 main 重来 |

## 模板 A：代码修复（exec）

```markdown
---
id: T-0101
title: 修复 LLVM 后端在 Windows 上的路径分隔符
repo: light
base: main
state: ready
owner: null
priority: P1
needs:
  - freebsd
paths:
  - src/codegen/
  - tests/test_llvm_paths.py
verify:
  - python -m pytest -q tests/test_llvm_paths.py
depends_on: []
lease_minutes: 120
timeout_minutes: 60
created: 2026-10-23T00:00:00+08:00
---

## 背景

（为什么做；复现步骤；相关文档/issue）

## 要做什么

1. …
2. …

## 不要做什么

- 不要动 stdlib/
- 不要顺手格式化

## 完成标准

- verify 全绿
- summary 里贴出关键输出
```

## 模板 B：跨平台验收（verify）

```markdown
---
id: T-0102
title: 验收 T-0101 的 Windows 腿
repo: light
base: task/T-0101
state: ready
owner: null
priority: P1
needs:
  - windows
paths: []
verify:
  - light compile examples/hello.light -o build/hello.exe
  - python -m pytest -q tests/test_llvm_paths.py
depends_on:
  - T-0101
lease_minutes: 30
timeout_minutes: 20
created: 2026-10-23T00:00:00+08:00
---

## 背景

T-0101 已在 FreeBSD 上修完，需要 Windows 实机确认。

## 完成标准

- 两条 verify 全绿
- summary 里贴 Windows 版本、clang 版本、EXE 路径
```

要点：

- `paths` 必须为空，否则 `verify` 模式的 agent 会被 `dispatch` 跳过（它不改代码）；
- `base` 写被验收的 `task/T-xxxx`，worker 会检出那条分支来验；
- 租约和超时都要短，VM 死了不占卡。

## 模板 C：诊断（verify）

```markdown
---
id: T-0100
title: 诊断 Windows 上 LLVM 编译失败
repo: light
base: main
state: ready
owner: null
priority: P1
needs:
  - windows
paths: []
verify:
  - light compile examples/hello.light -o build/hello.exe > build/diag.log 2>&1 || true
depends_on: []
lease_minutes: 30
timeout_minutes: 20
created: 2026-10-23T00:00:00+08:00
---

## 要做什么

跑上面的命令，把 build/diag.log 的关键行、Windows 版本、clang --version
写进 `.hive/summary.md`。不要改代码。
```

## 模板 D：GUI / 手动（manual）

```markdown
---
id: T-0103
title: 用 Trae 把设置页改成新布局
repo: light
base: main
state: ready
owner: null
priority: P2
paths:
  - playground/static/
verify:
  - python -m pytest -q tests/test_playground.py
depends_on: []
lease_minutes: 240
timeout_minutes: 180
created: 2026-10-23T00:00:00+08:00
---

## 背景

GUI agent 在 worktree 里直接改；改完写 `.hive/summary.md`。
GUI 卡超时统一给 180 分钟（实测小浣熊一张文档卡用了约 65 分钟）。
```

## 反模式

| 反模式 | 后果 | 改法 |
|---|---|---|
| 一张卡改 3 个仓库 | worktree 跨仓、commit 混乱 | 拆成 3 张卡 + `depends_on` |
| 没有 `verify` | 结果无法判定，只能人看 | 至少加一条 `pytest`/`compile`/`test -f` |
| `paths` 写整个仓库 | 和别的卡冲突 | 写到目录/文件级 |
| 验收卡带 `paths` | 被 `dispatch` 跳过 | 验收卡 `paths` 留空 |
| 一张卡跑 3 小时 | 机器一挂全丢 | 拆小，`timeout_minutes` 收紧 |
| 任务卡里放 token | 泄漏进 git 历史 | 用环境变量/凭据服务 |

## 编号与命名

- 任务号 `T-0001` 递增；验收卡可以 `T-0101-V`，但 `id` 必须匹配文件名。
- 分支固定 `task/T-0101`；不要手工改分支名。
- 结果分支 `res/T-0101` 由 worker 推，`close` 时归档并删除。
