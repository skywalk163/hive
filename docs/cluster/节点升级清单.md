# 集群节点升级清单

> 换 `hive` 代码后，**每个节点都要各自更新并重启自己的集群进程**。
> 租约、选举、心跳这些状态是**主控签发的**：只升级跟随者没用，主控跑旧代码
> 就会继续按旧参数下发。这份清单解决的就是「改好了但没生效」。

## 为什么需要这份清单

2026-11-25 修掉两个租约 bug 并推到三端（`554cb2b`、`4730460`）：

- `_adopt_leader_locked(refresh_lease=True)` 只续本机租约，没写回
  `nodes[leader]["lease_until_epoch"]`，被维护循环的「防御性收敛」压回旧值
  → 每轮「续租 → 收敛 → 判过期 → 清空 → 重新采纳」；
- `DEFAULT_LEADER_LEASE_S` 与 `DEFAULT_IDLE_HEARTBEAT_S` 都是 `5.0`，空闲时
  心跳与租约同频撞车，现改为 `max(默认值, 空闲心跳 × 3)` = 15s。

实测结果：**只有本机（DESKTOP-6LFQUO8）生效**。主控 fb98 仍在跑旧代码，
下发的 `leader_lease_until` 还是 `now+5s`，跟随者只能照收 —— 所以
`state.json` 里 `leader_lost(主节点租约过期)` 仍会和 `leader_seen` 成对出现。

## 升级步骤（每个节点各做一遍）

### 0. 先查有没有在跑的任务

**这一步不能省。** 重启会中断该节点上正在执行的卡。

```bash
hive status                 # 看有没有 running
hive cluster status         # 看本节点角色与在线情况
```

- 有 `running` 的卡：等它跑完，或先 `hive block <TID>` 挂起再重启；
- 自己是 leader 且集群还有别的 follower：**先升级 follower**（见下节顺序）。

### 1. 更新代码

```bash
# fb98（FreeBSD）
git -C /home/skywalk/dswork/hive pull --ff-only

# IC6RTQ4（win11）
git -C C:\dswork\hive pull --ff-only
```

只用 `pull --ff-only`：
- 若本地有未提交改动，先 `git stash` 或问人，**不要** `reset --hard` 覆盖；
- 若 ff 失败说明有分叉，**停下**问人，不要 `push --force`。

### 2. 确认落后已清零

```bash
hive cluster restart      # 启动闸会先对比本仓 HEAD 与 origin/main 并告警
```

启动闸（`84760b4`）在 `cluster start/restart` 时会自检：落后就打印
`⚠ 正在运行的 hive 落后远端 N 个提交` 并给出上一条命令。看到这个警告，
说明第 1 步没生效。

## 重启顺序

**先 follower，最后 leader。**

先换主控会让集群短暂无主（租约到期 → 重新选举），影响面最大；follower
先换则集群一直有主，最坏也只是某个跟随者的视图短暂滞后。

1. 先重启 follower：**IC6RTQ4**（`C:\dswork\hive`）
2. 再重启 follower：**DESKTOP-6LFQUO8**（本机，已是最新）
3. 最后重启 **leader：fb98**（`/home/skywalk/dswork/hive`）

fb98 重启期间会发生一次主控切换（term +1），属正常现象。

## 升级后怎么验

### 1. 主控下发的租约要 ≥ 10s

旧代码是 `now+5s`，新代码是 `now+15s`。直接问接口：

```bash
curl -s http://192.168.0.88:8788/api/cluster/health | \
  python -c "import json,sys,time; d=json.load(sys.stdin); \
print('租约剩余 %.1fs' % (d['leader_lease_until_epoch'] - time.time()))"
```

**判定：租约剩余 ≥ 10 秒**（旧代码只有约 5s）。若仍显示 4~5s，
说明那个节点还是旧代码，回到第 1 步。

### 2. 租约过期不再成对出现

```bash
python -c "import json,os,collections; \
d=json.load(open(os.path.expanduser('~/.hive/cluster/state.json'),encoding='utf-8')); \
evs=d['state']['events']; c=collections.Counter(e['type'] for e in evs); \
print('leader_lost=%d leader_seen=%d' % (c['leader_lost'], c['leader_seen']))"
```

升级前两者数量接近相等（修前实测 55 / 54）。升级后观察 5 分钟，
`leader_lost` **不应再增长** —— 主控活着却反复"判死又复活"就是租约撞车的症状。

### 3. 日志不再刷屏

```bash
grep -c "采纳主控" ~/.hive/cluster/cluster.log
```

修复前同一 term 内累计过 44692 次。升级后空闲时这个计数应保持不动。

## 红线

- 不许 `git reset --hard` / `push --force` / `--no-verify`；
- 不许在还有 `running` 任务时重启对应节点；
- **不许手改 `state.json`** 或伪造租约数字来让"升级成功"看起来成立 ——
  判据要能由上面三条命令自动复现；
- 本清单只覆盖「部署 + 验证」。若发现代码还有问题，另开卡，不要在这里顺手改
  `hive_cluster.py` 的租约/选举逻辑。

## 一句话版本

```bash
# 每个节点：先查任务 → pull --ff-only → cluster restart
hive status && hive cluster status          # 有 running 就等
git -C <该节点的仓路径> pull --ff-only
hive cluster restart                        # 启动闸会告警是否真更新了
# 顺序：follower 先，leader 最后
```
