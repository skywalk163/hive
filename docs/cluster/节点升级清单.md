# 集群节点升级清单

> 换 `hive` 代码后，**每个节点都要各自更新并重启自己的集群进程**。
> 租约、选举、心跳这些状态是**主控签发的**：只升级跟随者没用，主控跑旧代码
> 就会继续按旧参数下发。这份清单解决的就是「改好了但没生效」。

## 为什么需要这份清单

2026-11-25 修掉两个租约 bug 并推到三端（`554cb2b`、`4730460`）：

- `_adopt_leader_locked(refresh_lease=True)` 只续本机租约，没写回
  `nodes[leader]["lease_until_epoch"]`，被维护循环的「防御性收敛」压回旧值
  → 每轮「续租 → 收敛 → 判过期 → 清空 → 重新采纳」；
- `DEFAULT_LEADER_LEASE_S` 与 `DEFAULT_IDLE_HEARTBEAT_S` 都是 `5.0`，空闲时
  心跳与租约同频撞车，现改为 `max(默认值, 空闲心跳 × 3)` = 15s。

修完当时的实测（11-25 03:00 前后）：**只有 DESKTOP-6LFQUO8 生效**。
主控 fb98 仍在跑旧代码，下发的 `leader_lease_until` 还是 `now+5s`，跟随者只能照收
—— 所以 `state.json` 里 `leader_lost(主节点租约过期)` 仍会和 `leader_seen`
成对出现。当晚的收口过程与实测数字见文末「2026-11-25 收口记录」。

## 升级步骤（每个节点各做一遍）

### 0. 先查有没有在跑的任务

**这一步不能省。** 重启会中断该节点上正在执行的卡。

```bash
hive status                 # 看有没有 running
hive cluster status         # 看本节点角色与在线情况
```

- 有 `running` 的卡：等它跑完，或先 `hive block <TID>` 挂起再重启；
- 自己是 leader 且集群还有别的 follower：**先升级 follower**（见下节顺序）。

### 1. 更新代码

```bash
# fb98（FreeBSD）
git -C /home/skywalk/dswork/hive pull --ff-only

# IC6RTQ4（win11）
git -C C:\dswork\hive pull --ff-only
```

只用 `pull --ff-only`：
- 若本地有未提交改动，先 `git stash` 或问人，**不要** `reset --hard` 覆盖；
- 若 ff 失败说明有分叉，**停下**问人，不要 `push --force`。

### 2. 确认落后已清零

```bash
hive cluster restart      # 启动闸会先对比本仓 HEAD 与 origin/main 并告警
```

启动闸（`84760b4`）在 `cluster start/restart` 时会自检：落后就打印
`⚠ 正在运行的 hive 落后远端 N 个提交` 并给出上一条命令。看到这个警告，
说明第 1 步没生效。

### 2.5 fb98 专属：换账号跑，别用 `hive` 别名

fb98 上这两件事和 Windows 节点不一样（2026-11-25 现场踩过）：

1. **仓和集群进程都属 `skywalk`**，`workbuddy` 账号连 `hive_autoupdate.py`
   都读不了（`PermissionError`），`git pull` 也会在 `.git/FETCH_HEAD`
   上被拒。用 `sudo -n -u skywalk` 换账号，并**显式给 HOME**，
   否则 `~/.hive/cluster` 会指到别的用户目录去：
   ```bash
   sudo -n -u skywalk env HOME=/home/skywalk \
     /usr/local/bin/python3 /home/skywalk/dswork/hive/hive.py \
     --dir /home/skywalk/dswork/hive cluster restart \
     --state-dir /home/skywalk/.hive/cluster --name fb98
   ```
2. **`hive` 不在 PATH 上**（`sh: hive: not found`），一律用
   `python3 hive.py --dir <仓路径> cluster ...` 这种全路径写法。

启动参数（`--store --claim-backend store --mcp --mcp-port 8790`）不用手抄：
`restart` 会从 `state_dir/config.json` 重建 argv，手抄反而容易漏 `--store`。
`/home/skywalk/dswork/hive/config.json` 那份是**死文件**，看都不看它。

### 2.6 `restart` 报「找不到 pid 文件」怎么办

老进程（`cluster.pid` 这个身份记录是后加的）没有落盘 pid 时，
`cluster restart` 会停在 `集群在运行，但找不到 pid 文件；请手动结束进程`，
然后 `start` 又看到端口已被占 → 什么都不做，看着像「重启成功」其实没换代码。

处理办法是**发 SIGTERM 让老进程自己优雅退出**（它的信号处理里会
`cluster.stop()`），确认端口不再响应后再 `cluster start`：

```bash
# 1) 找到老进程（属主必须是那个跑集群的账号）
ps -o user,pid,etime,command -ax | grep "cluster serve" | grep -v grep
# 2) 用属主身份发 TERM，等它退出（等不到再查日志，别直接 KILL）
sudo -n -u skywalk kill -TERM <PID>
# 3) 换新代码重新拉起（参数从 config.json 重建，不要手抄）
sudo -n -u skywalk env HOME=/home/skywalk /usr/local/bin/python3 \
  /home/skywalk/dswork/hive/hive.py --dir /home/skywalk/dswork/hive \
  cluster start --state-dir /home/skywalk/.hive/cluster --name fb98
```

升完检查两处：`ps` 里新进程的 `etime` 是分钟级，`health.uptime_s` 归一。

### 2.7 重启主控 = 换主，别按老地址验

主控重启期间会发生一次选举，**主控权通常落到别的节点上**（2026-11-25 实测
`fb98` 重启后由 `DESKTOP-6LFQUO8` 接任，term 3923 → 3925）。
所以「主控下发的租约 ≥ 10s」必须照着 health 里的 `leader` 字段去问那一台；
顺手确认新主控自己也是新代码（`uptime` 短 + 租约 ≥ 10s），否则白换。

### 2.8 ⚠ 在 agent 的 exec/后台任务里起集群会被回收（最容易误判成成功）

**这是本清单里最危险的一个坑**：它当场所有判据都满足，事后才失效。

现象（2026-11-25，`DESKTOP-IC6RTQ4`，出自 T-0473 的记录）：

- `hive cluster restart` / `cluster start` 打印「集群已启动」，**当场 `health`
  也通**、`uptime` 归零、租约升到 14s —— 看起来完全成功；
- **工具调用一结束，进程就消失**：端口不通、集群视图里变 `dead`；
- 改用计划任务拉起，同样被结束（Windows `LastTaskResult=0xC000013A`，
  即 Ctrl+C 语义）；
- `cluster.log` 里**没有 traceback** —— 它不是自己崩的，是被外部终止，
  所以去日志里找异常会一无所获。

实际时间线：`09:57:48` 重启成功并测到 `uptime` 归零、租约 14.2s；
**`10:01:01` 被回收**（约 3 分钟后），节点从 `alive` 变 `dead`；
最后由常驻方式重新拉起才稳定（`uptime` 0.05h、租约 13.5s）。

**根因**：某些 agent 沙箱会在**工具调用结束时回收「脱离会话」的子进程**。
集群进程是后台常驻的，正好落在这个判定里。所以「调用当场 health 通」
不构成成功证据。

**判定失败的信号**：重启后 `uptime` 很小、当场 health 通，但**过一会儿就没了**。

**正确做法** —— 在**普通终端 / 登录会话**里执行，或走计划任务：

```cmd
:: 常驻脚本方式（节点名与用户按实际替换）
C:\Users\<user>\.hive\run-cluster-<节点名>.cmd

:: 或用计划任务
schtasks /Run /TN HiveCluster-<节点名>
```

**不要**把集群进程套在 agent 的 exec / 后台 job 里跑 —— 会被回收。

**交付前必做**：重启后**隔 3~5 分钟复采一次** `health.uptime_s`，
确认进程还活着且 `uptime` 仍在正常增长。只看当场那一次会被假成功骗过去，
这正是 IC6RTQ4 那次反复的由来。

## 重启顺序

**先 follower，最后 leader。**

先换主控会让集群短暂无主（租约到期 → 重新选举），影响面最大；follower
先换则集群一直有主，最坏也只是某个跟随者的视图短暂滞后。

1. 先重启 follower：**IC6RTQ4**（`C:\dswork\hive`）
2. 再重启 follower：**DESKTOP-6LFQUO8**（本机，已是最新）
3. 最后重启 **leader：fb98**（`/home/skywalk/dswork/hive`）

fb98 重启期间会发生一次主控切换（term +1），属正常现象。

## 升级后怎么验

### 1. 先逐节点看：还有谁在跑旧代码

**判据跟着节点走，不要只看一个数。** 旧代码的节点不认主控下发的租约时长，
而是拿自己的默认值（5s）重算一遍，所以它自己的 `/api/cluster/health`
永远报 4~5s —— 这个 4~5s 就是「这台还是旧代码」的指纹。

```bash
python - <<'PY'
import json, time, urllib.request
for name, base in [("fb98", "http://192.168.0.88:8788"),
                   ("IC6RTQ4", "http://192.168.0.101:8788"),
                   ("6LFQUO8", "http://192.168.0.100:8788")]:
    d = json.load(urllib.request.urlopen(base + "/api/cluster/health", timeout=4))
    left = d.get("leader_lease_until_epoch", 0) - time.time()
    print(f"{name:9} role={d.get('role'):8} up={d.get('uptime_s', 0) / 3600:5.1f}h "
          f"租约剩余={left:5.1f}s leader={(d.get('leader') or {}).get('name')}")
PY
```

- `up` 几个小时的进程 = 老进程（改完代码没重启）；
- `租约剩余` 4~5s 的节点 = 旧代码；≥ 10s = 新代码。

### 2. 主控下发的租约要 ≥ 10s

旧代码是 `now+5s`，新代码是 `now+15s`（`max(默认值, 空闲心跳 × 3)`）。
直接问**主控那台**的接口：

```bash
curl -s http://192.168.0.88:8788/api/cluster/health | \
  python -c "import json,sys,time; d=json.load(sys.stdin); \
print('租约剩余 %.1fs' % (d['leader_lease_until_epoch'] - time.time()))"
```

**判定：租约剩余 ≥ 10 秒**（旧代码只有约 5s）。若仍显示 4~5s，
说明主控还是旧代码 —— 主控重启后可能换了台（见下条），要照着
`leader` 字段去问那一台。

### 3. 租约过期不再成对出现（注意 120 条环形缓冲）

`state.json` 的 `events` 只保留最近 120 条，而且卡级 `lease_expired`
（任务租约）会把它冲满 —— **直接数 `leader_lost` 的总数会忽大忽小，
不能当判据**。要看的是「新增」：采样期间 `leader_lost` 有没有增长。

```bash
python - <<'PY'
import collections, json, os, time
p = os.path.expanduser("~/.hive/cluster/state.json")
def snap():
    st = json.load(open(p, encoding="utf-8"))
    st = st.get("state", st)                     # 两种落盘格式都兼容
    c = collections.Counter(e["type"] for e in st.get("events", []))
    return c["leader_lost"], (st.get("leader_id") or "")[:8]
lost0, lid0 = snap()
flips = []
for _ in range(18):                              # 3 分钟，10s 一拍
    time.sleep(10)
    lost, lid = snap()
    if (lost, lid) != (lost0, lid0):
        flips.append((round(time.time()), lost0, lost, lid0, lid))
    lost0, lid0 = lost, lid
print("leader 变化次数:", len(flips), flips[:5])
PY
```

空闲 3 分钟里 `leader_lost` **不应增长**、`leader_id` **不应变化**。
主控活着却反复"判死又复活"就是租约撞车的症状。

### 4. 日志不再刷屏

```bash
grep -c "采纳主控" ~/.hive/cluster/cluster.log
```

修复前同一 term 内累计过 44692 次。升级后空闲时这个计数应保持不动。

## 红线

- 不许 `git reset --hard` / `push --force` / `--no-verify`；
- 不许在还有 `running` 任务时重启对应节点；
- **不许手改 `state.json`** 或伪造租约数字来让"升级成功"看起来成立 ——
  判据要能由上面三条命令自动复现；
- 本清单只覆盖「部署 + 验证」。若发现代码还有问题，另开卡，不要在这里顺手改
  `hive_cluster.py` 的租约/选举逻辑。
