# 冲突与锁模型详解

> 本文是 hive 防冲突机制的专文。新人写卡时最常犯的错，是把 `paths` 写成整仓或留空，
> 反而制造假冲突或真冲突。本文把「怎么声明、为什么这么判、判错了会怎样」一次讲透。
> 配套规则见 [任务卡模板.md](任务卡模板.md)、[多机并行开发.md](多机并行开发.md) §4.1 与 §5。

---

## 当前模型

一句话总览：**分支隔离 + claim 租约 + `paths` 互斥 + `land` 串行，四层保障**。

| 层 | 机制 | 防的是什么 | 在哪实现 |
|---|---|---|---|
| 分支隔离 | 每张卡一个 `task/T-xxxx` worktree | agent 之间物理上就看不到对方的未提交改动 | `Worker.prepare` 建 worktree |
| 租约锁 | `claim/T-xxxx` git ref，`push` 非快进即失败 | 同一张卡不会被两个 agent 同时干 | `Worker.claim`（`hive.py`） |
| 路径互斥 | dispatch 检查 `paths` 重叠 + `HIVE_MAX_PER_REPO` | 两张不同的卡改同一片文件 | `Hive._paths_conflict`（`hive.py:1099`） |
| 合流串行 | `land` 一次合一张，冲突显式暴露 | 最后合并时的互相覆盖 | `Hive.cmd_land`（`hive.py`） |

关键点：**前两层管「谁在干、能不能同时干」，第三层管「派不派得下去」，
第四层管「合流时翻不翻车」**。四层互补，缺一层都会留下漏洞——例如分支隔离只保证
「干活时不冲突」，但两张卡改同一文件各自都能提交，`land` 时才暴露冲突（详见
[与 land 的关系](#与-land-的关系)）。

## paths 字段

`paths` 是任务卡 frontmatter 里的一个可选列表，声明「这张卡会动哪些文件 / 目录」。
它是防冲突的**第一道闸**：两张同时在飞的卡，只要 `paths` 有重叠，dispatch 就不会
把它们同时派出去。

```yaml
paths:
  - src/codegen/          # 目录（带尾斜杠，覆盖其下一切）
  - tests/test_llvm_paths.py
```

规则与惯用法：

- **宁写文件级、别写整仓。** `paths: [src/]` 会覆盖 `src/` 下所有文件，等于和任何碰
  `src/` 的卡都冲突，白白牺牲并行度。
- **验收（verify）卡必须留空。** 验收卡不改代码，只跑命令；若带了 `paths`，`dispatch`
  会把它当成「会改代码的卡」而跳过它，导致验收永远不派。正确写法见
  [任务卡模板.md](任务卡模板.md) 模板 B（`paths: []`）。
- **没声明 `paths` = 可能改任何地方。** 这一条会触发「保守冲突」（见下一节），所以
  `paths` 留空只适合 verify 卡，代码卡一定要写。
- `paths` 只在 **dispatch 阶段** 用于互斥判断；它**不是**强制性的写入沙箱——agent 改了
  `paths` 之外的文件，提交时若开启了严格模式会被拒绝（见 `Worker.submit` 里的
  `out_of_paths` 检查）。

## 目录前缀匹配

这是 hive 现行（也是唯一上线）的冲突判定算法，代码在 `hive.py:1089` 的
`Hive._path_overlap` 与 `hive.py:1099` 的 `Hive._paths_conflict`。

### 判定规则

`_path_overlap(x, y)` 的核心逻辑：

```python
def _path_overlap(x: str, y: str) -> bool:
    nx, ny = x.strip().rstrip("/"), y.strip().rstrip("/")
    if not nx or not ny:
        return True          # 空串等于「任何地方」
    if nx == ny:
        return True
    return nx.startswith(ny + "/") or ny.startswith(nx + "/")
```

也就是说：**两条路径声明「任一方向是另一方的祖先目录」就判冲突**（`a/b` 是 `a/b/c` 的
前缀，或反之）。

`_paths_conflict(a, b)` 再用它做两两比较：

```python
def _paths_conflict(self, a, b) -> bool:
    pa = [p for p in (a or []) if str(p).strip()]
    pb = [p for p in (b or []) if str(p).strip()]
    if not pa or not pb:
        return True          # 任一方没声明 paths = 冲突
    return any(self._path_overlap(x, y) for x in pa for y in pb)
```

### 例子

| 卡 A `paths` | 卡 B `paths` | 是否冲突 | 原因 |
|---|---|---|---|
| `src/` | `src/a.py` | **冲突** | `src/` 是 `src/a.py` 的祖先目录 |
| `src/a.py` | `src/b.py` | **不冲突** | 互不为祖先目录 |
| `src/` | `tests/` | **不冲突** | 完全不相交 |
| `src/` | （空） | **冲突** | 任一方未声明 = 保守冲突 |
| （空） | （空） | **冲突** | 两边都「任何地方」 |

注意 `src/a.py` vs `src/b.py` 这个例子：目录前缀匹配能正确判它们**不冲突**——
前提是两张卡的 `paths` 都**精确到文件**。一旦某张卡为了省事写成了 `src/`，它就和
`src/b.py` 冲突，并行度立刻损失。这正是 [文件级锁 locks（规划）](#文件级锁-locks规划)
要解决的痛点。

## 文件级锁 locks（规划）

> **状态：规划中，尚未合入主干。** 本节描述的 `locks` 字段来自任务卡 **T-0163**
> （截至本文写作时由 `workbuddyai-win` 认领、仍在开发中）。当前 `hive.py` 线上版本
> **只有** `paths` 目录前缀匹配，**没有** `locks`。请勿把它当成已上线能力。

### 为什么需要它

目录前缀匹配有个硬伤：它只能表达「一个目录及其所有子项」。当两张卡其实只分别改
`src/a.py` 和 `src/b.py` 时，只要有一方不得不声明 `src/`（比如它还要顺手改 `src/` 下
好几个文件），dispatch 就认为它们打架，无法并行。缺少「我精确改这几个文件」的语义。

`locks` 字段用来补这个洞：让冲突判定从「目录前缀」细化到「精确文件集合」。

### 规划的三种声明形式（来自 T-0163）

| 声明 | 形式 | 含义 |
|---|---|---|
| `src/a.py` | 精确文件（无尾斜杠） | 仅该文件 |
| `src/` | 目录前缀（带尾斜杠） | 覆盖 `src/` 下所有 |
| `src/*.py`、`**/test_*.py` | 简单通配（`fnmatch`） | 命中即冲突 |

`T-0163` 计划新增 `conflict.py`，提供 `_lock_matches(lock, other)` 与
`_locks_conflict(a_locks, b_locks)`：两张卡**都**声明了非空 `locks` 时走精确逻辑；
否则回退到现有 `_paths_conflict`（向后兼容，旧卡行为不变）。

### 规划中的并行示例

> 以下例子描述 T-0163 落地后的**目标行为**，当前版本尚不支持。

- 卡 A `locks: [src/a.py]`，卡 B `locks: [src/b.py]` → **不冲突**，可并行（精确文件互不相干）。
- 卡 A `locks: [src/a.py]`，卡 B `locks: [src/]` → **冲突**（目录覆盖文件，旧逻辑也冲突）。
- 卡 A `locks: [src/*.py]`，卡 B `locks: [src/a.py]` → **冲突**（通配命中）。
- 卡 A `locks: [src/a.py, tests/x.py]`，卡 B `locks: [src/b.py, tests/y.py]` → **不冲突**。

保守回退：一方声明了 `locks`、另一方 `paths` 为空 → 仍按旧逻辑判**冲突**，绝不因为
「一边有锁」就放松对未声明方的警惕。

## 与 land 的关系

`land` 是合流环节（`hive.py` 的 `cmd_land`）。它默认 dry-run，会先在临时 worktree 里
**真做一次 merge**，冲突是真的冲突，不是猜的；`--apply` 才推 `main`。

要反复强调一句话：**分支隔离保「干活时不冲突」，但不保「合流时不冲突」**。

两张卡各改 `src/a.py` 和 `src/b.py` 固然互不干扰、各自顺利提交；但若两张卡都改了
`README.md`，dispatch 的 `paths` 互斥可能没拦住（比如一方 `paths` 漏写），它们各自
都能提交成功，直到 `land` 合流那一刻才暴露冲突。所以：

- **`paths` 写准**仍是第一道防线——它让 dispatch 在派发阶段就把「会撞车」的卡错开；
- **必要时 `depends_on` 串行**——真要改同一个文件，就用 `depends_on` 让一张卡等另一张
  合入后再上，从根本上消除合流冲突；
- 这套组合拳的官方说明见 [多机并行开发.md](多机并行开发.md) §5「为什么文件不会打架」。

简言之：`paths` / `locks` 决定「能不能同时飞」，`land` 决定「合流时会不会翻车」，二者
缺一不可。

## 填写建议

给写卡人的实操清单（对照 [任务卡模板.md](任务卡模板.md) 的反模式表）：

1. **宁写文件级，别写整仓。** `paths: [src/a.py, tests/test_a.py]` 远胜 `paths: [src/]`。
   目录越宽，假冲突越多，并行度越低。
2. **验收卡 `paths` 留空。** verify 模式不改代码，写了 `paths` 会被 dispatch 跳过。
   模板见任务卡模板 B。
3. **代码卡一定要写 `paths`。** 留空 = 「可能改任何地方」= 和所有卡保守冲突，反而派不出去。
4. **真要改同一个文件，用 `depends_on` 串行。** 别指望 `paths` 能解决「同一文件两次改写」
   的合流冲突——它防的是派发，不防合流。
5. **`locks` 现在别用。** 它还在 T-0163 规划中、未合入。当前只认 `paths` 目录前缀匹配；
   等 T-0163 上线后，再把「精确文件 / 通配」需求迁到 `locks`。
6. **别把 token / 密钥塞进任务卡。** 用环境变量或凭据服务（反模式表同款提醒）。

一句话：**把 `paths` 当「我承诺只碰这些文件」来写，越具体越好；跨文件、跨同文件的活，
用 `depends_on` 而不是 `paths` 来协调。**
