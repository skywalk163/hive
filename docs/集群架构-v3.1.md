# Hive Agent 协同系统 · 架构与实现基线（v3.1）

> 状态：**实现基线，取代 v3 草案；P0/P1 + P2a store 核心已落地，P2b（store 读缓存/result
> 镜像）进行中（2026-10-29）。**
> P0 范围：status 默认不写 Git、orchestrate leader gate、land 发 `repo.updated` + 每机 SyncAgent。
> P1 范围：`hive daemon` + `127.0.0.1:8790` MCP HTTP、per-agent token、只读缓存、stdio 桥。
> P2a 范围：SQLite store、leader CAS、op 复制、选举限制、`claim_backend=store` 的 claim/lease；
> dispatch/assign 全量迁移、result 归档、coordinator 进 hived 仍属 P2b。
> 目标规模：**70 个并发 Agent × 7 张卡/Agent/天（约 490 张/天）**，并可扩展到 **100 个节点**。
> 一句话：每台机器一个常驻 `hived`，本地全量副本 + 分区内多数复制；Agent 只连
> `127.0.0.1:8790`；Git 只在**建卡 / 结果归档 / 合并关闭**三个里程碑写。

---

## 0. 一页结论

- **拓扑是运行态，不是配置项。** 1 台能起，100 台能加；成员靠发现，不靠固定列表。
  选主、复制、收敛按 OSPF 的思路做：Hello/Dead、DR/BDR、LSA 序号、区域、抑制。
- **单节点故障不阻塞开发。** 分区内多数继续；孤立节点等 `solo_grace=15s` 后自选 leader，
  写入标 `unreplicated`；`arbiter=auto` 在 Gitea 可达时做一次 CAS 仲裁，稳态零写入。
- **一致性分层。** `claim / lease / result` 走 durable op log + 分区内多数复制；
  `progress` 走 ephemeral 通道，可丢最后几秒；election restriction 防止已 ACK 的 op 丢失。
- **Git 只做里程碑。** 协调仓每张卡约 3 次 push；490 张/天约 1,500 次/天。
  代码仓每次 land 一次 main push → 约 490 次 CI/天。**Gitea CI 当前已关闭**；
  重新开启时才是真正的瓶颈。
- **MCP 走 HTTP。** `127.0.0.1:8790/mcp`，四个目标客户端已确认支持 Streamable HTTP；
  `hive mcp connect --stdio` 保留给 CLI/测试/应急。
- **明确不保证**：单节点分区最后几秒的进度；分区期间可能重复干活；Gitea 挂时 land 延后。

## 1. 现状基线（开发前必须知道的事实）

### 1.1 发现 / 注册 / 选主已经存在

[集群服务.md](集群服务.md) + [hive_cluster.py](../hive_cluster.py) 已实现 UDP 发现、
注册、term/vote/incarnation 选主、心跳、租约、事件。**不重造选主**；本次是把集群从
“旁路”提升为“控制面主通道”，并修掉 100 台规模下的 O(N²)。

### 1.2 Git 当前是消息总线，这是 Gitea 压力的根因

| 操作 | 现状 | 代码位置 |
|---|---|---|
| `push_status` | 每任务每 **60 秒** force push 一次 `status/<tid>` | [hive.py:3144](../hive.py#L3144) / [hive.py:3196](../hive.py#L3196) |
| `_refresh_lease` | 每 `lease/3`（默认 60 分钟）push claim 分支 | [hive.py:3111](../hive.py#L3111) |
| `assign` / `task new` / `close` / `land` | 均 commit + push | [hive.py](../hive.py) |
| 一张 2 小时任务 | **约 125 次 Git 写** | 实测口径 |

70 Agent 规模下，这不是“Gitea 不够快”，是**写模型错了**。

### 1.3 “主控”不是唯一执行者，代码同步只在主控那台生效

- `orchestrate` 没有 leader gate（[hive.py:2740](../hive.py#L2740)），两台机器都跑会重复
  dispatch / land；
- `sync-repos` 只在跑 orchestrate 的机器上每 tick 对所有仓 fetch + pull
  （[hive.py:1693](../hive.py#L1693)），**其它机器不会因为“light 完成了”而同步**；
- [T-0193.md](../tasks/T-0193.md) 记录的就是“land 那台自己反而不会更新主检出”。

### 1.4 MCP 入口现状

每 agent 一个 stdio 进程（[mcp_server.py:4](../mcp_server.py#L4)），协议版本
`2024-11-05`（[mcp_server.py:43](../mcp_server.py#L43)），需要配命令、clone、agent 名；
现有 **22 个工具**（15 个 worker + 7 个 controller，见附录 C）。没有本机固定入口。

### 1.5 集群状态是软状态

内存 + 每秒 `state.json` 快照，事件 500 条封顶；不是持久复制。主节点挂了，最后约 1 秒的
进度可能丢；`claim` 仍以 Git 为准，所以新主不能无缝接管在飞任务。

### 1.6 100 台会爆的三个点

1. follower 两两心跳：O(N²)；
2. leader 把事件广播给所有 follower：O(N)/事件；
3. 每个任务的 progress 都进事件流：O(N × 任务数)。

100 台、70 progress/s 时，两个点就能到 7,000–10,000 条/秒；必须改成聚合 + 订阅，
否则“100 台照样起”只是口号。

## 2. 设计原则

1. **拓扑自适应**：成员集合来自发现，不写死节点数；1..N 用同一套协议。
2. **Git 是归档，不是运行时总线**：高频状态走 store/集群；Git 只落里程碑。
3. **每个节点都能当 leader**：leader 只做串行化与聚合，不是唯一入口；本机 `hived` 永远可读。
4. **分区可用优先，安全可选**：默认 `partition-tolerant`；要绝对不重复就开 `strict` + 仲裁。
5. **只快进、不强制**：代码同步/合并永远 `ff-only`；dirty/diverged 跳过并告警，绝不 reset。
6. **零第三方依赖**：Python 标准库 + git；SQLite 是标准库。

### 2.1 不变的部分

- 任务卡格式、`paths` / `verify` / `depends_on` 语义不变；
- worker `hive work` 的命令行、worktree 隔离、claim 语义（迁移期）不变；
- `land` 的单仓合并 / close 语义不变；
- MCP 工具名不变，新增只增不改；
- `hive cluster` 命令保留为 `hive daemon` 的别名；旧脚本不用改。

## 3. 目标架构

### 3.1 进程模型

**每台机器一个 `hived`**，它是现有 `hive_cluster.Cluster` 的**同进程演进**，不是第二个守护进程：

```
hived (one process, one identity, one PID)
├─ Cluster       发现 / 心跳 / 选主 / 任期 / 投票
├─ Store         SQLite WAL：tasks/claims/results/ops/nodes/sync_cursor
├─ OpLog         追加、复制、commit_index、快照
├─ MCP HTTP      :8790（仅 127.0.0.1）
├─ Coordinator   仅 leader：watchdog / dispatch / land / gc
├─ SyncAgent     repo.updated 事件 + 游标 +/- 补偿
├─ ArchiveWorker accepted 结果 → Git 归档
└─ Health/Metrics
```

- `hive work` 仍是独立 worker 进程；`hived` 可选监督，不强绑。
- 看板 `dashboard/` 仍是独立进程（8787，只绑本机）。
- `hive cluster serve` 保留为别名，转发到 `hive daemon serve`；旧脚本不用改。
- **不新起第二个发现/选主进程**；`hived` 就是集群进程的扩展。

### 3.2 端口

| 端口 | 协议 | 服务 | 绑定 | 说明 |
|---|---|---|---|---|
| 8787 | TCP | 看板 | `127.0.0.1` | 现有，不改 |
| 8788 | TCP | 集群 HTTP | `0.0.0.0` | 注册/心跳/投票/状态/复制 |
| 8789 | UDP | 发现 | `0.0.0.0` | 同网段；跨网段用 seed |
| **8790** | TCP | **MCP HTTP** | **`127.0.0.1`** | Agent 唯一入口；不对外 |
| 8791–8798 | — | 预留 | — | 不再把 8791 当 seed 端口 |
| 8799 | TCP | 测试/冒烟 | `127.0.0.1` | 现有 |

> 8790 已分配给 MCP HTTP（见 [端口与服务规划.md](端口与服务规划.md)）；默认值仍只在

### 3.3 三层

| 层 | 放什么 | 频率 | 谁说了算 |
|---|---|---|---|
| 控制面 cluster | 成员、选主、任期、op log、租约、进度聚合 | 秒级 | 当前 leader（term fencing） |
| 本地副本 store | SQLite WAL：tasks/claims/results/ops/nodes/sync_cursor | 每次写落盘 | 本机；leader 复制 |
| 归档面 git | 任务卡、结果、代码 | 每任务约 3 次 | 人 / leader，里程碑 |

### 3.4 写链路

```
agent → 127.0.0.1:8790 → hived（本地 WAL）
                         ├─ 读：本地副本，毫秒级
                         └─ 写：转发 leader → CAS + op log → 多数 follower → ACK
                                                   ↓
                                            Git（结果/关闭/建卡）
```

## 4. 自适应成员与选主（OSPF 式）

### 4.1 成员

- 发现：UDP multicast/broadcast Hello（默认 1s，带 jitter）+ 静态 seed 兜底；
  跨网段/容器/云主机只配 seed。
- 软状态：`alive → suspect → dead`；超时默认 4s，可调；重启用 `incarnation` 覆盖旧记录。
- 没有固定成员表；1 台也能起，100 台也能加。`cluster_id` 做租户/区域隔离。

### 4.2 角色

| 角色 | 职责 |
|---|---|
| leader | 串行化 claim/assign、发 land 令牌；聚合进度；发布 `repo.updated`；运行 coordinator |
| backup leader | 持续接收 op log，leader 失联时优先参选，缩短空窗（BDR 思路） |
| follower | 服务本地读、转发写、跑本机 worker、参与投票 |
| witness（可选） | 只投票/仲裁，不存任务、不跑 MCP；放在第三个故障域 |
| observer | 只读，不参选（看板/外部工具） |

### 4.3 选举

- `term + vote`；候选人向**当前可见的 electable 节点**拉票；多数 = `floor(voters/2)+1`。
- `partition-tolerant`：voters = 本分区可见的 electable；`strict`：voters =
  `membership_ttl`（默认 5 分钟）内见过的 electable，避免分区两边各自把对方算没。
- 单节点：`voters=1` → quorum=1，直接是 leader。
- **election restriction**：候选人最后一条日志的 `(term, index)` 必须 ≥ 投票人的；
  否则拒绝投票。没有这条，“已 ACK 的 op”会在换主时丢（见 §5.4）。
- **solo_grace**：节点发现没有 leader、且可见 voters 只有自己时，等 `solo_grace`（默认 15s）
  再自选；避免瞬时抖动导致双主。
- **backup leader**：leader 定期把 `commit_index` 和自身健康发给 backup；leader 失联时
  backup 优先参选；仍然走投票，不搞“指定继承”。
- 旧 leader 看到更高 term 立即让位；所有写带 term，旧 term 返回 `409 stale`。

### 4.4 2 节点行为（不选 CP/AP，按状态机）

| 状态 | 行为 |
|---|---|
| 2 台都活 | leader + follower；claim/result 复制 2/2 后 ACK |
| 1 台死 / 失联 > dead interval | 幸存者等 `solo_grace` → quorum=1 自选 leader，继续接活；写标 `unreplicated`，同伴回来补同步（`strict` 下不 solo，只读） |
| 网络分区 | 两边都等 grace；都可能自选；恢复后 `term + node_id` 收敛；重复 claim/result 对账（`strict` 下两边都只读） |
| 要绝对不重复 | `safety_mode=strict` + `arbiter=gitea/witness`：进入单活前 CAS 一次，拿不到就只读 |

**代价说清楚**：分区期间两边都可能当主，可能重复干活。用 `solo_grace` 压窗口，用
lease TTL/term/fencing 收口；要彻底避免，才需要仲裁。**仲裁是可选策略，不是拓扑前提。**

### 4.5 仲裁（可选）

- `arbiter=none`：纯 OSPF 式，solo 后接受 `unreplicated`；默认 `auto` 在 Gitea 可达时升级为 CAS。
- `arbiter=gitea`：ref `refs/hive/arbiter/<cluster_id>`，payload
  `{term, leader, expires_at, incarnation}`；用 non-fast-forward push 做 CAS。
  只在“从 follower 变 solo leader”时写一次；稳态零写入；续租按 TTL 的 1/3。
- `arbiter=witness`：第三个故障域上的轻进程，只回投票/仲裁；不存任务。

`arbiter` 只决定“用哪种仲裁”；是否允许无仲裁 solo 由 `safety_mode` 决定：

| safety_mode | 无仲裁/无多数时 | 适用 |
|---|---|---|
| `partition-tolerant`（默认） | `solo_grace` 后 solo；写标 `unreplicated` | 优先不停活；接受分区重复 |
| `strict` | 只读，等多数/仲裁回来 | 绝对不能重复；2 节点单机故障 = 只读 |

`arbiter=auto`：Gitea 可达 → 必须先 CAS；不可达 → 按 `safety_mode` 降级。
`arbiter=gitea`：必须 CAS，拿不到就只读（即使 `partition-tolerant`）。
`arbiter=witness`：同上，仲裁方换成 witness。

所以默认 `partition-tolerant` **不是严格 CP**；要严格 CP 用 `strict`（2 节点单机故障只读）。

部署建议（不是协议前提）：1–2 台用 `partition-tolerant` + `arbiter=auto`；3 台以上用
`strict`（多数派）；100 台再按 area 分片。`strict` 下 2 节点单机故障只读，这是选择，不是缺陷。

### 4.6 100 台：拆掉 O(N²)

| 现状 | 100 台的问题 | v3.1 |
|---|---|---|
| follower 两两心跳 | 约 1 万条/s | 默认只跟 leader 心跳；广播域可用时用 multicast Hello；backup 只跟 leader |
| leader 广播事件给所有 follower | 每事件 × 100 | 只发状态变化；follower 拉 delta/snapshot；progress 不进事件流 |
| 每个 progress 都广播 | 70/s × 100 | leader 聚合，1–2 Hz；只有看板订阅；worker 只收自己的任务事件 |
| 全量 state 每次心跳 | 带宽爆炸 | 心跳只带 `generation`/`commit_index`，变更才拉 delta |
| 新节点全量历史 | 越拉越慢 | 先拿 snapshot，再按 `seq` 追增量 |

- 50+ 台按 `cluster_id`/area 分片；跨区走 backbone，或直接多 cluster。
- 限速：每节点事件队列 + 合并窗口；慢节点降级为 snapshot 拉取。
- 传输：HTTP 长轮询/SSE；100 连接用线程池；500+ 再考虑 asyncio。

### 4.7 OSPF 映射

| OSPF | hive | 说明 |
|---|---|---|
| Hello / Dead | 心跳 / 租约 | 1s / 4s，可调 |
| Neighbor FSM | join / suspect / dead | 软状态，无固定成员表 |
| DR / BDR | leader / backup leader | 减少切换空窗，不是单点 |
| LSA seq/age | op log term/seq | 新旧覆盖，恢复收敛 |
| Area | cluster_id / area | 50+ 台分层 |
| Flooding pacing | 事件合并/限速 | 不逐条广播 |
| Graceful restart | resign / handover | 主动让位 |
| Authentication | cluster token | 局域网信任 |

> OSPF 也不是强一致：收敛期间可能短暂环路/黑洞。hive 的 claim 需要额外的 lease/fencing，
> 这是 OSPF 没有的；不要指望路由协议直接提供互斥。

## 5. 写链路与一致性

### 5.1 Claim 是 leader 上的 CAS

```
claim(T) = CAS(state[T] == ready -> claimed,
               owner=A, lease_id=uuid, term=leader.term, lease_until=now+TTL)
```

- 只有 leader 执行；follower 转发；抢不到立即返回持有者，不重试。
- 返回 `lease_id / lease_until / term / leader_url`；worker 后续续租/交结果都带 `lease_id`。
- `lease_ttl=600s`，`lease_renew=180s`；worker 死亡后最多 10 分钟回收，不再是 180 分钟。

### 5.2 两条通道

| 通道 | 内容 | 持久化 | ACK | 丢失边界 |
|---|---|---|---|---|
| durable op log | claim/lease/result/close/assign/dispatch/task ingest | SQLite + 多数 follower | 多数复制后 | 单节点分区例外 |
| ephemeral progress | progress/step/message/日志 | 内存 + 每秒批量落本地 | 不要求 | 可丢最后几秒，只影响看板 |

`progress` **不进** op log；否则 70/s 的进度会把日志和复制打爆。

### 5.3 多数复制

1. leader 追加 op（`term, seq, op_id, type, payload`）到本地 WAL；
2. 并行发 follower；follower **fsync 后**回 ACK；
3. leader 收到多数（含自己）→ 推进 `commit_index` → 应用状态机 → 回客户端；
4. 未达多数的 op 不 ACK；客户端拿 `E_NO_QUORUM` + `retry_after_ms`，用同一 `op_id` 重试；
5. 组提交：2–5ms 窗口批量 fsync，70 个 claim 的早高峰也不会被磁盘打散。

`seq` 全局单调：新 leader 从 `last_seq+1` 继续，不按 term 重置；比较用 `(term, seq)`，
不要用随机 `lease_id` 排序。

### 5.4 为什么必须有 election restriction

> 3 节点 A/B/C。A 是 leader，把 op X 复制到 B 后 ACK，A 立刻 `kill -9`。剩下 B、C；
> C 的日志少 X。若 C 发起选举且 B 投票给 C（没有日志新旧检查），C 当选，X 丢——
> 尽管它已经 ACK。

多数票本身不够，因为 C 不在 X 的复制集合里。必须让投票人检查候选人日志：
`(last_log_term, last_log_index) >= voter 的`，否则拒票。多数复制 + election restriction
一起，才保证“已 ACK 的 op 在单节点故障后仍在”。

### 5.5 换主与追平

- 新 leader 先向同伴交换 `last_log_index / commit_index`，补齐缺口，**再服务写**；
- 追平前只读；缺口太大直接拉 snapshot；
- 上任后把在飞租约标 `grace_until = now + 120s`；宽限期内不重派；
- 旧 leader 的写带旧 term，全部 `409 stale`；worker 收到 409 后刷新 leader URL 重试。

### 5.6 ACK 分级

| 信息 | ACK 条件 | 说明 |
|---|---|---|
| claim / lease | leader WAL + 多数 follower fsync | 单节点分区例外，标 `unreplicated` |
| result | 多数复制后 `accepted` | 异步归档 Git；`archived` 才是最终 |
| close / land | Git push 成功 | 需要 Gitea；失败可重试 |
| progress | 不要求 | 合并写，允许丢最后几秒 |

### 5.7 幂等与 fencing

- 所有写带 `op_id`（客户端生成 UUID）；leader 以 `op_id` 去重，重试返回同一结果。
- 所有写带 `term`；旧 term 拒绝。
- claim/result 带 `lease_id`；lease 过期/被抢后，旧 worker 的 `hive_submit` 返回
  `E_LEASE_LOST`，结果进 `quarantined`，不覆盖新 lease 的结果。
- land/close 带 `expected_state`；状态已变则拒绝，让调用方重读。

### 5.8 结果归档状态 + 任务终态

| 状态 | 含义 | 看板 |
|---|---|---|
| `accepted` | 多数副本已有结果，未归档 | done（待归档） |
| `archived` | `results/T-*.json` 已进 Git | done（已归档） |

任务终态沿用现有语义：`done` = 有结果、已 archived 且 close 提交完成；
`closed` = 无结果作废（cancelled）。**不要把 `closed` 当成结果状态。**

- `land` 前必须 `archived`；没有就由 ArchiveWorker 补归档，再 land。
- ArchiveWorker 由 leader 或具备 `archive` 角色的节点运行；用 `archive_queue` 抢锁
  （`UPDATE ... WHERE state='pending'`），同一 task 只推一次；失败退避重试。
- 全集群断电重启：扫描 `accepted`，从任一有副本的节点补归档；都没有才回 `ready`。
- 两边都干了的，按 `(term, lease_op_seq)` 取新：term 大者优先，同 term 比 claim 的 op seq；
  `lease_id` 只做 fencing，不做排序。旧结果 `quarantined`，看板标红，人工裁决。

### 5.9 claim_backend 切换

- 集群级 `claim_backend = "store" | "git"`，启动时定死；**不做按请求 fallback**。
- P2a 已实现 `store`：Worker 的 claim/续租/释放、`Hive.claim_info`、take/MCP claim 的
  Git assign、close 清 claim 都切到 store；默认仍是 `git`。
- P2b 才把 dispatch/assign、result 归档、coordinator 完整迁入；混跑期旧节点只读。
- 回滚：drain 掉在飞 claim → `--claim-backend git` 重启 → 从 store 重建 claim。

## 6. 代码同步

### 6.1 事件 + 游标

`land` 成功发：

```json
{"type":"repo.updated","task":"T-0193","term":12,
 "repos":[{"name":"light","sha":"abc123"},{"name":"hive","sha":"def456"}]}
```

每台机器的 SyncAgent：

1. 用本机 `repos` 映射找路径；
2. 主检出干净才 `fetch + merge --ff-only`；dirty/diverged 跳过并标红；
3. 每仓记 `last_synced_sha`；启动/重连按游标补齐；
4. 事件漏了也不怕：每 5 分钟（带 jitter）`git ls-remote` 对比游标，变了才 fetch。

### 6.2 repo 与 sync_repos

- 现有任务卡 `repo` 是**主代码仓**（land 只合这一个）。
- 新增可选 `sync_repos`：land 后额外要同步的仓，默认 `["hive"]`（协调仓本身）。
  例如 light 卡：`repo: light`，`sync_repos: [hive]`；各机有 light 和 hive 就都 ff。
- **多代码仓任务**（一张卡同时改两个代码仓）不在 v3.1 范围；land 仍单仓。
  不要用 `repos` 同时表达“任务要改的仓”和“land 后要同步的仓”，会歧义。

卡面新增（都可选）：

```yaml
sync_repos: [hive]
idempotent: false
```

`sync_repos` 默认空，land 事件仍总带协调仓 `hive`；`idempotent` 只用于 AP/重试判定。

### 6.3 安全边界

- 只 pull 主检出，不动 task worktree；不 `reset --hard`、不 `--force`、不自动解冲突。
- dirty/diverged：跳过 + 看板标红 + 日志；本机改动原样保留。
- 串行 + 去抖 + 失败退避；Windows 文件锁重试；合并期间暂停同仓 pull。
- 子模块/LFS：默认不递归；需要时在 repo 配置里显式开。
- land 那台自己也走同一函数，立即更新主检出（修 [T-0193.md](../tasks/T-0193.md)）。

### 6.4 land 的落点

land 需要代码仓，leader 不一定有（例如 Windows verify 机）。不要让没有 repo 的 leader 直接 merge：

- leader 只发 `land_lease`（task/repo/term），从 `nodes` 里选一个有该 repo 的节点执行；
- 执行节点做 fetch/merge/push/close，把结果回报 leader；
- 没有节点有该 repo → `E_NO_REPO`，任务保持 `submitted`/待 land；
- 同一 task 的 land_lease 串行；旧 term 的 lease 失效。

这样“任何节点都能当 leader”和“land 必须有 repo”不冲突。

### 7.1 HTTP 入口

### 8.1 SQLite 表

| 表 | 关键列 | 说明 |
|---|---|---|
| `meta` | key, value | schema_version、term、commit_index、cluster_id |
| `nodes` | node_id, name, host, port, incarnation, role, last_seen, status, priority, capabilities, repos_json | 成员 |

| `ops` | seq, term, op_id UNIQUE, type, task_id, payload_json, ts | durable op log |

索引：`claims(state, lease_until)`、`ops(term, seq)`、`results(task_id)`、
`sync_cursor(repo, node_id)`、`archive_queue(next_attempt_at)`。

### 8.2 持久化参数

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;      -- durable op；progress 可用 NORMAL
PRAGMA busy_timeout = 5000;
PRAGMA foreign_keys = ON;
```

- 单写线程（hived），读用只读连接；CLI 通过 HTTP 读，不直接开写连接。
- 组提交：2–5ms 合并 fsync；claim 峰值 70 个也不会被磁盘打散。
- 结果 payload 上限 1MB；大 diff/日志留在 Git 分支，store 只存摘要与路径。

### 8.3 快照与压缩

- 每 10,000 ops 或 24h 做一次 snapshot；`snapshots` 记录 `last_seq`。
- follower 落后超过 `ops` 保留窗口 → 直接拉 snapshot。
- ops 保留 7 天供排障；之后删；审计看 Git 的 results/tasks。
- 迁移用 `PRAGMA user_version`；升级前备份 `hive.db`；只做向前迁移。

### 8.4 Git ↔ store 对账

- Git `tasks/*.md` 是**任务定义**的真相；store 是**运行时状态**。
- 启动/每次 fetch：按文件 hash 做 `task_upsert`。Git 赢定义字段（title/repo/base/paths/
  verify/depends_on/priority）；store 赢运行时字段（state/owner/retries/lease/result）。
- 人工改卡：下次 ingest 更新定义；正在跑的任务不因改卡而中断，dispatch 用新定义。
- 删除卡：不物理删 store；标 `cancelled`，审计后清理。
- close/land：把最终 state/owner/retries 写回卡再提交；这是 Git 与 store 的唯一强制合流点。
- `reopen`/`block`/`unblock`：store 先改，close 时把摘要写进卡；Git 历史只留最终态。
- 迁移后 CLI/看板一律读 hived；直接读 Git 卡面只用于审计/离线恢复。

## 9. 状态机

### 9.1 任务

```
draft -> ready -> assigned -> claimed -> running -> submitted -> done
                    |            |          |            |
                    +-> blocked -+          +-> failed --+-> ready (retry)
any -> closed（作废，无结果）
```

| 迁移 | 触发 | 守卫 |
|---|---|---|
| ready→assigned | dispatch | 依赖完成、能力匹配、无路径冲突 |
| assigned→claimed | worker claim | CAS 成功、lease 获得 |
| claimed→running | 首次 progress | lease 有效 |
| running→submitted | result accepted | lease_id 匹配、多数复制 |
| submitted→done | archived + close | Git push 成功 |
| ready/assigned/claimed/running→blocked | controller | 记录原因 |
| failed→ready | retry | 未超 max_retries |
| any→closed | close（无结果） | 记录原因；不产生 done |

### 9.2 租约

`none → active → renewing → released / expired / lost`

- `active`：claim 成功；`lease_until = now + 600s`。
- `renewing`：`hive_extend_lease`；每次 +600s，旧 `lease_id` 不变。
- `expired`：leader watchdog 回收；任务回 `ready`。
- `lost`：worker 收到 `E_LEASE_LOST`；停止工作，结果进 `quarantined`。

### 9.3 结果/归档

`none → accepted → archived`；异常分支 `quarantined`。

- `accepted`：多数副本；单节点分区例外（quorum=1，标 `unreplicated`）；可看板显示。
- `archived`：Git 有 `results/T-*.json`；`archived_sha` 记录。
- 结果归档后，任务卡由 close 置 `done`；无结果的关闭走 `closed`（作废），不是结果状态。
- `quarantined`：lease 过期/冲突/旧 term；不覆盖新结果，人工处理。

### 9.4 节点/leader

- 节点：`joining → alive → suspect → dead → left`；重启 `incarnation++`。
- leader：`follower → candidate → leader → resigning`；term 单调；旧 leader 收到更高 term 立即降级。

## 10. 容量与 SLO

### 10.1 70 × 7 的算法

按 **70 个并发 Agent、每个 Agent 每天 7 张卡** 理解：

| 指标 | 数值 |
|---|---|
| 任务量 | 70 × 7 = **490 张/天** |
| 并发 | 70（每个 Agent 同时 1 张） |
| progress | 70/s（1s 一条，合并后） |
| durable 写 | claim/result/close/task ≈ 2,000/天；lease ≈ 0.2–0.4/s（约 17k–35k/天） |
| op log | 约 5–10 MB/天（含 lease）；snapshot 后更小 |
| SQLite | < 1 GB/月（含结果摘要） |

> 如果“7 任务/人”指的是 **490 张同时飞**，progress 是 490/s，需重新做分片/限流；
> 本文按 490/天 设计。任务时长也要对口径：490/天、70 并发，按 10h/天平均约 1.4h/张；
> 若任务普遍 2h，实际约 350 张/天。

### 10.2 Git / CI 预算

| 仓库 | 每任务 | 490/天 |
|---|---|---|
| hive 协调仓 | 建卡 1 + 结果归档 1 + close 1 = 3 | 约 1,470 次 push/天（约 1 次/分钟） |
| 代码仓 | land main merge 1 | 约 490 次 main push/天 |
| CI（若开启） | 每次 main merge 触发 | **约 490 次 CI/天** |

**CI 现状：已关闭（2026-10-29 决定）。** P0/P2 的 Git 写入预算只按仓库 push 算；
重新开启 CI 时，再评估 490 次/天和合并队列（3–7 个 runner，或批量合流）。
Agent 开发速度超过 CI 承载时，优先关 CI/批量合流，不阻塞任务流转。

### 10.3 SLO

| 指标 | 目标 |
|---|---|
| claim p95（LAN，3 节点） | < 100ms |
| leader 切换 | < 8s（优雅 1–2s） |
| 进度可见延迟 | < 2s |
| 代码同步延迟 | < 30s（事件）；< 5min（补偿） |
| 结果归档延迟 | < 60s |
| leader CPU / 内存 | < 30% / < 300MB |
| 100 节点网络 | < 1MB/s（聚合后） |
| 单机故障任务回收 | ≤ 10min（lease TTL） |

### 10.4 压测

- 70 个模拟 Agent，1 progress/s，490 claim/天，峰值 70 并发。
- 1/2/3/10/100 节点；记录 claim p95、leader CPU、复制延迟、DB 增长、网络。
- 混沌：kill -9 leader/follower、分区、Gitea 挂、磁盘满、时钟偏差、SQLite 恢复。

## 11. 安全

| 面 | 措施 |
|---|---|
| MCP | 只绑 `127.0.0.1`；每 Agent token；`Origin`/`Host` 校验；不开 CORS |
| Cluster | LAN + 共享 token；跨公网必须 TLS 反向代理（v3.1 不内置 TLS） |
| Gitea | token 走 env `HIVE_GITEA_TOKEN` 或 0600 文件；不进配置、不进日志 |
| 本机文件 | `~/.hive/` 0700；`hive.db`、token 文件 0600 |
| Token 生命周期 | `hive agent enroll` 生成；`hive agent revoke` 吊销；90 天轮换 |
| 日志 | 过滤 `Authorization`、token、Gitea URL 里的凭据 |

威胁模型：本机恶意进程、局域网嗅探、token 被盗、恶意任务卡。对应：loopback + token、
LAN token/TLS、吊销/轮换、任务卡路径白名单 + verify。

> 容器/WSL 里 `127.0.0.1` 可能不是宿主：需要 `host.docker.internal` 或显式 LAN 绑定 + token；
> 这是部署配置，不是协议问题。

## 13. 故障矩阵

| 故障 | 目标行为 | 代价 / 边界 |
|---|---|---|
| 单台 follower 掉线 | 主继续；该机租约到期后任务重排 | 该机 worktree 丢失，任务重跑 |
| 主节点掉线 | 1–8s 选新主；新主追平日志；在飞租约宽限 120s | 最后约 1s 进度可能丢；已 ACK 的 claim/result 不丢 |
| 2 节点分区 | 两边等 15s；都可能自选；恢复后按 term 收敛 | 可能重复干活；`arbiter=gitea` 可避免（Gitea 可达时） |
| 3+ 节点分区 | 多数派继续；少数派按 `safety_mode` 只读或 solo | `strict` 少数派只读；`partition-tolerant` 少数派可 solo |
| Gitea 挂 | claim/status/dispatch 继续；result 排队；land 暂停 | 代码合流延后，不卡干活；新建卡暂停 |
| 全集群断电 | 各机 SQLite + Git 重建；未完成任务回 ready | 未归档 accepted 结果从副本补归档；都没有才重跑 |
| agent/MCP 崩 | 租约到期回收；幂等重试 | 当前步骤重做 |
| 磁盘满 | 拒绝新写并告警；Git 里程碑仍在 | 人工清理；只读降级 |
| 时钟偏差 | lease 用 leader 时间；客户端只传剩余 TTL | 需要 NTP；偏差 > TTL/3 告警 |
| SQLite 损坏 | 从 snapshot/同伴重建；Git 兜底 | 丢最后未快照的 progress；任务状态从 Git 重建 |

## 15. 落地顺序

### P0（低风险，先见效，约 1 周）

- `status` 不再 push Git：进度只进集群；无集群时只在里程碑写（开始/结束），不再 60s。
- `_refresh_lease` **保留**：P0 阶段 claim 仍在 Git，停掉会让 180 分钟长任务被误回收。
- `orchestrate` 加 leader gate：只有 leader 跑；无集群时照旧；写前校验 term。
  （P0 仍需至少一台机器跑 `hive orchestrate`；P2 收进 hived 后由 leader 自动运行。）
  P0 先给节点加 `coordinator` 标记（实现为 `electable` / `--no-elect`），只有 coordinator
  参选 leader；verify-only 机器做 observer，否则 Windows 验证机当主会让 land 找不到 repo。
  没有 coordinator 的集群退回旧行为（不 gate），并打告警。
- `land` 发 `repo.updated`；每机 SyncAgent + 游标 + 5 分钟补偿；land 那台立即更新主检出。
  （P0 先把 SyncAgent 挂在 cluster 进程，P1 随 hived 同进程化；没起 cluster 的机器保留
  `hive sync-repos` 轮询兜底。）
- 指标/日志：leader/term、同步游标与失败；归档积压属 P2。`hive cluster sync`/`GET /api/cluster/sync` 可查。

**退出标准**：2 小时任务协调仓 push 从约 125 降到 5–7 次；同步延迟 < 60s；无重复 land。
**回滚**：`HIVE_STATUS_GIT=1` 恢复旧行为。

### P1（本地入口，约 1–2 周）

- `hived` 单进程：Cluster + Store（先只读缓存）+ MCP HTTP 8790 + token + stdio 桥。
- MCP 读写先代理现有 Git 逻辑；claim 语义不变。
- `hive daemon` CLI；`hive cluster` 别名；systemd/rc.d/NSSM 模板。

**退出标准**：四个客户端全流程；本地读 p95 < 5ms；换主时本地入口不断。
**回滚**：保留 stdio；HTTP 可关。

### P2（控制面迁移，P2a 已落地）

- claim/assign/dispatch/lease/result 进 store；op log + 多数复制 + election restriction。
- Coordinator 进 hived；`hive orchestrate` 保留为兼容入口（内部调同一循环）。
- 结果 `accepted/archived`；ArchiveWorker；land 前强制归档；任务终态 `done/closed`。
- `claim_backend` 集群级切换；Git claim 只做回滚路径。
- 租约 TTL 600s、续租 180s；fencing。

> **P2a 已落地**：`hive_store.py`（SQLite/op log）、leader CAS、同步复制、选举限制、
> `claim_backend=store` 的 claim/lease/release/close。
> **P2b 核心已落地**：store 读缓存、result accepted/archive、dispatch/assign、
> 两阶段提交/commit_index/追平、op log 压缩/snapshot、可选 coordinator 进 hived；
> 极端分区混沌和真四客户端压测待完善。

**退出标准**：§16.1–16.4 全过；协调仓 ≤3 push/任务；换主不重派在飞任务。
**回滚**：drain → `claim_backend=git` → 从 store 重建 claim。

### P3（硬化，持续）

- 100 节点：去 O(N²)、multicast Hello、聚合/订阅、area。
- `strict` 模式、`arbiter=gitea/witness`、备份 leader。
- 混沌测试、Windows/FreeBSD 服务、看板、文档、容量压测。

## 17. 迁移与回滚

1. **Stage 0**：全机升级到 v3.1，`claim_backend=git`，store 只读缓存；行为不变。
2. **Stage 1**：3 节点 canary 开 `claim_backend=store`；旧节点只读；双读单写。
   迁移期旧 CLI/看板直接读 Git 卡面会看到旧 `state`；必须走 hived API，或把 runtime 镜像到
   低频 `state` ref。
3. **Stage 2**：全量 store；Git claim 只保留回滚代码；观察 2 周。
4. **Stage 3**：删除 Git claim 写路径；保留导出/重建工具。

**回滚**：drain 在飞 claim → 切 `claim_backend=git` → 从 store 快照重建 claim →
旧节点恢复写。回滚期间不接受新 claim，但不丢已有结果。

**混版**：握手带 `protocol_version`；旧节点不认识 store op 时只读；不允许两边同时写。

## 附录 D：术语

| 术语 | 含义 |
|---|---|
| hived | 每机常驻进程：集群 + store + MCP + sync + coordinator |

| archived | 结果已进 Git `results/` |
| unreplicated | 单节点分区接受的写，尚未复制到其他节点 |
| claim_backend | `store` 或 `git`，集群级切换，不按请求回退 |
