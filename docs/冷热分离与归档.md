# 冷热分离与归档（T-0219）

## 1. 问题：列表页在为「历史」付全价

`hive status --json` 是看板首屏的唯一数据源，它每次把 `tasks/T-*.md` **全量**解析，
再把每张卡的**详情**一起塞进 JSON：

| 字段 | 来源 | 单卡量级 |
| --- | --- | --- |
| `verify[]`（含每条命令的 `tail`） | `results/<tid>.json` | 数百字节 ~ 数 KB |
| `result_summary`（完整结论文本） | `results/<tid>.json` | 数百字节 ~ 数 KB |
| `summary`（首行截 60 字） | `results/<tid>.json` | ~60 字节 |
| `paths/verify/needs/depends_on`（卡面） | `tasks/<tid>.md` | 数百字节 |
| 运行时派生（claim/fence/stale/…） | claim 分支 / status 分支 | ~300 字节 |

实测：`dashboard/status.json` 已 **362KB / 85 张卡（83 done）**，每 30 秒重写一次。
done 卡占了绝对多数，而列表页根本不需要它们的 `verify` tail 和整段结论。

按当前增速（约 +10 卡/周），几百张卡时单次快照 1~2MB，看板首屏与 `status --json`
都会明显变慢；而其中 95% 的字节属于「早就完事、只看一眼状态」的冷卡。

**结论**：列表页要的是「摘要」，不是「详情」；冷卡要的是「还能查到」，不是「每次都下发」。

## 2. 目标与非目标

目标：

1. 列表只回**摘要字段**（10 个），详情按 `id` 现取；
2. 已完成的冷卡从热目录移出，落 `tasks/archive/YYYY-MM/`，**只移动、不删除**；
3. 归档**可回滚**（`--restore`），回滚后详情与归档前完全一致；
4. 迁移幂等：老库（v1）能原地升到 v2，连跑两次结构不变。

非目标（本卡不做）：

- 不删任何卡，不做压缩包，不重写 `results/<tid>.json` 结构（land/close 在写它）；
- 不动看板前端（列表分页/虚拟滚动是后续卡）；
- 不改 `tasks` 表的既有列语义，加列一律带迁移。

## 3. 摘要表 `task_summary`（store v2）

```sql
CREATE TABLE IF NOT EXISTS task_summary (
    id           TEXT PRIMARY KEY,
    title        TEXT NOT NULL DEFAULT '',
    state        TEXT NOT NULL DEFAULT '',
    repo         TEXT NOT NULL DEFAULT '',
    priority     TEXT NOT NULL DEFAULT '',
    owner        TEXT NOT NULL DEFAULT '',
    created_at   TEXT NOT NULL DEFAULT '',
    finished_at  TEXT NOT NULL DEFAULT '',
    summary_head TEXT NOT NULL DEFAULT '',
    archived     INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_task_summary_state_finished
    ON task_summary(state, finished_at);
CREATE INDEX IF NOT EXISTS idx_task_summary_repo_state
    ON task_summary(repo, state);
```

字段口径：

- `created_at` ← 卡面 `created`；
- `finished_at` ← `results/<tid>.json` 的 `finished_at`，缺失退回 `accepted_at`；
- `summary_head` ← 结果 `summary` 的**首行前 120 字**（列表只用来做一行提示）；
- `archived` ← 1 表示该卡已移入冷目录。

两张索引对应两个真实查询：`(state, finished_at)` 支撑「按状态取最近完成的 N 张」，
`(repo, state)` 支撑「某仓库还有多少在跑」。不做 `title` 全文索引——列表不搜标题。

**为什么要有这张表**：Git 里的卡是「任务定义 + 最终归档」的真相，但列表页每 30 秒
重新解析一遍上百个 Markdown 是纯浪费。摘要表是它的**物化视图**，供后续 HTTP/MCP
列表接口直接读，不必再走 Git。本卡只保证它与 Git 卡面同源、可重建（`refresh_summaries()`）。

## 4. 热窗口：`HIVE_ARCHIVE_DAYS`

- 常量 `DEFAULT_ARCHIVE_DAYS = 14`（`hive_archive.py`）；
- 环境变量 `HIVE_ARCHIVE_DAYS` 覆盖；`--days N` 优先级最高；
- 语义：**完成时间**早于 `now - N 天` 且状态为 `done`/`closed` 的卡算冷卡；
- `N <= 0` 视为「不归档任何卡」（逃生阀，便于临时关掉自动归档）。

注意：判据用的是**完成时间**而不是卡面 `updated`。卡被 reopen 再 close 时
`finished_at` 会更新，所以「归档后又被改过」的卡不会被误判成冷卡。

## 5. 冷数据布局

```
tasks/
  T-0231.md                     ← 热卡（列表扫描范围）
  archive/
    2026-09/
      T-0102.md                 ← 冷卡（带 archived: true）
      T-0107.md
    2026-10/
      T-0198.md
results/
  T-0102.json                   ← 保持原位，不动结构
```

- 分片键取 `finished_at` 的 `YYYY-MM`，不取归档动作发生的时间——否则同月完成的卡
  会因为晚几天归档而散落在不同分片里。
- 只 `move`，不 `rm`。冷卡原样保留正文，`grep -r "关键字" tasks/archive/` 照样能搜到。
- **移动用 `os.replace` 原子改名，不是「写一份新的 + 删掉旧的」**。两个理由：语义上
  这是移动而非复制后删除，不会出现「两份都在」或「两边都没有」的中间态；环境上，
  `unlink`/`rmtree` 在受限环境里会被安全守卫按次计数，批量归档 50 张卡直接撞阈值中断。
  改名失败时把刚打的 `archived` 标记撤回，卡继续以热卡身份留在原处。
- `tasks/T-*.md` 的 glob **不递归**，所以移进 `archive/` 的卡自动退出 `cards()`，
  列表页不再看到它们——这是「热窗口」的实现方式，不需要额外的过滤代码。

## 6. 详情懒加载契约

| 入口 | 返回 | 成本 |
| --- | --- | --- |
| `hive status --summary [--json]` | 10 字段摘要，默认**只含热卡** | 卡面 frontmatter + `results/` 的 summary 首行；**不读** `verify` tail / 正文 |
| `hive status --summary --include-archived` | 摘要 + 冷卡（`archived: true`） | 同上 + 冷目录扫描 |
| `hive status --json` | 旧全量（不变） | 全量解析 + 结果详情 |
| `hive result <tid>` / `Hive.card(tid)` | 单卡详情 | 单文件 |

契约三条：

1. **列表只回摘要**：摘要行里不出现 `verify`、`result_summary`、`body`；
2. **详情按 id 现取**：`Hive.card(tid)` 先查 `tasks/<tid>.md`，未命中再查
   `tasks/archive/*/<tid>.md`，两者都是单文件读，与总卡数无关；
3. **冷卡不静默消失**：`--include-archived` 必须能列出它们，且 `archived` 为真。
   这是「归档 ≠ 删除」的可观测证明。

## 7. 回滚：`--restore`

```
python hive_archive.py --dir . --restore T-0102
```

步骤（顺序即失败回滚顺序）：

1. 在 `tasks/archive/*/T-0102.md` 里找文件；找不到 → 报错退出，不动任何东西；
2. 目标位置 `tasks/T-0102.md` 已存在 → 报错退出（**绝不覆盖**热卡）；
3. 读出 frontmatter，**原地**重写一份删掉 `archived` / `archived_at` 两键的卡；
4. `os.replace(src, dst)` 原子改名回 `tasks/`；改名失败则把标记撤回（冷卡原样留在
   冷目录），不留半成品；
5. 若 `results/T-0102.json` 存在，不改它（结构不变是硬约束）。

回滚后 `archived` 复位（键不存在 ⇒ 假），详情可读，`status --summary` 默认重新包含它。

## 8. 迁移 v2：`PRAGMA user_version`

```
v1: 只有 meta/tasks/claims/results/ops 五张表，user_version = 0（旧库从没设过）
v2: + task_summary + 两张索引，user_version = 2
```

- 版本号用 **`PRAGMA user_version`**（SQLite 原生，跟着库文件走，不依赖 `meta` 表里
  那条可能被手工改坏的记录）；`meta.schema_version` 同步写成 `2` 只为兼容旧读者。
- 迁移体全部 `CREATE TABLE/INDEX IF NOT EXISTS` + `PRAGMA user_version = 2`，
  因此**重复执行不产生任何结构变化**（幂等）。这是判据 1 的直接来源。
- 老库升级不重建任何表、不搬数据：`task_summary` 首次为空，由 `refresh_summaries()`
  从既有 `tasks`/`results` 灌一遍即可，失败也不影响 claim/lease 主链路。

## 9. 判据与实测

四条判据都要**反证**（能证明「不做这件事就会红」）：

1. **迁移幂等**：同一路径连开两次 `Store`，`PRAGMA user_version` 均为 2，
   `sqlite_master` 的 `(type, name, sql)` 集合逐字相同；
2. **体积腰斩**：60 张卡（50 张完成于 30 天前、10 张新卡）→ 归档 50 张后，
   `status --summary` 体积相对归档前**下降 ≥ 50%**；同时
   `--include-archived` 仍能列出全部 60 张，其中 50 张 `archived: true`；
3. **可回滚**：`--restore` 后该卡文件回到 `tasks/`、`archived` 键消失、
   详情可读（正文与归档前逐字一致）；
4. **dry-run 零副作用**：归档前后对 `tasks/` 做目录快照（路径 + 大小 + mtime 集合）
   diff，必须完全相同。

实测数字（本机 Windows / Python 3.14，60 卡样本：50 张完成于 40 天前 + 10 张 1 天前，
每张卡带 304B 的 `verify` tail 与 20 行正文；脚本 `_r219_scratch/measure_219.py`）：

| 阶段 | 通道 | 字节 | 条目 |
| --- | --- | --- | --- |
| 归档前 | `status --json`（旧全量） | 77313 | 60 |
| 归档前 | `status --summary` | 17203 | 60 |
| 归档后 | `status --json`（旧全量） | 12893 | 10 |
| 归档后 | `status --summary` | 2873 | 10 |
| 归档后 | `status --summary --include-archived` | 17153 | 60 |

- 判据 2：`status --summary` **17203 → 2873 B（下降 83.3%）**，远超 50%；
  旧全量通道同样下降 83.3%（77313 → 12893），说明省下的就是被移走的 50 张冷卡。
- 冷卡没有消失：`--include-archived` 仍是 60 条（17153 B），50 条 `archived: true`。
- 耗时（含进程启动 + `git ls-remote`，单次抖动大，只作量级参考）：旧全量 32.2s → 6.6s；
  摘要通道 1.7s ~ 3.9s。摘要通道的绝对耗时主要被 `git ls-remote` 与 Python 启动占掉，
  与卡数几乎无关——这正是「列表页不该按卡数线性变慢」的验证点。

## 10. 风险与边界

- **归档判据依赖 `finished_at`**：`results/<tid>.json` 缺失的 done 卡（历史遗留）退回
  卡面 `updated`；两者都解析不出来 → 视为「不可归档」，宁可留在热区也不误移。
- **并发**：归档是「读卡 → 移文件 → 写卡」三步，不是事务。若期间有人 `reopen`，
  可能出现「卡在冷目录但状态已改」。处置：`reopen`/`close` 走 `sync_main()` 后按
  `Hive.card()` 的「热→冷」回退查找，能找到就照常操作；本卡不引入锁。
- **`archived` 是卡面字段**，因此必须进 `TASK_FIELDS`（`hive.py`），否则 `write_card`
  会把它丢掉——这是 T-0219 实现期最容易踩的坑。
- **不动 `results/<tid>.json`**：land/close 在写它，改结构会同时打断看板与 land 自检。
