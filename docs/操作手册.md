# 蜂巢（Hive）操作手册

> 面向：每天早上坐下来干活的你，和接在 dsh Web 里的总控 AI。
> 目标：用最短的命令完成「建卡 → 分派 → 看进度 → 验收 → 合并」。
>
> **你是第一次接进来的 AI agent？** 先读 [AGENT 快速上手](AGENT快速上手.md)——
> 那份按 agent 视角写，从配置 MCP 到交第一张卡，含实测输出和踩坑；本手册是给人和总控看的全量命令参考。

## 1. 角色

| 角色 | 在哪 | 干什么 |
|---|---|---|
| 人 | 任意 | 定优先级、review 关键 diff、合并 `main` |
| 总控 Chief | fb88 的 dsh Web | 拆卡、`dispatch`、读结果、写验收卡 |
| worker | fb88 / win10 / GUI | 领卡、干活、跑 verify、推结果 |
| Gitea | fb5:3000 | 代码与任务真源、CI |
| `hive.py` | 每个 clone 的根目录 | 工具本体 |

## 2. 第一次初始化

```sh
# 开发机：把工具仓推到 Gitea（仓库名 hive，空仓即可）
cd ~/dswork/hive
git remote add origin http://192.168.1.5:3000/skywalk/hive.git
git push -u origin main

# 任意机器：clone 后补齐任务目录
git clone http://192.168.1.5:3000/skywalk/hive.git ~/hive
python3 ~/hive/hive.py --dir ~/hive init
```

`init` 会创建 `tasks/ inbox/ results/ agents/`，并保证 `hive.py` 在仓库根目录。

登记 agent：

```sh
python3 ~/hive/hive.py --dir ~/hive agent add \
  --name fb88-dsh --mode exec --command "dsh --profile headless -" \
  --capabilities freebsd python compiler pytest \
  --worktrees /home/skywalk/.hive/wt
```

> **`repos` 只登记确实要干活的代码仓。** light 事故之后，`tests/test_repo_scope.py`
> 有静态守卫：`repos` 里出现 `ALLOWED_REPOS` 之外的名字，测试立刻红；出现
> `FORBIDDEN` 里的名字，也立刻红。当前白名单是 `hive` / `lightharness` / `light` /
> `lightmem`（后三者分别服务于 0.2.1-rc.3 升级线、light 编译器/运行时修复、光明记忆），
> `FORBIDDEN` 为空。
> 要接入新仓，按这个顺序走：① 确认对方仓库的接入约定（推哪个分支、能不能碰 main）；
> ② 登记进相应 `agents/*.json`；③ 把仓名加进测试的 `ALLOWED_REPOS`。
> 要退役某个仓，反向操作：先把仓名塞进 `FORBIDDEN`，再清掉各 agent 的登记，
> 顺手处理还在飞的卡（改派或作废）——测试会逼你直面这件事。

Windows 用 `windows/bootstrap.ps1`，见 `windows/README.md`。

## 3. 每天的命令

```sh
H="python3 ~/hive/hive.py --dir ~/hive"

# 看板
$H status

# 体检：任务卡、租约、结果、agent 配置
$H doctor

# 自动分派（先 dry-run，确认后 --apply）
$H dispatch
$H dispatch --apply --limit 3

# 单张卡
$H assign T-0101 --agent fb88-dsh
$H result T-0101
$H retry  T-0101            # 续用原分支
$H retry  T-0101 --fresh    # 从 main 重来
$H close  T-0101 --note "已 land 合入"

# 统计：成功率 / 中位耗时 / 按 agent / 按仓库
$H stats
$H stats --days 7

# 分支清理：代码仓里已合并的 task/verify 分支（合并后跑，默认 dry-run）
$H prune
$H prune --apply
$H prune --repo hive          # 只清一个仓
```

`dispatch` 的规则：

1. 只看 `state=ready` 且没有 owner 的卡；
2. 依赖必须都 `done`；
3. agent 必须声明了 `repo` 和任务卡的全部 `needs`；
4. `verify` 模式的 agent 不接带 `paths` 的卡（它不改代码）；
5. 已分派未领取也算负载，不超过 `max_concurrency`；
6. 默认 dry-run，`--apply` 才写。

`prune` 的安全规则（删的是**代码仓**的分支，不是协调仓）：

1. 只认 `task/*` 和 `verify/*` 两种前缀，其它分支一概不碰（只枚举这两个前缀，结构性保护）；
2. 两条同时满足才删：**已合并进** `origin/main`（真合并或 squash 后内容一致）**且不在飞**
   （没有 claim/assigned 状态的卡没有结果）；
3. 默认 dry-run 只列计划；`--apply` 才推 `:refs/heads/<branch>` 删远端，本地分支能删就删
   （还被 `--keep` 的 worktree 占着时只删远端）；
4. 本地 `verify/*` 遗留也一并清（verify 模式不推远端，worktree 删了分支还在；
   这种分支 worker 随时能按 base 重建，删不丢东西）。

## 4. 总控的一天

**早上**

```sh
$H doctor
$H stats --days 7
$H status
```

把失败/过期的卡拉出来：`$H result T-xxxx`。决定：改卡、`retry`、还是换 agent。

**拆卡**

一张卡只做一件事，写清楚：

- `paths`：允许改的路径（互斥，避免冲突）；
- `verify`：至少一条能自动判定的命令；
- `needs`：平台/能力标签（`windows`、`exe`、`freebsd`）；
- `depends_on`：前置卡。

**分派**

```sh
$H dispatch --apply
```

**验收**

```sh
$H result T-0101
git -C ~/dswork/hive fetch origin
git -C ~/dswork/hive diff main...origin/task/T-0101
```

本地子集绿了就 `hive land T-0101 --apply` 合入 main（见 §5.1）。

**收口**

```sh
$H close T-0101 --note "已 land 合入"
```

`close` 会把结果归档到 `main:results/T-0101.json`，删掉 `claim/res` 分支。

### 4.1 人工领取 / 提交：不依赖 worker 自动跑

GUI agent（小浣熊 / WorkBuddy）也可以**不启动 worker**，由人手工领取、手工提交，
主控再验收合入：

```bash
# 1) 看板上有什么
hive status                    # 全部任务
hive status --json             # 机器可读

# 2) 手工领取：assign + claim + 建 worktree，并标记领取 agent
hive take T-xxxx --agent workbuddy
#    会打印：工作目录 / 任务卡 / 完成后要写的 summary.md

# 3) agent 做完后，回主控提交：commit + push + verify + 写结果
hive submit T-xxxx             # --keep 保留 worktree
#    验证不通过会写 failed，改完再 submit 一次

# 4) 主控验收、合入后
hive close T-xxxx
```

注意：

- `take` 和「跑 worker」二选一。如果这个 agent 的 worker 正在跑，它会自己领取并
  等你写 summary，不要再用 `submit` 抢跑；
- 面板（dashboard）目前是只读的，写操作走 CLI（`take` / `submit` / `close`）；
- `take` 之后即使 worker 没跑，worktree 也在 `/home/skywalk/.hive/wt/<agent>/<tid>`，
  chroot 里是同一个路径。
- **协调仓里未提交的改动不会被 `take` / `work` 抹掉**。worker 启动和轮询都走
  `sync_main()`（对齐或领先就不动工作区，落后且干净才 reset，落后且脏直接报错），
  不再是裸 `reset --hard`。所以你可以放心把草稿写到一半放着；真遇到「落后且脏」，
  它会明确报错让你先处理，而不是悄悄丢掉。
  （MCP server 仍用独占 clone 并在每次调用时 reset —— 那是它读到最新卡的前提，
  所以别把 MCP 的 `--dir` 指向你正在干活的主工作区。）

## 5. 分支与合并

```
task/T-0101 ─┐
task/T-0102 ─┼─▶ land ──▶ main（ff 优先；冲突置 conflict 交回总控）
task/T-0103 ─┘
```

- 一卡一 worktree、一卡一分支；worker 不碰主 checkout。
- 共享文件（版本号、CHANGELOG）由总控在合并时统一改，或单独开“收口卡”。
- 合入冲突由 `land` 检出：卡置 `conflict` 并列出冲突文件，总控解决后重跑
  `land --apply`，不手工在 main 上解半天。

### 5.1 `hive land`：自动合入

以前最后一步靠人手工 `git merge` + `hive close`。现在可以直接：

```sh
$H land T-0101            # 预演：会不会冲突、合进去是哪个 commit（默认不动任何东西）
$H land T-0101 --apply    # 真的合进 main 再 close
$H land --all --apply     # 按优先级把能合的都合掉
$H land T-0101 --json     # 给脚本用
```

合入条件（不满足就 `blocked`，并把原因列出来）：

1. 有结果且 `status == done`；
2. 结果里每条 verify 退出码都是 0；
3. 卡还没 close；
4. `depends_on` 的卡全部 close。

**合并是在临时 worktree 里做的**（`~/.hive/land/<tid>`，用完就拆），不碰你的主 checkout，
也不用 `git clone`。预演不是靠 `merge-tree` 猜的 —— 是真的把 merge 跑了一遍，
所以报冲突就是真冲突。merge 命令显式带上 `-c user.name=...`，不依赖机器有没有配 git 身份。

- **默认 dry-run**：不加 `--apply` 什么都不推。
- 冲突一律不自动解、不 force push；`--json` 里 `conflicts` 给冲突文件清单，
  照 §5 的规矩回给 owner 开新卡。
- `--all` 遇到冲突就**停下**（后面的卡多半建立在它之上），已合的保留。

| 输出 status | 含义 |
|---|---|
| `landed` | 已合入 main 并 close |
| `would-merge` | 预演通过，等 `--apply` |
| `conflict` | 真冲突，看 `conflicts` 字段 |
| `failed` | 合并挂了但不是文件冲突（git 的原话在 `problems` 里） |
| `blocked` | 不满足合入条件，看 `problems` |

### 5.2 `hive audit`：合并前审一眼

```sh
$H audit T-0101        # 一张卡
$H audit --all         # 所有已有结果的卡（待合并清单）
$H audit T-0101 --json # 给脚本用
```

比对「agent 说做了什么」和「diff 里真有什么」：

- 卡片声明的 `paths` vs 实际改动文件；
- **越界改动**（改了白名单外的文件）；
- 每条 verify 的退出码；
- summary 全文（人来判断有没有吹牛）；
- `risk: warn` 时会列原因：没写 verify / 没声明 paths / 有越界改动 /
  **summary 里出现「没能跑」「无法验证」「未测试」这类口供**。

最后一条最有用：T-0101 那张卡的 agent 自己在 summary 里写了「没能跑测试」，
结果照样判 done —— 有了 audit，这种卡在合并前就会被点名。

### 5.3 paths 越界检测

自举时**代码仓和协调仓库是同一个目录**，agent 能顺手改掉自己的任务卡（`tasks/*.md`）、
别人的结果（`results/*.json`）。现在 worker 提交前会算一次改动清单，跟卡面声明的
`paths` 比对：

| 模式 | 行为 |
|---|---|
| 默认 | 只警告：越界写进结果 `out_of_paths` 字段和日志，任务照常完成 |
| `HIVE_STRICT_PATHS=1` | 判失败：不提交、不跑 verify，error 里列出越界文件 |
| agent 配置 `"strict_paths": true` | 同上，只对这一个 agent 生效 |

`paths` 为空表示不约束（不检查，但 audit 会提醒一句）。
默认不阻断是为了别一上来就把正常流程卡死；等卡面的 paths 都写得靠谱了再开严格模式。

### 5.4 一条运维约定（先看这个）

**跑 hive 的写命令之前，把自己手头的改动提交掉。** 现在代码上已经收口了
（每个命令只提交它该动的文件，见 §5.5），但养成这个习惯更省心。

### 5.5 写命令的提交范围

`commit_and_push` 现在带 `paths`，每个命令只提交自己该动的文件：

| 命令 | 提交什么 |
|---|---|
| `task new` | `tasks/<tid>.md` |
| `assign` / `take` / `retry` | `tasks/<tid>.md` + `inbox/<agent>/<tid>.md`（+ 归档结果） |
| `close` | `tasks/<tid>.md` + `results/<tid>.json` |
| `agent add` | `agents/<name>.json` |
| `dispatch --apply` | 批量时把上述文件按卡汇总 |

老行为（`git add -A`）留着没删，但会打一条告警日志，让 `doctor` 也能发现。

## 6. 租约、故障与验收机制

| 情况 | 处理 |
|---|---|
| VM 死机 / 机器断电 | 等 `lease_minutes` 到期 → `$H gc` → `$H retry T-xxxx` |
| 卡被占着但人想重派 | `$H retry T-xxxx --agent 别的agent` |
| agent 跑飞 | `timeout_minutes` 会硬杀；`--keep` 保留 worktree 排查 |
| 结果分支推不上去 | 看 `~/.hive/agents/<agent>/logs/T-xxxx.log` |
| 重复执行 | 只会发生在有人手工删了 claim 又没删 res；`doctor` 会报 |
| `unable to read sha1 file` | 服务端自动 gc 与并发 fetch 撞了；见 §8 |
| worker 崩 / 机器死，卡卡在 in-flight | 调度 `hive watchdog --apply`，死卡自动退回 ready 重派 |

### 6.1 `hive watchdog`：自动回收死卡

worker 跑飞、机器断电、claim 被 gc 误删，都会留下「卡在 assigned/running 但没人接」的孤儿卡，
一直占着并发额度。看门狗把这些卡自动退回 `ready`：

```bash
$H watchdog            # dry-run：只报告会回收哪些，不动手
$H watchdog --apply    # 真回收：死卡退回 ready，清空 owner，等 dispatch 重派
$H watchdog --minutes 30 --apply   # 租约过期/无 claim 超过 30 分钟才回收
```

判定（都以「claim 已失效」为前提）：
- `orphan_running`：state=running 但 claim 分支没了（崩溃 / 被 gc 清掉）
- `zombie`：claim 的 agent 没在 agents/ 登记
- `stale`：claim 的 lease_until 已过期（活着的 worker 有心跳续租，不会触发）
- `orphan_assigned`：state=assigned 但一直没来 claim，且分派时间超过 `--orphan-grace`（默认 30 分钟）才回收
- `land_lag`：已经有结果却还停在 in-flight —— 那是 land 的活，只提示不回收

配套：worker 运行时会自己续租（心跳），所以「租约过期」= 真死了，不会被误杀。
`orphan_assigned` 的分派时间从 `inbox/<agent>/<tid>.md` 里读——刚分派的卡在 grace 内
**不会被误杀**，留给 worker 去领；只有「分派了很久都没人来领」的死卡才会被退回 ready。

```bash
$H watchdog --orphan-grace 30 --apply   # 分派超 30 分钟没领的卡才回收
```

### 6.1.1 重试熔断：不会无限重派

一张注定失败的卡（verify 恒红、或 agent 一领就崩）会被判死 → 退回 ready → 重新分派 →
再判死……如果不加限制，`orchestrate` 常驻着会 7×24 小时不停烧 agent 时间（exec agent 还是
真花钱的 LLM 调用）。所以回收有额度：

- 卡面 `max_retries`（默认 **3**，`hive task new --max-retries N` 可改，
  `0` = 一次都不许自动重派）；
- 每次自动回收消耗一次额度（`retries + 1`）；
- **额度用尽后不再退回 ready，改判 `blocked`**，并在卡里写明原因。
  `blocked` 会被 `dispatch` / worker / `orchestrate` 全部跳过，等于自动退出流水线；
- `hive doctor` 会单独点名「重试额度烧光」的卡，和「等外部资源」的 blocked 区分开；
- watchdog 的 `--json` 里这类卡的 `action` 是 `block`（不是 `reclaim`）。

人工显式 `hive retry` **不受此限**——人在明确要求重跑就照做，只会在超额度时提醒一句。
要恢复自动重派：`hive retry <tid>`，或把卡面 `max_retries` 调大。

### 6.1.2 卡住了怎么手动干预：退回待领取 / 重开 / 关闭作废

四个动作语义完全不同，看板按钮同名，别混：

| 动作 | 命令 | 结果 | 什么时候用 |
|---|---|---|---|
| 退回待领取 | `hive unassign T-0001 --reason "…"` | `ready`，清空 owner | 这张卡还要做，只是换人 / 等资源 |
| 重试 | `hive retry T-0001 [--agent X]` | 回 `assigned`，保留或换 owner | 同一台机器再跑一遍 |
| 关闭作废 | `hive close T-0001 --note "…"` | **没有 result → `closed`** | 这张卡不做了 |
| 重开 | `hive reopen T-0001 --reason "…"` | `done`/`closed` → `ready` | 关错了，或者又想做了 |

要点：

- `close` 以前**无条件**写 `done`，把「中途掐掉」和「真的做完」混成一件事。T-0181 就这么丢的：
  看板点「终止」→ 卡变 `done`，实际一个 `result` 都没有，看板上和完成长得一模一样。
  现在按有没有 `res/<tid>` 结果自动判定：有 → `done`，没有 → `closed`（作废）。
  需要强制时用 `--as-done` / `--as-cancelled`。
- `close`（作废）和 `reopen` 都会把**现场**写进卡面备注：原状态、原 owner、有无结果、失败原因。
  半年后回看也知道这张卡为什么停在这儿，而不是只剩一句「看板操作」。
- 看板对应关系：异常列 → 「退回待领取 / 改派 / 重试 / 关闭作废」；已关闭列 → 「重开」。
  这三个写操作都会弹原因输入框（默认值带现场），原因会进卡面。
- 已在 `done` / `closed` 的卡是终态，`unassign` 会直接报错 —— 要改变现状就先 `reopen`。

### 6.2 `hive orchestrate`：总控进程（替代人工 drive）

把「看门狗 → 分派 → 合入 → 体检」串成一个常驻循环，让 exec 类任务从 `ready` 到 `closed`
全自动跑完，人只需要在 `needs_review` / `conflict` / `blocked` 等卡点介入。

```bash
$H orchestrate                       # 常驻：每 60s 一轮，直到 Ctrl-C
$H orchestrate --once                # 只跑一轮就退（适合 cron / 手动触发）
$H orchestrate --iterations 10       # 跑满 10 轮退
$H orchestrate --interval 30 --no-doctor --json   # 30s 一轮，每轮打印 tick JSON
$H orchestrate --stop-file /tmp/hive.stop   # 出现该文件就优雅退出
$H orchestrate --no-dispatch --no-land      # 只跑看门狗+体检（只回收，不分派不合入）
```

每轮 tick 顺序（任一阶段抛错都 catch 住、记 log、继续下一轮，绝不整进程崩）：
1. `watchdog --apply`（回收死卡 / 孤儿 / 僵尸；`--watchdog-minutes` 默认 180、`--orphan-grace` 默认 45）
2. `dispatch --apply`（把 `ready` 卡分派给空闲且能力匹配的 exec agent）
3. `land --all --apply`（把 verify 全绿、依赖就绪的 `done` 卡合入并 close）
4. `doctor`（报告问题，不改动）

设计边界：
- **只负责「脑」**：总控只做分派+合入+回收，worker 仍是各机器独立进程（自己的 `loop`）。两者解耦。
- **manual agent 的卡不碰**：dispatch 既有「人工优先」逻辑保留，留给人工 `take`/`submit`。
- **安全默认**：三个写操作本身都是「带 `--apply` 才真改」，这里显式传了 `--apply`，没有新的破坏性开关。
- **不要当 MCP 工具用**：`orchestrate` 会常驻阻塞，不适合做成 MCP 工具。要「带判断的总控」，
  用 controller MCP（`hive_dispatch` / `hive_land` / `hive_watchdog` …）由 LLM agent 自己循环调。

### 6.3 `hive llm`：LLM 总控（带判断的总控）

`orchestrate` 是确定性的「脑」，只在 verify 全绿时自动 land；遇到 `needs_review` / `conflict` /
`failed` / `blocked` 这些需要判断的卡点就绕开。`hive llm` 用 LLM 当决策核心，每轮把 hive 当前状态
喂给 LLM，让它从 **controller MCP 工具面**里挑一个动作执行，直到它认为没事可做。

```bash
$H llm --llm heuristic             # 无 key 回退：等价「不做危险决策的 orchestrate」
$H llm --llm openai --apply        # 真 LLM 决策 + 真改 main（需 OPENAI_API_KEY）
$H llm --llm openai --apply --max-iter 8 --stop-file /tmp/hive.stop
$H llm --mcp                       # 走真·MCP stdio 客户端（spawn mcp_server.py），默认 in-process 复用
$H llm --once                      # 只跑一轮决策就退
```

每轮 tick：拿 `hive_whoami`（controller）快照 → 渲染成紧凑文本 → 问 LLM「下一个动作」→ 执行（带 apply 安全闸）→ 记进滚动历史（防绕圈）。LLM 回 `done` / 到 `--max-iter` / `--stop-file` 出现 / 一轮无动作 → 结束。

工具面 = controller MCP 工具（`hive_land` / `hive_close` / `hive_retry` / `hive_assign` /
`hive_dispatch` / `hive_gc` / `hive_watchdog`）＋ 只读 introspection（`hive_whoami` /
`hive_list_tasks` / `hive_get_task` / `hive_stats` / `hive_doctor`）＋ 合成 `done`。
`InProcessBackend` 直接复用 `mcp_server.HiveMcp` 的 handler（同一套代码），`McpStdioBackend`
则真 spawn `mcp_server.py` 走 JSON-RPC 握手——所以「带判断的总控」和 controller MCP 是同一工具面。

安全闸（和全仓一致：破坏性操作默认 dry-run）：
- 没传 `--apply`：dry-run 类工具（land/dispatch/gc/watchdog）被强制 `apply=false`（只预演）；
  `hive_close` / `hive_retry` / `hive_assign` 这种无 dry-run 的破坏性操作直接跳过不执行。
- LLM 客户端：`OpenAiClient` 用标准库 `urllib` POST 到 `${OPENAI_BASE_URL}/chat/completions`
  （model = `${OPENAI_MODEL}`），零第三方依赖；无 key 时自动回退 `HeuristicClient`。
- **不自动解冲突、不 force push**：`hive_land` 冲突时只回 error，LLM 总控不得自行解冲突。

### 6.4 草稿：让 agent 也能出题

以前只有人会写卡，吞吐卡在出题这一端。现在 agent 可以出草稿，人只做「同意/打回」。

```sh
$H draft new T-0130 --repo hive      # 生成模板到 drafts/T-0130.md
#   ...agent 或人把四段填好（背景/目标/红线/验收）...
$H draft lint                        # 校验全部草稿
$H draft lint T-0130                 # 只校验一张
$H draft adopt T-0130                # 过 lint 才转正，进 tasks/ 并入队
$H draft list                        # 看有哪些草稿
```

`draft_lint` 的 error 会挡住转正：没填 repo、repo 没被任何 agent 登记、
**一条 verify 都没有**、`needs` 里有没有任何 agent 能满足的能力、依赖不存在的卡。
最后两条正是 T-0102 那种僵尸卡的成因 —— 它 `needs: windows` 而没有一个 agent 声明，
以前会永远躺在 ready 里骚扰 dispatch，现在从源头就拦住了。

warning 只是提醒：没声明 paths（改动范围不受约束）。

**设计意图**：草稿是给人 review 的界面。agent 一次出十张是廉价的；人只做
「同意/打回」这个 O(1) 的判断，而不是从零写卡。这个比例才是能不能把吞吐提上去的关键。

### 6.5 验收强度

verify 命令有强弱之分。`grep -q 同仓 hive.py` 这种只查痕迹的，agent 改个字符串就能过；
`python3 -m pytest tests -q` 才是真的在执行被测对象。

```sh
$H result T-0101          # 每条 verify 标强弱，整卡给结论
$H doctor                 # 只有弱验收的卡会被点名
```

三种结论：

| 结论 | 含义 |
|---|---|
| `strong-pass` | 全绿，且至少一条强验收 |
| `weak-pass` | 全绿，但只有 grep/test -f 这类弱验收 —— **成果没被真正执行验证** |
| `fail` | 有红的 |

混合 shell 管线（`grep x && pytest`）按**最弱的一环**算 —— 只要有一段是弱检查就算 weak。
这是刻意的：整条命令绑在一起时，看板只看最终退出码，看不出是哪条在把关。

`hive draft lint` 现在会**拦住没有强验收的草稿**，不让它转正。

### 6.6 复盘：`hive digest`

```sh
$H digest --days 1                    # 今天发生了什么
$H digest --days 1 --out docs/lessons.md
$H digest --json                      # 给脚本/看板用
```

输出四块，重点是**失败归因**：超时 / verify 未通过（附上具体哪条命令挂了）/
paths 越界 / 分支推送失败。每类列出卡号，一眼看出是「卡写得太难」还是「环境不稳」。

另外两块是「耗时最长的 5 张」和「反复重跑的卡」—— 前者说明卡拆得不够小，
后者说明第一版验收就没过。

`digest` 是**只读**的：不写任务卡、不推分支，`--out` 只写一个普通 markdown 文件。

配套的 `docs/lessons.md` 是「同类坑别再踩第二次」的清单。新增教训的三个来源：
digest 的失败归因、`hive audit` 的风险标记、agent 自己写的 summary。

### 6.7 状态机

| 状态 | 含义 | 谁能动它 |
|---|---|---|
| `ready` | 待领取 | `dispatch` / worker |
| `assigned` | 已分派未领取 | worker |
| `running` | 已领取在干 | worker |
| `needs_review` | 等人确认（草稿卡流程预留） | 人 |
| `conflict` | 合并冲突，必须尽快解 | 人（`retry` 后重来） |
| `blocked` | 等外部资源 / 等条件 | `hive block` / `hive unblock` / MCP `hive_block` |
| `done` | 已关闭 | — |

后三种是「交接态」：`dispatch` 和 worker 都会跳过。`conflict` 会被 `doctor`
当**错误**报（退出码非 0），因为它不解决后面全堵着；`blocked` 只是等待，报 warning。

```sh
$H block T-0102 --reason "等 Win10 VM 装好 Python"
$H unblock T-0102 --reason "环境好了"
```

## 8. 已知坑：服务端自动 gc

240 次快速 push 后立刻 clone，复现过：

```
error: unable to read sha1 file of tasks/T-0222.md
fatal: unable to checkout working tree
```

原因是裸仓的 `receive.autogc` 默认开启，`gc --auto` 会后台跑，和并发的 clone/fetch 抢对象。
处理（在 Gitea 的仓库目录，或任意自建裸仓）：

```sh
git -C /path/to/hive.git config receive.autogc false
git -C /path/to/hive.git config gc.auto 0
# 夜间空闲时手动 gc
git -C /path/to/hive.git gc --prune=7.days
```

测试仓和 soak 已经默认关掉自动 gc；Gitea 仓建议在低峰期做一次。

### 8.1 exec worker 后端：必须用 linuxulator 里的 node

FreeBSD 原生 node（node22/node24 端口实测）把 `internal/*` 模块全关掉了，
`dsh` 的 app-boot 一 `require('internal/modules/esm/loader')` 就崩
（`host preparation failed: Cannot find module 'internal/modules/esm/loader'`）。
所以 `agents/*.json` 的 `command` 必须指向 `scripts/dsh-exec`：

- 它在 `/compat/ubuntu`（linuxulator）里用 WorkBuddy 自带的 Linux node 跑
  `dsh-headless`，node 路径 `/home/skywalk/.workbuddy/binaries/node/versions/22.22.2/bin/node`
  （真实路径 `/opt/WorkBuddy/resources/runtime/node`，宿主看不到，只能 chroot 内访问）；
- stdin/stdout 原样透传，与 hive exec worker 约定一致；`dsh-headless` 自己补 `DEEPSEEK_API_KEY`。
- 症状：worker 秒领秒交、结果为空、verify 空跑通过 → 先查这个后端是不是真的能跑
  （`echo hi | scripts/dsh-exec` 应回一句）。

## 11. exec 模式：dsh（FreeBSD + linuxulator）

fb88 上跑 CLI agent 用 `dsh --profile headless -`（prompt 从 stdin 进，答案进 stdout）。
这台机器**没有原生 FreeBSD node**，唯一的 node 是 WorkBuddy 自带的 Linux 构建
（跑在 linuxulator 上，`process.platform` 报 `linux`），而 dsh 的 FreeBSD distfile
只带 freebsd 原生绑定——直接跑会 fatal：`No usable native binding found ...`。

一次性修法（已执行，可复现）：

```sh
cd ~/dswork/hive
./scripts/patch-dsh-linux-bindings.sh     # npm 下载两个 linux 绑定解压进 dist 树
printf '只回复 OK' | ./scripts/dsh-headless --profile headless -   # 验证
```

- `scripts/dsh-headless`：封装。负责找 node（PATH 优先，退回 WorkBuddy 自带）、
  从 `~/dswork/.env` 取 `OPENAI_API_KEY` 当 `DEEPSEEK_API_KEY`，然后转调 dsh。
  `DSH_DIST` / `DSH_NODE` / `HIVE_ENV` 可覆盖。
- `agents/fb88-dsh.json` 的 `command` 已指向该封装。**worker 启动时读一次 agent 配置**，
  改 command 后必须重启 worker 才生效。

重启 worker（原来跑在 tmux 里；tmux 客户端二进制已不在。**必须用 setsid**：
nohup 只是忽略 SIGHUP，进程仍在使用者的进程组里，从 WorkBuddy/agent 的 shell
里启动会随那条命令结束被回收——2026-10-23 实测死过一次；setsid 开新会话才能活）：

```sh
kill <旧 worker pid>
cd ~/dswork/hive
setsid python3 hive.py --dir ~/.hive/clones/fb88-dsh work --agent fb88-dsh \
  < /dev/null >> ~/.hive/agents/fb88-dsh/logs/worker.log 2>&1 &
```

排查顺序：绑定没补（跑 patch 脚本）→ key 没进环境（封装会自动补）→
node 找错（`DSH_NODE` 指死）→ 看 `~/.hive/agents/<agent>/logs/T-xxxx.log`。

## 12. 常驻集群：建议每台都跑，但不是必须

集群把「谁在线、谁在跑哪张卡、进度到哪一步、谁是主节点」做成秒级在线层；
git 仍然是 claim/result/land 的唯一真相。**建议每台跑 agent 的机器都起一个节点**，
不跑也能正常干活，只是跨机进度要等下一次 `git fetch`，主节点故障时也没有自动接管。

### 12.1 启动与观察

```sh
H="python3 ~/hive/hive.py --dir ~/hive"

$H cluster start                  # 后台常驻（首次会自动发现同网段节点）
$H cluster status                 # 本机角色 / 主节点 / 在线数 / 任期
$H cluster peers                  # 节点表
$H cluster events                 # 最近事件
$H cluster watch                  # 持续监听（主节点切换、任务进度、租约）
```

`hive work` / `hive orchestrate` 启动时会自动 `cluster ensure` 并周期性守护；
关闭自动拉起：`HIVE_CLUSTER_AUTOSTART=0`。

### 12.2 故障切换与一致性

- 主节点优雅退出（`cluster stop` / Ctrl-C）：先发 `resign`，通常 1~2 秒出新主；
- 主节点崩溃/断电：跟随者靠租约超时发现，通常 5~8 秒出新主；
- 任期 `term` 是 fencing token：旧主节点的写入会被新主节点以 `409 stale` 拒绝；
- 节点重启用递增 `incarnation` 覆盖旧记录，避免「死亡传闻」复活；
- 新主上任给在飞租约默认 120 秒恢复宽限，避免刚换主就重派；
- 跟随者之间也会互发心跳，避免主节点死后 B/C 各自以「单节点多数」当选。

分布式消除的是**单点**，不是物理上的「永不宕机」：所有节点同时断电、网络全断、
Git 中心仓不可达时仍会降级。需要更严格的多数派语义就用 3 节点，2 节点是
「可用性优先」的取舍。

### 12.3 端口与接入

集群默认 HTTP `8788`、UDP 发现 `8789`；跨网段/广播被挡时用静态 seed：

```sh
$H cluster start --seed 192.168.1.5:8788
$H cluster join 192.168.1.5:8788
```

跨机建议配置同一个 `HIVE_CLUSTER_TOKEN`。完整端口规划见
[`端口与服务规划.md`](端口与服务规划.md)，集群协议/API/排障见
[`集群服务.md`](集群服务.md)。

## FAQ

> 面向**人和总控**的高频疑问，每条给一句「详见」，深挖看对应章节或 `docs/lessons.md`。

### Q1 写卡最容易踩哪些反模式？

- **`verify` 没真跑过**：`lessons.md` 第一条，T-0114 的验收命令自己写错（`sys.exit` 没 `import sys`），
  submit 判 failed，代码其实全对。→ 写卡后**先手动跑一遍所有 verify 再入库**。
- **`paths` 没写全**：T-0112 顺手改了 README 但没声明，被自己的越界检测抓了、只能回退重写。
  → 文档改动通常动 README + 手册 + CHANGELOG，三个都列上。
- **`needs` 没人能满足**：T-0102 写 `needs: windows` 却没有任何 agent 声明，躺成僵尸卡。
  → 现在 `hive draft lint` 会拦；写正式卡前先 `hive agent list` 看一眼。
- **卡太大**：digest 里耗时最长的是一张文档卡，干了 83 分钟。→ 能一屏说清的卡才派出，说不清先写草稿。

详见 `docs/lessons.md` §一「写任务卡」。

### Q2 并行度怎么定？

一句话：**并行度 = 你能审得过来的 diff 数**。`dispatch` 的并发锁粒度是 **paths 不是 repo**——
同一仓里改互不相干目录的卡可以并行；`paths` 重叠（含父子目录）或没声明 `paths` 的才互相排队，
上限 `--max-per-repo`（默认 1）。详见 §3、§6.2 与 [`多机并行开发.md`](多机并行开发.md)。

### Q3 `hive land` 撞冲突怎么办？

`land` 一律**不自动解冲突、不 force push**，只报冲突文件清单（`--json` 的 `conflicts` 字段），
并按 §5 的规矩**回给 owner 开新卡**，不手工在 `main` 上解半天。`--all` 遇到冲突会**停下**——
后面的卡多半建立在它之上，已合的保留。详见 §5.1。

### Q4 卡卡在 `assigned` / `running` 一直没人动，怎么回收？

worker 跑飞、机器断电、claim 被 gc 误删，都会留下「卡在 in-flight 但没人接」的孤儿卡。用看门狗：

```sh
$H watchdog            # dry-run：只报告会回收哪些
$H watchdog --apply    # 真回收：死卡退回 ready，清空 owner，等 dispatch 重派
```

判定都以「claim 已失效」为前提（`orphan_running` / `zombie` / `stale` / `orphan_assigned`）。
注意重试熔断：同一张卡自动回收会消耗 `max_retries` 额度（默认 3），用尽后改判 `blocked`、
自动退出流水线。详见 §6.1、§6.1.1。

### Q5 集群要不要每台都跑？端口记不住怎么办？

建议每台跑 agent 的机器都跑 `hive cluster start`：不跑也能用，但跨机进度会退回到
等 `git fetch`，主节点故障也不会自动接管。端口只记四个：看板 **8787**、集群 HTTP
**8788**、发现 UDP **8789**、冒烟 **8799**；`hive ports` 看规划，`hive ports --check`
看占用，详见 [`端口与服务规划.md`](端口与服务规划.md)。详见 §12。
