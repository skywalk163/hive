# 蜂巢（Hive）操作手册

> 面向：每天早上坐下来干活的你，和接在 dsh Web 里的总控 AI。
> 目标：用最短的命令完成「建卡 → 分派 → 看进度 → 验收 → 合并」。

## 1. 角色

| 角色 | 在哪 | 干什么 |
|---|---|---|
| 人 | 任意 | 定优先级、review 关键 diff、合并 `main` |
| 总控 Chief | fb88 的 dsh Web | 拆卡、`dispatch`、读结果、写验收卡 |
| worker | fb88 / win10 / GUI | 领卡、干活、跑 verify、推结果 |
| Gitea | fb5:3000 | 代码与任务真源、CI |
| `hive.py` | 每个 clone 的根目录 | 工具本体 |

## 2. 第一次初始化

```sh
# 开发机：把工具仓推到 Gitea（仓库名 hive，空仓即可）
cd ~/dswork/hive
git remote add origin http://192.168.1.5:3000/skywalk/hive.git
git push -u origin main

# 任意机器：clone 后补齐任务目录
git clone http://192.168.1.5:3000/skywalk/hive.git ~/hive
python3 ~/hive/hive.py --dir ~/hive init
```

`init` 会创建 `tasks/ inbox/ results/ agents/`，并保证 `hive.py` 在仓库根目录。

登记 agent：

```sh
python3 ~/hive/hive.py --dir ~/hive agent add \
  --name fb88-dsh --mode exec --command "dsh --profile headless -" \
  --capabilities freebsd python compiler pytest \
  --repo light=/home/skywalk/src/light \
  --worktrees /home/skywalk/.hive/wt
```

Windows 用 `windows/bootstrap.ps1`，见 `windows/README.md`。

## 3. 每天的命令

```sh
H="python3 ~/hive/hive.py --dir ~/hive"

# 看板
$H status

# 体检：任务卡、租约、结果、agent 配置
$H doctor

# 自动分派（先 dry-run，确认后 --apply）
$H dispatch
$H dispatch --apply --limit 3

# 单张卡
$H assign T-0101 --agent fb88-dsh
$H result T-0101
$H retry  T-0101            # 续用原分支
$H retry  T-0101 --fresh    # 从 main 重来
$H close  T-0101 --note "已并入 integration"

# 统计：成功率 / 中位耗时 / 按 agent / 按仓库
$H stats
$H stats --days 7

# 分支清理：代码仓里已合并的 task/verify 分支（合并后跑，默认 dry-run）
$H prune
$H prune --apply
$H prune --repo light        # 只清一个仓
```

`dispatch` 的规则：

1. 只看 `state=ready` 且没有 owner 的卡；
2. 依赖必须都 `done`；
3. agent 必须声明了 `repo` 和任务卡的全部 `needs`；
4. `verify` 模式的 agent 不接带 `paths` 的卡（它不改代码）；
5. 已分派未领取也算负载，不超过 `max_concurrency`；
6. 默认 dry-run，`--apply` 才写。

`prune` 的安全规则（删的是**代码仓**的分支，不是协调仓）：

1. 只认 `task/*` 和 `verify/*` 两种前缀，`main` / `integration` / `release/*` 永远不碰；
2. 两条同时满足才删：**已合并进** `origin/main`（真合并或 squash 后内容一致）**且不在飞**
   （没有 claim/assigned 状态的卡没有结果）；
3. 默认 dry-run 只列计划；`--apply` 才推 `:refs/heads/<branch>` 删远端，本地分支能删就删
   （还被 `--keep` 的 worktree 占着时只删远端）；
4. 本地 `verify/*` 遗留也一并清（verify 模式不推远端，worktree 删了分支还在；
   这种分支 worker 随时能按 base 重建，删不丢东西）。

## 4. 总控的一天

**早上**

```sh
$H doctor
$H stats --days 7
$H status
```

把失败/过期的卡拉出来：`$H result T-xxxx`。决定：改卡、`retry`、还是换 agent。

**拆卡**

一张卡只做一件事，写清楚：

- `paths`：允许改的路径（互斥，避免冲突）；
- `verify`：至少一条能自动判定的命令；
- `needs`：平台/能力标签（`windows`、`exe`、`freebsd`）；
- `depends_on`：前置卡。

**分派**

```sh
$H dispatch --apply
```

**验收**

```sh
$H result T-0101
git -C ~/src/light fetch origin
git -C ~/src/light diff main...origin/task/T-0101
```

跑 CI 或本地子集，绿了再合 `integration`。

**收口**

```sh
$H close T-0101 --note "已并入 integration"
```

`close` 会把结果归档到 `main:results/T-0101.json`，删掉 `claim/res` 分支。

### 4.1 人工领取 / 提交：不依赖 worker 自动跑

GUI agent（小浣熊 / WorkBuddy）也可以**不启动 worker**，由人手工领取、手工提交，
主控再验收合入：

```bash
# 1) 看板上有什么
hive status                    # 全部任务
hive status --json             # 机器可读

# 2) 手工领取：assign + claim + 建 worktree，并标记领取 agent
hive take T-xxxx --agent workbuddy
#    会打印：工作目录 / 任务卡 / 完成后要写的 summary.md

# 3) agent 做完后，回主控提交：commit + push + verify + 写结果
hive submit T-xxxx             # --keep 保留 worktree
#    验证不通过会写 failed，改完再 submit 一次

# 4) 主控验收、合入后
hive close T-xxxx
```

注意：

- `take` 和「跑 worker」二选一。如果这个 agent 的 worker 正在跑，它会自己领取并
  等你写 summary，不要再用 `submit` 抢跑；
- 面板（dashboard）目前是只读的，写操作走 CLI（`take` / `submit` / `close`）；
- `take` 之后即使 worker 没跑，worktree 也在 `/home/skywalk/.hive/wt/<agent>/<tid>`，
  chroot 里是同一个路径。

## 5. 分支与合并

```
task/T-0101 ─┐
task/T-0102 ─┼─▶ integration ──CI 绿 + 人 review──▶ main（批量）
task/T-0103 ─┘
```

- 一卡一 worktree、一卡一分支；worker 不碰主 checkout。
- 共享文件（版本号、CHANGELOG）由总控在合并时统一改，或单独开“收口卡”。
- 冲突回给 owner 作为新卡，不要在 integration 上手工解半天。

## 6. 租约与故障

| 情况 | 处理 |
|---|---|
| VM 死机 / 机器断电 | 等 `lease_minutes` 到期 → `$H gc` → `$H retry T-xxxx` |
| 卡被占着但人想重派 | `$H retry T-xxxx --agent 别的agent` |
| agent 跑飞 | `timeout_minutes` 会硬杀；`--keep` 保留 worktree 排查 |
| 结果分支推不上去 | 看 `~/.hive/agents/<agent>/logs/T-xxxx.log` |
| 重复执行 | 只会发生在有人手工删了 claim 又没删 res；`doctor` 会报 |
| `unable to read sha1 file` | 服务端自动 gc 与并发 fetch 撞了；见 §8 |

## 7. 安全

- 每台机器一个 Gitea token，只授权需要的仓库；
- `main` 保护，worker 只推 `task/*`、`claim/*`、`res/*`；
- 任务卡不放密钥；
- GUI agent 用单独账号，出事能一键吊销；
- chroot 里的小浣熊/WorkBuddy 用 manual 接入，见 `docs/CHROOT_GUI_AGENTS.md`；WorkBuddy 当前以 skywalk 跑；若改回 root 注意文件属主；
- WorkBuddy 实测以 root 跑：不要给它宿主仓库写权限。

## 8. 已知坑：服务端自动 gc

240 次快速 push 后立刻 clone，复现过：

```
error: unable to read sha1 file of tasks/T-0222.md
fatal: unable to checkout working tree
```

原因是裸仓的 `receive.autogc` 默认开启，`gc --auto` 会后台跑，和并发的 clone/fetch 抢对象。
处理（在 Gitea 的仓库目录，或任意自建裸仓）：

```sh
git -C /path/to/hive.git config receive.autogc false
git -C /path/to/hive.git config gc.auto 0
# 夜间空闲时手动 gc
git -C /path/to/hive.git gc --prune=7.days
```

测试仓和 soak 已经默认关掉自动 gc；Gitea 仓建议在低峰期做一次。

## 8.1 exec worker 后端：必须用 linuxulator 里的 node

FreeBSD 原生 node（node22/node24 端口实测）把 `internal/*` 模块全关掉了，
`dsh` 的 app-boot 一 `require('internal/modules/esm/loader')` 就崩
（`host preparation failed: Cannot find module 'internal/modules/esm/loader'`）。
所以 `agents/*.json` 的 `command` 必须指向 `scripts/dsh-exec`：

- 它在 `/compat/ubuntu`（linuxulator）里用 WorkBuddy 自带的 Linux node 跑
  `dsh-headless`，node 路径 `/home/skywalk/.workbuddy/binaries/node/versions/22.22.2/bin/node`
  （真实路径 `/opt/WorkBuddy/resources/runtime/node`，宿主看不到，只能 chroot 内访问）；
- stdin/stdout 原样透传，与 hive exec worker 约定一致；`dsh-headless` 自己补 `DEEPSEEK_API_KEY`。
- 症状：worker 秒领秒交、结果为空、verify 空跑通过 → 先查这个后端是不是真的能跑
  （`echo hi | scripts/dsh-exec` 应回一句）。

## 9. CI 监控

`scripts/ci-check.sh` 读 Gitea Actions 的 runner 状态 + 指定仓库最新 run，写
`dashboard/ci.json`（供面板展示），stdout 一行摘要：

```bash
CI_REPOS="skywalk/hive" ./scripts/ci-check.sh
# ci-check: runners=online (1), repos: skywalk/hive:Running
```

- 凭证复用 `HIVE_ENV` 里 `gitea =` 那行（默认 `~/dswork/.env`）；
- runner 列表走 `/api/v1/admin/actions/runners`（需要管理员 token）；
- Gitea 1.24 没有 run 列表 API，最新 run 从 Actions 页面解析；
- `serve-dashboard.sh` 默认每 `CI_EVERY`（6 次 × `INTERVAL`）刷一次 `ci.json`。
- 看板顶部已有 **CI 状态条**：runner 在线/离线 + 各仓最新 run 状态（#编号 + 标题），
  30s 自刷新；数据来自 `GET /ci.json`（serve.py 白名单已加）。

## 10. 度量

看板：`PORT=8787 ./scripts/serve-dashboard.sh`，浏览器开 `http://127.0.0.1:8787`。

| 指标 | 命令 | 目标 |
|---|---|---|
| 周期时间 | `stats` 中位耗时 | < 45m |
| 一次通过率 | `stats` 成功率 | > 70% |
| 人工介入 | 手工记 | < 10m/卡 |
| 重复执行 | `doctor` | 0 |
| 冲突率 | 合并时统计 | < 10% |

## 11. exec 模式：dsh（FreeBSD + linuxulator）

fb88 上跑 CLI agent 用 `dsh --profile headless -`（prompt 从 stdin 进，答案进 stdout）。
这台机器**没有原生 FreeBSD node**，唯一的 node 是 WorkBuddy 自带的 Linux 构建
（跑在 linuxulator 上，`process.platform` 报 `linux`），而 dsh 的 FreeBSD distfile
只带 freebsd 原生绑定——直接跑会 fatal：`No usable native binding found ...`。

一次性修法（已执行，可复现）：

```sh
cd ~/dswork/hive
./scripts/patch-dsh-linux-bindings.sh     # npm 下载两个 linux 绑定解压进 dist 树
printf '只回复 OK' | ./scripts/dsh-headless --profile headless -   # 验证
```

- `scripts/dsh-headless`：封装。负责找 node（PATH 优先，退回 WorkBuddy 自带）、
  从 `~/dswork/.env` 取 `OPENAI_API_KEY` 当 `DEEPSEEK_API_KEY`，然后转调 dsh。
  `DSH_DIST` / `DSH_NODE` / `HIVE_ENV` 可覆盖。
- `agents/fb88-dsh.json` 的 `command` 已指向该封装。**worker 启动时读一次 agent 配置**，
  改 command 后必须重启 worker 才生效。

重启 worker（原来跑在 tmux 里；tmux 客户端二进制已不在。**必须用 setsid**：
nohup 只是忽略 SIGHUP，进程仍在使用者的进程组里，从 WorkBuddy/agent 的 shell
里启动会随那条命令结束被回收——2026-10-23 实测死过一次；setsid 开新会话才能活）：

```sh
kill <旧 worker pid>
cd ~/dswork/hive
setsid python3 hive.py --dir ~/.hive/clones/fb88-dsh work --agent fb88-dsh \
  < /dev/null >> ~/.hive/agents/fb88-dsh/logs/worker.log 2>&1 &
```

排查顺序：绑定没补（跑 patch 脚本）→ key 没进环境（封装会自动补）→
node 找错（`DSH_NODE` 指死）→ 看 `~/.hive/agents/<agent>/logs/T-xxxx.log`。
